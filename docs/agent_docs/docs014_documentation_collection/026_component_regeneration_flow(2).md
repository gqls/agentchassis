# 026 — Component Regeneration Flow

## Date: 2026-04-20

---

## Purpose

Describe how `StoreGeneratedComponentAction` handles the two cases of
"store this generated component" — creation of a new library entry, and
regeneration of an existing one — plus how version history and dependent
page rebuilds are handled.

Intended audience: anyone extending component-creator, debugging
unexpected component behaviour, or writing related agents that also
create or update components.

---

## The two paths

`StoreGeneratedComponentAction` is called at the end of the
component-creator workflow with LLM-generated output. What happens next
depends on whether a component with the same `function` name already
exists:

```
LLM output arrives
       ↓
parseGeneratedTemplate  (extract html_template, schema, function, isDark)
       ↓
separateInlineJS         (pull <script> bodies into js_content)
       ↓
Structural checks 1/2/3  (HTML structure, unclosed <style>, empty schema)
       ↓
Load existing component  (SELECT by function, is_active, forked_from IS NULL)
       ↓                       ↓
    found                  not found
       ↓                       ↓
  isRegeneration = true    isRegeneration = false
       ↓                       ↓
       └──────────┬────────────┘
                  ↓
       Layer 1 pre-store validation
              (on NEW template,
               regardless of path)
                  ↓
          ┌───────┴───────┐
          ↓               ↓
    PASSED          FAILED
          ↓               ↓
  ┌───branch───┐   Return error,
  ↓            ↓   don't touch DB
REGEN        CREATE
  ↓            ↓
Snapshot      INSERT new row
old state     ↓
  ↓          Snapshot as version 1
UPDATE
in place
  ↓
Mark pages pending
+ rerender items per site
  ↓            ↓
  └─────┬──────┘
        ↓
  ScoreAndPersistComponent
        ↓
  markPagesForRebuild (pending pages using this section_type)
        ↓
  Return status payload
```

The key design decision: **Layer 1 runs regardless of which branch is
taken**. A bad template never touches the DB — whether the existing
component is healthy or broken, the rejection is the same.

---

## The "existing component" check

The check is a single SELECT:

```sql
SELECT id, html_template, input_schema, js_content
FROM content_components
WHERE function = $1
  AND is_active = true
  AND forked_from IS NULL
LIMIT 1
```

The three predicates matter:

- `is_active = true` — soft-deleted rows don't count. If a bad component
  was deactivated to clear the way, the LLM's new output takes the
  create path.
- `forked_from IS NULL` — per-site forks don't block library-level
  regeneration. Component-creator operates on the canonical library
  version.
- `function = $1` — the function name is the stable identity for a
  component across versions. Display names and descriptions can vary;
  function does not.

`LIMIT 1` is defensive: the schema's `idx_cc_tool_function_unique`
partial index (on tools) and general expectation enforce one active
non-forked row per function name. If there are multiple, we take one
arbitrarily — but this shouldn't happen in practice.

---

## The create path

Runs when no matching row is found:

1. **INSERT** a new row into `content_components` with all the standard
   metadata (display_name, category, section_type, semantic_tags, etc.)
2. **Snapshot as version 1** to `component_versions` so history is
   complete from the first version. Best-effort — a failed snapshot
   logs a Warn and continues.
3. **Score the new row** via `ScoreAndPersistComponent` which populates
   `quality_score`, `quality_issues`, and the structural booleans.
4. **Mark pages for rebuild** that were waiting for this section_type
   (plan_sections creates work items referencing components that don't
   exist yet; these get unstuck when the component materialises).
5. **Return** `status: "created"`.

---

## The regenerate path

Runs when an existing row is found:

1. **Load the existing state** — html, schema, js_content — which will
   be snapshotted before it gets overwritten.
2. **Read MAX(version_number)** from `component_versions` for this
   component so the new snapshot gets MAX+1. If the query fails the
   default is 0 (next snapshot will be version 1). Unique index
   `(component_id, version_number)` ensures monotonic numbering.
3. **Snapshot the OLD state** to `component_versions` with:
   - `version_number` = MAX+1
   - `changed_by` = `component-creator:regen`
   - `change_source` = the originating work item's `source` field, or
     NULL if there wasn't one
   - `change_description` = "Regenerated by component-creator"
   
   Best-effort: a failed snapshot logs Warn and continues. Loss of
   history is worse than nothing, but leaving a broken template in
   place is worse still.
4. **UPDATE in place** replacing html_template, input_schema,
   js_content, and is_dark_section. The UUID is preserved.
5. **Mark dependent pages pending** — `markPagesPendingRebuild` sets
   `build_status = 'pending'` on every `page_components` row pointing
   at this component. It does NOT overwrite `rendered_html` (that's
   per-page, needs variable substitution).
6. **Raise one `needs_rerender` work item per affected site**.
   `markPagesPendingRebuild` returns the distinct site_ids touched.
   For each, `createRerenderWorkItem` inserts a work item with
   `item_key = component_regen_rerender:<component-uuid>` — the
   `idx_swi_dedup` unique index `(site_id, item_key)` prevents
   duplicates if the same regen is retried while a previous item is
   still pending.
7. **Score the updated row**.
8. **Return** `status: "regenerated"` with `previous_version`,
   `new_version`, `pages_marked_rebuild`, `affected_sites`, and
   `rerender_items_created`.

### Why UPDATE in place rather than deactivate + INSERT

All dependent tables reference `content_components.id` as a foreign
key: `page_components`, `site_components`, `area_components`,
`link_registry`, `component_versions`, `style_collections`, `layouts`.

If we INSERTed a new row with a fresh UUID, every dependent record
would still reference the OLD id — which is now either stale (if we
kept the old row live) or inactive (if we soft-deleted it). Pages
using this component would break until a separate relink step ran
everywhere.

UPDATE in place sidesteps the whole dependency graph. Foreign keys
keep resolving, no relink step needed.

## The rejection path

Layer 1 pre-store validation runs on the new template BEFORE either
the create or regenerate DB write. The checks:

- `template_closed` = true (balanced section tags)
- `has_data_component` = true (data-component attribute present)
- NOT (`template_variable_count = 0` AND `schema_field_count > 0`) —
  this is the "provocation-feed bug": schema declared 51 fields but
  the template had 0 placeholders for them
- If template has placeholders, schema and template must be in sync

On failure, the action returns `fmt.Errorf(...)` with a list of
blocking issues. The work item fails. The existing component — if
there was one — is untouched. Component-quality-auditor will
continue flagging the broken component on subsequent scans.

The design choice here: **broken new output never overwrites existing
state**. An existing broken component is at least running against
live traffic in some form; a half-written replacement with validation
errors is strictly worse.

## Version history

`component_versions` is populated on every create and regenerate.
The schema (as of April 2026) is:

```
id                 UUID PK
component_id       UUID → content_components(id)
version_number     int  (unique per component_id)
html_template      text
css_template       text  (unused — section components embed CSS in html_template)
input_schema       jsonb
change_description text  ("Initial version — created by component-creator", etc.)
changed_by         text  ("component-creator:create", "component-creator:regen", etc.)
change_source      text  (the originating work item's source field, nullable)
created_at         timestamptz
```

See `014_site_snapshots_and_revert.md` for the full population-
patterns table across `StoreGeneratedComponentAction` and
`UpdateComponentHTMLAction`.

### Use cases

The history lets us:

- Roll back a regeneration that produced a worse component (manual:
  read row N-1, write back via admin UI or direct UPDATE)
- Browse change history by source ("all regenerations caused by
  component-quality-auditor", "everything changed by
  manual_regen_after_prompt_fix")
- Diff two versions to understand what changed
- Opt a specific site back to an earlier version (future: requires
  per-site fork mechanism on top of the current library model)

The `component_versions` rows are NOT automatically cleaned — they
accumulate. If that becomes a storage problem, a pruning policy
similar to `page_component_history` (keep last N per component)
would apply.

## Page rebuild propagation

When a component's template changes, every page using it needs to
re-render so the HTML it emits reflects the new template. The
mechanism has two parts:

### Part 1: build_status flag on page_components

`UPDATE page_components SET build_status = 'pending' WHERE component_id = $1`
flags every page_components row pointing at the regenerated
component. This is a state marker — it says "this row is out of
date" — but it doesn't trigger anything on its own.

### Part 2: needs_rerender work item

The trigger is a work item in `site_work_items` with
`handler_agent = 'rerender-pages'`. One item per affected site,
created during the regen path after `markPagesPendingRebuild`.

The `item_key = component_regen_rerender:<component-uuid>` is scoped
to the component, so two concurrent regens of different components
on the same site produce distinct work items that can both be
processed. Repeat regens of the same component dedup via the unique
index.

### Why both?

The `build_status = 'pending'` flag alone isn't enough because nothing
queries `page_components` for pending rows — the dispatch mechanism is
work-item based, not flag-scanning. The work item alone would be
enough for the rerender pipeline, but the build_status flag is useful
for observability and lets auditors check "are there pages stuck in
pending that haven't been picked up?".

## Contrast with `UpdateComponentHTMLAction`

Both actions write to `component_versions`. They differ in trigger and
scope:

|  | `StoreGeneratedComponentAction` | `UpdateComponentHTMLAction` |
|---|---|---|
| Called by | component-creator workflow | tool-improver and similar |
| Input | LLM JSON output (template + schema) | Pre-improved HTML string |
| Handles schema | Yes — updates `input_schema` too | No — only `html_template` |
| Version snapshot | Always (on create and regen) | Optional (`create_version = true`) |
| Rerender item | Creates its own (one per affected site) | Left to the workflow (separate step `create_rerender_item`) |
| Changed_by value | `component-creator:create` / `component-creator:regen` | `update_component_html` |

The split comes from different flows. Component-creator's workflow is
`store_component → complete` with no separate rerender step, so the
action owns that side-effect. Tool-improver's workflow has an explicit
`create_rerender_item` step, so the action doesn't duplicate it.

Both actions mark `page_components.build_status = 'pending'` but
neither overwrites `rendered_html` — that's per-page content needing
variable substitution, regenerated by the rerender pipeline.

## Failure modes and recovery

### Layer 1 rejection

**Symptom:** Work item fails with error message listing blocking
issues. `component_versions` unchanged, `content_components` unchanged.

**Recovery:** Read the blocking issues. Typically this means the
component-creator prompt produced output the validator can't accept.
Revise the prompt, redeploy, retry the work item.

### Snapshot fails but UPDATE succeeds

**Symptom:** `content_components` has new template, but
`component_versions` missing a row for the intended version_number.

**Recovery:** Acceptable by design — regen proceeds. History has a
gap. If the gap is a problem, a follow-up INSERT into
`component_versions` with the missed version_number and the old
template (which is lost unless someone captured it from logs) could
patch it. In practice, tolerate the gap.

### Rerender work item dedup prevents re-queue

**Symptom:** Regen complete, but no new `needs_rerender` item
appears. Existing item with same `item_key` is still pending.

**Recovery:** Expected behaviour. The existing item will process
against the newly-updated component. No action needed.

### Dispatch fails to pick up the rerender item

**Symptom:** Work item sits at `status = 'triaged'` for extended
period without being claimed.

**Recovery:** Check `build-dispatch-loop` is running. Check the
site's `build_queue` isn't empty. Scheduler may not be firing.
Investigate the dispatcher, not the regen path.

### Full-writer rebuild drops an interactive/tool section (CONFIRMED 2026-06-22)

**Symptom:** a page that hosted an interactive tool/game (the
component stored as a section's `rendered_html`) is rebuilt and comes
back as plain content — hero + a `generic-text-block` fallback, no
`<canvas>`/`<script>`. `page_components` shows the tool gone;
`page_component_history` shows the interactive section present at an
earlier timestamp and overwritten.

**Cause:** the rebuild ran through `page-build-handler` →
`page-content-writer`, which regenerates the page from `plan_sections`.
The plan does not include the interactive tool (it isn't a planned
content section — it's a tool component attached to the page), so the
writer produces content for the planned sections only and the tool is
discarded, falling back to `generic-text-block`. Triggered most often by
a `link_resolution_rebuild` (intended as links-only but routed through
the full writer — there is no `item_type` branch in the handler) or any
`needs_page`/`needs_content_page` against a tool page. The
content-regression guard does NOT catch it because the lost bytes are
markup/JS, not prose. Attribution note: the overwrite row in
`page_component_history` carries NULL `source_item_id`; trace the writer
via `orchestration_states` filtered by page_id+time, not the work-item
timestamp (the work item's `completed_at` is the orchestration END; the
child writer does the write mid-run).

**Recovery:** re-run the tool-recreation for the page to regenerate and
reattach the interactive component — but fix the routing first, or the
next content/link rebuild drops it again. Fix direction: route link
maintenance through a preserve-sections re-render path (reuse the
`page_rerender` machinery); stamp `source_item_id` into
`page_component_history`; add an interactivity-aware guard in the save
path that blocks/escalates an overwrite dropping a `<canvas>` /
`data-component` section. See 016b debugging guide ("interactive page
rebuilt as content"); 020 Tool Lifecycle; 002 (Work-item routing →
interactive-page hazard).

## Deploy order when changing this code

The regen path touches three layers:

1. **Schema** — the `change_source` column on `component_versions` is
   a prerequisite. Migration `migration_component_versions_change_source.sql`.
2. **Go binary** — chassis with updated
   `store_generated_component_action.go` and
   `update_component_html_action.go`.
3. **Agent definitions / prompts** — the component-creator prompt
   still needs the `placeholder` funcMap in `RenderPromptTemplate`
   (deployed April 2026) to render correctly. Prompt updates don't
   require a binary redeploy.

Correct order for new installs or major rollouts:
`migration → binary → prompt updates → regen work items`.

For already-running systems with the new binary, just apply the
migration (additive column, safe). Subsequent regens will populate
`change_source`; existing rows keep NULL.

## Pre-store validation, error logging, and LLM reliability

## Date added: 2026-05-11

### The validation gate

Before `StoreGeneratedComponentAction` writes a generated component to
`content_components`, it runs `scoreComponent` and rejects the output if
any of these are true:

- Template is not closed (unbalanced `<section>` tags)
- Template is missing the `data-component` attribute
- Template has zero `{{.var}}` placeholders despite a populated schema
  (or a substantive >500-char template)
- Schema and template variables don't match in both directions
- Template contains literal `<no value>` strings (Go template render
  artifacts mistakenly stored as source)

`scoreComponent` lives in `compute_component_quality.go`. Its template-
variable extractor parses the template with Go's `text/template/parse`
package and walks the parse tree to collect every `*parse.FieldNode`
identifier. This replaces the earlier regex-based extractor, which had
to be updated each time a new Go-template construct turned up
(`{{range .X}}`, `{{$.X}}`, `{{with .X}}`, etc.). The parser stays
correct as the template language evolves, since it IS the language
definition.

The schema-field extractor also recognises Tier D array sub-schemas:
sub-schema field names declared inside `fields.X.items` (where
`fields.X.type=array`) are considered valid template-variable targets
but are NOT required to appear in the template. The LLM may declare a
sub-schema catalog of available fields and choose to use a subset; the
unused ones are not flagged.

### Persistent rejection records

When validation rejects an LLM-generated component, the action writes a
structured row to `agent_error_log` via `recordValidationRejection`.
The row carries:

- `site_id`, `domain`, `work_item_id`, `orchestration_id` — context
- `agent_type='component-creator'`, `step_name='store_component'`,
  `action='store_generated_component'`
- `error_code` — one of `component_validation_rejected`,
  `component_validation_orphan_schema_field`,
  `component_validation_unknown_template_var`
- `severity` — `warning` for bookkeeping mismatches,
  `error` for structural failures
- `context` JSONB — the score breakdown plus arrays of
  `orphan_schema_fields`, `unknown_template_vars`, `blocking_issues`,
  `all_issues`. Function name, section type, template/schema lengths.

This makes failure patterns queryable. Example queries:

```sql
-- Which schema fields does the LLM most often declare-but-not-use?
SELECT
    jsonb_array_elements_text(context->'orphan_schema_fields') AS field,
    COUNT(*) AS rejection_count
FROM agent_error_log
WHERE error_code = 'component_validation_orphan_schema_field'
  AND occurred_at > NOW() - INTERVAL '7 days'
GROUP BY field
ORDER BY rejection_count DESC
LIMIT 20;

-- Which functions repeatedly fail validation?
SELECT
    context->>'function' AS function,
    COUNT(*) AS rejection_count,
    array_agg(DISTINCT error_code) AS codes
FROM agent_error_log
WHERE error_code LIKE 'component_validation_%'
  AND occurred_at > NOW() - INTERVAL '7 days'
GROUP BY function
ORDER BY rejection_count DESC;
```

### Why we don't auto-correct

Earlier proposals considered automatically dropping orphan schema fields
before storing. Rejected. The dropped fields are LLM-declared intent
that we'd be silently discarding; the right place to fix the LLM is the
LLM, not the storage gate. Auto-correction also masks systematic
problems — if the LLM keeps declaring `nav_label` and not using it, we
want that visible as a pattern, not auto-corrected away each time.

The validator's job is to enforce the contract loudly. The LLM is
expected to meet the contract. When it doesn't, we either:

- Retry (current behaviour, capped at 3 attempts)
- Adjust the prompt (next iteration when patterns emerge from
  `agent_error_log`)
- Move the bit the LLM struggles with out of the LLM's hands (see
  Decomposition below)

### Decomposition: move list-reconciliation out of the LLM

The most common failure mode is bookkeeping mismatch: the LLM produces
a structurally valid template but the schema's field list doesn't
exactly match the template's variable references. LLMs are unreliable
at exact list reconciliation; deterministic code is great at it.

Several pieces of the component contract are mechanical and don't need
the LLM's judgement. Proposed moves out of the LLM's hands:

1. **Root `<section>` wrapper and `data-component` attribute.** Always
   `<section class="{function}-section" data-component="{function}">`.
   No reason the LLM should write this; we can wrap its inner HTML at
   store time. Removes a thing the LLM sometimes gets wrong
   (wrong class name, omitted attribute, wrong tag).

2. **Tier D sub-schema fields.** The resolver
   (`platform/orchestration/actions/queryresolve`) is the authority on
   what fields a `query.pages_where_type:X` returns. Currently each
   component-creator output redeclares these (`title, url,
   meta_description, nav_label`) per component. Move the declaration to
   queryresolve and have the validator look there. The LLM stops
   declaring sub-schema fields entirely; it just uses them.

3. **Schema field list derived from template (more ambitious).** If
   `extractTemplateVariables` already produces the canonical field list,
   the schema's `fields.X` entries could be derived rather than
   LLM-declared. The LLM still provides per-field metadata
   (`source`, `llm_guidance`, `fallback`) but the KEY list is
   parser-extracted. Eliminates direction-2 mismatches by construction.

Order of work: (1) first — small, isolated, immediate reliability gain.
(2) next — also small, removes a class of LLM-declared variation.
(3) only if (1) and (2) haven't gotten us to high reliability.

### LLM model choice

Worth noting but not the lead lever. The current `component-creator`
agent uses `claude-sonnet-4-6`. A larger model (e.g. opus) would
improve consistency but adds latency and cost ~3-5x. Right ordering:

1. Move bookkeeping out of the LLM's hands (Decomposition above).
2. Tighten the prompt for what remains, informed by
   `agent_error_log` patterns.
3. Only if those don't reach high reliability, consider a bigger model.

Model choice should follow problem decomposition, not lead it.

### What "high reliability" means

Target: a freshly-launched site's adoption + plan + build cycle produces
a deployable site WITHOUT manual SQL intervention to fix component
output. Measurable by:

- Zero `agent_error_log` entries with severity=`error` from
  `store_generated_component` during a full site build
- All `severity=warning` entries are recoverable by retry within the
  configured attempt cap

The validator's role in that target is to fail loudly and informatively
at the EXACT moment the contract is broken, not at render time when the
symptom is "page looks wrong."

### Operational notes

- Removing the `agent_error_log` rejection rows is fine — they're
  diagnostic, not part of the build pipeline. A periodic cleanup that
  deletes rows older than 30 days is reasonable.
- The validator's pre-store check is the strict gate. Post-store there
  is a less-strict quality auditor (`ComputeComponentQualityAction`)
  that scores already-stored components periodically. The auditor
  surfaces drift over time; the pre-store validator prevents bad
  components landing in the first place.
- Hand-written components (`created_from='manual'`) bypass the
  validator entirely — they're a database UPDATE, not a workflow run.
  Migrations that hand-write components must therefore be careful to
  set the quality columns (`quality_score`, `quality_issues`,
  `schema_template_synced`, etc.) consistently with what the validator
  would have computed. See migration 041 for a worked example.
