# NOTES — Running Synthesis: Framings and Principles

**Status:** running. A list of synthesis points and design framings that have crystallised across the conversation, captured as reusable lenses for further design work, not as a final theory. Added to as new ones surface.

Organised by theme. Each item is a principle with a short rationale, brief enough to be a reusable lens rather than a paragraph of philosophy.

---

## Context substrate

- **Documentation is code.** Standards, intent, and trajectory are operational inputs to code generation, not passive reference. Versioned, drift-tested, composed deterministically.
- **Authored vs derived.** Two epistemic categories: owner + lifecycle (can be wrong, needs maintenance) vs no-owner true-right-now readout (can't be wrong, only current or superseded). Source code sits on the line — authored, but also ground truth.
- **The change layer between.** Diffs of code and logs are derived (auto-generated, true by being actual) but narrative (tell the story of what changed) — the natural audit and learning surface.
- **References, not copies.** A chat full of pasted code holds copies; a chat that fetches the file when it needs it holds references. Authored layers point at derived rather than paraphrase, so they don't drift when reality moves.
- **Salience over presence.** LLMs lose the bigger picture because local detail is more salient mid-reasoning, not because text fell out of the window. The lever is salience at the moment of decision.
- **Right altitude at the right moment.** Depth is a virtue, not only a failure mode. Blanket-mission-everywhere degrades implementation steps; selective surfacing serves both correctness and bigger-picture fidelity.
- **Two staleness modes, two fixes.** Authored drift: keep authored thin and pointer-rich. Derived snapshot-staleness: fetch at reasoning time, not paste-time.

## Trust, reliability, and the ratchet

- **Bottleneck is trust, not capability.** Reframes "make it autonomous" as a reliability problem: bound uncertainty per step to progressively remove the human.
- **Automation is a per-capability ratchet, not a switch.**
- **Bidirectional ratchet.** Trust can be lost, not only gained. This is the safety property that lets the ratchet advance at all — graduating a capability isn't an irreversible bet.
- **Trust ledger as the master knob.** One control surface governing both how conservatively something is produced (cascade floor) and whether it applies without a human (gate).
- **Verifiability + containment.** Two factors; both needed to climb; the weaker holds the ceiling. Verifiability = ground truth; containment = blast radius / reversibility.
- **Ceiling vs maturity.** High ceiling + low maturity = invest (it converts to ratchet progress). Low ceiling regardless of maturity = invest in good HITL ergonomics, not in removing the gate.
- **Reliability cascade per task:** reuse → generate+verify → compete+judge → HITL. Highest-reliability tier first. **Reuse-before-recreate is load-bearing for reliability, not just tidiness.**
- **Apparent contradictions can be graduated states, not bugs.** When two rules seem to conflict ("everything is gated" vs "the mechanical layer is confirmed by reality"), check whether one is the default starting position and the other is what a trust mechanism eventually permits. They may be the same rule at different maturity levels — the gate is the start; graduation relaxes it.
- **Cold start at the most conservative level.** A new (tenant, capability) pair starts at `confirm_every`, never inherited-higher. Trust is earned per tenant from the most cautious starting point.
- **A capability is a unit of trust, not a unit of agent.** Capabilities aren't 1:1 with agents — "propose a schema migration" or "roll back to known-good" may span several. So the capability (with its ceiling) lives in its own catalog, referenced by the agents that exercise it, rather than as an attribute of any one agent. Trust attaches to the capability; agents are how it's exercised.

## "Right" as balance, not a single answer

- **"Right" is a requirement-relative balance** among conflicting dimensions (fast/secure/generic/simple/functional). Not pick, not merge.
- **Authored solutions are extremes that bound the space.** The mediator finds the requirement's point inside it.
- **Priority is not global.** It comes from the why-chain's priority profile, modulated temporally by direction-of-travel.
- **Order, not numeric weights.** Avoid false precision; external events arrive as "X now outranks Y," not as weight tweaks.
- **Drop-out as mode change.** A satisfied concern demotes from author to checker (passively verifying); re-promotes if a later change breaks it. **Unifies the checker and multi-author models as two modes of one process.**
- **Convergence separates resolvable tensions from the irreducible one.** Non-convergence is the escalation signal — it identifies the genuine tradeoff that needs a judgement, with everything else settled around it.
- **Multi-author surfaces tradeoffs vividly; it cannot resolve value-laden conflicts.** Option-generation engine, not decision engine. Decision still lands in the authority model.
- **Candidate owned by no concern.** Shared artifact + change log, seeded deliberately from the profile's dominant dimension. Rounds = premised diffs the mediator adjudicates. Path-dependent — converges near the seed; rival-base proposals are the gated escape for structurally different solutions.

## Governance and HITL

- **Confirm-not-initiate.** Decision reasoning is agent-led; the human confirms via a decision package (summary + tradeoffs + explicit choices). The hard job becomes "agent explains well enough that a human can confirm responsibly," not "human authors from scratch."
- **Every decision publishes its reasoning, not just its outcome.** Foundational. Drift detection, the N-round process, and the trace all stand on it. "Chose X because [premise]" is reusable; "chose X" teaches nothing later.
- **Drift detection = gap between a decision's logged premise and the current premise.** Possible only because reasoning is published.
- **Heuristic decisions emit decision + provenance.** Information availability, not information presence. A heuristic that decides invisibly hides drift; a legible one lets later judgement start from "here's what was already decided and on what basis."
- **Provenance informs weighting, not deference.** Knowing which concern authored a solution shapes how to read it; authority comes from the requirement-relative priority, not the loudest voice.
- **Two precedence directions in inheritance.** Normal entries are child-wins (local refinement); sealed constraints are ancestor-wins (legal floors, mission non-negotiables). Sealing prevents a leaf's prior relaxation defeating a new law.
- **Three resolutions to a disagreement: code drifted / doc drifted / legitimate exception.** The default presumption is set by the source-of-truth choice (docs-authoritative → default = code drifted), but the human can pick any. **Default ≠ only.** This is where docs-authoritative earns its keep without becoming rigid.
- **The user-rep is a different *kind* of advocate.** Curators advocate for concerns (correctness, consistency); the user-rep advocates for intent (fidelity to what the user wants). The coordinator arbitrates between them; the user-rep is the check on the coordinator's framing power.
- **"Sufficiently adopted" via both self-judge and mediator-judge**, with the residual recorded if the mediator dismisses an unsatisfied concern. Override doesn't erase; it logs.
- **One path to the privileged state.** When a transition must be gated (here: `proposed → active`), route it through a single component, not reimplemented in each producer. Multiple implementations of a gate are multiple chances to weaken it; one path (the central confirmer) makes confirm-not-initiate airtight and auditable in one place rather than a discipline spread across agents.
- **Newer supersedes pending.** When a new proposal arrives for a target that already has an unresolved one, the newer wins and the older expires. Better never to confirm something reality has overtaken than to block on a stale proposal. Prefer freshness over queue order when the world can move under a pending decision.
- **A system that records its own changes shouldn't re-investigate the ones it made on purpose.** The tool watches for changes so it stays honest about its own effects — but when it deliberately applies a change a human just approved, it should note that change without treating it as something new to re-check. Tell apart "I just did this on purpose, already reviewed" from "something changed, go look." The first needs no re-work; the second does. (Changes the tool generates but that haven't been reviewed still count as the second kind.)

## Build vs operate

- **The two routes unify at the context layer, not at "website is code."** Both run on thin authored + thick live derived; vertical (infra vs web) changes which slices, not the machinery.
- **Build vs operate asymmetry.** Build is isolatable (competition safe); operate is live/stateful (competition risky, lean on known-good + canary + rollback).
- **Rollback can be trusted autonomously earlier than roll-forward**, because returning to a known-good state is the inherently safe direction.
- **Cross-cluster: boundary made invisible by design** (same Kafka talk-back, same DNS for remote DB) → theory barely expands. Mostly new capabilities, not new theory.
- **Defect-vs-partition disambiguation.** Quarantine infrastructure-attributed failures from the trust signal, or transient flakiness will de-graduate capabilities that are actually fine.

## Onboarding and config

- **The config has three layers with different derivability:** mechanical (discovered + probed), conventions (inferred or doc-sourced — confirmed), intent (elicited). They are not one onboarding problem; they are three uneven ones.
- **Progressive onboarding.** Mechanical value first, ramp not cliff; never "done" — config tracks the repo.
- **Config is a maintained artifact** with the standards' lifecycle. Drift detection, confirm-not-initiate, per-entry provenance (discovered / inferred / supplied).
- **Inference quality scales with codebase quality.** The messier the repo, the less it teaches; the more a tenant needs the tool, the less their repo can teach it. Surface uncertainty rather than silently picking; inconsistency detected is itself output.
- **Extraction is inferred-then-confirmed even in docs-authoritative mode.** The docs are the source, not extraction's authority. Hallucinated conventions would manufacture drift.
- **Coverage honesty.** Don't imply a clean audit when half the conventions weren't checkable. Report what was checked and what couldn't be — three buckets (deterministic violations, heuristic candidates, unchecked judgement), not one number.
- **Conventions have two roles: audited and guiding.** Some atoms appear in the drift audit; some load into generation context; some both. Un-auditable conventions are not lost — they contribute on the input side rather than the output side.
- **LLM as judgement-checker is itself only a candidate flag, never a verdict.** The same LLM-uncertainty problem the wider cascade exists for. Don't create a weaker authority channel by trusting it as a verdict — narrow where to look, leave the verdict to a human.
- **Exceptions feedback.** Marking a disagreement as a legitimate exception is recorded against location + convention, so the audit doesn't re-flag — it becomes incremental.
- **Our own setup is the template, not a special case.** The docs-vs-code disagreement list from our own onboarding is the drift detector's first run, on us — a free audit of where the code drifted from its own documented standards.
- **Inspection is fact, interpretation is proposal.** Reading a file's contents is fact; deciding what it *means* (which Makefile target is "the test command"; that a directory called `actions/` holds the actions in this codebase's sense) is interpretation, which is inferred-then-confirmed even at the mechanical layer. The pattern applies where it is least expected.
- **Probing is declared.** No execution without a plan emitted first, with rationale. Necessary for sandboxing tenants (the security contract); useful as audit for our own use (what did the agent actually do).
- **Confirmation by reality.** The mechanical layer can be confirmed by probe success — the recorded commands actually running is the strongest confirmation any config layer can carry. This is why the mechanical layer climbs the ratchet fastest of the three: conventions and intent cannot be confirmed by reality and depend on human confirmation as the only available authority.
- **The interview is progressive, never finite.** Up-front elicitation captures the top of the tree; leaves are captured just-in-time as work happens. The intent layer fills out with usage rather than as a setup tax. Initial onboarding stops asking when the top is covered; the rest fills as the tool is used.
- **Value-return per exchange.** Each elicited piece changes the next interaction immediately (capturing the mission tethers the next generation to it; capturing an area's priority order is what the mediator uses in the next tradeoff). The tenant should never feel they have given several answers and gotten nothing back.
- **Proposal-confirmation vs free elicitation.** Lean proposal-confirmation where evidence exists (low friction); free elicitation where it does not. Pure either is wrong — free is the blank-page problem; pure proposal-confirmation anchors the tenant on the agent's guess. Mitigation: proposals cite their evidence so a wrong inference is contestable.
- **Capture vs use are separate roles, separate agents.** The intent-elicitation agent captures intent (onboarding); the user-rep advocate uses intent (runtime decision). Same concept, two roles. Keeps elicitation unpressured by live decisions and advocacy undistracted by capture.
- **The dependency graph is the flow plan.** Sequencing follows dependencies, not process preference: run in series where outputs feed downstream, run in parallel where they don't. Reading the dependencies *is* designing the flow.
- **Onboarding never reaches "fully done."** Active-with-pending is the steady state. Maintenance takes over from "enough to use" rather than "complete." This is the progressive principle applied to the lifecycle, not just to the interview.
- **The orchestrator coordinates and surfaces; it does not extract.** Same boundary applies to any layer-coordinating orchestrator: dispatch to the specialists, route gates to the human, surface state — but do not start doing the specialists' jobs, or boundaries blur and the orchestrator inflates.
- **Same code for our use and for tenants.** Only the entry point and isolation context differ. The engine/config split principle applied to the orchestrator itself.
- **Maintenance is where the ratchet gets its long-run signal.** Drift detection is not a separate upkeep function from the bidirectional trust ratchet — it is the source of evidence the ratchet acts on. Without something playing this role, the ratchet has nothing to move on. Immediate verification pass/fail is the wrong timescale for trust; sustained no-drift and repeated-drift are the right ones.
- **Drift triggers follow the change layer.** Diffs to docs/code/objective-tree nodes are the natural event source; the periodic sweep catches what events missed. No separate sensor — the change layer is the source.
- **Targeted re-validation, not full sweeps.** When something changes high in a tree, check only the descendants whose entries reference or override the changed dimension. Efficient maintenance is implicated-only-recheck — the priority-profile maintenance pattern generalised across the config.
- **Surface drift in priority order, not all at once.** Over-surfacing causes alert fatigue and the signal is ignored; under-surfacing lets drift accumulate. Critical drift immediately; low-impact drift periodically; the tenant's attention is earned, not consumed.
- **Contracts are the bottleneck for coherent implementation.** Agents specced individually can each look fine while quietly disagreeing on the shape of the artifact they all produce or consume. A system-view check is what surfaces these — and the shared contracts have to be settled before implementation, not as you go. The load-bearing one is usually the artifact every agent touches (here: the active config).
- **Compute on read for freshness; log the result at point of use for retrospect.** Derived values (the effective priority profile, the constitution view, the applicable-standards bundle) are computed fresh on each read so ancestor changes propagate automatically without stored derivations going stale. But the result *at the moment it was used* is recorded in the decision log so the historical state is reconstructable. The active value is always fresh; the log is audit, not source — it wasn't authoritative when written and isn't authoritative now. Combined with versioned atoms, this gives full retrospective reconstructability without poisoning the present.
- **When compute-on-read is too expensive, store the value but keep its inputs authoritative.** The middle path between "store (goes stale)" and "recompute every read (costly)": store the derived value for cheap reads (e.g. a capability's ceiling), but treat its inputs (verifiability, containment) as the source of truth, so a change to an input triggers a gated re-proposal of the stored value rather than silent drift. Same discipline as compute-on-read — the inputs are authoritative — differing only on whether the value is recomputed each read or stored and refreshed on input change.
- **State vs history are different artifacts.** State is mutable, derived from history, and is what's *used* at runtime (the trust ledger). History is immutable, append-only, and is what's *audited* (the decision log). Same source, different access patterns. Mixing them contaminates both — reading old state means walking history; reading history means walking history; the present is always the present.
- **The bidirectional ratchet is asymmetrically governed.** Tightening (de-graduation, lowering trust) may auto-apply with notification when evidence is severe. Loosening (graduation, raising trust) is always confirm-not-initiate. The asymmetry is the safety property: losing trust is reversible; falsely gaining trust permits mistakes to apply unsupervised. Make it easy to be cautious, hard to be incautious.
- **The ceiling is structural; the level is built.** A capability's ceiling (the max trust it can ever reach) is determined by its verifiability + containment — a property of the capability, not the tenant. The trust level a tenant has reached for it is built by use and lives on the per-tenant ledger row. Same capability, different levels for different tenants, but the same ceiling for all.
- **In-band events close the loop on self-modification.** When the tool itself causes a change (the bundle builder applies a confirmed code change; a layer agent flips a row to active), it emits a change event so the maintenance agent sees its own effects. Otherwise the tool's own changes evade the drift detector and the decision log — the system would become blind to itself. State changes emit; computed-view refreshes don't.
- **The trigger filter is computed from the mechanical config.** Compute-on-read applied to routing — when the mechanical config changes (docs move, new code root added), the filter updates automatically on next event. No separate maintained mapping to drift out of sync with reality.

## Process and adoption

- **Two goals on one ramp.** The verification harness and bundle that improve today's workflow are literally the first rungs of the autonomy ratchet — no fork between "fix the workflow" and "automate."
- **Walk one capability through the whole machine before generalising.** Vertical slice first; horizontal expansion on proven rails.
- **Dogfood the ratchet.** Each new piece is itself adopted under the trust model it implements: starts at confirm-every, graduates on evidence.
- **Continuous with today, not a replacement.** The current chat workflow is the starting trust level; adoption progressively automates it.
- **Design for the optimal, deliver incrementally.** Early phases expose the interfaces the cascade / checkers / mediator will plug into, so reaching the optimal is adding components, not rebuilding. The seams are the way to get to optimal sooner.
- **Review contracts against each other, not in isolation.** Each contract can read fine alone while quietly disagreeing with another — a reference shape that fits two tables but not the third, a status used in one place and absent from the enum. The cross-contract reading is the check that catches these; do it before code.
- **Verify reuse claims against live schemas (schema-before-SQL, applied to contracts).** A contract that claims to mirror or extend an existing table is an assumption until the real schema is inspected. Correct the contract to match reality, not the reverse. Design-level reuse claims need the same verification as the SQL would.
- **Checking reuse claims reveals reuse you didn't assume.** Verification isn't only validation — inspecting the real `site_work_items` turned up `approval_mode`, `pipeline`, `depends_on`, retry counters, and `item_key` dedup that the contract had reinvented or omitted. The act of checking often finds *more* to reuse than the claim assumed; budget the inspection as discovery, not a rubber stamp.
- **Reuse-before-recreate applies to control mechanisms, not just functions.** The confirm-not-initiate gate was being designed as new machinery when `approval_mode` already encoded exactly that in the existing table. Before building a gate, a queue, a status lifecycle, check whether the system already encodes it — control mechanisms hide in existing schemas as readily as helper functions do.
- **Design artifacts conform to the house style too.** The chassis uses text+CHECK (not native enums), `version`+`previous_version_id` (not `supersedes`), and `deleted_at` (not `status=archived`). A new contract must match these storage-layer conventions, the same way new code matches the code conventions — the conventions agent's remit extends to the schema layer.
- **Scope a shared shape to what it describes.** The common provenance shape belongs on config-entry tables, not on events, logs, state, or queues. Don't universalise a shared structure onto things it doesn't describe — confirming intentional scoping prevents a later "fix" that forces false uniformity.
- **Checking the real system can prove an assumption wrong, not just a name.** Looking at the real `agent_definitions.capabilities` showed it holds loose descriptive tags, not the references the contract assumed — so the whole idea of how two things connected was wrong, not just a label. Check the real thing before wiring anything to it; you may be wrong about the connection itself.
- **If one shared shape is undefined, look for its neighbour.** The bundle shape was missing in exactly the way the active-config shape had been — one step further along the same path. When you find one undefined shared artifact, check the things just upstream and downstream of it; the same gap tends to repeat.
- **Fail loudly; don't quietly tolerate the unexpected.** The house rule (from the naming work) is that readers should not paper over odd inputs and carry on — that just hides the real problem. New parts (the bundle builder, the confirmer, the trigger filter) should stop and surface an unexpected shape, not normalise it away.
- **A strong rule usually has a scope; don't stretch it over everything.** "One path to active" covers the config tables; the trust ledger is a separate domain with its own gated flow. The asymmetric de-graduation isn't a hole in the rule — it's outside the rule's scope. When a rule feels universal, name what it actually covers.
- **In a system where behaviour is stored as data, "the code" is partly in the database.** Here workflows are jsonb on `agent_definitions`, tools are rows in `content_components` at tool level, prompts are text columns. So the context a task needs includes definition rows, fetched like source files, and the reuse-search has to cover them — the common duplication isn't a repeated function, it's a near-copy of an existing workflow or agent. (And as ever, these live where the schema says, not where you'd guess — there's no `workflows` table.)
- **Reading the system's own design is not sensitive; reading content or customer data is.** Split database reads by kind: definition data (the design) and operational data (the telemetry) are routine context for our own use; content/customer data is the smaller, gated set where privacy matters, mainly in the service. Gate the minority, not the common case.
- **Probe before you fetch; check the result against the gates.** You can't know a query's result size until you run it, and results are often bigger than expected. So the flow is multipass: probe (count + shape), check against size and sensitivity gates, then fetch the right form — full, a sample, an aggregate, or just a pointer ("N rows matched, here's the query"). An oversized result becomes a summary or a pointer, never an unbounded dump. This is "inline what's needed, point at the rest" applied to data.
- **For debugging, the run narrative beats the row state.** What a task usually needs is not "what does this row say now" but "what happened on this run" — the spawn tree, the step sequence, the errors, the logs, the messages. Tie it all together by the run's correlation key (here, `orchestration_id`) so the evidence is one coherent run, not scattered lines.
- **A healthy-run signature turns log-reading into diff-reading.** Capture the expected step sequence and spawn-tree shape of a good run, then on failure diff the actual run against it and show where they diverged. It localizes the break instead of making someone scan everything — verification applied to runtime behaviour, not just to code output.
- **The debugging guides you already wrote are authored knowledge to capture, not just docs to read.** Known failure fingerprints (a signature + the commands that confirm it + the fix) have the same shape as standards and should be surfaced for the matching task the same way. Seed them from the existing guides; grow them as run-signature diffs reveal new ones.
- **A capability's availability scales with what the codebase provides; discover the structure, don't assume it.** Many of the useful capabilities (definition-data fetch, run traces, run signatures, log correlation) only work if the codebase has a particular structure — a correlation key, telemetry tables, named logged steps, data-stored behaviour. Those are rich on our own codebase, so build the optimal version against it first — but they are facts to discover per codebase, recorded in the config, with each capability degrading (to a weaker form, or "unavailable because no X") rather than breaking where the fact is missing. Don't bake your own codebase's shape into what should be generic engine capabilities.
- **A capability that rests on a manual convention is only as reliable as the convention's coverage.** The run trace depends on every agent logging the run id — a convention that's mostly followed but never audited. So the reliability question isn't "is this the rule" but "how completely is it actually followed," and the gap is fixable (add the missing log lines), not a hard limit. This holds even on the home codebase, where the structure exists but the enabling convention isn't verified everywhere — which makes convention coverage a thing the drift audit measures, not assumes.

## Building discipline (edge cases caught before building)

- **Self-referential structures need a cycle guard.** Trees (parent links), version chains, and related-links can loop if one bad edit gets in, and a root-to-leaf walk over a loop hangs forever. Check for cycles on write, and make the walk detect-and-fail as a backstop. A human confirming the edit doesn't prevent this — they can confirm a loop by mistake.
- **A multi-step apply must be all-or-nothing.** When applying one change means several writes plus emitting an event, a crash in the middle leaves a half-done state (a live row with no log entry; no event, so nothing downstream notices). Put the writes in one transaction and the event in an outbox written in the same transaction, so a crash leaves a clean state and a retry finishes the job.
- **Read a consistent snapshot when you assemble from several tables.** If you read table A, then table B, and a change lands between, you get a mix that never coherently existed. Read the set at one point-in-time.
- **One live thing per target, all the way down.** A dedup on the queue isn't enough if the underlying proposed rows can still pile up. Extend "at most one live X per target" to every layer, and clean up the underlying row when the queue item is expired.
- **Bulk operations need bulk confirmation.** A gate that asks for one confirmation per item becomes a wall when something produces a large batch at once (the first onboarding). Keep the gate, but let a whole reviewed batch be confirmed together; per-item confirmation is for the steady trickle, not the initial flood.
- **Don't let transient or infrastructure failures lower trust.** A flaky test or an infra blip isn't a regression. Filter those out before any evidence is allowed to reduce a capability's trust, or one blip collapses trust and triggers a confirmation flood.
- **Tell "not yet" apart from "broken."** Missing data because something hasn't been onboarded yet is normal and should degrade gracefully; missing data because something is malformed is a fault and should fail loudly. The fail-loud rule is for faults, not for not-yet-authored.
- **Derived indexes and caches go stale silently.** A search index over code or data gives wrong answers, not errors, when its source changes. Refresh it on change and stamp it with a freshness time so it can say how current it is rather than imply it's live.
- **Config and deliverables are different gated paths.** Changing the tool's own knowledge of a codebase goes through one gate (confirm-not-initiate); the tool's actual outputs — code, and here workflow/agent edits — go through a different one (trust level + verification). Don't build one gate for two jobs.
- **Scope a guard to exactly its target.** The "don't re-check what was just confirmed" guard must exempt re-checking *that entry*, not the legitimate downstream effects of it (confirming a new rule should still trigger checking existing code against the rule).
- **Probe by limit, not by count.** To learn whether a result is too big, fetch one more than the cap and see if you hit it — counting a filtered query is as expensive as running it.
- **Log what was actually shown, not what was assembled.** If the thing handed to the model is a rendering of the structured context, take the record of "what it saw" from the rendering, or an audit will claim it saw things the rendering dropped.
- **Don't force a reasoning premise on a mechanical step, and don't log the logging.** A mechanical assembly has a rule-trace, not a reasoned premise; record what it actually has. And writing a log entry is a side-effect of a decision, not itself a decision — no recursion.
- **Recovery must not depend on the thing being recovered.** A tool that can change the platform it runs on can break its own ability to run. The rollback path must work without the tool — no routing through the agents it would be rolling back.
- **Author the vocabulary before classifying into it.** The fixed sets things get sorted into (the concern taxonomy, the priority dimensions) must exist before the agents that sort into them can run. Seed them first.
- **Validate the premise with a thin slice before building the infrastructure for it.** A pile of well-specified machinery can all rest on one unproven assumption. Before building it, run the cheapest end-to-end slice that tests the assumption directly (here: hand-write a flat constitution, assemble one bundle, paste it in by hand — no contracts). If the premise holds, build the infrastructure to scale it; if not, you've saved the build. Good specs keep; the slice de-risks.
- **The loop runs on outcomes — make sure outcomes are recorded, not just inputs and decisions.** You can log every input and every decision and still have no feedback signal. A trust ratchet or improvement loop needs the *result* (did it pass, get reverted, need a human fix) as a first-class record, separate from the decision and its inputs. Without an outcome record the loop has nothing real to move on.
- **Blast radius caps trust.** The more a capability can break, the lower its ceiling — regardless of how verifiable it is. A capability that edits the system itself (low containment, can break everything including the tool) should never be fully autonomous; one whose effects are contained can graduate higher. Containment, not just verifiability, sets the ceiling.
- **Self-modification is a residual risk you manage, not solve.** A system that changes itself can drift past its own checks — gradual degradation that still passes verification, not a crash. Manage it with conservative early trust, a human in the loop, external rollback, and a low ceiling where the blast radius is the system itself; don't assume the safeguards close it completely.
- **Record what actually went in, don't plan to reconstruct it later.** You can often rebuild "what context did this have" by replaying the assembly from the logged inputs — but only while the assembly logic is unchanged and the sources still exist. Change the logic later and the replay gives you today's result, not the one that was used. A manifest captured at the time (the filenames, ids, versions, queries that actually went in) is more robust and cheaper to read than reconstruction. (Same root as "log what was shown, not what was assembled.")
- **A record of what was included can't tell you what was missing.** "Missing" is relative to what should have been there, which you only know in hindsight. So a context manifest makes the "did it have what it needed" diagnosis *possible* (you can see X wasn't there) but doesn't perform it — you still supply the knowledge that X was relevant. Necessary, not sufficient; don't expect it to flag its own gaps.
- **A record earns its keep only when the artifact isn't already in front of you.** In the thin slice the bundle is rendered and pasted by hand, so it's fully visible every time — a separate record of it is redundant. Records pay off once the thing becomes automated and unattended. Don't log what you're already looking at.
- **Within a thin slice, build toward the piece that produces the thing under test, and hand-feed the rest.** The assembler (which produces the bundle being evaluated) comes before the schema extractor; feed the schema by hand for the first runs rather than block on building it. Sequence to the artifact you're trying to judge; stub or hand-supply its neighbours.
- **A bigger context window is not the fix for too much context.** Models don't use a full window evenly — accuracy and recall degrade as it fills (context rot), and the very large windows are premium-priced and tier-gated. So a large bundle is a smell, not a goal: include less, don't buy a bigger window. The cheapest, most relevant context usually beats the most context. (Aim to stay inside the standard window; treat needing the giant one as a signal the selection is too broad.)
- **The call graph is a quality lever, not just a size one.** Pulling the functions actually involved (callers/callees) instead of whole packages or directories shrinks the bundle *and* keeps the model in the zone where it uses context well. Size and quality improve together.
- **For stable, reused context, caching changes the economics.** When a large prefix is reused across a session, prompt caching makes re-sends cheap (reads a fraction of base price). Cache the stable parts (rules, reference docs, code context); leave the changing task/question uncached. This shifts the question from "what can I afford to send" to "what should it see" — which loops back to: send what's relevant, not everything.
- **Some features carry liability — treat it as a first-class review concern.** When a generated feature could create legal exposure (claims, advice, regulated or sensitive content), that needs its own review, the way correctness and house-style do — a concern in the standards taxonomy and possibly a dedicated review agent. Consider it when developing new features, not after.
- **A fuzzy brief must be expanded before targets can be resolved.** You can't pick the in-scope files for an under-specified task until the brief is consolidated into something concrete. So the first pass on a vague task is a framing pass (intent and the relevant existing material at a high level) to expand the brief into a spec; only then can implementation targets be named. Target resolution depends on a clear brief.
- **Hand-built context is the spec for automated context.** When experts pack context by hand for a task, that package is ground truth for what the tool should assemble. Checked against real hand-built manifests: the call-graph slice the tool builds is the same artifact they extract by hand (the relevant whole functions, with line ranges, chosen over the full dump); the standing rules they restate at the top of every handoff are the constitution; the docs they attach are the reference layer. Matching expert hand-curation is the validation that the approach is right — and where the hand-built version has something the tool doesn't, that's precisely the next thing to build.
- **The authoritative source must be the one analysed — a stale checkout ships wrong code confidently.** In a deployed, multi-repo reality the current version of some code can live in the running system, not the on-disk tree, and a stale snapshot looks identical to a fresh one. So analyse the current source of truth and record what was analysed (the commit/SHA), so staleness is visible rather than silent. Same family as the stale search index: derived-from-stale-source is silent wrongness.
- **Live state and run evidence are confirmed-essential for debugging, not speculative.** Every real debugging task's hand-built manifest reached for live table content, a fresh schema dump, and run/error/pod state — the operational and runtime-evidence layers. They are core to a debug bundle, not nice-to-haves; the thin slice defers them, but the need is real and proven.
- **A past failure mode can become the intended mechanism when the goal changes.** The image model answering "several icons" with one gridded image was a defect when you wanted separate icons; for "make one coherent sheet and slice it" that same grid is exactly what's wanted. Before working around a tendency, check whether a reframing of the goal turns it into the feature. What you fight under one objective you can harness under another.
- **Prefer the option that deletes a component, not just the one that works.** Choosing CSS `background-position` over physically cropping the sheet didn't merely pick a styling approach — it removed the need for any image-cropping step at all. When comparing routes, weight the one that subtracts a part to build and maintain; the cheapest code is the code you don't write.
- **Build the general structure, exercise the simple case.** Support the fuller shape in the data model and code paths (many sheets, finer scope) but run only the one simple instance (a single site sheet) to start. This keeps the first version simple to ship and reason about while leaving the growth path open — extension without the cost of building every branch up front. (A sharpening of "design for the optimal, deliver incrementally": the abstraction is cheap now, the unused branches are not.)

### Reuse-checking (finding code that already solves the problem)
- **Checking for reuse is a retrieval problem with a judgement tail, not a generation problem.** So most of it is algorithmic: with a maintained index (signatures, types, call graph — the analyser already half-builds this), "have we solved this?" is a query, and the model sees the query's results, not the whole codebase. The real question isn't "how much code can we afford to send", it's "how good is the index and retrieval". That dissolves most of the "we need access to huge swathes of code" premise — you need a query interface, right up until the final call.
- **Split "identical" from "similar" — they're different mechanisms.** Near-duplicate detection is algorithmic and high-precision (token/AST fingerprinting, structural hashing) — no model needed. "Similar / something to build on" is semantic and fuzzy: same problem, different names and structure, which lexical and structural matching miss — that's where embeddings (cheap, self-hostable, a vector op not a generation call) earn their place. One mechanism doesn't serve both.
- **The cheapest reuse check is a maintained capability catalog.** A vocabulary of what the system can already do turns the first reuse question into a lookup, not a code search. Cost is keeping it current; payoff is short-circuiting most of the work.
- **Recall is the whole game; a pre-filter that drops the real match is worse than no check.** The model then never sees the match and writes a confident duplicate — exactly what the rule exists to prevent. So tune every narrowing layer for recall over precision (fifteen candidates including the right one beats five that exclude it), and treat a reuse check with silent false negatives as actively harmful (it manufactures false confidence), not merely unhelpful.
- **A cheap/self-hosted model should narrow, not decide.** Its job is recall-preserving compression of the candidate set; if it makes the reuse *decision*, the hard judgement has moved to the weaker model and its drops are unrecoverable downstream. Narrow with the cheap layers, decide centrally with the strong model on a small shortlist seen in full.
- **Split the check by timing: fuzzy retrieval before generation, precise clone-check after.** Near-duplicate detection works far better against a concrete draft than a fuzzy intent (a real artifact to fingerprint), so run it post-generation as a pre-merge guardrail; run the fuzzy "is there something to build on" retrieval pre-generation to inform the work. Some of the check belongs after the model writes, not before.
- **A reuse index rots like any derived-from-source artifact.** (Same family as code-freshness and the stale search index.) Stale index → false negatives → can't find code added recently. It needs incremental refresh on change; the heuristic approach trades context cost for index-maintenance cost.
- **You can't tune a reuse finder's recall without ground truth, and the dangerous error is invisible by construction.** The missed match leaves no trace. Get a test set of known reuse cases (past duplications caught in review are the obvious source) or you're blind on the one number that matters.
- **Justify the pre-LLM heuristic layer on quality, not token cost.** Caching and large windows make raw volume cheaper than it feels, but a stuffed window is used worse (context rot), so the case for narrowing is recall + less rot. And don't reach for a model where a deterministic score already separates candidates — sequence the layers (catalog → lexical/structural → embeddings → cheap rerank) and stop as soon as one is good enough.
- **Signature+docstring embeddings are a retrieval substrate, not a dedup optimisation.** Their biggest use is target resolution — task → candidate in-scope set, the largest manual step in the tool; reuse-finding is just one query against the same vectors. They also catch semantic neighbours the call graph misses (related problem, no call edge between them), give "where do we handle X?" navigation, and feed capability-catalog curation (cluster symbols; flag code that maps to no cluster). So build it once to serve all of these, not narrowly for duplication — and "leave it as an optimisation for later" is the right timing but the wrong category: it enables retrieval the deterministic layers can't do, it isn't speeding up something that already works.
- **Defer embeddings as the *next retrieval layer*, not as a nice-to-have, and add them only when measurable.** Sequencing: get the deterministic baseline in first (name/lexical + structural + call graph) — it may cover much of target resolution and candidate-finding for free; add embeddings when it demonstrably misses, with a ground-truth task→files set so you can tell they actually beat the baseline. The trigger that flips it from "later" to "next" is starting to automate scope selection.
- **The cheap signature+docstring embedding is only as good as the docstrings.** A task phrased by behaviour won't sit near a function whose docstring doesn't describe that behaviour, and much code has thin/what-not-why docs. If retrieval underperforms for that reason, the fix is richer input (the body, or an LLM-generated one-line what/why per symbol) at higher cost — decide that from measured recall, not upfront.
- **At this scale embeddings need no vector database.** A few thousand symbols is a small matrix; brute-force cosine in memory over a stored vector set suffices. The standing-infrastructure cost is smaller than it sounds — the real costs are the embedding model and keeping the vectors fresh as code changes (the index-staleness problem again).

### Testing the tool (evidence, not just design)
- **Design has outrun evidence — the next high-value step is a real run, not more design.** The approach is validated by reasoning: against the hand-built manifests, and by writing the context packs by hand. But the assembler has never been run on a real task and its output read, which is the thin slice's entire purpose ("does the assembled bundle beat hand-curation, and what does it miss"). Past this point more design has diminishing returns until a bundle is actually produced and judged.
- **With a hand-built baseline and a tool, the test is the diff between them.** Run the tool on a task you also have a hand pack for, and compare. The places you'd add or drop scope are the target-resolution signal; gaps in the neighbourhood are the call-graph's limits (e.g. interface dispatch); wanting live rows over schema is the data signal; a bloated bundle is the "scope too broad" signal. The delta points to where to invest far better than more upfront design does.
- **Keep the tool as the subject and use a live task as the probe.** A real task (imagery) earns its place as the example that exercises the tool and surfaces its gaps — not as a feature to finish. The task's job is to make the tool's weaknesses visible.
- **The existing hand-built gather script is a coarse version of the whole bundle.** `package_page_build_debug.sh` concatenates a hand-picked set of directories + files *and* appends a read-only live capture (schema, the decisive queries, the agent-definition workflows, pod state). That is code + schema + live data + definitions + runtime in one file — almost exactly what the tool is meant to assemble automatically. The tool is the leaner, automated version of the same artifact; the one piece the script omits is the constitution (it leans on the handoff for standing rules). The hand script is the spec *and* the working fallback.
- **The first real comparison cut both ways — and that's the finding.** Run against skinner-box, the coarse whole-directory gather pulled 110 files when the task turned on ~14 (over-includes: test files, an example doc, unrelated utilities → 1.7 MB), but it also **caught wiring the narrow scope missed** (`registry.go`, the page-build action neighbours) because it deliberately keeps the shared/registration layers for reuse-discovery. So completeness and leanness genuinely trade off; neither broad-directory nor narrow-naming alone is right. This is exactly the scope-delta and neighbourhood-adequacy signal predicted for a first real run — evidence, not design.
- **The call graph's specific blind spot is registration/wiring code.** A name-matched call graph won't reach `registry.go` and similar, because registration happens through an init/registry mechanism, not a call from the in-scope symbol. So the assembler needs a force-include for wiring/shared files (the way the script keeps them for reuse-discovery), or the user adds them by hand with `-scope`. A concrete, durable instance of "the call graph misses things", alongside interface dispatch.

### Shape of the eventual tool (so trial pieces graduate, not get thrown away)
- **A bundle has two halves; one tool makes each.** The gather script produces the code + data + runtime + definitions half; the handoff/pack produces the framing half (task, next action, the decisive fork, standing rules, what's already resolved). Neither alone is sufficient context for a fresh chat — together they are the bundle. This is the constitution+task vs code+data split, seen in practice: a fresh chat with only the gathered code/state could re-derive the diagnosis but would lack the prescribed move, the fork, and the rules.
- **Two goals diverge; name which you're serving.** Getting a task done (use the ready script + handoff) and advancing the tool (run the assembler on the same task and learn from the diff) are different objectives. The assembler is currently the *experiment*, not the shortcut — leaner but less complete (misses wiring). Don't conflate "do the task" with "test the tool"; decide which the current move is for.
- **The eventual tool is workflow + spawned-agents + optional HITL + front-end + generic — so anchor the thin-slice CLIs as prototypes of specific actions.** The mapping: analyser → an indexer action (+ a refresh trigger on change); assembler → a code-context action, with target-resolution as a sibling and the first natural HITL stop (confirm the scope before assembling); dbcontext → a data-context action (the multipass probe-gate-fetch); the pre-merge near-duplicate review, the reuse review, and liability review → build-time review contributors; the constitution → the active-config (tenant rules/standards/objectives). Each responsibility is a separate spawned agent/container so the logs and responsibilities stay distinct, replying on the caller's responses topic, as the platform already does. Genericity comes from per-tenant config plus pluggable per-language analysers (Go now via go/ast, others later through the same bundle contract — the way deploy already has github-now / other-adapters-later). Build each trial piece in this shape so what a trial teaches (e.g. the wiring-include) lands as a feature of the action that ships, not as throwaway scaffolding.
- **Two layers, both multi-agent — keep them distinct.** The website-builder (the chassis: adoption, planner, content, research, imagery, rerender, deploy) is the subject the tool helps develop, and a product in its own right. The context tool is the development layer that assembles task context and verifies changes to that builder (and, generically, to any codebase). The builder builds sites; the tool builds reliable changes to the builder. Neither replaces the other; focusing on the tool hasn't dropped the builder — it sits one layer down.
- **The remaining gaps are all "find", not "include".** The tool can include any code (`-scope`) or any doc (`-doc`), but it can't yet *find* the relevant one for a task automatically. Target-resolution (which code), matched-standards retrieval (which guidelines), and the wiring-include (the code a call graph can't reach) are the same missing capability from different sides — selection/retrieval, not inclusion. Concretely for documentation: the analyser reads code only; guidelines enter via the always-on constitution plus manual `-doc`; auto-selecting the relevant guideline is the deferred standards/docs contributor — a named-but-hand-filled slot in the bundle.
- **"Different angles" are all contributors; "checkers" are a separate concept.** The build's different angles are two kinds of *contributor*: context contributors each assemble one slice of the bundle (code, data, runtime, standards), and build-time review contributors each review the proposed change from one angle (reuse, duplication, liability, morality, correctness), raising a concern that revises the change or gates via HITL. Separate containers keep each angle's logs and responsibility distinct. **Checkers are not these:** in the web tool a checker is an improvement-loop agent that continuously monitors *deployed* sites against the plan/spec (the existing `check_*.go` family), usually with a fixer — it runs post-deployment, on a loop, in the builder/operate layer, not in the build path. Whether the initial builds reuse some of the same checks is unconfirmed and is to be investigated separately. (The website-builder layer also has its own context-angle agents — research, content, design, imagery — same pattern, lower layer.)
- **A morality review is a distinct angle from liability, and must apply a configured standard, not a baked-in view.** Liability asks "will this get us sued or fined"; morality asks "is this right" — they overlap but some legal things are still wrong. The tool must not hard-code one moral view: the morality review (a build-time contributor) applies a *layered, configured* standard held in the active-config — a base framework the operator chooses (for marketing sites, advertising/consumer-protection standards like the UK ASA/CAP code and CMA guidance, plus recognised AI-ethics frameworks for the generation angle), the operator's own judgement on top with priority, and later jurisdiction/government guidance and a current-focus overlay as higher-priority dated sources. It runs at two altitudes (per-output, and a vertical-level gate at intake on the domain/objective), and because moral calls are contested it routes hard cases to a human (HITL) rather than auto-resolving. The tool applies the configured standard and flags; it is not the moral authority.
- **A trial finding can land as a tool feature, as intended.** The first adoption run showed the call graph misses wiring/registration files (`registry.go`); that taught the rule, and the rule shipped as the assembler's `-include` flag (force-include named wiring/shared files regardless of the call graph). The trial's output was throwaway; the capability it specified is now in the tool — the "build trial pieces so they graduate" principle, demonstrated.
- **First real assembler run, on the actual adoption code, confirmed the thesis and the limits.** Scoped to the two decisive functions (`LoadPageSectionsFromSpecAction`, `PlanSectionsAction`) with `-include registry.go`, it produced a ~30 KB bundle against the script's ~1.7 MB (≈57×), and the call graph surfaced exactly the readiness/section-resolution helpers that matter (`planSection`, `createDeferredItems`, `loadComponentSchemas`, `resolveSectionComponent`, …) — neighbourhood adequacy confirmed for this task, with the `registry.go` wiring now present via `-include`. Two honest caveats: the neighbourhood is only as complete as the analysed tree (six files here, so it's a floor — a full-tree run would also pull callees living in other files), and the genuinely-missing contributor for a debug task is runtime evidence (the run trace/errors the script's live-capture block carried but the assembler still stubs).
- **Runtime evidence is built, by extending dbcontext rather than adding a tool.** `dbcontext -runtime-site <domain>` (optionally `-runtime-page`) pulls recent `agent_error_log` rows and the `site_work_items` lifecycle and renders a "Runtime evidence" block; the assembler's `-runtime <file>` slots it into that section. It reused dbcontext's psql/CSV/table machinery (reuse before recreate). On the skinner-box data the lifecycle it pulls *is* the diagnosis — the timed-out original item and the empty-but-`complete` retry. The two tables it queries (`agent_error_log`, `site_work_items`) are the ones whose schema is confirmed; the run-state table (`orchestration_states`) is left for `-rows` until its schema is verified.
- **Target resolution has a deterministic baseline before any embeddings — and it shows its own recall gap.** `resolve_targets.go` scores symbols against the task by name/path/doc word-overlap and proposes the `-scope` set (plus wiring `-include`s by detecting registry-like files). On the skinner-box task it ranked `PlanSectionsAction` first and surfaced the whole section-planning cluster and `registry.go` — but it ranked `LoadPageSectionsFromSpecAction` (also decisive, name echoing "load/spec" not the task's "plan/ready/count") below the cut. That miss is the exact recall gap embeddings fill, and the baseline says so itself. Sequencing held: lexical first (cheap, no infra, and useful), embeddings later when there's a ground-truth set to prove they beat it.
- **Omitting bodies shifts the burden of completeness onto the assembler — the complement is giving the model a retrieval tool, not abandoning curation.** Signatures-not-bodies buys focus and token-efficiency but removes the model's ability to grep the codebase itself; if the bundle omits a body it needs, it's stuck, and the onus is on us to have included the right files. The fix isn't to dump more — it's an on-demand search/read tool the model can call to fetch what the seed bundle lacks (the index, call graph, body-by-line-range, `dbcontext`, and the lexical resolver are already its backends). This is how capable coding agents work: a small seed plus tools to pull the rest. Not a bad idea — a good one — with caveats: it complements curation rather than replacing it (a good seed means fewer fetches); the same size discipline applies to fetched results (probe, signatures first, bodies only when needed) or context rot returns; it should offer both lexical and semantic search (so it's the same investment as the embedding layer, seen from the agent's side); read-only and tenant-scoped; and record what was fetched (provenance). It also shifts the shape from "assemble-and-paste a bundle" to "assemble a seed and serve tools" — which is exactly the agentic/workflow form the tool is heading toward, so it's a direction to take when the tool becomes agentic, not a contradiction of the bundle approach.
- **Stay foundation-model-agnostic; the embedder (and any model call) sits behind an interface, and we have our own models to serve it.** The platform has a small Ollama CPU model (the `ollama-adapter` / `ollama-eval` pods) for cheap, local embedding and inference, and Thunder GPU (the finetuning-flywheel project) for heavy/bulk work. So the model-dependent layers can use a real self-hosted model (e.g. `nomic-embed-text` via Ollama) rather than a stand-in or an external API — and because it's behind an `Embedder` interface, the model stays swappable. Model-agnosticism is a hard constraint, not a preference: don't couple the tool to any one provider's mechanisms.
- **The embedding layer is built (`embed.go`) — mechanism verified, real recall pending a model run.** `embed build` indexes the analyser's symbols (name + kind + signature + doc + path, embedded then L2-normalised) and `embed query` returns cosine top-k for a task; two embedders — an Ollama client (POST `{model,input[]}` to `/api/embed`) and an offline token-hashing stand-in. Tested here with the stand-in (proves index→cosine→rank→suggested-scope) and against a stub HTTP server (proves the Ollama request/response handling, batched build + single-text query). The stand-in is *not* semantic, so the recall gain over the lexical baseline is only demonstrable by running `query -ollama` against the real model, and only *measurable* once a ground-truth task→files set exists. Index and query must use the same embedder (same vector space). Next: merge the lexical and semantic candidate sets into one `-scope` proposal.
- **PARKED for a dedicated discussion: provider-native tool use vs a model-agnostic second round-trip.** The agentic search-tool direction would normally use the model's native tool-calling, but that is provider-specific and breaks model-agnosticism. The model-agnostic alternative: the model states what it needs in its text/JSON output, the orchestrator fulfils it via our tools, and feeds it back on the next API turn — no provider tool-calling. Attractive because it keeps agnosticism and full control over what's fetched (so the size discipline still applies); the tradeoffs are added latency (full round-trips vs streamed tool calls) and needing the model to emit a reliably-parseable need-spec. Flagged, not resolved — to compare properly when the tool goes agentic.
