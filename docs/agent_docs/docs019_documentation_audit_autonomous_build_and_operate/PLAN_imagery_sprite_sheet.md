# PLAN — sprite-sheet imagery (one coherent sheet, CSS-sliced)

The framed feature, with decisions locked. A site generates **one coherent source image** as an N×M grid of small glyphs in a single style; the browser slices it with CSS `background-position` into icons, bullet glyphs, and nav accents. The aim: visual coherence (all glyphs share one style/palette), low cost (one generation), and low-res accents that take some communication load off text.

This plan is simple-first with hooks for later granularity. Build the structure to allow many sheets at finer scope; exercise only one site sheet now.

---

## Decisions (locked)

| Decision | Choice | Hook for later |
|---|---|---|
| Sheet scope | **One per site** | `scope` column already supports `page`/`section`; later emit more rows |
| Regions | **Known N×M grid, fixed coordinates** | grid plan in JSONB can grow / go non-uniform |
| Slicing | **One sheet + CSS `background-position`** (web sprite) | derived-asset columns exist if we ever want physical slices |
| Model | **Banana / gemini-3-pro-image-preview** | adapter routes by kind; other kinds unaffected |
| Bullets/nav | **CSS `::before { background: … }`** (simplest reliable) | richer per-component use later |

**The reframe that makes this cheap:** the model's tendency to answer "several icons" with a single gridded image — a defect when you wanted separate icons — is exactly what a sliceable sheet wants. We harness the grid instead of fighting it.

**The simplification CSS positioning buys:** no Go image cropping. The sheet is one asset; "slices" are CSS rules computed from the grid geometry. There is no slicing action to build.

## Flow

1. **Plan.** Planner emits one `site_plan_imagery` row: `scope='site'`, `kind='sprite_sheet'`, prompt for a clean N×M grid (one glyph per cell, reading order, single flat style/colour, flat background), plus `cell_names` naming each cell's intended glyph (e.g. 3×3: `search, menu, arrow-right, check, info, download, star, mail, chevron`).
2. **Generate.** Image-build-handler routes `sprite_sheet → Banana`, requests the sheet at the fixed size, stores one `assets` row.
3. **Emit sprite CSS.** A small step computes the stylesheet from the grid geometry + cell names: for cell *(r,c)* → `.sprite-<name> { background-image:url(<sheet>); background-position:-<c*cellW>px -<r*cellH>px; width:<cellW>px; height:<cellH>px; background-size:<sheetW>px <sheetH>px; }` (scaled down for low-res display). Store as a `css_snippet` for the site. This is the "slicing", in CSS, generated by code — compute-on-read from {grid plan, fixed dims}, nothing extra persisted.
4. **Consume.** Renderer includes the snippet; bullets/nav/section accents use `::before { content:''; display:inline-block; }` + a `.sprite-<name>` class. Simplest reliable placement; richer use later.

## Phasing (simple first; stop and eyeball between phases)

- **Phase 0 — confirm + fix geometry.** Fresh `\d site_plan_imagery`, `\d assets`, `\d css_snippets`; confirm the renderer's CSS-inclusion path; lock the grid (start 3×3 @ 768²). No code yet.
- **Phase 1 — sheet generation.** Planner emits the one site `sprite_sheet` row; adapter routes to Banana; sheet stored. **Gate: eyeball the sheet** — is it a clean, coherent, flat-background grid?
- **Phase 2 — sprite CSS.** Emit the stylesheet from grid + dims; store as a site `css_snippet`. **Gate: a test page shows the right cell for a given `.sprite-<name>`.**
- **Phase 3 — consume.** Wire bullets/nav/one section's accents to the classes via `::before`. **Gate: rendered on one real site, readable, accents land.**
- **Phase 4 — granularity (later, only if the simple version earns it).** Per-page/section sheets (more rows at finer `scope`); a vision step to verify/auto-map cells to intended glyphs; more cells; physical-slice fallback if CSS positioning proves limiting.

---

## Risks / open

- **Cell-content alignment (the real risk).** The model may not place the intended glyph in the intended cell, or may drift in count/order. First cut: ordered-grid prompt + **eyeball and assign meanings after** (treat the sheet as "N coherent glyphs", map names to cells once it's generated). Later: a vision check that maps cells → intended names and re-requests on mismatch. Don't assume cell (r,c) is the requested glyph until verified.
- **Low-res legibility.** Glyphs shrunk to bullet/nav size must stay readable; tune cell count and display size on a real site (Phase 3 gate).
- **One sheet's style vs varied needs.** A single site sheet trades per-glyph relevance for coherence — accepted for now; per-section sheets are the Phase 4 release valve.
- **Schema reality.** Everything above assumes the JSONB hint columns and the `css_snippets`/render path are as remembered — confirm with fresh `\d` before any migration or SQL.
