What "vertical-exemplar research synthesis" means, plainly. Take a concrete case: someone hands the system smithlocks.co.uk, a locksmith. Today, the system researches that domain only — searches for it, scrapes it if it exists, classifies it. It never looks at anyone else. The problem statement asks for more: find the best existing locksmith websites (the "vertical" is the niche — locksmithing; the "exemplars" are the best sites in it), read them, and work out why they succeed — do they lead with emergency call-outs? Do the good ones show response-time maps, pricing calculators, accreditation badges? What tone, what page structure, what tools? "Synthesis" is the step that turns five scraped websites into a short written conclusion: here is what works in this niche and why — reasons, not copies. That conclusion gets saved as a spec (vertical_landscape) so the later steps that decide strategy and page structure can read it and build on it. In one sentence: look at the best of the competition, understand why it works, write the lessons down where the planner can see them.
What a "hop" is. The build system moves work like a relay race. The baton is a row in the site_work_items table; each baton names which agent should carry it (handler_agent). A scheduler sweeps every 30 seconds, picks up an unclaimed baton, and runs the named agent. That agent does its one job, writes its findings into the site's shared notebook (site_specs), then creates the next baton and stops. One hop = one baton, one agent, one notebook entry, one new baton. The current relay: research this domain → decide the strategy → write the brief → plan the site → build each page. Adding the exemplar-research hop means inserting one more baton pass between the first two legs: research this domain → research the niche's best sites → decide the strategy → …
The design choices, spelled out. A new agent rather than a bigger classifier, because your own rule is distinct responsibilities: the classifier's job is "understand this one domain", the researcher's is "understand the niche" — and separate agents keep logs and maintenance separate, which is also why it's a hop and not a sub-workflow. Inserted after the classifier because the researcher needs the classification ("this is a locksmith site") to know what to search for, and before the strategist because strategy is the first consumer of the lessons. Reuse-only because every step it needs — search, scrape, format, one LLM call, spec write, create-next-item — already exists as an action, so the whole agent is one database row, no Go, no image build. Written as a spec rather than passed in messages because specs are the per-site shared memory across hops (and we just spent a week learning what happens when messages get big).
