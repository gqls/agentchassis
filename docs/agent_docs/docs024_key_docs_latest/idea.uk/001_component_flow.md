Here's how pages are built, traced through the page-build-handler definition plus docs 027 and 003.
The build separates site-level chrome from per-page sections, and page-rerender assembles them. Components live in content_components — each row is a function (the kebab-case identifier) plus an html_template that carries its own scoped CSS, which is why every section arrives with an inline <style> block. Variants are separate functions (hero, hero-split, header-professional-dark, header-minimal-light, footer-4-column).
Header, footer and head are site-level, and they flow down a chain: the layout declares default_header_component_id / default_footer_component_id; install_site_composition copies those onto the new style_collections row; update_site_defaults copies those onto site_components.component_id; and renderAndStoreSiteComponent renders the template into site_components.rendered_html. If the style collection's header id is NULL or site_components isn't linked, it drops through to a hardcoded RenderFallbackHeader.
Per-page sections go through plan_sections inside page-build-handler, which picks section functions from a global component library — and 027 is explicit that layout-aware section selection is future work, not built. page-content-writer writes the prose per section, save_page_sections persists each to page_components, and page-rerender concatenates page_components.rendered_html in order, wraps it with the site header/footer, and commits to git → B2. Colour adapts via the inheritance model in 003: styles.css sets body { color: var(--color-text) } and headings/text use var(--section-*, var(--color-*)), so light sections inherit the palette automatically while a dark section sets --section-* on its own container — a sanctioned override, not a bug in itself.
