# Where we are — the diagnosis loop's blind spot

Plain prose, append-only, newest at the bottom.

---

## 2026-08-10 — what was wrong, and what I did about it

You asked for item 5 of the five rulings: let the diagnosis loop see the
orchestration states table. Here is what that turned out to be.

**The background.** When we ask the diagnosis loop to investigate something, it
builds itself an evidence pack — recent errors, work items, the run states, some
code — and part of that pack is a list of the database tables that exist, so it
can write its own follow-up queries against real table and column names instead
of guessing. Twice recently we pointed it at the hero/logo bug and twice it came
back saying it couldn't verify anything. The second time it explained itself: it
had tried to look up a run by `id`, the real column is called `orchestration_id`,
and — this is the important bit — it said it **couldn't see that table in its
list at all**, so it wouldn't guess again and wanted a human to tell it the
column name.

**What I expected to find.** One table accidentally left off a list.

**What was actually there.** The list isn't hand-written; it's generated by a
filter that keeps tables whose names start with `site`, `page`, `content` or
`flow`. That filter was sensible when someone wrote it. Since then the evidence
pack grew new sections that read other tables — and nobody updated the filter.

So I checked which tables the pack itself reads, against which ones the filter
lets through. Six tables read; **one** of them survived the filter. The pack was
handing the loop rows of data from six tables while telling it the shape of one.
Out of 433 tables in the database, the list showed 26.

**The bit that made it worse than a missing table.** The list is headed "Schema
(live tables)" and then just stops. It never mentions that it's a filtered view.
So from the loop's side, a table that was filtered out and a table that doesn't
exist look exactly the same. That is why it asked for a human rather than just
trying another query: it had no way to tell "I can't see it" from "it isn't
there". If I'd only added the missing table, we'd have fixed that one run and
sat waiting for the next table to go missing the same expensive way.

**What I changed.** Three things.

The first: the tables the evidence pack reads are now always listed, whatever the
filter says. Not as a hand-typed list that will rot — the code now has a test
that reads the pack's own database queries and fails the build if someone adds a
query for a table that isn't covered. So the next person to add a section can't
quietly recreate this.

The second: the list now says it's filtered. It states how many tables it's
showing out of how many exist, says plainly that a missing table doesn't mean a
non-existent one, and tells the loop it can just ask for any other table's
columns using the read-only query channel it already has. That last sentence is
the one I care about most — it turns "I need a human" into one more query.

The third: tests, including one where I deliberately broke the code to check the
new safety net actually catches it. It did.

**Three things I got wrong on the way**, since they're the useful part. I ran a
check on whether the list already carried a "this is filtered" warning, and my
query accidentally searched the entire 80,000-character document instead of just
that section — it said yes. If I'd believed it I'd have skipped the second change
above, which is the one that generalises. Then a keyword search told me the word
"relevance" was in the section; it was a column called `relevance_score`, not a
warning. And my new safety-net test, on its first run, reported a database table
called "the" — it had been reading English prose out of the source code rather
than SQL. The obvious patch was to teach it to ignore the word "the", which would
have made it a bit weaker every time anyone wrote another sentence in that file;
I made it read only the SQL instead. When I then guarded against SQL it *couldn't*
see, it immediately caught a query I'd written badly myself ten minutes earlier.

**Where this stands.** The code is committed and it's gone to the review council
(reference `df9dae6c`). But it is **not live**. Go changes only take effect when a
new image is built and rolled across the fleet, and that's your `make release`, not
something I should fire. Until then nothing has changed in production.

And I want to be straight about the finish line: checking that the table now
shows up in the evidence pack is **not** proof this worked. The real test — which
the commission specified and I agree with — is to re-run the diagnosis on the
hero/logo bug and watch its follow-up query actually execute instead of erroring.
That needs the roll first.

**What this unblocks.** Item 1's research. The commission put item 5 first
precisely because the question "where does `image_url` get lost?" is one whose
evidence lives in the run-states table, and the loop couldn't address that table.
Once this ships, that question is answerable by the tool instead of by hand.
