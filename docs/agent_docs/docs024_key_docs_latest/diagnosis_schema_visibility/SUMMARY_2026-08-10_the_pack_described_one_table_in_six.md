# SUMMARY — 2026-08-10 — the evidence pack described one table in six

## What we're trying to do

Make the diagnosis loop able to investigate bugs whose evidence lives in the
platform's central run-state table. More broadly: stop the loop's evidence pack
from silently hiding the shape of the data it is showing.

## Where we've come from

The loop was pointed twice at the hero/logo bug (`bugs_open/236`) and twice
returned UNVERIFIABLE. The second run said why: it had queried a run by `id`,
the real column is `orchestration_id`, and it could not find that table in the
evidence pack's schema listing — so rather than guess again it asked for a human.

That reads, to a casual eye, like "your premise was wrong". It wasn't. The loop
could not address the table at all, for reasons entirely unrelated to the
hypothesis under test. The owner ruled on 2026-08-10: *"yes, let diagnosis loop
see the orchestration states file."*

## What we've done

Found the producer, which the commission had left `[UNVERIFIED]`: a Go helper,
`gatherSchema`, in the gather action itself — not a config step, so it needs an
image.

Then found the problem was five times larger than the ruling assumed. The schema
listing is generated by a relevance filter (`site%`, `page%`, `content%`,
`flow%`) that selects **26 of 433** tables. Of the **six** tables the evidence
pack itself renders rows from, exactly **one** survived that filter. The pack was
showing rows from six tables while describing the columns of one.

And a second defect the ruling had not named: the listing never said it was
filtered. A filtered-out table and a non-existent table rendered identically —
which is precisely why the loop asked for a human instead of issuing another
query.

Shipped three changes, committed `5f8a326fc`:

- the tables the pack reads are listed unconditionally, beating both filters and
  sorting first so truncation cannot reach them;
- the listing now states its own coverage, that absence is not non-existence,
  and that any unlisted table can be read through the read-only query channel
  that already exists — without a human;
- a test that re-derives the table list from the action's own SQL, so the next
  section added cannot recreate the blindness. Proven by mutation, not by a
  green run.

Measured rather than asserted: one caller; no live config overrides the defaults;
the new query returns 31 tables live; +4% on bundle size; table cap untouched.

## Where we are now

**Committed, reviewed-pending, and not live.** The council gate has it
(`df9dae6c`). Go changes are inert until an image is built and rolled, releases
are whole-fleet, and the owner runs them.

Nothing here should be described as working in production. The verification that
settles it is deliberately not "the table now appears in the pack" — it is
re-running a diagnosis whose evidence lives in that table and watching its
follow-up query execute instead of erroring 42703. That is blocked on the roll.
