# PLAN — bug 392: a link-less page is published and nothing ever reads the note that says so

**Lane opened 2026-08-25** by session `bugs_open/387` after finishing 387. Bug was UNOWNED (no
lane dir; `who-owns.py 392` → none; routed at `bugfix_092_writer_link_constraints`, quiet since
2026-07-31). Planned with two independent fable planners plus first-hand live measurement.

## The defect

`prepare_link_context_action.go` loads the pages a writer may link to. On DB failure it degrades
deliberately (`buildLinkConstraintText` returns *"There are NO pages available to link to…Do NOT
create any internal links"*), returns `nil` error, and writes one `agent_error_log` row
`LINK_CONTEXT_UNAVAILABLE`. **Nothing reads that row.** Degrade-not-fail is `bugs_closed/092`'s
deliberate design and is NOT in dispute; the gap is everything after it.

## Owner decisions (taken before planning, binding)

- **D1 — artefact check, cause-agnostic.** Detect the DAMAGE (a deployed prose page carrying no
  writer-authored internal links), not this one cause. The log-row reader is kept as a second
  trigger so 392's acceptance is met and its registry entry can flip to `consumed`.
- **D2 — prove by inducing the failure on a canary**, verified at the SERVED page.

## Evidence `[MEASURED 2026-08-25]` — queries in RUNBOOK

- `LINK_CONTEXT_UNAVAILABLE`: **2 rows ever**, both 2026-08-24 14:21Z, two sites, DB query timeout.
- **No live damage today**: agritec.uk `seaweed-and-the-carbon-question` was rewritten 1h later
  and carries 3 prose links; remortgagecalculator.uk `what-your-number-means` FAILED mid-build
  and has no `page_components` at all. **This is a latent class defect, not a live incident.**
- Deployed active pages with zero prose anchors in `content_data`: **411 of 736**. On the prose
  page types (`blog-post` 31/164, `guide` 59/98, `content` 97/158) = **187**.
- Of those 187, **48 are `rebuild_policy='owned'` — 48 of 48**, i.e. every owned page in the
  population is link-less. Actionable remainder: **139**.

## Five findings that decided the design

1. **The row already joins to the exact page.** `context` holds only `site_id`, but the
   first-class column `orchestration_id` IS populated (`log_action_error.go:99-112`), and
   `orchestration_states.collected_data->'input_data'->'current_page'` resolved the exact page
   for **both** rows. Recording `page_name` at write time is still worth doing — orchestration
   rows are reaped, the log row lives 365 days.
2. **The instrument decides the answer.** `rendered_html` includes template nav/hero/CTA and
   reads 2–3 on a page whose writer wrote nothing (140/737). `href="/` in `content_data`
   measures the writer's prose anchors (411/736). Structured `cta_url`/`link_url`/`hero_url`
   are real links chosen by a *different* mechanism and are excluded by design. **I got this
   wrong first and corrected it — logged in `WRONG_CALLS.md`.**
3. **`page_rerender` CANNOT repair this — 392's own candidate 1 is wrong as written.** Live
   `agent_definitions`: `page-rerender` neither spawns `page-content-writer` nor knows
   `edit_live`; `page-build-handler` does both; and `page-content-writer` is the **only** agent
   fleet-wide running `prepare_link_context`. The missing links live in `content_data`, which a
   rerender regenerates *from*.
4. **The repair machinery is already live.** `content_rewrite` → `page-build-handler` →
   `page-content-writer`, ~30/day. `discovery_checks/check_orphan_pages.go` is this bug's
   near-inverse and its `(future handler)` comment is **stale** — `internal-linker` is live with
   7 completions to 2026-08-24.
5. **The discovery-check framework is live, hot and self-closing.** `source='discovery'` filed
   659 items across 27 sites in 3 days. `CheckResult.Resolved` closes items on **positive
   re-observation** only (RFC_010, owner ruling 2026-08-02).

## The design

One new discovery check in the existing in-process fleet. **Nothing new is deployed** — no
service, no image, no cron slot, no handler, and (see D3 below) no change to any live agent.

### D3 — the two fable planners disagreed; this is the resolution

The framework planner proposed teaching `internal-linker` an `outbound` direction so its
`plan_links` step picks targets and anchor text. The reuse-first planner rejected that: the
repair already runs through `page-content-writer`, **the one agent that runs
`prepare_link_context`**, so the writer receives a fresh allow-list and selects its own targets —
an LLM planning step upstream is redundant, and it means editing a live shared agent that the
`webdesign_tool_rebuilds`/`353` lanes are actively watching.

**Resolution: the reuse-first route, with one detail taken from the framework planner.**
No `internal-linker` migration. But the item MUST carry `spec.mode='edit_live'` — migration
`299_edit_live_channel_for_content_rewrite_writer.sql` exists precisely so the writer *edits*
current sections instead of regenerating them (`load_current_section_content_action.go:95-98`,
built for `bugs_open/178`). **`internal-linker`'s inbound branch never sets it, which is why its
own rewrites risk 178-style prose destruction. We do not inherit that gap.**

### Part 1 — the detector (`platform/`, council-scope)

`platform/orchestration/actions/discovery_checks/check_missing_prose_links.go`, sibling to
`check_orphan_pages.go`, registered by `init()`, enabled on the quality rotation by a `_HOLD`
seed after the roll (the `603_enable_page_list_stale_HOLD.sql` pattern, with its positive and
negative `service_binary_capabilities` controls — an unregistered name is warn-and-skip, i.e.
silently inert while reading as enabled).

**Instrument, stated in the file header**: internal prose anchors in the decoded string values of
deployed `page_components.content_data`, identified with `datahelpers.ExtractHrefs` +
`ClassifyLinkScope` (`links.go:42,109`) — the same helpers the deploy gate and
`check_phantom_internal_links.go` use, so "internal link" means one thing across all three. NOT
`rendered_html`; structured link fields excluded by design.

**Files when ALL hold**: `page_type ∈ {blog-post, guide, content}`; zero internal prose anchors;
prose mass ≥ ~1,500 chars; the site has ≥3 other linkable pages (same predicate as the writer's
allow-list, `prepare_link_context_action.go:54`); `rebuild_policy IS DISTINCT FROM 'owned'`; and
no open rebuild-shaped item already names the page.

**Non-vacuity control, two layers** — a DB-pinned demand control would be self-blinding here
(the known-positive population is exactly what this mechanism drains, so it goes red the day the
check succeeds). Instead: (a) an in-run canary grading fabricated cases through the pure
predicate, including a fixture whose only link is a structured `cta_url` and which MUST classify
link-less — the instrument statement as a test; drift → return error, and an errored check can
neither file nor retract; (b) the per-type census emitted as a Finding every run.

**Self-closing**: `Resolved` populated on positive re-observation, narrow detector-scoped
`ItemKey` only, never `AllOfType` — so it can never close `check_orphan_pages`' inbound items.

### Part 2 — the repair item

`item_type='content_rewrite'`, `handler_agent='page-build-handler'`, `PageID` set (keeps
`verifier_coverage_test.go:251`'s "all carry page_id" invariant true), `severity=low`,
`spec={mode:'edit_live', reason:'missing_prose_links', page_name, page_id, suggestion:"weave 2–4
contextual internal links into the existing prose, using only pages from the internal-linking
allow-list; change nothing else"}`. `ItemKey` shares `internal-linker`'s namespace,
`internal_link:<page>`, deliberately and with the comment at the callsite that
`work_items_common.go:433-441` requires — so the two producers co-dedup and a rewrite either one
files heals the page for both. Registered per the owner ruling of 2026-08-02 §1, which is what
makes converging producers RFC-free.

### Part 3 — the 392 arm

Same file: `SELECT … FROM agent_error_log WHERE error_code='LINK_CONTEXT_UNAVAILABLE' AND
resolved=false AND site_id=$1`; resolve to the page; if still link-less, file (the row is a
trigger that bypasses the page-type and substance gates); resolve **only on a healed verdict**
via `UPDATE … SET resolved=true, resolved_at=now(), resolved_by='missing_prose_links:<verdict>'
WHERE id=$1 AND resolved=false` (`cmd/content-loss-check/main.go:354`, the estate's only
precedent). Writer gains `page_name`/`page_id` in its `context`. Registry flipped to `consumed`
**in the same commit**, with `reader` file:line and `reader_sink: agent_error_log`.
⚠ The code literal must live in the **reader's own file** — the checker accepts a same-file
const, not one imported from another package (`findingcodes.go:443-450`).

## Blast-radius control

`maxItemsPerPass = 2` per site visit × the quality rotation's ~3.1 site passes/day ⇒ **≤ ~6 new
items/day fleet-wide**, ≤20% on top of the existing ~30/day `content_rewrite` flow, draining 139
over ~4–6 weeks deliberately. Owned pages are **findings-only, never work items** — filing
against them would park 48 rows of exactly the shape `bugs_open/396` was filed about. Plus
`idx_swi_dedup`, the 3h anti-churn window, and the two-strike park that converts a page the
writer cannot fix into a visible `unresolved` rather than a loop (`content_rewrite` runs ~21%
failed/wont_fix, so this matters).

## Verification

Canary on a page that currently HAS links, so the before-state is not vacuous:
`pool-energy-utilities.internal` (about 2, faq 3) or cookly.uk's guide (3).

**Induction — the safe route, settled by reading the code.** `resolveLinkContextSiteID`
(`:296-311`) says *"An explicit config value wins"*, and an unparseable `site_id` lands in the
same `default:` arm as a timeout (`dbFailure`, `dbConsulted=false`, `degraded=true`), so every
line from the degrade onward is real. The writer's `collected_data` fallback is empty (0/26,
`:84-90`) and will not mask it. Scope it by dispatching at a short-lived **cloned** agent
definition, not by editing the shared one.
⚠ **Rejected: the framework planner's `LOCK TABLE pages` route.** It reproduces the original
failure string exactly, but stalls every query touching `pages` fleet-wide for up to ~130s. The
clone route's only difference is the recorded failure string, which nothing branches on.
⚠ **Rejected: hand-inserting a synthetic row.** It proves the reader and not the chain, and
pollutes a code whose rows are evidence.

Then: verify links 3 → 0 at the served page; let the chain run unaided; **verify at the served
page** with `scripts/probe-page-url.sh` (never a composed URL); re-run and confirm `Resolved`
closes the item and the row resolves.

**Tests, mutation-proven both ways**: delete the page-type gate → the `tool` negative must fail;
empty the anchor regex → the positive must fail; delete the site-precondition → the 2-page-site
case must fail. Verify each deletion actually fails before committing — that verification IS the
mutation check.

## Governance

In council scope: the check + test, the writer's context enrichment (`platform/`), and any
`_HOLD` enable seed (HOLD is explicitly in scope). Out of scope, refused client-side: the
registry JSON, the bug-file correction, the register entry, these docs.
**No `council-scope.sh` / `098 SCOPE_PATHS` widening is incurred** because nothing lands in
`cmd/` — that file warns the omission would be silent.
**Not architecture-scope**, and the RFC_022 conditions are to be **enumerated with the query**,
not asserted — asserting without it is itself the objection.

## Sequencing

Go is inert until a roll; DB config is live on apply. So: commit check + test + writer
enrichment + registry flip together (council submission alongside, `Council-Submitted:` trailer)
→ build and roll from committed HEAD, prove with `service_binary_capabilities` positive/negative
controls → apply the enable `_HOLD` by hand → canary → record.
