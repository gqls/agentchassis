There's a single global IMAGE_TAG (currently v1.0.1066) and one agent-chassis binary that runs every dynamic agent — page-content-writer, page-rebuild, the lot — via agent_definitions config. So my Go change ships as a new chassis tag, and update-agent-images-v2 repoints all agent rows at it. The targeted path is make quick-agent-update IMAGE_TAG=v1.0.1067 (build → push → kustomize → DB image_tag → restart the agent-chassis deployment), plus make update-and-restart-orchestrator for the generic-orchestrator statefulset, since both run the chassis. The full make release would rebuild and redeploy everything at the new tag — fine if the tree is clean, riskier if other services have in-flight changes. Rollback is symmetric and cheap: the old image already exists, so update-agent-images-v2 IMAGE_TAG=v1.0.1066 + a rollout restart reverts without a rebuild.

A site's colour choice lives in a record called its style collection, and that collection is meant to name which header and footer component the site uses. A build step, update_site_defaults, copies that choice into the site_components table, and site_components is what actually gets rendered onto the pages. When that chain is intact, a light collection names a light header and footer and the site renders light chrome. For idea.uk the chain is broken — the step didn't run, or the collection names no header — so the build drops to a header that is hardcoded dark. Repairing the chain so a light collection produces a light header and footer, and as a backstop making that fallback header read the palette so even it comes out light, is needed whichever lane we choose, and it's the lowest-risk change, so it goes first. Once the proper light header renders, the little patch-ups that currently paper over the dark fallback — removing its stray search icon, un-stacking its nav — aren't needed at all.
