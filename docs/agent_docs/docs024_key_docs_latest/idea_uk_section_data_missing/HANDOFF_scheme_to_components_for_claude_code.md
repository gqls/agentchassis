# HANDOFF — scheme reaches components (for Claude Code)

Date: 2026-07-02. Status: investigation complete enough to decide; no code or DB changes made anywhere in this thread. One design decision gates the fix specification (see §Decision). Companion files from the chat thread: `RUNBOOK_scheme_to_components.md` (commands + check results), `running_notes_scheme_to_components.md` (journal), `PLAN_scheme_to_components.md`, `REFERENCE_styling_render_pipeline.md`.

## The problem

The chassis resolves each site to a light or dark design scheme, and the scheme itself travels correctly: idea.uk resolved light, its layout (`tool-portal-light`) emits light values for the page, surface, header and footer CSS variables, and the renderer only adds white-text (`--section-*`) overrides when a palette is dark, which idea.uk's is not. The failure sits in the component library that supplies the HTML. Components carry their own inline CSS, and much of the library was written assuming a dark site: the active hero and call-to-action paint their bands from palette variables but pair them with literal white text and an unconditional declaration of the dark-text context; the active footer consumes the correct light footer-background variable yet still declares white text over it; 37 of 84 active section components self-declare the dark context and 15 carry literal hex backgrounds. On a light site these assumptions override or bypass the correct variables, so sections render dark — or, in the footer's case, light-with-white-text, unreadable. idea.uk's deployed pages additionally appear to predate the current library (the active header component is already fully variable-driven and would render light today), so part of what is visible is stale rendered HTML. Underneath it all is one design question the library currently answers three conflicting ways: when a section's band is dark by design, who supplies the matching text colours — the component, the renderer, or the layout.

## Established (verified) mechanism

- styles.css is built by `RenderCSSFromSpecAction` (render_css_from_spec_action.go) in three parts: (1) the layout `css_template` rendered as a Go text/template over merged palette/typography/token maps (`{{palette "key" "fallback"}}` helper — fallback used when the palette lacks the key); (2) `css_snippets` append; (3) `buildSectionDefaults` append (color_util.go) — emits dark `--section-*` on `body` only when palette background or surface is dark (WCAG luminance), plus a dark-surface variant on 5 fixed classes (`.features/.services/.differentiators/.about/.faq-section`). On a light palette it emits nothing and everything falls back to `var(--color-*)`.
- Element rules follow the Colour Inheritance Model: `var(--section-*, var(--color-*))`.
- Chrome variables exist and flip with scheme. `tool-portal-light`: `--color-header-bg #faf8f3`, `--color-header-text #1a1a1a`, `--color-footer-bg #f1ede4`, `--color-footer-text #1a1a1a`; `tool-portal-dark`: `#121212 / #e0e0e0 / #0d0d0d / rgba(224,224,224,.8)` and `--color-cta-bg #1e1e1e`. The light layout is MISSING `--color-cta-bg`; no `--color-cta-text` pair exists anywhere. idea.uk's palette (`palette-idea-uk`) has only the 8 core slots — no specialised chrome slots — so the layout fallbacks are what it gets, and they are correct per scheme.
- Chrome selection at page compile: `CompilePageSectionsAction` → `InjectHeader/InjectFooter` → `RenderHeader/RenderFooter` (component_library.go ~1264–1440): `style_collections.header_component_id` (ALWAYS NULL — `install_site_composition` inserts NULL and nothing anywhere writes it non-NULL; effectively a dead column) → `GetComponentByFunction("site-header")` (the single library-wide active one) → else `RenderFallbackHeader/Footer`, which hardcode `background: ctx.PrimaryColor` (default `#1a1a2e`; idea.uk `#1A1816`) + literal white text. The separate `render_site_components` path writes `site_components.rendered_html` but the compile path does not read it.
- `is_dark_section` is a component-level boolean authored by the component-creator LLM (`store_generated_component` extracts it from generated JSON). It currently has no effect on the stylesheet: `queryDarkSectionsForCSS`/`buildCSSsectionStyles` compute per-section `SectionStyles` entries from it (with fallback dark list hero/social-proof/call-to-action/testimonials) but NO active layout consumes `{{range .SectionStyles}}` — built, disconnected.
- Improvement-loop fixers exist (color-variable-fixer agent → `fix_hardcoded_colors` + `fix_forced_text_colors`; nav-link-fixer → `fix_nav_link_templates`; `fix_component_template`). They patch template + rendered HTML and the chrome re-render pattern is `render_site_components` with `force_rerender`. As aimed today they are scheme-blind and ENFORCE the component-owns contract (`fix_forced_text_colors` injects dark `--section-*` into is_dark_section components). USER DIRECTION: fixes must land at initial render (library/composition/renderer); the loop fixers remain available as backstop, never required for new builds.
- Class contract is inconsistent: layouts style `.{function}-section`; the 5 surface sections + footer honour it; hero emits `.hero`, CTA emits `.cta-section`. Every component root does carry `data-component="{function}"` (naming contract, component_validation.go) — an attribute selector `[data-component="X"]` would sidestep the class mismatch if the renderer ever needs to target sections.

## Check 2 results (templates + blast radius, run 2026-07-02)

- Active `site-header` (generated): fully variable-driven (`var(--color-header-bg, var(--color-background))`, `var(--color-header-text, var(--color-text))`). Renders light on idea.uk. Needs nothing.
- Active `site-footer` (generated, is_dark_section=t): HALF-migrated. `background: var(--color-footer-bg, #1a1a2e)` (light on idea.uk) but self-declares `--section-text: rgba(255,255,255,.9)` etc. → white-on-cream, unreadable; newsletter input/border use white alphas → invisible on light. A live bug on any light site the moment the footer renders.
- Active `hero` and `call-to-action`: no hex backgrounds — bands come from `var(--color-primary/secondary/accent)` (hero also has the image + dark-overlay branch, correct on any scheme) — but both pair the band with literal `#fff` text and an unconditional dark `--section-*` block. On idea.uk (primary `#1A1816`) they render near-black bands with white text: readable, deliberate-looking dark bands on a light site.
- `features`: already correct ("Layout only - colors inherited").
- Blast radius (active, forked_from IS NULL): sections 84 total — 15 hex backgrounds, 37 self-declare `--section-*`; header-level 4 total (only one is `site-header`; 2 of 4 self-declare); footer 1 (the half-migrated one).
- The generated footer proves the component-creator prompt currently emits half-migrated components. Whatever is decided must be encoded in the creator prompt + the 003 checklist (its Dark Section Contract item currently REQUIRES self-declaration for is_dark_section=true) or the library keeps drifting.

## The Decision (gates the fix spec)

Gating design question for the user: **on a light site, are dark hero/CTA bands acceptable — even desirable — design, or must a light scheme be able to render fully light?** Then choose the single owner of band text-context:

- **Alt 0 — stale-build + point bugs.** Verify staleness (Check 3), rebuild idea.uk, fix the footer text + the two fallback functions + the creator prompt. No architecture change; dark bands accepted. Leaves 37 self-declarers latent and mixed conventions.
- **Alt A — codify component-owned bands.** Contract becomes: a component that paints its own band MUST declare its own text context; a component whose background the layout/renderer paints MUST NOT. Fix only violations (the footer; any surface-painted self-declarer from 3c; the 15 hex ones). Cheapest coherent end-state; amends 003's blanket rules in both directions; scheme can never lighten hero/CTA.
- **Alt B — renderer-owned per-section context.** Connect the existing disconnected mechanism in Go (append `buildCSSsectionStyles` output the same way `buildSectionDefaults` is appended — no layout edits), key off `is_dark_section`, target `[data-component="X"]` selectors, then strip self-declarations from components. Single owner; per-component lightening by flipping the flag; but `is_dark_section` is LLM-authored and scheme-blind (flag hygiene becomes the maintenance surface) and migration touches all 37 templates + re-renders. Note: stripping WITHOUT connecting the renderer first breaks dark bands on light sites (dark ink on near-black) — order matters.
- **Alt C — layout-owned pairs (generalise what chrome proves works).** Add `--color-cta-bg`/`--color-cta-text` (and hero-band equivalents if wanted) per layout; band components consume the pair with dark fallbacks. The layout — the thing that owns scheme — decides whether a light site's CTA band is dark-accent or light. Touches the two tool-portal layouts now (others inherit via fallbacks), hero + CTA templates, footer fix. Most design control; more variables to curate.
- **Alt full-025 — Phase 4.5 as written** (`data-section-bg` attribute; renderer selector replaces the 5-class list; dual-write migration). Additionally buys the dark-site surface generalisation, which is orthogonal to this complaint; biggest touch; still needs a band-text answer (B or C) on top.

Questioning doc 025 (why it is not simply "the answer"): its Phase 4.5 solves the renderer's hardcoded 5-surface-class list — a dark-site generalisation idea.uk never hits (light sites render surface classes correctly today). Its premise "components must never declare `--section-*`" conflates renderer-painted surfaces (where declaring is hazardous — the footer bug) with self-painted dark bands (where the declaration is load-bearing — strip it and CTA text goes dark-on-dark on light sites). And renderer ownership only works if the renderer knows each band's darkness, which reintroduces the component's intent (`is_dark_section` or an attribute) one hop removed. Within "renderer owns", 025's attribute vehicle is also not the cheapest available — the SectionStyles mechanism is ~built and could be appended in Go without touching 18 layouts.

## Invariant no-regret fixes (safe under every alternative — implement whenever ready)

1. Fix the active generated `site-footer`: text consumes `var(--color-footer-text, var(--color-text))`; drop the white `--section-*` block and white-alpha surface/border (use `--color-surface`/`--color-border` or footer-scoped equivalents).
2. Make `RenderFallbackHeader`/`RenderFallbackFooter` (component_library.go:1375/1405) consume `var(--color-header-bg)`/`var(--color-header-text, var(--color-text))` and footer equivalents instead of `ctx.PrimaryColor` + literal white (~10 lines each).
3. Fix the component-creator prompt + 003 checklist so newly generated components consume the variable model instead of assuming dark (the footer proves live drift). Align `fix_forced_text_colors` with whatever contract is chosen so the backstop doesn't fight the fix.
4. Add `--color-cta-bg` (and decide `--color-cta-text`) to `tool-portal-light` — one line — regardless of alternative, so the variable set is symmetric.
5. After code/library changes: rebuild idea.uk via a full page build (`site_work_items` insert, pipeline=build, handler_agent=page-build-handler, status=triaged — NOT `needs_rerender`, which reassembles stored HTML and may not re-render templates; reconcile this in 016 vs 026 if rerender is preferred) and refresh chrome via `render_site_components` with `force_rerender`.
