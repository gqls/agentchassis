## 3. THE WORK — the per-subject recipe, proven once, now to be repeated

The owner's direction is to take on the backlog. The recipe below is not hypothetical —
it is exactly what closed P1+P2 for `teaser-reveal-panel`, generalised. **Per subject:**

1. **Read the real thing before authoring anything** (S1). For a component:
   `page_components.rendered_html` for a live placement, `content_components.js_content`,
   `input_schema`. For a tool: the deployed page itself. The teaser fence was RIGHT because
   its author discovered the reveal was native `<details>` and the sibling-close lived in
   fleet-shared `snippets.js` — checks written from the PLAN's prose alone would have
   asserted the wrong mechanism.
2. **Author the fence** in the browser-runner check vocabulary (RUNBOOK §8). Use
   `has_visible_area` (TL-034 is fixed; new fences should carry it). Profile-gate
   aggressively — budget ~3–5s per evaluation in-cluster against the **120s whole-request
   deadline** (§10's table). No `selector_count` as a count assertion (it is
   behaviourally `selector_exists`).
3. **Trial it offline**: `scripts/try_fence.go <fence.json> <url>` — genuinely generic,
   zero changes needed for components. 15/15-with-reconciled-arithmetic is the bar.
4. **Mutation-prove it** (S2): `prove_fence_can_fail.go` is **NOT generic** — its mutant
   list is hardcoded to `tool-review-council-simulator`. Copy the architecture of
   `prove_fence_can_fail_teaser_reveal_panel.go` (baseline-first, one mutant per check,
   coverage table, `page-serves-200` survives every mutant, asset-override for behaviour
   living in shared JS). Every check watched red under its own mutant, or the fence is
   not proven.
5. **Persist** via RUNBOOK §9 (supersede-then-insert, generated by a Python script —
   never a shell heredoc, the body contains triple backticks), assert lengths inside the
   transaction, then **read it back out and re-run the fence from the DB copy**.
6. **Dispatch S6 for real**: tools → `tool_acceptance_run.sh <site> <domain> <function>`
   (§10); components → `scripts/DISPATCH_s6_component_run.sh` (committed 2026-08-05 —
   the P2 script was nearly lost to scratchpad cleanup; its header carries the
   preconditions and the negative-control page rule). Read the result per §10: skips by
   REASON, `__step_error` not `error`, `COMPLETED` is not success.

**Naming precondition, tools especially:** `doc_plans.subject_key == pages.name (or
'tool-'||name) == content_components.function` or the run skips-as-clean.
`CHECK_naming_contract.sh` passed 0-broken on 2026-07-31 — re-run it before starting; the
population moves.

## 4. Phasing — calibrate before committing to 147 subjects

**Do NOT start grinding through 147 subjects linearly.** The honest first move is a
**calibration tranche of ~5**, then a cost report back to the owner to set pacing:

- **2–3 tools** that already pass the naming contract and serve a live page — cheapest,
  single page, existing dispatch trigger, the tool convention is well-worn (13 tools
  already have PLANs to copy the shape from).
- **1–2 section components**, chosen for placement count (blast radius) and behavioural
  simplicity — a static render-only component's fence is small (exists / visible /
  no-js-errors / page-200) and its mutation prover trivial; `teaser-reveal-panel` is the
  worked example for anything interactive.

Record wall-clock and iteration count per subject in NOTES as you go. After ~5, write the
cost-per-subject into `README_where_we_are` and ask the owner how fast to go. 147 fences
at even 30 min each is ~10 sessions of work — pace is an owner call, not a default.

**Prioritisation within the backlog** (from P3-as-relabelled): cheapest/most-evidenced
first. Placement count for components is one `GROUP BY` on the census join; tools with
recent acceptance-sweep activity or live traffic first if any signal exists.
