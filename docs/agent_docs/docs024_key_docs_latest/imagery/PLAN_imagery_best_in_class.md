# PLAN — Imagery: best-in-class sites (imagery programme, stage 3)

**What this project is about (read this first).** This repo (agentchassis) is an
autonomous agent platform that plans, builds, and operates a fleet of content
websites — tools, guides, games, news feeds, and articles. Sites are planned by
LLM agents (`build-site-planner`), content and imagery are generated by worker
agents through a Kafka-orchestrated work-item pipeline, and finished assets are
committed to each site's git repo for static deployment. An imagery pipeline
already exists and is verified end-to-end: the planner emits a structured
imagery plan (`site_plan_imagery`, kinds `logo|hero|illustration|icon|infographic`),
discovery checks turn unfulfilled plan rows into work items, `image-build-handler`
routes generation to one of two providers (Stability SDXL for photographic work,
Google "Banana" `gemini-3-pro-image-preview` for flat icons/illustrations), and
`asset-deployer` commits optimised images to the site's git repo, after which the
page re-renders. **robot-hands.com** (an industrial-gripper site, currently being
rebuilt fresh with a news section) is the testbed. This document plans the next
stage: raising the sites' visual quality to *best in class* — data-accurate
infographics, brand-consistent graphic language, content-linked card imagery,
illustrated bullets and lists, copyright-safe product sketches, news-item
imagery, and image performance budgets — with an audit loop that enforces the
standard rather than hoping for it.

Companion documents:
- `RUNNING_NOTES_imagery_best_in_class.md` — turn-by-turn discussion log, updated every session.
- `RUNBOOK_imagery_best_in_class.md` — the tasks the human operator performs (credentials, backups, approvals, verification).

Naming note: earlier imagery work used Phase 0–6 and 2A–2H. To avoid collision,
this plan's phases are numbered **I0–I8**.

## 1. The brief (as given, then expanded)

The user's brief (2026-07-08): make the sites *look and feel* best in class.
Infographics illustrating major news points, latest data, and historical trends —
especially for issues current in users' minds. Graphic artefacts that help
readability and promote the domain brand (professional / usable / friendly, per
site). One consistent good logo throughout the life of the site. Images above
linking/descriptive cards that reflect the content, and similar themed images on
the content itself. Interesting design treatment of bullets and lists (relevant
graphics as bullet points). Sketch illustrations of products where copyright is
a risk — altered viewpoint, product shown in a relevant setting; pencil sketch,
watercolour, or CAD-like diagram depending on how technical the product is. News
feed and individual news items illustrated so the reader gets background at a
glance (e.g. a price graph above an article about a sudden price change).
Appropriately sized images (sprite sheets for bullets). robot-hands.com is the
working domain while building. Few limits — this is exploratory.

Expanded into concrete capability goals:

| # | Goal | What "done" looks like |
|---|------|------------------------|
| G1 | **Brand kit & logo permanence** | Each site has one approved logo used everywhere (header, favicon, OG cards) for its whole life. A machine-readable per-site imagery style guide (palette, medium, mood, reference images) that every generation honours. |
| G2 | **Data-accurate infographics** | Charts of *real* data (latest figures, historical trends) rendered by code — never by a diffusion model — with an LLM editorial layer for titles, callouts, and annotations. Used on tools, guides, and news. |
| G3 | **Content-linked card imagery** | Every linking card (blog index, news feed, tool directory, related-content blocks) carries an image that reflects the content behind it, and the content page carries the same or a sibling image — visually one family. |
| G4 | **Graphic design artefacts** | Bullets/list markers as relevant themed glyphs (sprite sheets), section dividers, borders, background motifs — readability-first, brand-consistent, cheap to serve. |
| G5 | **Copyright-safe product sketches** | Stylised product illustrations (pencil sketch / watercolour / CAD-like per product type), viewpoint deliberately altered from source photos, product placed in a relevant setting. Clearly derivative works, never facsimiles. |
| G6 | **News imagery** | Every news item gets an at-a-glance image chosen by kind: a data chart when the story is data-driven (price moves, trends), an illustration/photo otherwise. Feed and article views share the treatment. |
| G7 | **Performance budgets** | Per-kind byte and dimension budgets, modern formats (WebP), responsive sizes, lazy loading, sprites for repeated small art. Enforced at deploy time and policed by a discovery check. |
| G8 | **Accessibility & sharing surface** | Alt text on every meaningful image; OG/social card images; favicon derived from the logo. Part of what "professional" means. |
| G9 | **Quality loop** | A vision-capable imagery auditor that checks delivered images against the brand style guide and the prompt intent, with bounded fix attempts and respect for locked/approved assets. |

## 3. The key structural expansion: two lanes of imagery

Everything built so far is **plan-driven**: `build-site-planner` decides at plan
time what images the site needs, and the loop fulfils that fixed list. Most of
what this brief asks for is **content-driven**: a card image belongs to an
article; a price chart belongs to a news item; a product sketch belongs to an
`affiliate_products` row. These arrive continuously *after* the plan is fixed,
at content-creation time, and their imagery must reflect the specific content.

Proposal:

- **Lane A — planned imagery** (exists): `site_plan_imagery` rows → work items →
  assets. Extended with new kinds (`sprite_sheet`, decorative artefacts) and
  brand-guide-aware prompts. The planner keeps requesting site/page/section
  imagery.
- **Lane B — content imagery** (new): imagery attached to content entities
  (articles / news items / products), requested at content-creation time or by
  discovery checks that sweep content tables for image-less items. The pattern
  already exists in miniature: `affiliate_products.custom_image_id` FK → `assets`.
  Generalise it: content entities get an image reference (or an
  `entity_type + entity_id` column pair on `assets`), a per-entity work item
  type, and a handler that composes the prompt *from the content itself* plus
  the site's brand guide.

Cards then follow for free: a card is a *view* of a content entity, so the card
image is the entity's image (or a purpose-built `card` crop of it) — which is
exactly the "image above the card reflects the content, and the content page
carries the same theme" requirement.

## 4. Design decisions (D1–D8 confirmed with user 2026-07-08 — see running notes Turn 2)

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | **Data graphics are code-rendered, never diffusion.** Charts come from real series + a charting library (go-echarts first candidate), LLM only does editorial annotation. | Diffusion models fabricate data; documented hard constraint. Best-in-class means *accurate*. |
| D2 | **Two lanes** (plan-driven + content-driven imagery) per §3, sharing the same generation/deploy/audit machinery downstream of the work item. | Reuse before recreate; only the *requesting* side is new. |
| D3 | **New kinds land as one migration + one Go change per batch**, `text` + CHECK (not enums), per repo convention. First batch: `sprite_sheet`, `card`, `product_sketch`, `og_card`. `chart` is deliberately NOT a `site_plan_imagery` kind — charts are Lane B artefacts rendered by code (D1) and stored as assets with their own purpose. | Keeps `chk_kind` and `validImageryKinds` in lockstep; keeps the diffusion pipeline away from data. |
| D4 | **Per-site brand guide as data.** A `site_specs` aspect (e.g. `imagery_style_guide`) holding palette, medium, mood words, negative directions, and 1–3 approved reference-image asset keys. Prompt composition reads it for every generation (extending the existing `imagery_direction` + `directionAppliesToKind` mechanism); Banana generations pass the reference images via `ReferenceImageURIs`. | This is the single biggest lever for "consistent, professional look". The plumbing (reference images, prompt composition, kind gating) already exists. |
| D5 | **Logo permanence = generate → human-approve → lock.** Approved logos (and any human-uploaded asset) are locked via the existing asset-locking columns; auditors and regeneration paths must skip locked assets. Favicon and OG card are *derived* from the approved logo, not independently generated. | "One consistent good logo throughout the life of the site" is a policy, not a generation feature. |
| D6 | **Icon strategy stays dual.** Lucide webfont for UI chrome (wire the validator — carried-over item); generated raster/sprites for decorative and topical glyphs. Bullets use the sprite sheet, not per-bullet images. | Locked lessons from 2026-05-20; sprites keep request count and bytes down. |
| D7 | **Product sketch styling is a constraint, not a knob**: stylised medium chosen per product category (technical → CAD-like line drawing; lifestyle → watercolour/pencil), viewpoint altered from source, in-context setting, "no brand markings/logos/text" hard-coded. Img2img from the cached photo is v2, only with the derivative-work framing. | Copyright safety by construction; matches the existing product illustration plan. |
| D8 | **Budgets enforced at deploy, policed by discovery.** Extend `ImagePurposes` with per-kind byte ceilings and WebP output where safe; add `image_weight_over_budget` discovery check; sprite sheet counts as one download for N glyphs. | Sizing was explicitly in the brief; enforcement beats intention. |

## ⚠️ HOW IMAGE SERVING ACTUALLY WORKS — read before debugging any "broken image"

*Added 2026-07-10 after the leopardess rebuild wasted a turn chasing a bug that did
not exist. An earlier version of this very box asserted that box's mistake. Corrected.*

There are **two different URLs** for every generated image, and confusing them is the
trap:

1. **`assets.url` — a 7-day presigned S3 URL. A throwaway source handle.**
   It expires (SigV4 caps `X-Amz-Expires` at 604800s = 7 days; this is a hard protocol
   ceiling, **not** a setting — you cannot make it permanent). It is **never** used to
   render a page.
2. **`/assets/images/<asset-key>.<ext>` — the durable, committed git path. This is what
   pages actually serve.** `deploy_image_asset` commits the optimised bytes into the
   `sites` repo; GitHub Actions publishes to Backblaze B2 (`portfolio-sites`); the
   Cloudflare worker (`scripts/cloudflare/worker.js`) re-signs each GET server-side, so
   the bucket stays private and the URL never expires.

At render time, `plan_sections` (`plan_sections_action.go:193, 260, 290`) computes
`storage.DeployedWebPath(asset_key, purpose)` and **never reads `assets.url`.** Verified:
zero `X-Amz` URLs appear in any deployed page's HTML.

**Therefore:** a presigned URL sitting in `assets.url` is cosmetic staleness, **not** a
broken image. Most rows have one simply because they predate the in-code url-flip
(`deploy_image_asset_action.go:250`, mirroring the one-shot `w9_04` backfill that
idea.uk received). Do not "fix" it by chasing presigned URLs.

**Debugging a genuinely missing image — do this, in order:**
1. Get the asset's real `asset_key` and `purpose` from the DB. **Do not guess the path.**
   (The wasted turn: curling `/assets/images/logo.png` on sites that have no `logo`
   asset at all, then concluding the pipeline was broken. robot-hands' real paths —
   `hero.jpg`, `hero-home.jpg`, `icon-*.jpg` — all return 200.)
2. Curl `DeployedWebPath(asset_key, purpose)`. A 404 there means **the bytes were never
   committed**, which is a generation/deploy failure or an asset that was never produced
   — not a URL-expiry problem.

**Where deploys run (by design, don't "fix" this):** `agent-chassis` carries the storage
credentials but deliberately **no `IMAGE_BUCKET`**, so it builds no storage client
(`agentbase/agent.go:294`) and `deploy_image_asset` fails there with *"storage client not
available"*. That is intentional — see `107_image_build_handler.sql:725`. Deploys run in a
**spawned** `asset-deployer`, into which `spawn_actions.go` injects `IMAGE_BUCKET` and the
storage creds (`isStorageEnabledAgent`). **Do not add `IMAGE_BUCKET` to the agent-chassis
deployment.** If you hand-trigger `asset-deployer` standalone it will fail, because it
skipped that injection — that is a triggering mistake, not a platform bug.

Injecting a *specific, pre-approved* image (e.g. an owner-chosen logo) has no generation
step to spawn; send the optimised file straight to the git-adapter — see
`docs/leopardessconsulting/scripts/commit_brand_assets.sh`.

Full corrected write-up: `docs/leopardessconsulting/AUDIT_verified_facts.md` D8.
Also from that workstream: a routing change (logo/illustration/infographic → Banana, so
reference images are honoured) is committed in `dynamic_adapter.go` but **not yet deployed**.
