Where tool acceptance criteria should live
Four candidate homes, judged on key, lifecycle, and owner:
site_specs (roadmap or a new aspect) has the right machinery — supersede versioning, pinning, admin surface, auditor loading — but the wrong key. Everything there is (site_id, aspect); tool criteria describe a function deployed across many sites. Site-keyed criteria duplicate per site and drift, and the improvement loop would load criteria for tools a site doesn't have. roadmap holds aspiration/milestones, not verification. There is already a criteria-shaped thing here at site scale — direction.must_have, the site's durable musts that auditors load — and that's exactly where per-site parametrisation of a tool belongs when it exists ("the calculator on this site must use GBP"), because it's genuinely site-scoped.
site_plans / directives fail on lifecycle and owner. The plan is the churniest artifact in the system — superseded on every re-plan, re-derived by sync (the whole plan↔pages divergence saga), and written by the planner LLM. Acceptance criteria exist to hold the bar still across iterations; putting the bar inside the artifact that regenerates most often hands it to an owner (the planner) whose job is to change it. Directives configure building, not verification. Disqualified regardless of their exact columns.
Findings' acceptance_test is the right pattern at the wrong duration: per-iteration done-ness that dies with the work item. That's a feature — but it means something durable must seed it.
The tool's doc_plans PLAN matches on all three axes: keyed by function (travels across sites and forks), supersede-versioned and pinnable (the same site_specs machinery, re-keyed — which is why the spec-aspect instinct was close), owned by creation + humans rather than the planner, and loaded at exactly the moments criteria are consumed (fix time, audit time). So: documents win, for structural reasons, not by default — and the relationship across scales is: durable type-level bar (PLAN criteria) → seeds per-iteration acceptance_test on improvement items → site-level musts stay in direction.must_have. Tool criteria are different in kind from site criteria (behavioural assertions checked against deployed pages/runtime by a browser or DOM check, vs qualities checked over content by an LLM auditor), which is the second reason not to co-locate them.
Format: a machine-extractable fenced ```criteria JSON block inside the PLAN body under "## Acceptance criteria" — the tool-doc-header precedent (structured block parsed out of a larger artifact) — so Tier-2/Tier-4 checkers get selectors/steps without a schema change, and the graduation rule can lift it to a column only if volume demands. Your check_tool_completeness upload slots in as Tier 0 of the ladder: generation-time output integrity (completion marker, balanced tags, length) alongside the header gate — it deliberately flags-but-passes, which is exactly the kind of event that should also append a doc_notes entry once the wiring exists.
