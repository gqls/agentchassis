# Where we are — bug 214, the imagery that was paid for and pointed at nothing

Owner's running log. Append only, newest at the bottom. Plain prose.

---

## 2026-08-10 — what this bug is, in plain terms

When the planner designs a site, it also plans the pictures: a hero for the about
page, four little icons for a section of it, and so on. It labels each picture with
the page it belongs to — it writes "about".

Then, a few lines later in the very same piece of code, the platform **renames the
page**. "about" becomes "about-index", "contact" becomes "contact-index", "news"
becomes "news-index". This renaming is deliberate and correct; it is how the platform
keeps page names consistent.

The problem is that nobody told the pictures. The page got a new name and the picture
labels kept the old one. So the label now points at a page that does not exist.

**Nothing looks broken when this happens, and that is why it survived.** You do not
get a missing-image icon on the site. You get a picture that was planned, generated by
a paid image model, uploaded, deployed — and then never put on any page, because the
label that was supposed to say where it goes points at nothing. The site simply looks a
bit bare, and every status in the database says "complete".

Today, across the sites that are live: **ten pictures are in that state, and eight of
them have already been generated and paid for.** They are sitting in storage, serving
correctly if you ask for them by name, and no page will ever reference them.

## 2026-08-10 — how I picked this one, since several of us are working at once

Nearly forty other sessions are working this repository right now. Before starting I
checked, three separate ways, that nobody else had this bug: what everyone has
committed recently, what the ownership script says, and — the one that actually
mattered — a search through every live session's own transcript for this bug's
filename. That last check found about thirty bugs with someone actively on them who
had not committed anything yet, so they were invisible to the first two checks.

Bug 214 came back clean. The lane that originally *found* it had explicitly written
that it was leaving it alone.

One thing worth knowing for next time: **the status line at the top of these bug files
is often out of date, and the truth is at the bottom.** One file I nearly picked says
"OPEN, unowned" in its first ten lines and "fixed and live" a hundred and seventy lines
later. I now read the end of a bug file before believing its beginning.

## 2026-08-10 — I got the size of the problem wrong first, and it would have been costly

My first measurement said twenty-two pictures were affected. The real number is ten.

The reason is worth stating because it is a trap anyone would fall into. There are two
tables that both list a site's pages: the **plan** (what we intend the site to be) and
the **pages** table (what is actually built and deployed). I measured against the plan,
because the plan is what the code I was reading writes to. But every piece of code that
actually *uses* these picture labels looks them up in the **pages** table instead.

So twelve of my twenty-two were fine. They looked wrong from where I was standing and
were perfectly correct from where it counts.

**If I had not caught that, the repair script would have broken twelve pictures that
work today** — on leopardessconsulting.co.uk and relojistas.com — by "fixing" them onto
names the live site does not use. The error was in the direction that flatters your own
fix, which is the direction nobody double-checks. It is written up in our shared
mistakes file.

## 2026-08-10 — what I have built

The fix is at the point where the labels are written, not on the ten broken rows. When
the planner's picture labels are written down, they are now checked against the list of
pages that plan actually contains, and a label using the old name is corrected to the
new one automatically.

Three things I was careful about:

- **Nothing is ever thrown away.** If a label names a page that genuinely does not
  exist anywhere in the plan — the planner asked for a picture on a page it never
  planned — the label is written down exactly as it is today, unchanged, and a
  permanent note is filed explaining that no page will pick it up. The old behaviour is
  preserved exactly, so nothing that works today can break.
- **I did not "fix" the section numbers.** Each label also carries a number saying which
  part of the page the picture belongs on. Some of those numbers are wrong. It turns out
  **nothing in the platform reads that number**, and I cannot know what the right value
  would have been — the information is destroyed in an earlier step. So the numbers are
  now recorded as anomalies rather than guessed at. Guessing would have risked breaking
  the whole site-plan save for no benefit at all.
- **I added a guard against a failure this fix could have introduced.** Correcting names
  means two different labels can end up identical, and the database refuses duplicates by
  aborting the *entire* plan save. That exact failure happened on the neighbouring table
  two days ago. There are no duplicates today, so this guard does nothing right now —
  it is there because my own change is what makes it possible.

## 2026-08-10 — the mistake I made in my own tests, which is the one I am least happy about

I wrote fifteen tests. They all passed. I then wrote in the file that they proved the
fix was properly connected up.

To check that claim I deleted the fix from the program and ran the tests again. **All
fifteen still passed.** Every one of them tested the new code directly, so not one of
them could tell whether the rest of the program was still calling it. The fix could
have been quietly disconnected by anyone, at any point, and the test suite would have
stayed green.

What makes this bad rather than merely careless is that **another session logged this
exact mistake in our shared mistakes file yesterday, and I had read it** before writing
mine.

I have since written a second, different set of tests that run the real code path and
check the actual value being saved to the database. Deleting the fix now makes them
fail. The false claim in the first file has been corrected where it stood rather than
quietly removed.

## 2026-08-10 — a collision with another session, in both directions, within an hour

The tidiest way to write part of this fix needed a one-line addition to a shared file.
When I went to commit, I found that file **already contained another session's
unfinished work**. Our commit rules cannot separate two people's edits to the same
file, so committing it would have pushed their untested work out to the live fleet
along with mine. That is not my decision to make, so I took my line back out and found
a different route that touches nothing shared. It is slightly less elegant and it is
pinned by a test so it cannot drift.

The same thing happened to me in reverse a few minutes later: another session committed
a register file while my own entry was sitting in it unsaved, so **my work went out
under their commit message**. Nothing was lost and I have not tried to undo it — we
only ever go forwards here. But it is a neat illustration of why we are told to commit
early and narrowly.

## 2026-08-10 — where this stands, and what is not done

The code is committed and has gone to the review council; the verdict has not come back
yet, and the commit is marked so it gets credited automatically when it does.

**The fix is not live yet.** It is Go code, so it does nothing until someone builds and
rolls a new chassis image. Until then the bug is still happening on every new site plan.

Two things still owed, and I want to be plain that they are not done:

1. **The repair script for the ten existing pictures is written but deliberately not
   run.** Running it before the code is live would fix them for exactly one planning
   cycle and then they would break again. It should be applied after the roll. It has a
   safety check that refuses to commit unless it repairs exactly the nine it should and
   leaves the one it cannot — and it fails if it repairs *too many* as readily as too
   few.
2. **Proof on the real system.** Everything I have shown so far is tests and database
   queries. The real proof is a site plan being written after the new code is live, with
   the labels coming out right — gamesdesign.co.uk is the best one to watch, since five
   of the ten broken pictures are on it.

One of the ten cannot be repaired by any script: mortgagecalculator.co.uk has a label
pointing at a page that does not exist under any spelling. Someone has to decide what it
was meant to be. I have left it alone rather than guess.
