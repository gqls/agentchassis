A build-dispatch-loop orchestration freezes at process_item_iter_N_spawn_handler and is never advanced again. The spawned page-rerender child answers its init handshake, the parent marks that awaited request processed and writes state, and then it never registers process_item_iter_N_call_handler and never writes state again, leaving the row in EXECUTING_STEP holding no waiting awaited request, so nothing but the 4-hour stale reaper can see it. It happens only on iterations entered from the error path, where the preceding iteration's call_handler reached retry_version 3 with status error and skipToNextLoopIterationForAsync advanced the loop. The evidence is in awaited_requests, which retains seven days and still holds the 2026-08-17 occurrences: reconstruct them per orchestration_id from step_name, retry_version, status, sent_at, processed_at and processing_started_at, matching an iter_N_call_handler at retry_version 3 and status error, the following iter_N+1_spawn_handler, and the absence of any iter_N+1_call_handler row. orchestration_states has already pruned those rows on its own much shorter horizon, so its emptiness there is retention and must not be read as absence of the defect. Two candidate mechanisms are already refuted and should not be re-proposed: the retry ticker's shared 60-second context, since claim batches are always size one and the freeze lands about twelve to thirty-five seconds into that budget, and the response-consumer context, which carries no deadline. The question is what kills the parent inside continueExecution for the next call_handler step on the response-consumer goroutine, immediately after handleCompleteResponse stamped the spawn processed, and in particular what differs about a continuation reached via skipToNextLoopIteration.
