site-work-orchestrator vs build-site-planner
These aren't two versions of the same thing — they're two architectures. site-work-orchestrator is the old monolith: one workflow that spawns planner/writer/reviewer, writes brief+plan specs, sync_pages_to_db, write_build_items, populate_nav, then inline generates and deploys logo + hero, selects a style collection, sets default components, renders components, renders+deploys JS, then loops over the emitted items and applies design — all synchronously in a single agent. build-site-planner is the thin planner: read_specs → plan_site → validate → write_site_plan → sync_pages → populate_nav → reconcile_site_plan, emitting needs_page + needs_rerender and delegating everything else to handler agents via work items. The thin-planner model is the one that matches your stated philosophy (simple workflows, sub-agents with separate responsibilities, clean logs), so the right question isn't "make build-site-planner do what the monolith does" — it's "is every piece the monolith did inline now emitted as a work item somewhere on the build path."

So beyond the design trigger, two candidates stand out.
Imagery is the same-shaped gap as design. write_site_plan records the planner's image requests in site_plan_imagery at build time (via flattenImageryBlock), but nothing emits needs_imagery at build time — only the loop's unfulfilled_imagery_plan does, and it's capped at 20 per pass. That's identical in structure to the design gap: intent recorded at plan time, work item emitted only by the improvement loop. The gamesdesign tally is consistent — zero needs_logo/needs_hero_image/needs_imagery. The honest caveat: the per-pass cap and the cost/rate profile of image generation suggest imagery might be intentionally loop-driven, unlike composition which 027 says is one-time-per-build. So this one needs an intent check before fixing — is a fresh site meant to have images at deploy, or is image generation deliberately deferred to the loop? If the former, the fix is symmetric: a build-time step (sibling to emit_design_items) that reads the current plan's site_plan_imagery and emits needs_imagery, reusing the unfulfilled_imagery_plan selection logic.
Site-status advancement is the other one to check. The monolith ends with an explicit update_site_status. On the build path I don't see an obvious terminal step that flips sites.build_status to deployed/active — and gamesdesign sits at pending. It's mid-build there so pending may be correct for now, but the question is what sets it when the last needs_rerender completes. Worth a quick trace of whether rerender-pages (or anything triggered at the end) advances the site status, or whether sites built via build-site-planner stay pending indefinitely.
Everything else the monolith did is accounted for by needs_composition (defaults + style) and needs_rerender (component + JS render), both of which the build path emits once the design fix is in.
