## 3. JSON-LD — DONE and verified the hard way

Council-APPROVED (`Council-Reviewed: 28d33692-698a-46ed-b46e-cfd3f700f6d4`), shipped in
`v1.0.1194`, and **verified on the wire, not by pod-grep**.

The pod-grep was done first (`injectPageJSONLD` present, negative control
`injectPageMicrodata` = 0) and **was deliberately not treated as proof** — this workstream's own
memory says a pod-grep proves the code is in the BINARY, never that it is on the feature's PATH,
and that exact mistake cost `bugs_open/085` a false "it's live" the day before.

So a page was forced through `assemblePage` and the SERVED page read:

```json
{ "@context":"https://schema.org", "@type":"WebPage",
  "@id":"https://relojistas.com/glosario/tourbillon.html",
  "name":"Tourbillon",
  "description":"Qué es un tourbillon: el escape alojado en una jaula giratoria, y por qué se asocia a la alta relojería.",
  "isPartOf":{"@type":"WebSite","name":"relojistas.com","url":"https://relojistas.com"} }
```

Valid JSON, inside `<head>`, correct `@id`/`url`. **This is the first schema.org markup any site
in the estate has ever emitted** (measured 07-28: 0 of 14).

**Rollout note:** it lands per page **at that page's next render**, so pages re-render into it
gradually rather than all at once. A follow-up commit (`ac5ef58b9`) naming every skip branch —
the council's `bug_historian` objection, fairly made — is **inert until the next roll after
v1.0.1194**.

## 5. Landmines — every one of these was paid for this week

- **`DEPLOY_USER=deploy` is NOT optional on `setup.sh`.** Omit it and the webroot is chowned to
  `www-data` and **every vm-sites deploy dies** (`rsync … Permission denied`, exit 23). I did
  this and only the owner's pasted CI error caught it — *every check I had run was a READ of the
  public site; what I broke was a WRITE by a third party.*
- **`MODE=update` still demands `DOMAINS` and `LETSENCRYPT_EMAIL`** (validated at `:44-45`,
  before the MODE branch at `:333`).
- **Cloudflare PREPENDS its managed `robots.txt`** to the origin's. Shipping your own changes
  nothing until **both** dashboard settings are off. **Verify per agent — one `curl` proves
  nothing**, the file is served conditionally.
- **Metadata-only page sections are undeliverable.** `sectionHasVisibleContent` strips
  `<script>`/`<style>` then requires >10 chars, so a JSON-LD section renders into
  `page_components` and is silently dropped at assembly. **JSON-LD must go in `<head>`.**
- **Chrome is a stored artefact** (`site_components.rendered_html`) that no page re-render
  rebuilds — use `nav_drift` → `nav-updater`, which queues the page re-renders itself.
- **A checkform that names the defect it expects cannot fail.** Three found here: a phantom grep
  searching for the two links already fixed; `grep -c 'mailto:'` on a CF site (CF rewrites
  them); `grep -c buscar-item` which matches the CSS that *defines* the class.
- **When a render "completes" but the page does not change, look for the DEPLOY artefact first.**
- **A work item can be marked `complete` over an error path.** The FAQ's first `needs_page` ended
  at `complete_error` ("page not found in database") and the item still said `complete`.
