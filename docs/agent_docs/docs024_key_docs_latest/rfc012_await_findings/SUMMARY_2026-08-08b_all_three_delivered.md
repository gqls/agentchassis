# SUMMARY 2026-08-08 (b) — RFC 012: all three instructions delivered, the reviewers turned round, and a reviewer's throwaway remark found a real fault

## What we're trying to do

Stop the platform destroying its own agents' work. When one of our agents both *works
something out* and *asks an outside service to do something*, the outside service's reply
overwrites the agent's workings in the permanent record. The status says complete, the reply
looks like the step's output, and nothing indicates anything was lost. The owner gave three
instructions: build the shared escape hatch properly, survey everything that reads those
records so the deeper fix becomes decidable, and turn a one-off audit into a standing check
that runs by itself rather than when someone remembers.

## Where we've come from

The earlier read-out this morning ended in an awkward place. The work was built, shipped and
running in production, the survey was delivered — and the reviewers had **turned the code
change down**. Not for its quality: the senior reviewer's own notes called it "genuinely
careful work". It refused because I had told it plainly that the submission form showed it
eight files out of thirty-four, and judging how far a change reaches is precisely its job. The
previous round had told me off for the opposite failure — describing work I had not shown —
so the two rounds together looked like a trap with no way out.

It was not a trap. It just needed reading properly.

## What we've done

**Both halves of the code change are now approved, and I changed no code to get there.** The
reviewer had named exactly what would satisfy it: the list of all the file names, which costs
nothing and does not use up the eight slots. I supplied it, generated by command rather than
typed, grouped so that a reader can see the shape of each group. And I split the submission
in two, because two reviewers had fairly pointed out I had bundled two unrelated pieces of
work into one round — a fact about my calendar, not about the code. Both rounds came back
approved within about ten minutes of each other.

**The last of the three instructions is done: the audit now runs itself.** It is a daily job,
live in production, verified by an immediate manual run rather than by assuming. It reads the
whole fleet directly, checks all one hundred and seventy-seven live agent definitions, and
writes a record of **every** run — including the quiet ones. That last detail is the whole
point: a check that only speaks when it finds something is indistinguishable from a check that
has silently stopped working, and we have been bitten by exactly that before. Now a missing
record means the job did not run, and can never be mistaken for good news.

**A reviewer's minor "approve, but" remark turned out to be a genuine fault, and finding it is
the most useful thing in this session.** One reviewer had asked, almost in passing, whether
the new audit's way of walking through agent definitions had been compared with an existing
tool sitting in the same folder that does something very similar. Nobody had looked. I looked.

The existing tool deliberately uses the platform's shared, official way of walking those
definitions, and says in its own comments why: a second hand-written version of the same walk
goes blind in its own particular direction, which is a lesson this codebase learned the hard
way once already. The new audit had written exactly such a hand-written version, and had
justified it with a reason that turns out to be untrue.

And it *had* gone blind. A repeating block of work in a definition can be written in one of
two ways, and the one the audit could not see is the one the platform *prefers* when both are
present. So on a definition using that form, the audit would have found nothing and reported
a clean bill of health. Worse, on a definition written both ways, it examined the half that
never actually runs — reporting a problem in something inert.

**The reason this is worth telling is that nothing could have caught it by running.** No live
definition currently uses the form the audit was blind to, so every real run was clean and
would have stayed clean until the first person who preferred that style quietly dropped out of
view. So the proof had to be built rather than observed: two tests that fail against the old
version and pass against the new one, plus a side-by-side run of both versions over the same
snapshot of the fleet showing the results are identical to the byte — which mattered, because
seventeen live agents do use the form it *could* see, and I had to show I had not disturbed
them.

**I also stopped and settled three challenges the reviewers made to how this lane proves
things**, rather than letting them sit on the record. One was wrong and I can show it. One was
right, and sharper than the reviewer put it: our standard way of confirming a change reached
production was checking two containers out of forty-two. One was a fair complaint that a
load-bearing claim had never actually been checked; it holds up, and now it is checked rather
than asserted.

## Where we are now

All three instructions are delivered. Both council rounds are approved. The standing check is
live and has reported its first clean run. There is nothing in flight that needs watching and
no verdict outstanding.

Two things are deliberately *not* done, and both are decisions rather than omissions. One
file that the earlier notes said to tidy up "when it is free to touch" will **not** be tidied:
the review that just passed states it stays as it is, and I can now show there is nothing to
gain — the two versions of the code in question are identical character for character, so
changing it would carry the risk of a slip for no benefit at all.

And the one loose thread I would hand to the next person: four reviewers, independently, put
their finger on the same soft spot in the new shared mechanism. If someone uses it and
*forgets* to fill in one particular detail, the system quietly fills it in wrongly, and no
test we have would notice. The eighteen places that use it today are all correct. The
nineteenth is the risk. They are right, the remedy is small, and it is written down where the
next person to use it will meet it.

## Where we're going

Three things, in order of value. Close that soft spot properly, so the mistake becomes
impossible rather than merely documented. Read the verdict of a diagnosis now running on a
suspected fault in how deployed images reach a page — where, in fairness, my own reading of
the code says it is broken, and my attempt to observe it happening found nothing either way,
so the diagnosis is genuinely testing a hypothesis rather than confirming a conclusion. And
then the deeper decision the whole survey was for — whether to change the overwrite itself —
which is the owner's to take, on evidence that now exists and says the cost is small and
specific.
