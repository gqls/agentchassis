## 1. What a catalogue entry IS (the "model page")

One page per hosted model. Ours are the first entries; a third party's later. Each entry has:

| part | what it holds | who supplies it |
|---|---|---|
| **owner** | us, or a submitter's account | the account that created it |
| **the case** | what the business was, what the model was trained to do, in the site's voice | the framework writes it from a brief the owner (or submitter) fills in |
| **before / after** | pairs: the same prompt answered by the base model and by the fine-tune | generated by us at hosting time, from a fixed prompt set, so the pairs are honest and comparable |
| **the model artefact** | a GGUF in B2 plus its licence, version-pinned, and the base model it came from | the owner uploads; we verify before it goes live (§4) |
| **try it** | the chat box, against THIS model, on the class the entry is priced for | the playground route, with a `model` selector (a change to PUB-006, see §6) |
| **price and class** | per booked hour, by GPU class; the free demo minute(s) if any | owner-set, within the posture (§5) |
| **terms** | the T&C the submitter agreed to, with the agreement click recorded | the account system (§3) |

Framework rule: the page is a normal site page with a `tool`-level component (the chat) and section
components (case, before/after, price), built by the pipeline from the entry's row. No hand-authored HTML
(owner ruling 2026-08-04). The entry row is the source; the page is a render of it.

## 2. Input mechanisms (how an entry gets in)

- **Ours:** a seed per entry, from the training run's own record (Phase 0 already writes a manifest
  with the adapter key, base model and dataset id). So "example after real example" is a seed per
  finished run, and the before/after pairs come from a fixed prompt set run at hosting time.
- **Third parties (later):** a form on the site (the estate has `static_site_form_endpoint`, live
  session; and the island already receives forms for the gripper intake) → an account (§3) → an upload
  of the GGUF to a per-account B2 prefix by presigned PUT (the same presign shape Phase 0 uses, minted
  in-cluster so no key enters a browser or a session) → a submission row → review (§4) → live.
- Question for the owner: **is third-party submission a 2026 thing or a "shape it now, build later"
  thing?** The shape below assumes the second.

## 3. Accounts, terms, and the agreement click

- An account is needed the moment someone other than us owns an entry, and again the moment anyone
  books an hour (so the booking → session handoff, Phase P step 5, needs it too). The estate does not have
  a customer account system today for framework sites `[CHECK: the vet-med / loancash lanes have none;
  webdesign.uk has none; Stripe is "his, and last"]`. So this is the first real one, and it is the largest
  piece here.
- **Terms and conditions:** one document (the finetuning.uk terms are "locked" as of 08-30; they will need
  a hosted-models section: licence warranty from the submitter, our right to remove, no illegal or
  infringing training data, no personal data without a basis, indemnity), shown before the upload, with
  the **agreement click recorded** against the account and the entry (who, when, which version of the
  terms). A re-agreement is required when the terms change.
- Question: **who writes the terms?** The owner wrote the current ones; the hosted-models section is
  legal text and should be his or a solicitor's, with the lane drafting questions, as for the 08-24 terms
  question list.

## 4. Removal mechanisms and what "verified before hosting" means

- **Removal, three doors:** the owner removes (a button on the entry, sets `status=removed`, the page
  is unpublished by the pipeline and the artefact is deleted from B2 after a grace period); we remove (a
  takedown for licence, content or abuse reasons, with the reason recorded and the owner emailed); a
  reported entry is **suspended first, reviewed second** (the page serves a holding notice, the model is
  unloaded). Every removal leaves a row; nothing is hard-deleted before the grace period.
- **Checks before an entry goes live:** the file is a GGUF that loads (`ollama create` on the demo box
  in a sandbox, then unloaded); the declared base model and licence match what the file's metadata
  says; the licence permits hosting and redistribution of the fine-tune (a version-pinned fact, as the
  three licences the site already registers are); a fixed **safety prompt set** is run and read by a
  person before publication; the before/after pairs are generated by US from OUR prompt set, so the
  submitter cannot hand us cherry-picked examples.

## 5. Pricing, and "ways to stop cheating"

- **Price:** per booked hour, by GPU class, and the class is the customer's choice (owner, this evening).
  Measured costs: a6000 $0.35/hr, a100xl $1.09/hr (vendor invoice 2026-08-18, per minute). At ×5:
  ~£1.40/hr and ~£4/hr. Owner said "increase the price", so the ×5 floor is a floor; the numbers are
  `[NOT DECIDED]`. A public free demo stays on the CPU box for the first entries.
- **Cheating, the ways I can see, and the control for each:**
  - *free-tier abuse* (someone scripting the free demo as an API): the route already has per-IP bands
    (60/h, 300/d), body caps and a 150-token reply cap; an account-bound free allowance per model is the
    next step.
  - *booked-hour sharing* (one booking, many users): a session token bound to one browser, one
    concurrent stream per booking, the hour measured on the server not the client.
  - *submitters gaming the before/after* (uploading a model tuned to our prompt set): the prompt set is
    not published and rotates; a held-out set is run at review.
  - *hosting someone else's model as your own*: the licence warranty in the terms, the base-model
    metadata check, and takedown.
  - *prompt-injection to get the base model to misbehave on our site*: the fixed system prompt the
    route already sends, the reply cap, and the demo being a small model with no tools.
- Question: **is "cheating" mainly the free tier, or the submitters?** The controls differ in cost.

## 6. What changes in what is already built

- **PUB-006 (the chat route) gains a `model` parameter** validated against the catalogue's live entries,
  and a per-model free allowance. Today it serves one model from env. That is an additive change, opt-in
  (an absent `model` keeps today's behaviour), and goes through the council like the route did.
- **The demo box hosts more than one model** only if it grows: 3.8 GB RAM, one 1.7B model loaded takes
  1.5 GB, `OLLAMA_MAX_LOADED_MODELS=1`. Several small models can be installed and swapped (cold load
  ~1.5 s each); anything bigger, or "snappy", is the booked GPU.
- **A catalogue table** (`model_catalogue`: id, owner_account_id, status, title, case brief, base model,
  licence fact id, artefact key, class, price, terms_version_agreed, agreed_at, created/updated), the
  before/after pairs as rows keyed to it, and the page built from it by the framework. Named here so
  the register can hold it when it exists; not built.

## 7. The order I would build it in, if the owner agrees with the shape

1. Ours-only catalogue: the table, a seed per finished run, the page type, before/after generated by us,
   the route's `model` parameter. No accounts yet (owner is the only owner).
2. Booking → session handoff (Phase P step 5) with the GPU class as a choice and the server-side hour.
3. Accounts + terms + agreement click, when the first third party is real.
4. Submissions, review and removal.

Each step is framework-built and council-reviewed; each has a measured cost before a price is set.
