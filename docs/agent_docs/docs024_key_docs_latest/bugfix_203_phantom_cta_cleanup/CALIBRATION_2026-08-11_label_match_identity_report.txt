correction section immediately below.

Compares OLD (committed HEAD, commit 8e6b86f2a) BestLabelMatch /
NewLabelMatchCandidate against NEW (this working tree) over BOTH candidate

DETECTOR (check_misdirected_cta.go's loadCTAMatchIndex) and the internal-link

--- CORRECTION (2026-08-11, same day, later pass) — a 4th ranking key was
    tried, calibrated, and DROPPED before shipping ---

The run this file originally recorded compared OLD against an intermediate
NEW that carried a 4TH ranking key after identity/total/interactive: on a
remaining tie, the candidate with the SMALLER total token-set size won
(replacing a straight alphabetical-by-name tie-break). That key has since
been REMOVED from BestLabelMatch (platform/orchestration/datahelpers/
label_match.go) after this same calibration data showed it was decided
almost entirely by tokenisation artefacts and site-wide generic words, not by
anything correlated with which candidate a label actually names. Three
concrete examples, with real numbers, from the run this file originally
reported: (1) on gaswholesalers.com, EVERY ONE of 9 already-correct, live CTA
labels ("Request a Wholesale Quote/Account", "Get Wholesale Pricing",
"Explore Wholesale Supply Solutions", "Read how wholesale pricing works")
flipped from the correct `/tools/tool-breakeven-volume-calculator.html` to
`/tools/supplier-comparison-calculator/index.html` — caused by a stray hyphen
in "Break-Even" tokenising into two words where the loser's own title used
the unhyphenated "breakeven", making the loser's token SET one entry smaller
and therefore the tie-break's arbitrary winner; (2) on vetcomparison.uk, the
CMA-obligation family flipped from `/tools/cma-obligation-checker/index.html`
to `/tools/compliance-deadline-calculator/index.html` purely because "cma"
sits in both candidates' identity tokens and the loser's title happened to be
longer; (3) on robot-hands.com, "Run Payload Calculation" and "Run the
Estimator" both flipped onto `/tools/matchmatrix/index.html` because its
title contains the generic imperative "Run", again shortening its token set
relative to the correct, more specific target. None of this tracked which
candidate the label actually names — it made ties WORSE than plain
alphabetical order, not better — so the key was dropped. This file is now
REWRITTEN in place (owner instruction: keep the still-accurate method and
scope-deviation sections, replace the numbers and changed-picks lists with
the corrected run) rather than left to describe scoring that never shipped.

--- METHOD ---

cmd/ctacalibrate imported the REAL datahelpers package — never a SQL
re-implementation of BestLabelMatch. Live-fleet data was pulled ONCE from
postgres-clients-0 via `kubectl exec ... psql` (641 pages, 476
ctaFieldNames-scoped page_components rows, 2026-08-11) and frozen to JSON, so
every build compared in this file (the original OLD/NEW pair and this
correction's regenerated NEW) runs against IDENTICAL inputs — no drift from
querying the live DB twice at different moments. OLD build = `git worktree
add <dir> HEAD` (commit 8e6b86f2a, the tree as committed before 253's fix).
Both pools' candidate-list and validity-set construction are a line-for-line
Go mirror of the real loaders (loadCTAMatchIndex for the detector;
loadInteractivePages + loadContentHubs + loadResolverPageSet +
candidatesFromHubs for the resolver) — read alongside the real source, not
guessed. `datahelpers.DeriveCTAURLFields` (the real, exported function) is
used to find each url field's label sibling from the component's actual
input_schema, exactly as resolve_internal_links_action.go's STAGE-1 code
does — this is NOT re-implemented either.

DEVIATION FROM SPEC, DISCLOSED: kubectl port-forward + a `database/sql`/
lib-pq TCP connection with a password read from the k8s Secret was specified
in the task brief, but reading that Secret's value was refused by this
session's tool-use classifier (a safety control, not a login failure). This
tree's own CLAUDE.md documents a working, password-free alternative —
`kubectl -n ai-persona-system exec -i postgres-clients-0 -- psql -U
clients_user -d clients_db` (local trust auth inside the pod) — which is what
every other cmd/ tool in this repo actually falls back to for a terminal
session (see cmd/component-render-check/rendercheck.go's own dbConn() doc
comment: "a session at a terminal reaches the DB through kubectl exec").
cmd/ctacalibrate therefore has NO live DB dependency inside the Go binary at
all: two `kubectl exec ... psql -tAc "SELECT jsonb_agg(row_to_json(t))..."`
dumps produce pages.json + cta_components.json once, and the tool's
"generate" mode reads those files. This is materially MORE rigorous for an
old-vs-new A/B comparison than two independent live connections would have
been (guarantees byte-identical inputs to both builds), so the deviation is
kept rather than fought further. This correction's re-verification pass
inherited the same deviation for free: cmd/ctarecalib never touched the DB
either, only the frozen JSON.

A STRUCTURAL NOTE, also confirmed by the numbers below: EXAMINED, MATCHED and
NEWLY-RESOLVED counts are mathematically invariant to a pure re-ranking of
BestLabelMatch — none of the three depend on WHICH candidate wins, only on
whether at least one candidate has any overlap at all, and whether the
current stored value was empty. Only OVERRIDDEN (and the implicit
"confirmed as-is" residual) can move under a re-ranking-only change. That is
exactly what the numbers show (examined/matched/newly-resolved identical
old->new in both pools below) and it is exactly the "risk-bearing" metric
CLAUDE.md's own bugfix trail already names as "the one to watch move".

--- WHY THE RESOLVER POOL BARELY MOVES: A STRUCTURAL DEGENERACY, MEASURED ---

candidatesFromHubs builds every candidate with navLabel="" (contentHub
carries no nav_label field at all — confirmed by reading the struct and the
call site). NewLabelMatchCandidate's identityTokens is always name+title,
and totalTokens is identityTokens ∪ LabelTokens(navLabel) — with navLabel
empty, totalTokens == identityTokens for EVERY resolver-pool candidate, in
BOTH the old and new builds (the old call site passed tokenSources =
(h.Name, h.Title) — the same two sources, just unioned instead of tracked
separately). So the headline change this fix makes — rank identity overlap
before total overlap — is a NO-OP in the resolver pool by construction:
identity and total overlap are always equal there. The DETECTOR pool is
where 253's actual headline mechanism (nav_label-driven false ties) shows
up, because loadCTAMatchIndex's candidates DO carry a real nav_label.

CORRECTED CODA: with key 4 dropped, this degeneracy predicts the resolver
pool should show ZERO changed picks against OLD — identity/total overlap can
never differ there, and the remaining ranking (interactive, then Name
ascending) is now IDENTICAL to OLD's own ranking (interactive, then Name).
That is exactly what the corrected numbers show: 0 of 784 resolver rows
change. The original run's 36 changed resolver picks (26 of them the
vonc.com "Enter/Run the Gauntlet" family, correctly flipping the already-
live `/tools/gauntlet/index.html` into favour) were caused SOLELY by key 4's
token-set-size tie-break reordering a genuine overlap TIE — not by 253's fix
— and vanished the moment that key was removed. This is a clean, independent
confirmation of the degeneracy argument, not just a restatement of it.
