The full path: content writer generates section text → extractResponseContent pulls it as a string → RenderComponentAction merges section content_data over base data and renders → CompilePageSectionsAction gathers sections_metadata → SavePageSectionsAction persists content_data + component_id to page_components.
The break is at the generation/parsing layer, and it's structural:
The writer's content extraction (extractResponseContent) returns a flat string. Components whose input_schema declares a structured field — like FAQ's questions: array of {question, answer}, min_items 3, source llm — need that string parsed into the structured shape before it can become content_data.questions. There's no step doing that mapping for arbitrary schema-driven fields. So:

A generic-text-block (wants one body string) → the string path fills it perfectly. ✅
A faq component (wants a questions array) → the string has nowhere to go; content_data.questions is never built; the template's {{range .questions}} iterates over nothing (or over empty placeholder objects). ❌

This also explains the NULL component_id: per the extractSectionFromMap comment, when a section's metadata isn't fully recovered (which happens when the structured render didn't produce a clean component-bound result), the save path can't link it, leaving component_id NULL — the orphaning we observed.
