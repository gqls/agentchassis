# Running notes — adopted tool pages have no widget (investigation, 2026-05-26)

Retrospective. Captures the thinking, the hypotheses, the dead ends, and *why* each decision was made — not just the conclusions (those are in `PLAN_tool_widget_clobber.md`). Written so the reasoning is recoverable, including the places we were wrong.

The single most useful thing in here: **the diagnosis changed three times**, and each change came from refusing to act on the current theory until it was checked. That discipline is the reason we didn't build the wrong fix.

---

## How the diagnosis evolved (the short version)

1. **Clobber (M1).** First theory: the widget was created at position 2, then a page rebuild deleted it. Confirmed as a *real defect in the code path* — but the DB then showed it was **not** what happened to these pages.
2. **Never generated, "no owner" (M2 + a wrong sub-claim).** Second theory: adoption captured text not JS, and *no agent owned generating the widget*. The "never generated" part held; the "no owner" part was **false** and we caught it before acting.
3. **Misroute via a canonical-name prefix desync.** Actual cause: the owner exists (`tool-recreation-handler`), but adoption misrouted tool pages to the static builder because a feature-map lookup missed. Fixed. **But** a fourth thing then surfaced — correctly-routed recreation still produced no widget — which is still open.

Each arrow above is a place we'd have wasted effort if we'd shipped on the prior theory.

---

## Phase 0 — Framing (before touching anything)

The symptom (tool pages showing a description, no working tool) has at least four distinct causes that need different fixes: never planned, planned-but-not-built, built-but-not-linked, or rendered-but-JS-broken. **Decision: do not guess which.** Read the intended architecture first, locate the exact link in the create→store→render chain that breaks, and let the evidence pick the cause.

This framing paid off repeatedly — every time a theory felt solid, the next read or query moved it.

One early concrete observation kept us honest: the same section UUID (`8d81e665…`) appeared on two different tool pages. A genuinely per-page generated section wouldn't share a UUID. Small, but it said "this is a data/linking issue, not LLM variance" before we had any other evidence.

---

## Phase 1 — The clobber theory, and the user's reframe

Reading the tool pipeline + page-build flow produced a clean, plausible story: the tool action writes the widget into `page_components` at position 2, then a `needs_content_page` build rebuilds the page's components from a section list and a `DELETE FROM page_components` wipes anything not in that list. The widget isn't in the list → gone.

The DB backed it: `pages.sections = []`, no `component_level='tool'` row, `generic-text-block` sitting at position 2. The code backed it: `save_page_sections` really does `DELETE` then re-`INSERT`, and its regression guard compares **visible text length** — structurally blind to a script-heavy widget (the prose replacement has *more* text, so the guard never trips).

**The user's reframe here mattered:** *"what is to say the page wants these sections in the first place — it may not."* That turned "the widget got clobbered" into a sharper question — *who decides a tool page's sections, and is the widget a first-class member of that authority?* It reframed the fix from "stop the delete" to "make the widget part of the single source of truth." We carried that framing forward even after the cause turned out to be different.

**Decision:** treat the clobber as a confirmed defect, but gate the fix on reading the section-authority chooser before assuming it was *the* cause. Good call — it wasn't.

---

## Phase 2 — The authority, and a second suspect appears

`load_page_sections_from_spec` settled one thing hard: `site_plan` is authoritative **and it overwrites `pages.sections` on every build**. So a fix that only set `pages.sections` in the tool action would be erased by the next build. **Decision: the fix has to live in the planner/`site_plan`, not the action.** (This later became moot for the real cause, but it was the right read of that code.)

Then `029` showed the pages were **adoption-shaped** (`tool-drop-rate-simulator`, `/tools/drop-rate-simulator/index.html`) — *not* what `create_tool_component` produces — and the leaked `/contact.html` / `/services.html` hero CTAs matched the `B-029-2` "generic component defaults" signature exactly.

**This is where we deliberately stopped trusting the clobber story.** Two mechanisms were now live: M1 (clobber) and M2 (widget never generated by adoption). **Decision: do not commit; disambiguate with the DB.** Refusing to commit here is what saved us from "fixing" a clobber that hadn't happened.

---

## Phase 3 — M2 confirmed, and a claim we'd later regret

Three queries decided it: no tool component existed for the site at all (D=0), the tool pipeline had never run (E = adoption recreate items only), and there was no history snapshot (F=0 → nothing was ever deleted). So **nothing was clobbered because nothing was ever there.** The widget was never generated. The `pages.sections = []` puzzle dissolved too: the sections came from the adoption crawl via the recreate path, never from `site_plan`.

**Decision:** reframe — M1 is latent (real, but not the cause here); M2 is live. We added tasks, wrote the debugging addendum, and — at the user's instinct — logged **T3**: `create_tool_component` and adoption should not diverge on page identity, and `create_tool_component` (the older surface) should be the one changed to use the canonical helper.

**The mistake:** in the responsibility analysis we asserted *"no agent owns ensuring a tool page has a working widget; if adoption can't capture one, generate one."* It felt right — adoption stops at text, the tool pipeline wasn't triggered, so the widget fell down a gap. We wrote it into two documents.

---

## Phase 4 — The correction (verify before acting)

The user did the most valuable thing in the whole investigation: *"can we make sure that is true before acting on it."*

It was not true. Searching the code:

- `apply_adoption_plan` already routes interactive pages: `if len(page.Features) > 0 → needs_tool_recreation → tool-recreation-handler`, else `→ page-build-handler`.
- `tool-recreation-handler` is a real, registered agent that LLM-recreates the widget, gates on `check_tool_completeness`, and deploys via `page-rerender`. It owns exactly the responsibility we'd said was unowned.
- `check_missing_tools` is a separate site-level trigger on top.

So the handoff exists and the owner exists. The real cause is a **misroute**: gamesdesign's tools had empty `Features`, so adoption sent them to the static builder. **Decision: retract the "gap" framing in both docs and flag it as checked-and-wrong; reframe the fix from "build a handoff" to "repair the existing route."**

The lesson is bigger than this bug: a plausible architectural claim ("nobody owns X") is exactly the kind of thing that *feels* verified because it explains the symptom. It needs a code search before it becomes a task, because the cost of acting on it (building a redundant pipeline) is high and the cost of checking it is one `grep`.

---

## Phase 5–6 — Pinning the mechanism, and a falsifiable prediction

Why was `Features` empty? `buildPageFeatureMap` keyed its map by the **raw** `fm["page"]`; the routing loop looked up the **canonicalised** `pageName`. And `CanonicalisePage`'s `tool` branch *adds* a `tool-` prefix. So the tool lookup (`tool-drop-rate-simulator`) never matched the stored raw key (`drop-rate-simulator`).

The decisive, satisfying part: **games carry a `game-` prefix in their raw name, and the `game` branch preserves it.** So the theory made a falsifiable prediction — *games should route correctly, tools should not* — i.e. the bug hits only roles whose canonical prefix differs from the raw key.

We checked instead of assuming:
- Query G (after correcting the column from `results` to `findings`): adoption *did* emit `interactive_features` for all six tools and five games — tools bare, games prefixed. Ruled out "detection emitted nothing" (b2).
- Query I: all five games routed `needs_tool_recreation → tool-recreation-handler`, complete; zero tools. **Prediction held exactly.**

**Decision on the fix shape:** key the feature map by the **canonical** name (the single join key the whole system uses by design), reusing `CanonicalisePage`. We explicitly rejected the minimal two-line alternative (look up by raw name) because it reintroduces a parallel raw-name join space that breaks the moment the LLM prefixes one array and not the other. Structural over expedient — and it cost nothing extra because the function already received `plan["pages"]`.

---

## Phase 7 — Producing the code

Two deliberate choices:

- **The merge was done programmatically** (copy the file, `str_replace` only the one function) rather than by re-typing 900+ lines. Reason: the standing rule against unintended variable-name changes. A by-hand re-emit risks silent edits; a targeted swap guarantees the other ~970 lines are byte-identical. Verified by diffing the head and tail.
- **T1b (backfill) was folded into T2, not built as a second emitter.** Two things emitting `needs_tool_recreation` for the same pages would split ownership. T2 (the discovery check) already detects widget-less interactive pages and backfills on its next run. A SQL backfill was rejected for a sharper reason: it would have to re-implement the canonical key matching *in SQL* — the exact fragility we were removing. Keep the canonicalisation in one place (Go, via `CanonicalisePage`).

---

## Phase 8 — The blocking finding (the theory was right but incomplete)

Then the verification queries did what verification queries are for: they broke the happy ending.

Query K: the five games — which routed correctly *all along* and whose recreation completed — were **widget-less** (`has_widget_component=f`, `has_script_section=f`). So **correct routing + completed recreation → no deployed widget.** The routing fix was necessary but not sufficient. If we'd shipped T1 and declared victory, the tools would have ended up exactly where the games already were.

We also held back from over-reading K. `has_script_section=f` can be a *false negative*: the snippets mechanism extracts inline `<script>` into `/assets/js/snippets.js`, and the widget might sit at a `component_level` we didn't test. **Decision: hold the trigger; do not mass-emit recreation; diagnose why correctly-routed recreation lands no widget — with a decisive page-component dump, not the indirect signal.**

A loose end appeared too: five `tool-game-*` *planned* tool pages, duplicates of the games. Unexplained — possibly recreation building a new page instead of populating the original.

---

## Phase 9 — The ground moved

The diagnostic queries (L/M/N) all returned **zero rows** — for pages and work items that had existed minutes earlier in step 8. A `LEFT JOIN` can't drop the page row, so those pages and items had genuinely been deleted/renamed. The parallel adoption chat had re-run adoption (or a reaper cleared items) between our two query rounds.

**Decision: stop diagnosing against a dead snapshot.** Re-baseline (R1–R3) against whatever exists now before re-pointing the diagnostics. The meta-lesson, now written into the plan: while the other chat is active, snapshot the inventory at the start of each session and treat name-specific reads as time-sensitive. The build_status drift we'd already noticed (`needs_rebuild → deployed`) had been the early warning.

## Principles that actually drove the work

These are the user's standing rules; noting where each one changed an outcome, not just that it was followed:

- **Don't jump to conclusions.** Held three different theories loosely; each was moved by the next query. The clobber theory in particular would have produced a real but irrelevant fix.
- **Verify before acting.** Phase 4. The "no agent owns it" claim was wrong and would have led to building a redundant handoff. One code search caught it.
- **Structural over quick.** Canonical keying over the two-line lookup hack; one emitter (T2) over two. The expedient options were genuinely tempting and genuinely worse.
- **Reuse what exists.** `CanonicalisePage` reused on both the fix and the check; programmatic merge to avoid disturbing working code.
- **Check the schema before SQL.** Caught `content_components` has no `site_id`, the `findings` vs `results` column, and deferred the `idx_swi_dedup` dependency rather than guessing it.
- **Distinct responsibilities, minimal overlap.** The clean split was: adoption *detects and routes*, `tool-recreation-handler` *generates*, T2 *backs up*. The bug lived precisely at a seam (the feature-map handoff), which is where the overlap/identity problems keep recurring (the `029` family).
- **Keep the flow in mind.** Tracing the actual call chain — `buildPageFeatureMap` → `pageFeatures[pageName]` → `adoptedPage.Features` → `if len(page.Features) > 0` — is what turned "tools have no widget" into "one map is keyed in the wrong space."

---

## What is still unresolved (so the next person isn't misled by the tidy narrative)

The routing fix is deployed, but the **recreation-loss defect (Phase 8) is open and blocking** — correctly-routed recreation did not produce a widget for the games, and we never got to find out why before the state reset. It could be a real handler/clobber defect or a detection artefact. Until R1 + a re-pointed L settle it, the user-visible symptom may not change. See `HANDOFF_2026-05-26_tool_routing_fix_deployed.md` §3 and §5 for the exact next sequence.

The honest summary: we found and fixed a clear, confirmed bug (the misroute), and in doing so uncovered a second one downstream that the fix can't reach on its own. That's progress, not closure.
