The end-to-end chain, as currently wired
Tracing from the submit script's entry message (system.agent.generic.requests, action=orchestrate, agent_type=domain-submitter) through the agent definitions and the Go actions:
domain-submitter            → needs_domain_research (triaged, prio 5)  → domain-research-classifier
domain-research-classifier  → writes identity/classification/content_direction/design_intent specs

→ needs_briefing (triaged, prio 10)        → build-briefing-agent
build-briefing-agent        → writes briefing spec
→ needs_site_plan (triaged, prio 15)       → build-site-planner
build-site-planner          → plan_site(LLM) → validate → write_site_plan → sync_pages → populate_nav → reconcile_site_plan
reconcile_site_plan         → needs_page × N (triaged, prio 50+)       → page-build-handler
→ needs_rerender (triaged, prio 99)        → rerender-pages
The engine driving it is build-pipeline-trigger (30s heartbeat): each tick runs find_dispatchable_site (items in status triaged/approved, no claimed item on that site), spawns build-dispatch-loop, which claims up to 5 items, spawns each item's handler_agent dynamically, calls it, and marks complete.
What is structurally sound
The chain is fully connected — no dangling handler_agent references. Every stage's create_work_item defaults status to triaged (confirmed in CreateWorkItemAction), and the trigger dispatches triaged items, so the pipeline self-advances without a manual triage step — roughly one pre-content stage per heartbeat tick, then up to 5 pages per tick once reconcile fans out. The chain is longer than the old submit-script comments imply: a domain-strategist and build-briefing-agent stage were inserted between the classifier and the planner. So the comments in 077_submit_domain.sh are stale, but the entry message itself is still valid.
