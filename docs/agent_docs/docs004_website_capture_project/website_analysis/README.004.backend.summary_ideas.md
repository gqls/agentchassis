Here is a detailed summary table of the "Day 2" (maintenance) and "Handoff" (WordPress) concepts we've just discussed.

### 🏛️ Summary of "Site Manifest" and "WordPress Handoff" Plans

| Concept / Problem | Key Agents & Adapters | Plan / Workflow | Key Outcome |
| :--- | :--- | :--- | :--- |
| **1. Handling External Edits**<br>(The "Sync" Problem) | • `git_hook_adapter`<br>• `Manifest Sync Agent`<br>• `Master Strategist` | 1. A `git_hook_adapter` (webhook) is hit on *any* `push` to a site's repo.<br>2. A `Manifest Sync Agent` checks the committer.<br>3. If the committer is **human**, the agent flags that site's `manifest.json` as `status: 'desynchronized'`.<br>4. The `Master Strategist` **stops** any future "Edit Workflows" and creates a **HITL task** ("Human must review/merge"). | **Safety & Robustness.** We protect human work from being overwritten and prevent our agents from acting on "stale" information. |
| **2. Adopting Existing Sites**<br>(The "Ingestion" Tool) | • `Chief Strategist`<br>• `Capture Bot`<br>• `Pattern Deconstructor`<br>• `Site Architect` | 1. The `Strategist` starts an **"Adopt" workflow** on an existing site's repo.<br>2. We run our standard **"Learn Loop"** (scrape, get `layout_map`, find structural blocks).<br>3. A new "Matching" step compares the found blocks to our *own* `in-house` component library.<br>4. The `Architect` generates a *new* `manifest.json` with `status: 'adopted_partial'`, linking found blocks to our components (with a `match_confidence`) or creating `stubs`. | **Extends Our System's Value.** We can "adopt" external sites and make them *partially* manageable by our "Edit Workflow" (e.g., for content changes). |
| **3. WordPress Handoff (Content)**<br>(The "Minimal Effort" Handoff) | • `WordPress Formatter` (New Agent)<br>• `Site Architect`<br>• `Content Pipeline` | 1. The `Architect` & `Content Pipeline` generate the full site (all pages, posts, etc.).<br>2. The `WordPress Formatter` agent **transpiles** all this content into a **single `wordpress-export.xml` file**.<br>3. The human developer's *only* task is to install a fresh WordPress + their theme, then run `Tools > Import` and upload this one file. | **Rapid, Maintainable Handoff.** The site is fully populated in minutes. The client gets a standard, maintainable WordPress site, not a custom, brittle system. |
| **4. WordPress Handoff (Stubs)**<br>(Handling Forms) | • `WordPress Formatter` | 1. We *do not* export complex, custom form code.<br>2. The `Formatter` is configured to know about common plugins (e.g., WPForms).<br>3. It inserts the plugin's **shortcode** (e.g., `[wpforms id="1"]`) directly into the exported page content. | **Maintains "Minimal Effort."** The developer just installs the standard plugin and creates the simple form. The page *just works*. |
| **5. WordPress Handoff (Styles)**<br>(Influencing Branding) | • `wordpress_adapter` (v2)<br>• `Site Architect` | 1. The `Architect` pulls the `branding` data (colors, fonts) from the `Strategy`.<br>2. The `wordpress_adapter` generates a simple **`.sql` file**.<br>3. This `.sql` file *injects* these color/font values directly into the WordPress `wp_options` database table, updating the theme's global style settings. | **Instant Branding.** The developer runs one SQL query, and their chosen theme's color palette and fonts instantly match the `Strategy`'s brand. |
