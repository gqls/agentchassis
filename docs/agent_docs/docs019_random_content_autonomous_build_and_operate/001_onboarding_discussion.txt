Good place to spend time, because onboarding is where the "documentation is code" thesis gets tested against reality: the config is itself authored knowledge about a repo, so deriving it is the same authored-versus-derived problem as everything else, one level up. Let me work through what the config actually is, then how it gets created, and where your own setup sits in that.

Start by separating what the config contains, because the parts have very different derivability, and lumping them together is what makes onboarding look like one hard problem instead of three uneven ones.

The first part is mechanically discoverable — what languages are present, the package and module layout, how the repo builds and tests, where files live. Much of this is sitting in the repo already: go.mod, the Makefile, the directory structure, CI config, the presence of a migrations folder. A scanner can derive most of it by inspection, and where it can't, it can run a probe (try the build command, see if it succeeds). This part is genuinely derived from the repo, low-stakes, and correctable by observing whether the verification harness actually runs. So onboarding the mechanical layer is: scan, propose, probe to confirm.

The second part is conventions — naming (your kebab-vs-snake distinction), the response-envelope shape, the orchestrator/handler boundary, "workflows stay simple, complexity in Go." This is partly discoverable by example: you can infer conventions statistically from the existing code ("functions here are named like this, actions return this shape"). But inference gives you what the code does, not what it's supposed to do, and those differ exactly where the code is wrong or mid-refactor. So convention inference is a strong draft and a weak authority — it proposes "this looks like your naming rule," and a human confirms or corrects. This is the authored-by-inference category from the context doc: the scanner reconstructs a likely convention from the code, but it only becomes authoritative on confirmation, because a convention is intent and intent is not fully recoverable from instances.

The third part is intent and standards — the why-chain, the priority profile, the direction-of-travel, the actual standards. This is largely not derivable at all. You cannot read "security outranks speed for this node" or "we're deliberately simple here for now" off the source. This is the part a tenant has to supply, and it is also the part that delivers most of the tool's distinctive value. Which produces an honest and useful framing: the mechanically-discoverable layer can be near-automatic, the conventions layer is inferred-then-confirmed, and the intent layer is elicited. Onboarding is not one process; it is automatic for the first, confirmatory for the second, and a structured interview for the third.

That third part is where your existing assets matter more than they first appear. You already have a briefing questionnaire and an intake orchestrator — structured elicitation of what a build is for. That is exactly the shape the intent layer of onboarding needs: a guided interview that extracts the why-chain and the priority profile from a person who holds them but has never written them down. So onboarding's hardest layer reuses a pattern you've built, pointed at a new subject (a codebase's intent rather than a website's brief). Worth treating the onboarding interview as a descendant of the briefing questionnaire rather than a new invention.

Now the move that makes this tractable rather than a wall: onboarding does not have to be complete to be useful, and it should be progressive. A tenant should get value from the mechanical layer alone — fresh code context, signatures, reuse search, schema — before any intent is captured, because that half already beats pasting into a chat. The conventions and intent layers are then filled incrementally, and the tool gets better as they are. This matters for adoption: a tool that demands a complete config before it does anything has a cliff at the start; a tool that delivers the mechanical value immediately and deepens as you feed it intent has a ramp. The progressive model also means onboarding is never "done" — it tracks the repo, which connects to the next point.

The part that is easy to miss: onboarding is not a one-time event, it is the same maintenance problem as the docs. A config derived today drifts as the repo changes — a new language appears, the build command changes, a convention shifts, an area's priority changes because of a law. So the config is authored knowledge that needs the same upkeep machinery we already designed: drift detection (the scanner periodically re-derives the mechanical layer and flags where reality diverged from the recorded config), confirm-not-initiate (proposed config changes are human-confirmed), and provenance (each config entry records whether it was discovered, inferred, or supplied, which tells you how much to trust it and who may change it). So "onboarding as a first-class deliverable" really means "the config is a maintained artifact with the same lifecycle as the standards," not "a good setup wizard." The wizard is the first pass; the lifecycle is the deliverable.

There is a genuine tension to flag rather than smooth over. Inference quality scales with codebase quality. On a clean, consistent repo, convention inference is strong and onboarding is fast. On a messy or inconsistent repo — which is most real repos, and possibly some tenants — inference produces a confident draft of conventions that are actually just the repo's bad habits, and confirming that draft codifies the mess as the standard. So the more a tenant needs the tool (because their repo is inconsistent), the less their repo can teach it, and the more the intent layer has to be elicited rather than inferred. The mitigation is to make the tool surface its uncertainty — when inference finds inconsistency ("functions are named three different ways here"), it should present that as a question to resolve, not silently pick the majority. Inconsistency detected during onboarding is itself valuable output: it tells the tenant where their own conventions aren't actually conventions.

For your own setup specifically, you are the ideal first onboarding case and you should treat it as the template, not as a special case you hand-wire. The mechanical layer is straightforward — Go, Postgres, the Makefile, the migrations, the chassis layout. The conventions layer is partly already written, because 001 and 003 and the naming FOCUS doc contain them in prose; so for your repo the conventions can be drawn from existing docs rather than inferred from code, which is a stronger source. The intent layer is what the constitution and the why-chain work from the adoption plan produces. So onboarding your own repo is: run the scanner for the mechanical layer, extract conventions from the existing standards docs (and confirm against the code where they disagree — those disagreements are bugs or drift worth seeing), and capture intent via the constitution and the objective-tree why-chain. Doing your own onboarding this way does double duty: it produces your config, and it exercises and shapes the onboarding process you will later offer to tenants, with the advantage that you can check the output against your own knowledge of the repo.

One thing I would build deliberately into your own pass, because it is the cheapest version of the inconsistency value above: where the conventions extracted from 001/003 disagree with what the code actually does, record the disagreement rather than resolving it silently. That set of disagreements is a free audit of where your codebase has drifted from its own documented standards — which is the drift detector running for the first time, on you, before a tenant ever sees it.

The piece I would settle next, because it determines how much of onboarding can be automatic versus interview, is the conventions layer specifically: for your repo, do we treat the existing standards docs (001, 003, naming) as the authoritative source of conventions and use the code only to find disagreements, or do we infer conventions from the code and use the docs to confirm? The two give different results exactly where the code and the docs have drifted apart, and which one you trust as the source decides what the tool does when they conflict. Which direction do you want for your own onboarding?
