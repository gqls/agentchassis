### PBP-001 — Rebuild vs rerender semantics and stale-render fossilisation
- **status:** deployed
- **status-evidence:** "the deployed pages are RERENDER output carrying stale stored renders … deployed hero consumes legacy `var(--accent-color, #0f3460)` … A full page-build-handler rebuild is required; `needs_rerender` would re-fossilise them" (idea.uk CHECK 4 evidence); RUNBOOK_linking_phantom_fixes(7) confirms the same distinction generically ("Render vs rebuild — what fixes what").
- **what:** Two distinct page-refresh routes with different semantics: `needs_rerender` (handler rerender-pages) reassembles stored `page_components.rendered_html` and injects stored chrome — it does NOT re-render component templates, so template changes never land and old renders fossilise; a full build (`site_work_items` insert: pipeline=build, handler_agent=page-build-handler) re-runs plan_sections and re-renders everything. Consequences: header/footer fixes need only re-render (data rebuilt fresh in Go); hero CTAs and hub URLs need rebuilds (stored data still carries phantoms). idea.uk had lived for weeks on reassemblies of early renders while the library advanced — the fossil tell is a legacy variable name in deployed HTML, and its count going to 0 is the proof a rebuild truly re-rendered. Docs 026 ("rerender reflects new template") and 016 ("patches in place") disagreed; evidence sided with 016. Related hazard: a content rebuild can de-tool a tool page (page-content-writer regenerates from plan_sections, which does not know the interactive tool — see the interactive-clobber entry).
- **sources:** RUNBOOK_scheme_to_components(50).md#CHECK-4-RESULTS; running_notes_scheme_to_components(55).md#So/#Sh; RUNBOOK_linking_phantom_fixes(7).md#2; NOTES(44) P4.2 result 2026-06-22
- **relations:** rerender fossilisation (rebuild-cascade register); no-LLM re-render path (PBP-013); dual chrome render paths
- **verify-later:** rerender-pages vs page-build-handler workflow definitions in agent_definitions; rerender_single_page_action.go

### PBP-003 — plan_sections field-source resolution semantics (on_missing, required, defer) + needs_section_data escalation
- **status:** deployed
- **status-evidence:** running_notes_14(26) Part 14p "RESOLVED 2026-06-06" with code-confirmed semantics; independently re-derived and confirmed on the vonc site 2026-07-02/03 (index went 3→6 sections after populating a cta spec + relaxing a required field) and again via idea.uk's differentiators investigation (W6.4).
- **what:** plan_sections classifies each planned section by resolving its schema fields: `source=llm` is always available; `query.*`/renderer/static resolve at render time or fall back; any other source runs the resolver. A REQUIRED field whose source doesn't resolve hits the `on_missing` switch, whose default case DEFERS the whole section ("default to defer for safety") — and empty `on_missing` defaults to `skip_field`, which is NOT a case in the required-field switch, so it silently falls through to defer. This is the trap that hid entire hub sections (a required `cta_url` with an unpopulated spec source deferred the whole section). Unresolvable required fields escalate a `needs_section_data` work item into needs_human_review; the page builds without the section — a loud drop, not silent. `on_missing: skip_field` is the established optional pattern (omit the field, let the template gate handle it). Authoring rule: never `required=true` + `on_missing=skip_field` — fix by populating the site data source or degrading the field. `closeResolvedDataRequest` self-closes escalations once the field resolves post-deploy.
- **sources:** running_notes_14(26).md#part-14o-14p; gobatch_01_plan_sections.md#Edit-A; docs/RUNNING_NOTES_vonc(36).md#2026-07-02; docs/016b_debugging_guide_merged(3).md#regenerated-content-section-is-deferred
- **relations:** section data source triad (site-plan-and-reconciler register, PLAN-009); save_page_sections layered guards (PBP-011); carry-forward path (rebuild-cascade register)
- **verify-later:** plan_sections_action.go on_missing switch (required branch has no skip_field case); needs_section_data item lifecycle

It answers **"may the generic builder write this page?"**, which has two independent NO answers, carried as a class: `refusalOwned` (`pages.rebuild_policy='owned'`, migration 164, unchanged) and `refusalToolPending` (**`page_type='tool'` with no live `component_level='tool'` component** — `bugs_open/450`). One SQL rendering (`toolShellPredicateFor`), one pure derivation (`genericBuildRefusal`), one kill-switch reading (`toolShellRefusalArmed`). Consulted at the writeWorkItem policy door (in-tx), `load_page_record`'s `refuse_owned_page` arm, `save_page_sections`, `AssemblePageAction`, the rerender escalation, and the build-selection exclusion (`genericBuildExclusionSQL`).
- **why it exists:** a plan names tool pages BEFORE their tools exist — tools arrive from the ~3h design rotation hours-to-days later, under names the planner never saw (**seotools.co.uk: 0 of 7 planned names matched what `tool-deployer` built**). Five generic producers then route the page to `page-build-handler`, whose guard asked only about `rebuild_policy`; a planned tool page is `'generic'`, so the builder wrote what the plan said — prose about the tool — and deployed it. ~~**61 tool-type pages with no tool-level component across 10 sites** `[MEASURED 2026-09-03, re-run of the filing census, identical]`~~ → **CORRECTED same day: 67 pages / 16 sites `[MEASURED 2026-09-03 ~12:0xZ]`.** The filing census was a FLOOR twice over, and the correction is the more useful fact: it excluded never-shipped pages (`deployed_at IS NOT NULL`, +4/4 — including the very sectionless variant `bugs_open/450` §7 calls the other branch of the fork, so **the class's own census could not see it**), and it did not test `cc.is_active` while **this guard does** (+9/4, four sites invisible to it entirely). ⚠ **The census that measured the bug was never the predicate the fix uses** — that drift is how a fix gets judged against the wrong denominator, and it is why the corrected query in the bug file is now the guard's own predicate. Also: any version of it is repair-INITIATED, not repair-COMPLETED — a page leaves the count when its component attaches, while the public sees prose until the rerender drains; all seven seotools URLs served 200 at ~56 KB with the tool's own headline and **not one `<form>`**. Control the same morning: advertise.co.uk, whose rotation happened to reach it before its plan persisted, so the plan named real tool components and nothing went wrong. **Ordering luck was the only difference.**
- **the load-bearing design choice — DERIVED, NEVER STORED.** The obvious fix marks the page (`rebuild_policy`, or a new `'tool-pending'` value). It was rejected on a measurement, not a preference: `rebuild_policy` is CHECK-constrained to `'generic'|'owned'` (migration 164) and **nothing in this estate has ever UPDATEd it** — two INSERT-time writers (`adopt_verbatim.go`, `create_report_page_action.go`), no transition in any handler, check or scheduler, in either direction. A flag set at plan time is a flag **nobody clears**, and the page would be protected for ever. Deriving the answer from the page's contents means it **lifts by itself** the moment the tool component is inserted.
- **the self-clearing claim is PROVEN AT THE ORDERING, not argued:** `deploy_tool_action.go` INSERTs the tool `page_components` row (step 5, `:517`) **before** `raiseToolContentItem` (step 6, `:564`), so the tool pipeline's own companion `needs_content_page` is written when the predicate is already false and is never parked. This was checked because a live lane (`portfolio_positioning`) was about to fire 8 `add_tool` items at exactly these shell pages; had the order been the other way, this change would have deadlocked their wave.
- **why the door and not the detector.** `bugs_open/450`'s candidate 3 was "never route a `page_type='tool'` target to `page-build-handler`" in `check_phantom_internal_links.go`. Not taken: the link repair is only the producer that fires FIRST on a fresh remake — `page_component_history` names four more (`empty_section` 3 pages/67 writes, `page_rerender` 3/20, `needs_page` 3/14, `needs_content_page` 2/8 in 14 days `[MEASURED 2026-09-02]`). A guard on one producer is a guard on one door; the two seams here are crossed by all of them. Independently, `availableBuilders` is **unreachable** from `discovery_checks` (import direction), which is why `bugs_open/220` deferred the same idea.
- **the two vocabularies this closes.** The plan validator's "owned" (`ReconcileSitePlanAction:270`, files `owned_page_review` on `plan.Role=='tool'`) and the save guard's "owned" (`rebuild_policy`) shared a word, had no join, and so the hold protected nothing. This does not unify them — it makes the SAVE side able to see the case the HOLD side was complaining about. ⚠ **The hold still has no consumer**; that is `bugs_open/450` candidate 2's residue and it is deliberately not what this fixes.
- **what it does NOT do, stated so nobody reads more into it:** it does not remove or repair the 61 existing shells (they are realised pages; cleanup is instance work, `portfolio_positioning`), it does not stop the PLANNER naming tool pages (that is the `enforce_tool_sources` plan-side arm, still to land), and it does not gate `rerender_single_page`'s re-assembly of existing components — migration 164 calls that the sanctioned owned-page deploy path, and gating it is the `bugs_open/210` family.
- **the receipt stopped lying.** The `owned_page_review` spec hardcoded `"rebuild_policy": "owned"`; on a 450 page that is **false** — the column says `'generic'`, which is the whole bug — and it would have sent every reader to check a column that disagreed with the row. - **kill switch `DISABLE_TOOL_SHELL_REFUSAL`**, ships **ARMED** (owner ruling against default-OFF switches that rot), scoped to the **new arm only** — disarming it must not cost migration 164's live ownership refusal, which protects real tools. Read in exactly one place so the Go verdict and the SQL exclusion cannot disagree; pinned by test in both directions.
- **known misfire class, named rather than discovered later:** the predicate inherits `page_type`'s classifier gaps. A page wrongly typed `'tool'` is refused — **loudly** (one deduped review row naming the retype remedy, parked items holding their dedup slots), never a silent shell. A ported tool living inline in a non-tool-level component is also classed as a shell and refused, which is **protective**: a generic rebuild would clobber it. ⚠ The first draft of this entry cited `578_retype_mislabelled_tool_rows_HOLD.sql` as evidence that mislabelled tool PAGES exist; that migration retypes mislabelled **`page_components`**, not `pages.page_type`, and **nothing in the tree retypes page rows** — the citation was wrong and is corrected here rather than repeated (WRONG_CALLS 2026-09-03).
