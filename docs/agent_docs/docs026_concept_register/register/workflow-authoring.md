### WFA-002 — `$ctx.` execution-context parameter namespace for `query_database`
- **status:** deployed
- **status-evidence:** live on chassis v1.0.1191 (digest `sha256:2f96b795a5c4…`), pod-verified `strings /app/agent-chassis | grep -c "unknown execution-context field"` → 1; first consumer live via migration `258_diagnose_loop_stamps_run_correlation.sql`, verified end-to-end on a real diagnosis 2026-07-28 17:05 (`spec.dispatch_correlation_id = 66a65287-…`).
- **what:** A reserved parameter namespace letting any workflow's `query_database` step bind **the identity of the run executing it** — `$ctx.correlation_id`, `$ctx.orchestration_id`, `$ctx.parent_orchestration_id`, `$ctx.orchestration_name`, `$ctx.client_id`, `$ctx.request_id`, `$ctx.step_name`, `$ctx.group_id` — as ordinary `$1`-style SQL parameters. Written as `'params', jsonb_build_array('$ctx.correlation_id')` beside the query. Before it, `query_database` could only bind values found in `collected_data`, and a run's own correlation is not there: it lives in the execution context. So a dispatch loop could claim a queued row but could not record **which run took it**, and every lane that wanted that had to grow a bespoke Go action. Additive by construction — only paths beginning `$ctx.` take the branch, and no `collected_data` key can start with `$`. An unknown field or an empty value is an **error**, never a silent empty string (a silently-empty bind fills a stamp column with `''` and looks populated in every subsequent query); there is deliberately no "optional" mode.
- **why it is registerable:** "which run picked this row up" is a question every queue-driven workflow on this platform has, not a diagnose-specific one. Any dispatch loop, claim step or audit trail can use it without new Go.
- **sources:** platform/orchestration/actions/execution_context_params.go; platform/orchestration/actions/database_actions.go#QueryDatabaseAction; docs024/bugfix_124_double_dispatch/PLAN_2026-07-28_double_dispatch.md §4 P3; docs/agent_docs/sql_for_agents/258_diagnose_loop_stamps_run_correlation.sql
- **relations:** SCH-012 diagnose-dispatch-loop (first consumer); work-item claim/dedup contract; diagnosis_artifacts correlation keying (`diagnose_assemble_bundle_action.go` writes on `params.ExecutionContext.CorrelationID`, which is what made the item↔run join impossible)
- **landmine:** **ordering is load-bearing and permanent.** A config binding `$ctx.…` run against a chassis that predates this action FAILS that step (`query param path '$ctx.correlation_id' resolved to nil`) — for a claim step that stops the whole lane. Ship the image, pod-grep, then apply the config; and a rollback below the image must revert the config too.
- **review status:** council **REJECTED** it (guardian veto on SCOPE — a platform seam inside a bug patch, corr `90361922`), then **OWNER RULING 2026-07-28: Option A — keep the code, fix the precedent.** The seam stays; the rule it produced is in `CLAUDE.md` §"Platform seams and the ordering exemption". Full review + costed options: `docs024/bugfix_124_double_dispatch/REVIEW_2026-07-28_ctx_namespace.md`. **Whether it should acquire a SECOND consumer is deliberately not ruled on** — nothing depends on it today, and a reviewer asked for it to be judged on its own merits.
- **measured, not asserted (the council forced these):** 63 `params` entries across every live workflow, exactly **1** `$`-prefixed (this one) ⇒ nothing can be shadowed. Of 34 files reading `ExecutionContext.CorrelationID`, only **2** bind it into SQL and 16 use it as a Kafka partition key — so this does **not** duplicate them and there is nothing to migrate.
- **verify-later:** `strings /app/agent-chassis | grep -c "unknown execution-context field"` on the running pod; `SELECT default_config->'workflow'->'steps'->'claim_item'->'config'->'params' FROM agent_definitions WHERE type='diagnose-dispatch-loop'`

### WFA-003 — Sub-workflow validation: nested loop steps are validated, by the same traversal the offline audit uses
- **status:** deployed — live on chassis **v1.0.1203** (`sha256:afd2a4683362…`), both replicas, 2026-07-29.
- **status-evidence:** pod-verified on BOTH replicas of v1.0.1203, 2026-07-29: `"uses fan_out, which cannot work inside a sub-workflow"` → 1, `"Substep declares fields"` → 1 (the round-2 single-sourced decoder), and the DELETE-marker `"Checking disconnected step: "` → **0** while its replacement `"Checking disconnected step for cycles"` → 1. **The colon matters:** the marker first written here was the phrase without it, which the replacement string still contains — that check returned 1 on a correctly-deployed image. Functional evidence, which the binary grep cannot give: **22 orchestration runs whose `workflow_plan` carries a `sub_workflow` since the roll (18:01→18:49Z), 21 COMPLETED, 0 validation errors**, one of them executing a loop-expanded substep (`process_item_iter_2_spawn_handler`) — so the nested traversal ran in production against real definitions and passed them.
- **what:** `ValidateWorkflow` now descends into steps nested inside a loop's `sub_workflow`/`substeps`, which until this change were extracted from config and executed directly by the loop action having been checked by **nothing** — 85 live steps across 18 agents. Three pieces: (1) `subWorkflowsOf` is the single definition of where a nested step lives, mirroring `loop_actions.go`'s precedence exactly (`substeps` wins; `sub_workflow` only if it is absent or empty); (2) `models.DecodeSubWorkflowStep` is the **one** nested-step decoder, called by the executor (`parseSubsteps`) and the validator alike — seven fields, returning the keys the runtime **drops** (`dependencies`, `sub_tasks`, `timeout`, `name`, `store_memory`, `target_agent_type`), which are reported rather than pretend-enforced; (3) `WalkSteps` is exported so anything asking "which definitions carry action X?" or "which (action, key) pairs are live?" asks it of the same step set the validator enforces against. `scripts/audit-config-keys.sh` is the first consumer, via `cmd/config-key-audit --live-pairs`.
- **why it is registerable:** it changes what "validated" GUARANTEES for every pipeline on the platform, and it exports a traversal any audit, census or migration over live workflow definitions should be using. The specific trap it removes is fleet-wide: a query over `default_config->'workflow'->'steps'` silently under-reports, and 25 of the 884 live (action, key) pairs existed only below that level.
- **hard errors vs warnings, and why the split is not arbitrary:** a fault is a hard error only where it is unambiguous **at any depth** — no action, a remote action with no topic, a nested `fan_out` (the decoder drops `sub_tasks`, so it would execute with none), an empty sub-workflow, a `start_step` naming no step of that sub-workflow, a cycle. Everything validation genuinely cannot see is a **warning**: a `next_step`/`error_step` out of a sub-workflow is legitimate — loop expansion passes it through untouched and it may resolve against the enclosing plan or against `<loop>_complete`, which the expander injects and which exists in no definition.
- **sources:** pkg/models/substep_decode.go; platform/validation/subworkflow.go; platform/validation/workflow.go#ValidateWorkflow; cmd/config-key-audit/main.go#emitLivePairs; scripts/audit-config-keys.sh; platform/orchestration/actions/subworkflow_decoder_lockstep_test.go; platform/orchestration/actions/subworkflow_live_dryrun_test.go; docs024_key_docs_latest/bugfix_144_subworkflow_validation/PLAN_2026-07-29_subworkflow_validation.md
- **relations:** SCR-003 declared config-key contract (this makes it reach nested steps); SCR-004 the fleet-wide coverage report (its denominator was measured over a population that excluded every nested-only pair); bugs_closed/101 (unknown config keys); bugs_closed/086 (the same class one level up — a field the plan-builder failed to carry); bugs_open/136 (the objection that found this)
- **landmine:** **the honoured field set is a statement about the EXECUTOR, not about `models.Step`.** Adding a field to `Step` does not add it to `SubWorkflowStepFields`; `pkg/models/substep_decode_test.go` fails until you decide, in code, whether the loop reads it or knowingly drops it. "Fixing" that test by widening the honoured set makes the validator vouch for a field nothing reads — which is the defect this entry exists to close, one level down. (Until the council's reuse seat objected, there were TWO decoders held together by a lockstep test; single-sourcing them is why that test is now a re-inlining guard rather than the guarantee.) **A second landmine for any future change to what "validated" means:** run the dry-run harness first — `SUBWF_LIVE_EXPORT=<export> go test ./platform/orchestration/actions/ -run TestLiveDefinitionsPassSubWorkflowValidation -v`. It validates each live plan twice, whole and with sub-workflows stripped, and only reports the DIFFERENCE, so a pre-existing rejection cannot be misread as damage from your patch.
- **measured before shipping, not argued:** 178 live definitions replayed — **0 newly rejected**; 3 rejected before and after (`html-developer-chunked`, `multipage-wrapper`, `html-assembler`, each naming an action in no registry; `bugs_closed/044` records these as retired definitions still flagged `is_active`). 85 nested steps / 18 agents / 19 sub-workflows. All 20 distinct nested actions are `IsLocal:true` and **none of the 85 carries a topic**, so the topic rule costs nothing today. 0 of the 66 nested `(action, key)` pairs trips the strict-config rule. Live step-config census: 1,173 object, 63 null, 0 other.
- **review status:** council **APPROVED round 1**, corr `9194bc97-8475-4022-b658-2ac64f06dd63` (4 advisory objections, none high-severity). Two were answered with code before committing: the reuse seat's (two decoders pinned by a test, not single-sourced) and the debug-historian's (`is_active` assumed to bound the blast radius — `processor.go:357-360` filters on exactly those three predicates, and re-running the dry-run over ALL 183 non-deleted definitions gives the same 0-newly-rejected answer). The guardian asks a HUMAN to settle the RFC-vs-bug-patch venue question and to confirm no consumer relies on today's silent pass-through; that is open and is recorded as open. **This is a platform seam** under CLAUDE.md's 2026-07-29 ruling — it changes what a shared mechanism guarantees — so the venue question (council gate vs RFC) was put to the reviewers explicitly rather than assumed away. Registered in the same commit that ships it, per condition (2) of the ordering exemption, which is now the whole of the requirement.
- **verify-later:** the pod-grep pair above after the next roll; `./scripts/audit-config-keys.sh` printing a non-zero "inside loop sub-workflows" count (a return to zero means the traversal broke, not that the fleet tidied itself)

### WFA-004 — Offline unregistered-action detector (`config-key-audit --unregistered-actions`)
- **status:** deployed (it is a standalone CLI tool, not a chassis-served mechanism — "deployed" here means committed and runnable; there is no image or pod to roll or verify against).
- **status-evidence:** run against the live DB 2026-07-30: 178 live, `is_active`, non-snapshot agents decoded, 0 undecodable, exactly 3 findings (`html-assembler`, `html-developer-chunked`, `multipage-wrapper`) — matching WFA-003's own independent measurement of the same 3 via the dry-run harness.
- **what:** A new mode on the existing binary, `config-key-audit --unregistered-actions`, that answers offline the question `platform/validation/workflow.go`'s `validateStep` and `subworkflow.go`'s `validateSubWorkflowStep` answer only when a message arrives: is this step's action neither locally registered (`actioncheck.IsLocalAction`) nor topic-routed? It walks the same live-export shape `--live-pairs` reads with the SAME `validation.WalkSteps` traversal WFA-003 registered, top-level and nested, so it cannot go blind in a direction the runtime validator doesn't. Deliberately mirrors the rule exactly, including not exempting `fan_out` — a fixture test (`TestFindUnregisteredActions`) pins that. `scripts/audit-unregistered-actions.sh` is the first consumer, mirroring `audit-config-keys.sh`'s DB-query/report shape.
- **why it is registerable:** any workstream doing `is_active` hygiene, dead-dispatch-edge cleanup, or a pre-roll sanity check on live agent definitions needs exactly this question answered, and it is now a report rather than something to re-derive from a rejected message.
- **sources:** cmd/config-key-audit/main.go#findUnregisteredActions,#emitUnregisteredActions; cmd/config-key-audit/main_test.go; scripts/audit-unregistered-actions.sh; bugs_closed/148_HANDOFF_2026-07-29_three_live_agents_name_actions_that_exist_in_no_registry.md
- **relations:** WFA-003 (shares `WalkSteps`, the traversal this depends on); bugs_closed/044 (first identified `html-assembler` et al. as retired-but-`is_active`; this makes the check re-runnable instead of a table that goes stale); bugs_open/148 §7 scopes fix candidates 2 (retire/repoint the two live dispatch edges into these definitions) and 3 (wider `is_active` hygiene) out as an owner call this tool informs but does not settle.
- **landmine:** a step with a topic is legitimately remote and dispatched by Kafka, not the local registry — "action not in registry" ALONE is not the defect, only the pair (no topic AND not local) is. A check that drops the topic condition produces a long false-positive list against every intentionally-remote step in the fleet.
- **review status:** out of the council gate's scope by the gate's own filter (`SCOPE_RE='^(platform|internal|pkg)/'`; this touches only `cmd/` and `scripts/`) — not submitted, per the gate's own cost model (docs/site/tooling changes are refused client-side rather than spending a credit).
- **verify-later:** `./scripts/audit-unregistered-actions.sh` — a return to a non-empty finding set that isn't these same 3 names a NEW unrunnable definition; a return to 0 means candidates 2/3 above were actioned.

### WFA-005 — `output_format` is a LIVE step contract, and a JSON step gets one corrective re-ask
- **status:** built (inert until the next chassis roll) — committed `4c1a97874`, `085160a6c`, `059ae2acd`. Council `576832f3` **APPROVED at round 2** (14 reviewers, 0 unreadable, 8 advisory objections, none high). Round 1 was REVISE on a gating objection from `debug_historian` — the depth claim above was asserted, not measured; it is now measured and the census corrected upward by one step and one agent.
- **status-evidence:** `go test ./platform/orchestration/actions/` green; the two behaviours verified BY MUTATION rather than by passing — reverting the `output_format` fallback fails 4 of the 6 new tests, removing the vocabulary allow-list fails the gate test specifically, restoring passes both. NOT yet pod-verified; see **verify-later**.
- **what:** Two contracts on `execute_llm_prompt`, both previously absent. **(1) The declared output key now works.** `getOutputType` read only `output_type`; the fleet writes `output_format`. Measured 2026-08-01 across all **135** active `execute_llm_prompt` steps (134 top-level + 1 nested in a loop's `sub_workflow`): `output_type` on **6**, `output_format` on **101** — **91** of them `json`, across **33 agents**, every council seat included. **Depth measured, not assumed** (the council gated round 1 on exactly this): all 101 sit at `config.output_format`, the map `params.StepConfig.Config` is; zero under `config.ai_service`, zero at step root. So ~75% of LLM steps declared an output contract that nothing honoured and silently received `getDefaultOutputInstructions()`, which mentions JSON nowhere, instead of `getJSONOutputInstructions()` and its "Ensure valid JSON syntax (proper quotes, commas, brackets)". The fallback is **vocabulary-gated** to `json|text|html|markdown`. **(2) A JSON-declaring step whose answer will not parse gets exactly ONE corrective re-ask** before the pre-existing text path, **and (3) if it still has no JSON afterwards the result carries `__json_contract_unmet`** — a marker, deliberately not a hard error, so the residual silent success is countable instead of invisible (failing loud would break 91 steps over content they did not author, `bugs_closed/073`). Corrective, not identical, because an identical re-ask reproduces the failure; the instruction branches on *which* failure occurred — truncated → same judgement materially shorter, malformed → same content as one valid JSON value with bracket balance spelled out. `resolveOutputType` exists so the instructions and the retry ask that question through one rule rather than two.
- **why it is registerable:** any workstream authoring an LLM step now has a config key that MEANS something — writing `output_format: json` buys both the JSON instructions and the re-ask, and writing nothing buys neither. That is not derivable from the config: until this commit the key was indistinguishable from a comment. 32 agent types inherit the change without their owners doing anything.
- **sources:** `platform/orchestration/actions/ai_actions.go#getOutputType,#resolveOutputType,#correctiveReaskPrompt,#markJSONContractUnmet,#ExecuteLLMPromptAction`; `platform/orchestration/actions/ai_output_contract_test.go`; `bugs_open/119_HANDOFF_2026-07-27_one_seat_emitting_malformed_json_costs_a_whole_council_round.md`; `docs/agent_docs/docs024_key_docs_latest/bugfix_119_seat_retry/`
- **relations:** `bugs_open/119` (the case); `bugs_closed/019` + `bugs_open/138` (truncation — the re-ask deliberately does NOT touch `salvageTruncatedReview` or the `Degraded` gating rule); `bugs_closed/076` (the `__truncated` marker contract, which the re-ask re-stamps from the response actually returned); `bugs_open/134` (the same class — a config key declared and inert); LCO-005/LCO-006 (`aiservice.IsTruncated`, reused here).
- **landmine:** **`output_format` is NOT this action's key alone — `query_database` reads the same name with a different vocabulary** (`array`/`object`, `database_actions.go:26`). That is why the fallback is allow-listed rather than a pass-through, and why widening the allow-list is not a free change: an `output_format` value that means "array" to one action must never select an instruction set in the other. Second trap: the re-ask fires on `declaredOutputType == "json"` only, so **giving a step `output_format: json` now costs it a possible second LLM call** — correct for a step that needs JSON, wrong for one that declared json loosely and is happy with prose.
- **review status:** **APPROVED**, correlation `576832f3-0d39-48b7-af18-97e06297900f`, round 2 — `Council-Reviewed:` trailer on `059ae2acd`, earned by a verdict that was read. Two advisory objections were acted on or checked: `diagnosis_guardian` (the brevity re-ask protected findings but not the citations under them — fixed), `llm_reliability` (claimed `GenerateText` does not decode `stop_reason` — refuted, all three providers return a `*TruncatedError`). **Six of the eight objections were an artefact**: the seats cited this entry's own landmine as evidence against the change that wrote it — see `016b` §9.
