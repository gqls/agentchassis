- **what:** A GLOBAL, cross-site registry (`directory_entities` UNIQUE(kind, slug) + `directory_claims`, migration 192) of entities whose every fact carries a verbatim-quote citation, re-verified live: the researcher chain (web_search → prepare_urls → batch_webscrape → LLM extract_claims → `verify_and_register_directory_claims`) registers a claim ONLY if its quote is present in the re-fetched source ("the model proposes; the string comparison disposes", `directory_claims.go`). Per-kind rendering is a closed profile set: `directoryCheckProfiles` (discovery checks per kind: `missing_<x>_section`/`_page`) + `directoryPublishProfiles` (render_directory → JSON files + components) + queryresolve case arms (`<spec_key>`/`<spec_key>_full`) + content_components rows. **The load-bearing guarantee: one kind = one identical list on every opted-in site** — `QueryDirectoryEntries` filters only `kind`+`status`, never site. Per-site filtering would change that guarantee and is architecture-review scope (deliberately avoided by one-kind-per-provider-class). Adding a kind is data-only across SEVEN places (profiles ×3, components, checks-array enablement, planner prompt, **and since 429 the publish trigger's VALUES kind→spec_key→components mapping** — a kind added in Go without that SQL row silently never publishes; LANDMINES has the entry) — NO schema migration (`kind` is unconstrained text). **Two of those seven fail SILENTLY and are worth stating as such** (both measured 2026-08-15): an unregistered check NAME in the checks array is skipped by the registry lookup, not an error — so a checks-enable migration can apply cleanly against a binary that lacks the check and do nothing (probe the binary with a positive AND negative control, never `strings`, never a discovery grep); and the planner prompt is the only place that decides whether a page is PLANNED at all — leave it out and the kind still works, but every site acquires its directory a full discovery round trip late, after the first deploy has shipped without it (the gap 433 closed).
- **intake sizing (added 2026-08-18, migration 471) — the yield is decided by SOURCE SHAPE, and that is measurable.** All-history yield per source domain: `savings-provider` got **12 of its 13 firms from ONE gov.uk list page**; `health-insurer` got all 10 from **two** specialist broker round-ups; `mortgage-lender` got 1 firm per source from four single-firm pages and sat at **2 firms**. Every high-yield source in the register's history is a **multi-firm enumeration that states a fact per firm** — so a run's yield is set by whether an enumeration page reaches the scrape set, not by the pipeline. 471 raised `max_scrapes` 4→10 / `num_results` 10→20 (sized against `bugs_closed/062`: **85 kB of scrape_results for 4 URLs measured** on orchestration `a5ba225c`, so 10 projects to ~210 kB against a ~1 MB `max.message.bytes` ceiling — a ~5× margin, measured not assumed), added four enumeration-shaped mortgage queries, and narrowed the prompt line calling third-party round-ups weak, which was the **opposite** of the measured history. Effect, four runs in ~15 min: 57 candidates, **42 registered, mortgage-lender 2 → 25 active named firms**. ⚠ **Discovery queries must stay < 200 bytes** — `web_search` drops a ≥200-char query as "likely an LLM error message" and the run then fails naming config keys, not length.
