### DGH-001 — Commit-is-deploy: git → GitHub Actions (self-hosted runner) → Backblaze B2 (+ chassis image-tag deploys)
- **status:** deployed
- **status-evidence:** Consistently described as live and in current use across six independent sourcings spanning legacy (docs017/002, docs004) through current (docs/RUNNING_NOTES_vonc) documentation; 102_blog_handoff: "Self-hosted GitHub Actions runner — deployed and running … Runner v2.333.1, pod in ai-persona-system namespace."
- **what:** The platform's standing deploy mechanism, converged on and restated by every era of documentation: individual commits per work item (or per page) are pushed via the git-adapter (a Kafka microservice on `system.adapter.git.requests`, `GitCommitAction` workflow-side) to a shared `sites` repo; a self-hosted GitHub Actions runner (pod in `ai-persona-system`) fires per commit, detects changed root-level domain directories, and runs `b2 sync --delete --skip-newer` to `b2://portfolio-sites/<domain>`, then purges the Cloudflare cache per zone (Cloudflare is DNS/cache-only for this path, not a proxy). There is no separate deploy step — "commit is deploy." Commit SHAs are recorded on pages and work items for traceability; the authoritative workflow lives in `gqls/sites/.github/workflows` (a stray copy under `.git/workflows` is a documented trap that GitHub never reads). Separately, chassis platform code ships as one global `IMAGE_TAG` running every dynamic agent via `agent_definitions` config — `make quick-agent-update IMAGE_TAG=…` (build → push → kustomize → DB image_tag → restart agent-chassis) plus `make update-and-restart-orchestrator` for the generic-orchestrator statefulset; a full `make release` bumps every service; rollback is symmetric and cheap (repoint to the old existing image, no rebuild). Workflow/`default_config` changes are DB-only and take effect immediately, while a chassis code revert only reaches the cluster on the next build/push — these are two different deploy surfaces with different latencies. The identical "commit is deploy" seam was later reused for a VM deploy target (destination swapped, mechanism preserved) — see register/vm-backend-sites.md (VMB-004, VMB-005).
- **sources:** 002(4)#Git commit strategy; 034_github_action.md; README_001_flow_notes.md; docs017_legacy_agent_rules_images_design_keydocs/002_standardising_deployment_implementation_plan.md, 023_maintenance_architecture_unified_v6.md#Git-Commit-Strategy; docs004_website_capture_project/webbuild_pipeline/001pipeline; ED/102_blog_handoff-2026-04-10.md#completed-this-session; docs/RUNNING_NOTES_vonc(36).md#2026-06-25-~18:00, docs/016b_debugging_guide_merged(3).md#orientation
- **relations:** git-adapter; Git-adapter non-fast-forward commit race (DGH-002); sites.github_repo deploy-target selector (DGH-003); Site manifest + external-edit desynchronisation detection (DGH-004); "git committed is not proof of new content"; deployed-binary-predates-disk (Chassis build/deploy practice, DGH-005)
- **verify-later:** gqls/sites .github workflow; B2 bucket layout; Makefile targets; agent_definitions.image_tag column use

### DGH-002 — Git-adapter non-fast-forward commit race (shared sites repo)
- **status:** aspirational
- **status-evidence:** "a latent bug today for concurrent multi-site builds… Fix: retry-on-non-fast-forward in updateRef… tracked as a guardrail"; explicitly noted as unconfirmed in production: "2026-06-04: the missing-homepage lead was NOT this race… remains a latent risk with no confirmed instance yet."
- **what:** `git_commit` publishes to the git-adapter (Kafka key = correlation_id), which does a GitHub Git Data API read-modify-write against the single shared `sites` repo with `force:false` and no retry. Same-site commits serialize safely via Kafka partition (same-site parallelism is git-safe), but different sites can hit different consumer replicas concurrently, and the loser's deploy fails silently on non-fast-forward push. This was initially suspected (but not confirmed) as the cause of a missing-homepage incident before an unrelated auto-complete bug was pinned as the real cause; it remains an open, unconfirmed reliability item. A proposed optimistic-concurrency retry (re-read HEAD, rebuild tree, re-commit) has not been built. Minor cosmetic sibling bug: the page-rerender commit-message template `"Rerender: {{.filename}}"` renders uninterpolated, and full-build deploys also commit as "Rerender: <page>" — the shared message format no longer distinguishes build from rerender.
- **sources:** running_notes_14(26).md#part-10; FOCUS_dispatch_throughput_and_claim_watchdog(3).md#git-deploy-path
- **relations:** Commit-is-deploy (DGH-001); deploy gate on sections_saved; dispatch throughput; Lever A prerequisite
- **verify-later:** git-adapter github_client.go CommitToRepo/updateRef retry behaviour; adapter.go consumer model (2 replicas, group git.adapter.group); commit-message templating scope

### DGH-006 — `delete_file`: the UNPUBLISH primitive (git-adapter verb + `retract_page_deployment`)
- **status:** deployed — **UNDER ARCHITECTURE REVIEW (RFC 011), council REJECTED 2026-08-03**
- **VETO ON RECORD, read this before building on it.** Council correlation `4a7f0877-4149-4431-97d4-318d093570a4` round 2 returned **REJECTED — hard veto from `guardian`**, with `architecture` signalling `needs_rfc`. The objection is to **how the capability reached production, not to the capability**: the `architecture` seat wrote *"expressing delete-as-null-sha inside the existing CommitToRepo path is the right reuse… On that axis the plan is sound and I'd carry it"*, and vetoed `delete_file` as a **new reserved verb on a shared adapter's action vocabulary** — the shape `bugs_closed/124`'s `$ctx.` namespace was vetoed for. The sub-question carrying most of the weight is the allowlist: `gitAdapterActions` gates what ANY workflow may ask the git adapter to do, and its own comment previously said destructive verbs were not reachable through it. **The verb is live and reachable today; whether it stays in the shared vocabulary is `architecture_review/RFC_011`'s to decide, and RFC 011's option B (keep the verb, remove it from the generic allowlist) is the filer's stated preference.** Do NOT extend this vocabulary further, and do NOT treat DGH-006 as settled precedent for the next adapter verb, until RFC 011 is broken by a human.
- **CORRECTNESS DEBTS on live code, from the same round — these are NOT packaging disputes:** (1) HIGH — `retract_page_graph.go`'s link census does not go through `linkablePageStatusPredicate`, which a landmine says an offline census over `pages` must; (2) MEDIUM — inbound references also live in structured `content_data` fields (`link_url`, `cta_url`, `*_url`) and an `href=`-only scan misses them, which can let a retraction proceed past a real inbound link — the exact case the owner's 2026-08-03 directive exists to prevent; (3) MEDIUM — the inbound-source logic is COPIED from `check_orphan_pages.go` rather than shared with it, and a drift warning in a comment is not a mechanism. **No retraction has been performed on any live site**; the capability is proven only on a scratch path.
- **status-evidence:** git-adapter `delete_file` verb + `GitCommitData.Deletions` + chassis action `retract_page_deployment`, shipped for `bugs_open/098`. Nine tests in `internal/adapters/git/github_client_delete_test.go`, each **proved by mutation** — reverting `TreeEntry.SHA` to a plain string, dropping the existence filter, hoisting the deletion resolution above the retry loop, and removing the path guard each fail exactly the test that names them, and pass again on restore. GitHub's deletion semantics were **probed on the live repo, not assumed** (POST `/git/trees` against gqls/sites master, 2026-08-02): null sha on a path that exists → 201; on a path that does not → **422 `GitRPC::BadObjectState`**. A tree object is created unreferenced, so the probe moved no ref and fired no workflow.
- **what:** Until this, **the platform could publish a page but had no implemented way to unpublish one** — the git-adapter's only deletion verb was `delete_repo`, which returns *"not yet implemented"*. Both `bugs_open/098` (an archived page keeps serving its frozen artefact, and every repair path skips archived rows on purpose so nothing can ever reach it) and `bugs_closed/125` (an orphan published to a wrong path could not be removed; the one live instance was deleted by the owner by hand) were blocked on the same absence.
  **A deletion is expressed as a KIND OF COMMIT, not a second write path.** In the Git Data API a removal is a tree entry whose `sha` is `null`, so `GitCommitData.Deletions` rides through `CommitToRepo` unchanged and inherits, by construction rather than by remembering: the ref-race retry (DGH-002's fix), the `{domain}/{path}` prefixing (so a deletion can only name a path a publish could have written), atomicity with writes in the same request (**a move is one commit**, so a page is never absent from both paths), and the credential boundary. A bespoke Contents-API delete would have had none of the four.
  `retract_page_deployment` is the page-level caller: paths are derived only from `pages.url` through the shared `datahelpers.PageFilePathFromURL` (PBP/125's one definition), a page whose url names no file of its own is **declined rather than sanitised**, a path an `active` page on the same site also derives is **refused**, and every refusal is returned rather than swallowed. Retraction works end to end because the far side was already reconciling: `gqls/sites`' deploy-to-b2 workflow runs `b2 sync --delete` + a Cloudflare purge on every push to `master`.
- **sources:** `internal/adapters/git/{interface,github_client,adapter}.go`; `platform/orchestration/actions/retract_page_deployment_action.go`; `platform/orchestration/actions/git_adapter_request_action.go` (allowlist); `bugs_open/098`; `bugs_closed/125`; `docs024_key_docs_latest/bugfix_098_unpublish_primitive/`
- **relations:** DGH-001 (commit-is-deploy — this is its inverse); DGH-002 (the ref-race retry this reuses rather than duplicating); `PageFilePathFromURL` (the one deploy-path definition, from 125); `bugs_open/098`; `bugs_closed/125`
- **RETRACTION IS A GRAPH OPERATION, NOT A FILE DELETION** (owner directive 2026-08-03, added the same day): removing the artefact alone trades one broken state for another. 098's second surface is relojistas, where the file was correctly deleted and every page then advertised the 404 from its own footer because the nav row was still `active`. So `retract_page_deployment` carries three further obligations, handled deliberately differently because they are different kinds of thing (`retract_page_graph.go`): an **editorial** inbound reference (body copy or site chrome) **REFUSES** the retraction and names the referrers — repairing prose is a content decision, and refusing makes "a retraction created a dead link" unreachable rather than merely detected; a **nav row** is **DEACTIVATED** (to `inactive`, never `archived` — both are excluded by every reader's `= 'active'` filter, but a second spelling is invisible to anyone querying by convention) *before* the artefact goes, so the transient state is a nav entry vanishing slightly early rather than a nav entry pointing at a deleted file; a **stranded outbound target** (a page whose last referrer was the retracted page) is **REPORTED**, because what to do about an unreachable page is a site-shaping decision that `discovery_checks/check_orphan_pages.go` already owns. The three inbound sources are copied deliberately from that check (nav / chrome / other pages' components) — CHANGE ONE, READ THE OTHER — but with a quote-delimited `href="<url>"` match instead of its substring match, because `/index.html` is a substring of `/learning-center/index.html`; the failure direction of each is argued in the file header.
- **LANDMINE:** **do not pass `sites.github_branch` to a commit or a retraction.** `gqls/sites` has NO `main` — it carries `master` (its default) and `750start` — while the column says `'main'` for most rows, and the B2 workflow triggers only on `master`. Deploys work solely because the commit path leaves the branch unset and `CommitToRepo` falls back to the repo default. Passing the column's value targets a branch that does not exist.
- **LANDMINE:** **`TreeEntry.SHA` is a `*string` and must stay one.** GitHub needs `"sha": null` for a removal; a plain `string` sends `""` (rejected) and `omitempty` drops the key entirely (not a deletion, a malformed entry). Nothing else in the codebase would notice the "tidy-up" — the null-sha test is the only thing standing between that edit and a silently broken unpublish.

### DGH-008 — `platform/publish`: the publish seam (opt-in hosted mirror of a built site)

The `cfpages` backend is registered but **NOT ARMED** — it refuses loudly; see the landmine below, and the arming step now carries an explicit obligation (architecture seat): write up the Direct Upload protocol decisions before building the client, not after. "Built" here means unit-proven, not exercised: no site has opted in yet. **PROVEN IN PRODUCTION 2026-08-16 on v1.0.1304** (stamp `5de6cddbe`, `b4981634d` ancestry verified with two controls). Canary noted.co.uk → noted.ugg2.com: full chain ran (tick → stamp → spawn → publish_site in a spawned storage pod), 8/8 objects copied, and the served `index.html` sha256 equals the origin hash captured BEFORE any publish existed; `published_hash` written only after that acceptance. Second tick returned `{published:false, skipped:true, reason:"no drift"}` with a tree_hash matching the stored value — publish-on-drift and don't-publish-without-it are both demonstrated. The first attempt (2026-08-15, v1.0.1303) failed at the first upload — B2's S3 gateway 411s a non-seekable body — fixed in `b4981634d` (buffer to seekable; both fakes now enforce the contract, mutation-proven). ⚠ **Every tick spawns a pod even for a no-op** (the drift check needs bucket credentials, so it cannot run on the chassis): interval set to 3600s, not 600s, after measuring pods accumulating one per tick.
- **status-evidence:** `go test ./platform/publish/ ./platform/orchestration/actions/` green 2026-08-15 including the mutation-style guard proofs (a corrupted destination copy fails publish; acceptance failure provably does NOT write `published_hash`); `SELECT count(*) FILTER (WHERE publish_target IS NOT NULL) FROM sites` → 0.
- **what:** Mirrors the built artefact tree in `b2://portfolio-sites/<domain>/` to a hosted copy, per-site opt-in via `sites.publish_target` (NULL = OFF, the 2026-08-02 opt-in ruling; deliberately NOT overloading `sites.github_repo`). A `scheduled_tasks` reconciler (`site-publish-reconciler`, one site per tick, least-recently-checked, selection-stamped in `site_publish_checks` per the migration-346 rotation pattern) dispatches `publish-reconciler`, which spawn→calls a `site-publisher` pod, which runs the `publish_site` action: hash the tree (`publish.TreeHash`, `th1:` = sha256 over sorted key/ETag/size), no-op on NULL target / no drift / empty tree, publish on drift via the backend named by `publish_target`, accept on SERVED BYTES (origin `index.html` sha256 vs the hosted copy fetched with a cache-buster), and only then write `sites.published_hash/published_at`. A failed or unaccepted publish leaves the drift standing for the next tick. Backends: `b2worker` (copy under a second hostname prefix in the same bucket, served by the existing `*.ugg2.com` worker — zero new infra, zero new credentials, per-key ETag-verified at the destination listing) and `cfpages` (Cloudflare Pages Direct Upload — the ruled primary, not yet armed).
- **consumer enumeration (2026-08-15, the RFC_022 shape — measured, not asserted):** `site-publisher` had ZERO consumers before its repurpose: 0 live workflows name it, 0 scheduled_tasks target it, 0 site_work_items route to it, and 0 orchestrations have EVER run as it (all-history query on orchestration_states). The row was a pre-070-refactor fossil (`upload_to_s3` into a nonexistent bucket "websites"); migration 422 snapshots it before repurposing. The new columns had zero readers/writers before this commit.
- **open review question (registered per the ordering-exemption's condition 2):** whether served-bytes acceptance on `index.html` alone is sufficient, or whether the reconciler should hash-verify EVERY served page before recording `published_hash` (cost: N fetches per publish vs one; the b2worker backend already ETag-verifies every object at the origin, so the gap is CDN-layer only). And whether `accepted:false` results should file a work item rather than rely on the next tick's retry being observed.
- **LANDMINE — `publish_site` MUST run in a spawned storage-enabled pod.** The standing chassis carries NO B2 credentials by owner ruling 2026-08-08 (`bugs_open/245` removed them; "do not re-add"), so the action constructs its own client bound to `portfolio-sites` — `params.StorageClient` binds IMAGE_BUCKET and is nil on the chassis. `site-publisher` is on the spawner's storage allow-list (`spawn_actions.go`), which is WHY the fossil type was repurposed rather than a new type minted. Scheduling `publish_site` into a chassis-run workflow fails at client construction, by design, loudly.
- **LANDMINE — the tree hash trusts B2 S3-gateway ETags.** For single-part uploads (everything `b2 sync` writes at site scale) the ETag is content-MD5 and stable across no-op syncs. A future writer that multipart-uploads site files would change ETag semantics and read as permanent drift — the reconciler would republish every tick. If a site republishes every tick with no content change, read this entry first.
- **LANDMINE — cfpages is a deliberate, loud gap, not a stub to "finish".** No CF_PAGES_API_TOKEN exists (owner key); the Direct Upload protocol is partly undocumented; a client written blind ships plausible-but-unproven code behind an APPROVED verdict (the MDL-040 class). Arming it = owner mints the token into `personae-platform-secrets` + spawner injects it for site-publisher pods + the client is built verify-as-you-go against the live API. Until then `publish_target='cfpages'` errors and the reconciler retries it every tick — do not opt a site into cfpages before arming.

### DGH-009 — `commit_site_file.sh`: a hand-publish path to a site's deploy directory that cannot lose the message or pick the wrong repo
- **status:** built and exercised 2026-08-16 — one live publish (`leopardessconsulting.co.uk/sitemap.xml`, git-adapter corr `142c4a2b`, commit `a1e07becb`, served file byte-identical to the input within ~90s)
- **status-evidence:** `docs/leopardessconsulting/scripts/commit_site_file.sh`; `PUBLISH_OK` receipt printed; `git show --stat a1e07becb` → `1 file changed, 36 insertions(+), 108 deletions(-)` (non-empty, which is the check that matters — see the landmine); `curl` of the served path diffs clean against the local input.
- **what:** `./commit_site_file.sh <domain> <commit_message> <repo_path>=<local_file> [...]` — publishes arbitrary files into `{domain}/` in the site deploy repo through the git-adapter's `commit` action on `system.adapter.git.requests`. Same contract as `deploy_image_asset`'s own commit, usable for files no action owns (`sitemap.xml`, `llms.txt`, hand-derived brand assets). Three things it fixes relative to the hand-rolled publishes already in the estate, each a recorded landmine: (1) the payload travels in the container COMMAND and the script prints `PUBLISH_OK`, instead of `kubectl run -i … kcat -P < file`, whose asynchronous stdin attach drops ~4 of 5 publishes at exit 0 with no receipt either way (the same fix `rerender_page_safe.sh` applies to the orchestration topic); (2) `repo_name` is READ from `sites.github_repo` (defaulting to `sites` only when NULL/empty) instead of hardcoded `"sites"`, which is silently wrong for the domains that serve from `vm-sites`; (3) repo paths are refused if absolute or containing `..`, since `CommitToRepo` builds `{domain}/{path}` and a leading slash yields an empty tree segment. Branch is never set, so `CommitToRepo` falls back to the repo default — `gqls/sites` has no `main`, and the B2 workflow watches `master`.
- **LANDMINE — `success:true` from the git-adapter is not evidence anything changed.** An unchanged file commits as an EMPTY commit and the adapter reports success with the file listed in `deploy_result`. Verify at `git show --stat <sha>` (subject-only output = empty commit = nothing deployed) AND at the served artefact, never at the adapter's reply.
