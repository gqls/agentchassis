### DGH-001 — Commit-is-deploy: git → GitHub Actions (self-hosted runner) → Backblaze B2 (+ chassis image-tag deploys)
- **status:** deployed
- **status-evidence:** Consistently described as live and in current use across six independent sourcings spanning legacy (docs017/002, docs004) through current (docs/RUNNING_NOTES_vonc) documentation; 102_blog_handoff: "Self-hosted GitHub Actions runner — deployed and running … Runner v2.333.1, pod in ai-persona-system namespace."
- **what:** The platform's standing deploy mechanism, converged on and restated by every era of documentation: individual commits per work item (or per page) are pushed via the git-adapter (a Kafka microservice on `system.adapter.git.requests`, `GitCommitAction` workflow-side) to a shared `sites` repo; a self-hosted GitHub Actions runner (pod in `ai-persona-system`) fires per commit, detects changed root-level domain directories, and runs `b2 sync --delete --skip-newer` to `b2://portfolio-sites/<domain>`, then purges the Cloudflare cache per zone (Cloudflare is DNS/cache-only for this path, not a proxy). There is no separate deploy step — "commit is deploy." ~~Commit SHAs are recorded on pages and work items for traceability~~ **CORRECTED 2026-08-19 (`bugs_open/315`) — NO commit sha is recorded anywhere, and no code writes one.** `[MEASURED 2026-08-19]` `information_schema.columns` holds no commit/sha column on `pages` OR on `site_work_items`; the one column that does exist, `page_components.deploy_commit`, is populated on **0 of 1,775 rows**, and `grep -rn "deploy_commit" --include=*.go .` over the whole repo **including tests** returns **zero lines**. `CommitToRepo` (`internal/adapters/git/github_client.go`) computes `newCommitSHA` and returns `repo.HTMLURL` instead, so the sha never leaves the adapter and the git-adapter's success payload carries no commit identity. Cost of the stale line: it tells a reader (and a council seat, which reads these entries as ground truth) that deploy traceability EXISTS, which is the exact premise `bugs_open/315` turns on. `pages.content_hash` is inert the same way — 0 of 786 rows, no writer. The authoritative workflow lives in `gqls/sites/.github/workflows` (a stray copy under `.git/workflows` is a documented trap that GitHub never reads). Separately, chassis platform code ships as one global `IMAGE_TAG` running every dynamic agent via `agent_definitions` config — `make quick-agent-update IMAGE_TAG=…` (build → push → kustomize → DB image_tag → restart agent-chassis) plus `make update-and-restart-orchestrator` for the generic-orchestrator statefulset; a full `make release` bumps every service; rollback is symmetric and cheap (repoint to the old existing image, no rebuild). Workflow/`default_config` changes are DB-only and take effect immediately, while a chassis code revert only reaches the cluster on the next build/push — these are two different deploy surfaces with different latencies. The identical "commit is deploy" seam was later reused for a VM deploy target (destination swapped, mechanism preserved) — see register/vm-backend-sites.md (VMB-004, VMB-005).
- **stamping order — WHEN `pages.deployed_at` becomes writable (`bugs_open/315`, migration 491 applied 2026-08-19):** `pages.deployed_at` is written only by `update_page_status` (`v3_site_actions.go:679`). `page-build-handler` and `tool-recreation-handler` USED to stamp it *before* their deploy was dispatched — their `save_sections` ran straight into an `update_status`, with the `deploy_page` (a `call_agent`) reached only afterwards. Migration **491** deletes that step from both; the stamp now happens inside the `page-rerender` they call, **after** its `git_commit`, keyed `page_id_field=rendered_page.page_id` rather than resolving the page by name. `[MEASURED 2026-08-19, post-491]` every remaining `deployed` stamper — `page-rerender`, `report-builder`, `section-editor` — is preceded by `deploy_page(git_commit)`.
  **⚠ It still records only that a commit was REQUESTED, not that bytes were published.** Those three do not read the commit's result (`deploy_result` appears nowhere in `v3_site_actions.go`), and the adapter's reply carries no commit identity to read — `CommitToRepo` computes `newCommitSHA` and returns `repo.HTMLURL`, a per-repo constant. Closing that is `architecture_review/RFC_038`, not this entry.
  **⚠ Deriving stamping order:** join each step to whatever step names it in `next_step`. `jsonb_each` key order is arbitrary and **reverses this particular sequence** — `page-build-handler` prints `deploy_page` above `update_status` and ran them the other way round.

### DGH-013 — `files_sha256` / `commit_sha`: the git-adapter reports what it DID, and `pages.content_hash` records it

- **status-evidence:** `go build ./...` clean, `go vet` clean on both packages, git-adapter and orchestration suites green (9 packages); both new guards mutation-proved (removing the base64 decode fails exactly the base64 assertion; swapping the subtree search for a literal path fails exactly the nested-shape test)
- **what:** `CommitToRepo` used to return `repo.HTMLURL` — a per-repo CONSTANT — while discarding the `newCommitSHA` it had just computed, so nothing downstream could name what had been written. It now returns `CommitOutcome{RepoURL, CommitSHA, Branch, AbsentPaths}`, and the adapter's reply gains **`commit_sha`** and **`files_sha256`** (committed path → sha256 of the exact bytes, hashed in the ADAPTER so the keys are the caller's own unprefixed paths, and hashing the DECODED bytes for base64 files). Chassis side, `update_page_status` takes one optional key **`deploy_result_field`** naming the deploy step's output field: it refuses the `deployed` stamp when that step reported a skip, and on success writes `pages.content_hash` in the same UPDATE as the stamp. **The column is touched ONLY when the guard ran, and then ASSIGNED, NULL included** — an earlier version used `COALESCE` on the reasoning that a stamp without a fingerprint should preserve the previous one, which is backwards: a stamp means NEW bytes went out, so any prior fingerprint is stale by definition and preserving it makes the divergence check convict a healthy page. NULL means "we do not know what we sent", which is what that check's `content_hash IS NOT NULL` predicate is for. This is the feature `RemovedConfigKeys["commit_from"]` said to implement rather than re-add.
- **⚠ the key CANNOT be a literal, and this is measured:** the 19 live `git_commit` steps carry **NINE distinct `output_field` names** (`deploy_result` on only three; `section-editor` uses `git_result`; two set none), so a hard-coded name is blind on 16 of 19 — and, since the guard must fail open, would wave them through in silence.
- **⚠ nor can it be a path index:** `deploy_result` has TWO live shapes — inline, and one level deeper (`<field>.response.<field>.response.data.…`) when the deploy is done by a called sub-agent, which is **57 of 744 orchestrations over 7 days**. ~~Resolution goes through `datahelpers.ExtractFields` scoped to the named subtree, which is collect-all/unique-or-nothing (RFC_029 §9), so an agent carrying several `git_commit` steps resolves to nothing rather than to a guess.~~ **CORRECTED 2026-08-19 (council round 2, gating objection from `prior_art_librarian`) — that guarantee DOES NOT EXIST in this build and the entry must not repeat it.** `findFieldRecursive`'s comment states unique-or-nothing as the RULING and then, four lines on, states the BEHAVIOUR: *"PHASE 1 (this build — instrument first, refuse second): conflicts still resolve, to the STABLE shallowest-first winner"*. Phase 2 flips conflicts to refusal and has not shipped. For this caller a guess is the worst outcome available — a fingerprint from the WRONG `git_commit` is silently and permanently wrong and would convict a healthy page for ever — so `deploy_evidence.go` now collects candidates ITSELF (`collectUniqueValue`) and REFUSES on conflict, mutation-proved both ways. **Delete `collectUniqueValue` in favour of the shared search when RFC_029 Phase 2 ships; until then, quoting the ruling does not inherit it.**
- **⚠ ORDERING RUNS BACKWARDS HERE.** `UpdatePageStatusInputSpec` is `StrictConfig: true`, so an undeclared config key FAILS VALIDATION rather than no-opping: **the image must roll BEFORE the config**, the opposite of the usual seed-after-image rule. 494 is `_HOLD`-suffixed so `SIDECAR_RE` keeps it out of `--apply` while still listing it.

Expected and bounded during a partial roll; a flood of them after both images are current is a real signal.
