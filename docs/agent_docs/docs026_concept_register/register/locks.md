### LOCK-001 — Pattern A (locked_at/locked_by) is the canonical lock mechanism; Pattern B (pinned) is dead
*(merged from 3 raw blocks: "Lock patterns A/B, Pattern B is dead" (U01); "Pattern A lock convention" (U19); "Locks — HITL durability across the platform" (U17a) — three restatements of the same foundational fact at different times)*
- **status:** deployed
- **status-evidence:** 041 Phase 2A: "a row is locked if locked_at IS NOT NULL"; independently confirmed 2026-05-19 verification ("Pattern B is unenforced in the current code — treat it as dead") and again in the canonical doc 031_locks(2) ("This doc is the canonical reference for lock semantics")
- **what:** Pattern A — a locked_at timestamp + locked_by identity column pair, with a partial index — is the dominant per-row lock mechanism, applied uniformly across sites, page_components, site_components, assets, and site_plan_directives. Hard locks ('admin', 'admin-removed', 'checkpoint', 'manual' upload) only humans clear; soft locks ('deploy', auditor names, 'audit-pending') agents may clear when a work item references the row. locked_by is a free-text convention, not a CHECK constraint, to allow new identifiers without a migration. Legacy Pattern B — a bare `pinned` boolean on site_specs — was never wired (no reads/writes; every spec write is supersede-then-insert with no guard) and new tables must use Pattern A instead. General lock-transfer rule during rebuilds: only the rewriting agent (e.g. write_site_plan) copies locks onto matching new rows by composite key; locked text beats an LLM rewrite; unmatched locks drop with a log. Locks and snapshots are orthogonal (prevention vs restore) — whether revert respects locks is an open question.
- **sources:** 031_locks(3).md; docs/agent_docs/sql_for_tables/041_assets.sql#Phase2A; docs/agent_docs/sql_for_tables/012_site_components.sql#phase-7a; WM/031_locks(2).md#the-two-patterns-in-use, #lock-transfer-across-rebuilds
- **relations:** Lock semantics hard/soft gate (LOCK-002); Site-level lock (LOCK-003); Timed-expiry/lock-model coherence project (LOCK-004); Adoption faithfulness via timed locks (LOCK-005, the adoption-specific instance of lock transfer)
- **verify-later:** \d site_specs pinned; write_site_plan lock-transfer code; check_component_lock.go IsHard classifier

### LOCK-002 — Lock semantics: hard gate for discovery, soft gate for execution, read-only rerender
*(merged from 2 raw blocks: the general platform doctrine (U01) and its confirmation via the assets-table rollout (U10))*
- **status:** deployed
- **status-evidence:** 013 Phase 1 shipped with four amended discovery checks; independently confirmed via the assets 2A rollout ("2A — assets.locked_at + locked_by delivered 2026-05-09")
- **what:** A lock means "human controls this", not read-only: an edit refreshes locked_at without unlocking; unlocking is a separate deliberate act. Discovery checks skip locked rows entirely (hard gate); execution agents process explicitly-targeted items regardless of lock state (soft gate); rerender reads everything unconditionally. locked_by vocabulary distinguishes human-only-unlock identities (admin/admin-removed/checkpoint) from agent-clearable ones (deploy/manual/auditor names) — no time-based expiry exists in production for this classification. Human uploads/locked assets are excluded from auditor queries and regeneration as a direct consequence.
- **sources:** 013#Three Levels of Lock, #How Agents Behave; 031(3)#rules; STATUS_imagery_2026-05-08.md#Phase-2A; PLAN_imagery_loop_closure.md#2A
- **relations:** Pattern A/B canonical mechanism (LOCK-001); Site-level lock (LOCK-003); growth budget; suppression
- **verify-later:** lock_helpers.go; four discovery checks' filters; check_component_lock.go; the store-asset lock guard `WHERE assets.locked_at IS NULL`

### LOCK-003 — Site-level lock (sites.locked_at)
- **status:** deployed
- **status-evidence:** "Phase 7: Site-level lock — prevents all automated agent activity" (012 tail); scheduled-task pre_query patched to exclude locked sites (020 site-lock section)
- **what:** locked_at/locked_by on the sites table acts as a master switch: when set, no automated agent activity (discovery, dispatch, improvement) touches the site at all. Scheduler pre_queries filter locked sites out of candidate selection, and LoadWorkItemsAction gates on it as well — the strictest of the platform's three lock levels (component, site component, whole site).

### LOCK-005 — Adoption faithfulness via 90-day timed locks: design, non-functional re-plan gap, and the undeployed fix
*(merged from 5 raw blocks: the design-agreed announcement, the policy-table entry, the page_components-locking-subsystem investigation that independently found the same gap, the superseded origination design, and the written-but-undeployed fix patch)*
- **status:** partial
- **status-evidence:** "Verified landed state (2026-06-05) … 053 schema — applied … 054 partially live (first-plan branch only) … write_site_plan Changes 1-3 — not deployed. Consequence: the 90-day re-plan window is non-functional. The only working faithful↔normal boundary today is the first-plan branch." Independently re-confirmed 10 days later from a different investigation (2026-06-15): "the 90-day RE-PLAN window is non-functional" with lock columns present but observed all-NULL on the pages actually checked.
- **what:** Adopted sites are meant to stay faithful to their source for 90 days before developing normally, enforced as a timed lock rather than a permanent flag (deliberately timed even though user-initiated, so nobody "fixes" it to permanent). Because site_plan_directives are plan-scoped and adoption itself writes no plan, the lock was redesigned to originate at the FIRST write_site_plan after adoption (detected by no-current-plan + pages-exist) rather than at adoption time itself (the original adoption-writes-locked-directives design was superseded once this schema constraint was found). As landed: only this first-plan convergence branch actually works. transferDirectiveLocks copies only locked_at/locked_by (no lock_type/lock_expires_at), so re-plans within the 90-day window rely solely on the LLM's "preserve existing pages" prompt, not on any lock. A three-part fix was fully specified (emit page-scoped preserve directives; lock them adoption/timed/90d on first re-plan; extend transferDirectiveLocks to carry type+expiry and release expired locks) but was never deployed — de-prioritised after the first-plan branch proved sufficient for the faithful first pass. Coexists without contention with separate 30-day deploy locks at component scope.

### LOCK-007 — Shared asset-lock guard: one predicate for every writer that replaces a site asset
*(added 2026-07-31, postdating the extraction freeze — the mechanism built to close `bugs_open/143`)*
- **status:** built, NOT yet deployed (Go; inert until the next chassis image is rolled — grep the pod for `lockedAssetKeys` before believing otherwise)
- **status-evidence:** `platform/orchestration/actions/asset_lock_guard.go` + `asset_lock_guard_test.go`, first consumers `derive_card_asset` and `derive_brand_head_assets`; full `platform/orchestration/actions` suite green 2026-07-31; the query PREPAREd and EXECUTEd against the live schema on site `4851f6fc-71cf-4160-a270-e03d6d3e0732`, returning exactly its 2 real locks (favicon, og_card) and correctly omitting an unlocked card key. Council gate submission `b5ff41f1-84bc-477b-a881-83e3d2e8a805`.
- **what:** `lockedAssetKeys(ctx, db, siteID, keys...) → assetLockSet` is the one place that answers "may automation overwrite this asset?" for any writer that replaces an asset — its DB row, its object in storage, or the file the row points at in a site repo. The write predicate is `assetAgentWritableSQL(alias)` and the read predicate is DERIVED from it (`assetLockedSQL = NOT(writable)`), never re-typed, because the defect being closed was a duplicated classifier where one copy sat at the wrong point in the sequence. The returned set carries `locked_by`/`lock_type`/`locked_at` and a `Describe(key)` renderer, so a refusal can name what an operator has to clear — live `locked_by` values are free-text sentences, so they are reported verbatim and never classified. **Two properties are deliberate and both fail CLOSED:** no `status` filter (`assets.status` is unconstrained text, so conditioning a safety guard on it fails OPEN the day a locked row carries an unenumerated status — this was argued and approved at council on the brand-head fix, corr `bfd73f71` round 1 HIGH), and **not expiry-aware** — bare `locked_at`, unlike the expiry-aware component predicate `pageComponentAgentWritableSQL`. Callers must treat an error as LOCKED. A source-level lockstep test pins the set of files on the `sendGitCommitRequest` path, so a NEW asset producer fails the build until it is deliberately classified in or out of the guarded population.
- **landmine:** **guarding the provenance upsert is NOT guarding the artefact.** `WHERE assets.locked_at IS NULL` on an upsert protects the DB row only; if the git commit runs first, the approved row survives and its file does not — and because the upsert's `sql.Result` is easy to discard, the suppressed write looks exactly like success (`derived: true`). The check must precede the commit, and a 0-`RowsAffected` upsert must be reported, not swallowed. Second trap: **`deploy_image_asset` deliberately has no lock check and must not be given one** — it commits bytes the named row already points at, so deploying a locked asset is publication of the approved artefact; guarding its `UPDATE assets SET url … WHERE id = $1` would leave a locked row pointing at an expiring presigned URL.
- **open review question:** should the asset predicate adopt LOCK-004's expiry-aware form? Doing so would WEAKEN three existing guards (`StoreAssetAction`, `ingest_staged_asset`, the brand-head check all test bare `locked_at`), i.e. change what the mechanism guarantees, so it is refused here as a side effect of a bug fix and left to LOCK-004's named Go predicate sweep. Measured 2026-07-31: 5 locked `assets` rows fleet-wide, `lock_expires_at` NULL on all 5 — the two readings are indistinguishable today, which is why the choice must be made on the guarantee and not on the data. **When LOCK-004 lands, `asset_lock_guard.go` is the one line it edits.**
- **sources:** `platform/orchestration/actions/asset_lock_guard.go`; `bugs_open/143_HANDOFF_2026-07-29_derive_card_asset_commits_before_lock_check.md`; `docs/agent_docs/docs024_key_docs_latest/bugfix_143_asset_lock_before_commit/`; commits `e9e345464` + `a22010eaa` (the brand-head precedent this generalises)
- **relations:** Timed lock-expiry / lock-model coherence project (LOCK-004 — this file is one of the ~11 `locked_at IS NULL` callsites that sweep must visit, now reduced to one); Pattern A/B canonical mechanism (LOCK-001); Lock semantics hard/soft gate (LOCK-002, whose "the store-asset lock guard" verify-later item this centralises)
- **verify-later:** pod-grep `lockedAssetKeys` after the next roll; whether `StoreAssetAction` and `ingest_staged_asset` should also delegate to the shared helper (they guard correctly today, but by hand — a fourth and fifth copy of the predicate)

### LOCK-006 — auto_lock_on_deploy trigger: assumed-live consequential mechanism, later revealed as a stillborn strict-mode artifact
*(merged from 2 raw blocks describing the SAME trigger at two different dates, with the later evidence directly overturning the earlier assumption — an explicit status-reconciliation case)*
- **status:** abandoned
- **status-evidence:** Earlier evidence (2026-07-01, vonc project): schema captures "trigger_auto_lock_on_deploy auto-locks on deploy … lock_type permanent|timed|review" and treats it as operationally significant (rebuilds/re-renders must check lock state), though all rows were observed NULL-locked in that corpus so the behaviour "never actually bit". Later, more specific evidence (2026-07-09, leopardess/social project) directly overturns this: "the strict-mode subsystem it belonged to was stillborn — no Go code reads schema_mode … snapshot columns never created … fired exactly once in the system's history"; the trigger was deliberately dropped via migration 009 on 2026-07-10 with its function body backed up. Per merge instructions, the later, more specific, dated finding governs the final status.
- **what:** page_components carries locked_at/lock_type/locked_by with a BEFORE UPDATE trigger intended to auto-lock components on deploy as part of a schema_mode='strict' governance subsystem. In practice it was never functional as designed: save_page_sections INSERTs rows already in the deployed state, so the trigger's UPDATE condition essentially never fires; its companion snapshot columns (schema_snapshot/content_snapshot) were never created; and nothing downstream ever read the lock or schema_mode. It nearly caused a collision with an unrelated section-editor fix (every edit would have locked its own row) before being identified and removed. schema_mode/strict_mode_trigger columns and orphaned lock/unlock functions were deliberately retained (not dropped) even though the trigger itself was removed.
