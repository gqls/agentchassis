### SEO-002 — Site discovery files generator (`scripts/site-discovery-files.py`)
- **status:** built and exercised — run against 3 sites 2026-07-28; relojistas.com's three files are LIVE. **Second live site 2026-08-16: leopardessconsulting.co.uk's `sitemap.xml` (27 → 36 urls, 36/36 probed 200). One defect found and fixed in the same pass — it did not filter `pages.noindex` (see below).**
- **status-evidence:** `scripts/site-discovery-files.py`; relojistas.com serves `/sitemap.xml` (18 urls), `/llms.txt` (18 pages), `/robots.txt` (own file, Cloudflare block confirmed off per-agent). Dry-run verified against oufe.com and robot-hands.com.
- **what:** Generates `robots.txt` (Content-Signal + Sitemap pointer), `sitemap.xml` (with lastmod) and `llms.txt` for ANY site, from the `pages` table. Dry-run by default; never commits or deploys. Encodes three rules learned expensively: (1) **probe every URL and list only 200s** — a sitemap advertising a 404 is worse than none, and on its first fleet run it declined to list a URL that was 404 at that moment — correctly, though that page was deployed 1.5h later, so a dropped URL means "not fetchable now", not "broken", and the tool should be run when the target site is not mid-build; (2) **llms.txt is built FROM the pages, not written ABOUT them** — each entry is the page's own `<h1>` and own first sentence, so nothing invents a claim about a site; (3) **it detects whether Cloudflare's managed robots.txt is being merged in**, and names the agents currently disallowed — because Cloudflare PREPENDS its file to the origin's rather than yielding, so shipping your own changes nothing until the dashboard setting is off.
- **CORRECTED 2026-08-16 — `live_pages()` did NOT filter `pages.noindex`, so this tool would advertise, in a site's own sitemap, a page the platform is actively telling crawlers to skip.** The column arrived after the tool (SEO-003, live chassis v1.0.1277, injects `<meta name="robots" content="noindex, nofollow">` on those pages), which is how the two came to contradict each other. **Latent, never live, when found:** exactly two rows carry `noindex` fleet-wide and the only `active` one — `vonc.com/tools/gauntlet/round.html`, meta tag confirmed served — is on a site with no `sitemap.xml` at all (404). Fixed with `AND noindex IS NOT TRUE`, proven in both directions: vonc.com counts **22 without the filter, 21 with**, and the regenerated file has 21 `<loc>` and 0 matches for `gauntlet/round.html`. **The general shape, for whoever adds the next page-level control: a generator that reads `pages` is a CONSUMER of every column that decides whether a page should be served or found, and it will not fail when a new one appears — it will silently keep answering the old question.**
- **LANDMINE — a "no such generator exists" claim in a handoff outlives its truth by days.** This tool's own arrival is the worked case: `docs/leopardessconsulting/HANDOFF_2026-08-14_services_restore.md` said *"No platform generator exists"* for sitemaps and pointed at a hand-rolled 2026-07-17 recipe. True when written, false from 2026-07-28, and the 2026-08-16 session that acted on it found this tool only by accident, in a comment in `discovery_checks/check_site_structural_validity.go`. **Grep the register before rebuilding anything** — one search for `sitemap` returns this entry. Logged in `WRONG_CALLS.md`.

### SEO-003 — Per-page search-exclusion opt-in (`pages.noindex` → `injectRobotsNoindex`)
- **status:** **LIVE and BEHAVIOURALLY PROVEN 2026-08-10** on chassis **v1.0.1277** (was: built 2026-08-09, inert pending roll)
- **status-evidence:** migration `docs/agent_docs/sql_for_agents/352_pages_noindex_flag.sql` applied 2026-08-09 (`UPDATE 1`, guard `DO`/`RAISE` induced-then-passed); census at apply time `is_true 1 / is_false 629 / is_null 0 / total 630`. Code: `platform/orchestration/actions/rerender_single_page_action.go` (`injectRobotsNoindex`, call site at assemblePage step 5a3), `platform/orchestration/actions/helpers.go` (`PageInfo.Noindex`). Tests `inject_robots_noindex_test.go`, 5 cases, both mutation-proven (neutered injection → 5 fail; loose `name="robots"` marker → the coexistence case fails).
- **what:** An opt-in boolean column on `pages`, default `false`, that makes the single-page rerender assembly path inject `<meta name="robots" content="noindex, nofollow">` before `</head>`. The gate (`if page.Noindex`) lives at the **call site** in `assemblePage`, not inside the helper, per the owner ruling of 2026-08-02 §2 (new authority on a shared seam ships as an opt-in field with the unsafe default OFF, so a reviewer of the caller can see the decision). Idempotent on its **own exact tag**, deliberately not on any `name="robots"` match: a foreign permissive `index, follow` meta must not silently disable it, and crawlers take the most restrictive of multiple robots directives, so coexistence still noindexes. Paired with `X-Robots-Tag: noindex, nofollow` on tools-api's `PublicRoundHandler`, which covers the JSON endpoint — a different URL that the meta tag cannot reach.
- **producer set / who sets the flag:** hand-set by migration only; there is no automated writer, and no agent or check emits it. One row true fleet-wide today: `vonc.com` `/tools/gauntlet/round.html` (`4629451e-e4f2-4fe2-b258-35107b5cb51e`), the Gauntlet round-record page, which serves published visitor UGC plus an AI verdict that may name real people.
- > **CORRECTED 2026-08-09 (same day, by the author, after the council's `editquality` seat asked for the right evidence): the landmine below is TRUE IN GENERAL and OVERSTATED FOR THIS PAGE.** `AssemblePageAction` carries `bugs_open/208`'s ownership guard (`multipage_actions.go:42-86`) and **refuses a `rebuild_policy='owned'` page before assembly**, so that path cannot silently strip the tag from one — it declines to touch it. The silent-drop case is **`generic` pages**. This entry's motivating page is **`owned`**, and all three work items ever filed against it are `page_rerender`/`page-rerender`, so the shipped fix sits on its real build path and is **not inert**. Residual that keeps the landmine live: the guard **fails open** when `rebuild_policy` cannot be read (`checked=false` → generic assembly proceeds, logging `OWNED_PAGE_GUARD_UNCHECKED` at high severity), so the exposure is countable rather than absent — `SELECT count(*) FROM agent_error_log WHERE error_code='OWNED_PAGE_GUARD_UNCHECKED';`
- **LANDMINE — the other head producer does NOT read this.** There are **two** page-`<head>` producers and only one honours the flag: `assemblePage` (`rerender_single_page_action.go`, the `page-rerender` path) does; `AssemblePageAction` (`multipage_actions.go`, live behind the `assemble_page` action, used by **3 active agent types** — `site-work-orchestrator`, `pageflow-builder`, `page-rebuild`) does not. So a rebuild through that path regenerates the page **without** the tag while `pages.noindex` still reads `true` — the wrong result looking exactly like the right one. This is the same divergence that left `injectPageJSONLD` (2026-07-28) and `injectCanonicalLink` (2026-08-02) on one path only; `noindex` is the third instance and the first where the consequence is a live privacy exposure rather than a missing SEO nicety.
- **open review question:** whether the two head producers should converge (one head-assembly seam both paths call) rather than each new head fix landing on one of them. That is architecture-scope by the 2026-07-29 ruling and is deliberately NOT decided here.
- **sources:** `bugs_open/232`; migration 352 + ROLLBACK; owner rulings 2026-08-02 §2 (opt-in field) and 2026-07-29 §1 (additive-and-inert is not guarantee-changing, so this went to the normal council gate, not an RFC)
- **relations:** SEO-001 (aspirational agent owning robots directives — this is the first robots directive the platform actually emits); SEO-002 (`robots.txt`/`sitemap.xml` generator, a site-level sibling to this page-level control); `bugs_open/232`; `architecture_review/RFC_020` (the wider third-party-harm question this was split out of, deliberately independent of it)
- **verify-later:** after the next chassis roll — pod-grep `injectRobotsNoindex`, then rerender the page and `curl` for the tag; and whether the two-head-producer divergence earns its own bug file

### SEO-004 — `save_page_meta_description` (the first writer that can REPAIR a page's meta description)
- **status:** built, **not yet exercised in production** — the Go half rides the next fleet roll; the config half (migration `485`) is live from 2026-08-19. Saying "deployed" would overstate it.
- **status-evidence:** action registered in `GlobalActionRegistry` as `save_page_meta_description` (`registry.go`, category `site`); five tests in `save_page_meta_description_test.go`, each proven load-bearing by a named mutation actually run (flip the `overwrite_existing` default → 2 fail; delete the `MetaDescriptionLooksInternal` branch → 1 fails; delete the guarded WHERE clause → 3 fail; restored → green). Migration `485` applied 2026-08-19 with `UPDATE 1` and a DO/RAISE verify, ledger-recorded `--record-only`.
- **what:** `pages.meta_description` had **seven** writers and every one was a create-or-upsert path, so the column was set at page birth or never — measured 2026-08-19, **407 of 731 active pages (55.7%) across 26 of 27 sites** had none (`bugs_open/320`). This action is the missing **persist** half: given a page id (or `site_id`+`page_name`) and a text field in collected data, it writes the column. It deliberately does **not** find the pages (that is `query_database`) and does **not** write the sentence (that is `execute_llm_prompt`), so a workflow composes the three and authorship stays with the framework per the owner's 2026-08-06 ruling. It reuses `datahelpers.MetaDescriptionLooksInternal` — the `bugs_closed/103` guard, exported for exactly this — rather than re-deriving the brief-vs-public rule.
- **the opt-in field, and its default:** `overwrite_existing` defaults to **false** (owner ruling 2026-08-02 §2 — new authority on a shared seam ships opt-in with the unsafe side OFF). By default it fills a blank and refuses a page that already has copy; the policy lives in the UPDATE's own `WHERE` clause (`$3::bool OR COALESCE(meta_description,'')=''`), not in a read-then-write, so it cannot race a concurrent writer.
- **⚠ LANDMINE — the failure this exists to end is a SUCCESSFUL no-op.** `content_rewrite` items filed against missing meta descriptions ran, **completed, and wrote nothing** (two measured: `ec701bb3-85e7-40e7-bff1-2ce1ae104861`, `13522562-2392-4db9-96b5-204ab67cb999`; both targets still 0 chars, one page touched by the handler after the item closed). The cause is ownership — `llm_fields`/`llm_field_specs` are per-SECTION, and this is a `pages` column, so no writer prompt can reach it. **So this action's result map always distinguishes a write from a refusal, with a named reason** (`empty_candidate`, `candidate_looks_internal`, `candidate_too_long`, `already_has_description`). A caller that reads only "did it error" reintroduces the original defect. A missing DB connection is an **error**, not a soft `{"updated": false}`, for the same reason.
- **the sibling half (M2), same bug:** `upsertPage`'s conflict clause was `meta_description = EXCLUDED.meta_description`, unguarded, three lines below a `nav_label` clause that WAS `COALESCE(NULLIF(...))`-guarded. Since `metaDescription` defaults to `""` when the page map omits the key, **every replan wrote a blank over whatever was there** — proven to have fired on four `robot-hands.com` pages that held 97/120/169/329 chars in an April `site_snapshots` entry and read 0 today. Now `COALESCE(NULLIF(EXCLUDED.meta_description,''), pages.meta_description)`: a non-blank incoming value still wins, only the destructive direction is closed. ⚠ **CORRECTED 2026-08-19 (council round 2):** this entry first said the guard "matches" `nav_label`. It is the MIRROR IMAGE — `nav_label` is `COALESCE(NULLIF(pages.…,''), EXCLUDED.…)` so the EXISTING value wins, while this lets the INCOMING value win unless blank. Both are deliberate and deliberately different (a description is plan-owned content that must stay revisable; a nav label should not be churned by every replan), so **do not unify them**. They share the NULLIF idiom, not the polarity.
