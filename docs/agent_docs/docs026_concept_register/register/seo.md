### SEO-003 — Per-page search-exclusion opt-in (`pages.noindex` → `injectRobotsNoindex`)
- **status:** **LIVE and BEHAVIOURALLY PROVEN 2026-08-10** on chassis **v1.0.1277** (was: built 2026-08-09, inert pending roll)
- **status-evidence:** migration `docs/agent_docs/sql_for_agents/352_pages_noindex_flag.sql` applied 2026-08-09 (`UPDATE 1`, guard `DO`/`RAISE` induced-then-passed); census at apply time `is_true 1 / is_false 629 / is_null 0 / total 630`. Code: `platform/orchestration/actions/rerender_single_page_action.go` (`injectRobotsNoindex`, call site at assemblePage step 5a3), `platform/orchestration/actions/helpers.go` (`PageInfo.Noindex`). Tests `inject_robots_noindex_test.go`, 5 cases, both mutation-proven (neutered injection → 5 fail; loose `name="robots"` marker → the coexistence case fails).
- **what:** An opt-in boolean column on `pages`, default `false`, that makes the single-page rerender assembly path inject `<meta name="robots" content="noindex, nofollow">` before `</head>`. The gate (`if page.Noindex`) lives at the **call site** in `assemblePage`, not inside the helper, per the owner ruling of 2026-08-02 §2 (new authority on a shared seam ships as an opt-in field with the unsafe default OFF, so a reviewer of the caller can see the decision). Idempotent on its **own exact tag**, deliberately not on any `name="robots"` match: a foreign permissive `index, follow` meta must not silently disable it, and crawlers take the most restrictive of multiple robots directives, so coexistence still noindexes. Paired with `X-Robots-Tag: noindex, nofollow` on tools-api's `PublicRoundHandler`, which covers the JSON endpoint — a different URL that the meta tag cannot reach.
- **producer set / who sets the flag:** hand-set by migration only; there is no automated writer, and no agent or check emits it. One row true fleet-wide today: `vonc.com` `/tools/gauntlet/round.html` (`4629451e-e4f2-4fe2-b258-35107b5cb51e`), the Gauntlet round-record page, which serves published visitor UGC plus an AI verdict that may name real people.
- > **CORRECTED 2026-08-09 (same day, by the author, after the council's `editquality` seat asked for the right evidence): the landmine below is TRUE IN GENERAL and OVERSTATED FOR THIS PAGE.** `AssemblePageAction` carries `bugs_open/208`'s ownership guard (`multipage_actions.go:42-86`) and **refuses a `rebuild_policy='owned'` page before assembly**, so that path cannot silently strip the tag from one — it declines to touch it. The silent-drop case is **`generic` pages**. This entry's motivating page is **`owned`**, and all three work items ever filed against it are `page_rerender`/`page-rerender`, so the shipped fix sits on its real build path and is **not inert**. Residual that keeps the landmine live: the guard **fails open** when `rebuild_policy` cannot be read (`checked=false` → generic assembly proceeds, logging `OWNED_PAGE_GUARD_UNCHECKED` at high severity), so the exposure is countable rather than absent — `SELECT count(*) FROM agent_error_log WHERE error_code='OWNED_PAGE_GUARD_UNCHECKED';`
- **LANDMINE — the other head producer does NOT read this.** There are **two** page-`<head>` producers and only one honours the flag: `assemblePage` (`rerender_single_page_action.go`, the `page-rerender` path) does; `AssemblePageAction` (`multipage_actions.go`, live behind the `assemble_page` action, used by **3 active agent types** — `site-work-orchestrator`, `pageflow-builder`, `page-rebuild`) does not. So a rebuild through that path regenerates the page **without** the tag while `pages.noindex` still reads `true` — the wrong result looking exactly like the right one. This is the same divergence that left `injectPageJSONLD` (2026-07-28) and `injectCanonicalLink` (2026-08-02) on one path only; `noindex` is the third instance and the first where the consequence is a live privacy exposure rather than a missing SEO nicety.
- **open review question:** whether the two head producers should converge (one head-assembly seam both paths call) rather than each new head fix landing on one of them. That is architecture-scope by the 2026-07-29 ruling and is deliberately NOT decided here.

### SEO-004 — `save_page_meta_description` (the first writer that can REPAIR a page's meta description)

- **what:** `pages.meta_description` had **seven** writers and every one was a create-or-upsert path, so the column was set at page birth or never — measured 2026-08-19, **407 of 731 active pages (55.7%) across 26 of 27 sites** had none (`bugs_open/320`). This action is the missing **persist** half: given a page id (or `site_id`+`page_name`) and a text field in collected data, it writes the column. It deliberately does **not** find the pages (that is `query_database`) and does **not** write the sentence (that is `execute_llm_prompt`), so a workflow composes the three and authorship stays with the framework per the owner's 2026-08-06 ruling. They share the NULLIF idiom, not the polarity.

### SEO-005 — Per-page Open Graph identity at assembly, and the document language carried by the head component (`head_assembly.go`)
- **status:** built and mutation-proven, **not yet live** — the Go rides the next fleet roll; the two migrations are authored and deliberately HELD until the binary is proven running (see the ordering trap below). Saying "deployed" would overstate it.
- **status-evidence:** `platform/orchestration/actions/head_assembly.go` (`spliceOpenGraph`, `headLangAttr`, `htmlDocumentOpen`), called from `assemblePage` (`rerender_single_page_action.go`) at two points; `head_assembly_test.go`, 10 behavioural claims, **every one proven load-bearing by a mutation actually run** (ledger in `docs024_key_docs_latest/bugfix_252_og_lang_assembly/NOTES_og_lang_assembly.md`, 2026-08-20 (c)). Full package suite green against a clean `git archive HEAD` extraction. Bug: `bugs_open/252` (og/lang slug).
- **what:** `site_components.rendered_html` holds **one `<head>` row per site**, and `assemblePage` reuses it for every page. So any page-scoped value a site-level render bakes into that row is a claim about every page at once. `spliceOpenGraph` **removes** `og:title`/`og:description`/`og:url` from the stored head and **injects** one per-page set — remove-then-inject, so it is idempotent by construction, repairs a head that already carries a wrong or duplicated value, and needs no chrome rebuild. `og:url` goes through `preferredPageURL`, the same helper `injectCanonicalLink` and `injectPageJSONLD` use, so **og:url == the canonical href == the JSON-LD `@id`** by construction rather than by three call sites agreeing. Correct-or-absent throughout (the LNK-005 idiom): no meta description means no `og:description`. Separately, `headLangAttr` + `htmlDocumentOpen` move the document language out of Go: the head component declares `lang`, sourced from `site_specs` `site_config.locale.lang` through the existing schema-driven config resolution (a second consumer of the STY-050 mechanism), and Go defaults to `en` when a site declares none — so a non-opted site's output is byte-identical to the hardcoded line this replaced.
- **the measured defect it ends:** 2026-08-19, **22 of 24** stored heads carried `og:url` pointing at the site HOMEPAGE — baked by `injectBrandHeadTags`, which has no page to ask — so all **700 assembled pages across 26 sites** declared the homepage's identity beside a canonical that correctly named the page. Verified at the artefact on `ai-agent-orchestration.com/about.html`, which also served **two `og:title` tags**, one blank and one site-level. **A missing og tag is silence and a scraper falls back sensibly; a wrong one is followed** — which is why this strips rather than fills.
- **⚠ LANDMINE — the fix candidate in the bug file would have fixed almost nothing, and the reason generalises.** `bugs_open/252` proposed the established idiom: put blank placeholders in the head, fill them at assembly (as `spliceMetaDescription` does). Placeholders existed on only **4** of 24 heads, and on those 4 they were already **shadowed by a filled duplicate** appended later in the same head by `injectBrandHeadTags`, whose idempotency guard tests `rel="icon"` OR `og:image` and therefore cannot see a blank `og:title`. The mutation that reproduces that candidate fails **five** of this entry's tests. **The general shape: an "opt-in placeholder" design assumes nothing else writes the same tag. Census the artefact for OTHER producers of your tag before choosing fill-a-blank over replace.**
- **⚠ LANDMINE — removing tags from a head changes the meaning of "first" for a neighbouring function.** `spliceMetaDescription`'s legacy fallback fills the **first** `content=""` anywhere in the head when the exact blank description tag is absent. Running `spliceOpenGraph` FIRST clears the blanks it owns, promotes `og:image` to first, and the page description lands in **og:image** — outside this function's strip set (deliberately: `og:image` is `bugs_open/322`'s, under its own landmine), so nothing cleans it. Hence the call order in `assemblePage` is description-splice **then** og-splice, which looks backwards and is pinned by `TestSpliceOpenGraphRunsAfterTheDescriptionSpliceForAReason`. **All 24 real heads take the targeted path today, so the order is currently unobservable on live data** — a fixture copied from a live head cannot show it, which is how the order was first chosen wrongly (`WRONG_CALLS.md`, 2026-08-20).
- **⚠ ORDERING TRAP for the rollout:** DB config is live the moment it applies; Go is inert until the roll. If the migrations land before the image, the OLD binary consumes the chrome-staleness edge — chrome re-renders under the old `injectBrandHeadTags`, pages re-assemble without the splice, `render_inputs` restamps, and **the detect→rebuild pipe goes quiet with the fleet still wrong**, needing a manual re-fire. Both migrations are named `_HOLD`.
- **this file is the NAMED SEAM for SEO-003's open convergence question.** `assemblePage` and `AssemblePageAction` remain two independent head producers and this fix lands on the first only — the **fourth** instance of that divergence (after `injectPageJSONLD`, `injectCanonicalLink`, `injectRobotsNoindex`). The question is still architecture-scope by the owner ruling of 2026-07-29 and is **not** decided here; what changed is that the next per-page head fix has a shared home instead of a fifth private helper inside the assembler. **Consequence for anyone verifying og:url per page: record which producer built the page**, or a correct fix reads as broken on a page rebuilt through `assemble_page`.
- **⚠ ESCALATION THRESHOLD, set by the council's `architecture` seat 2026-08-20 (corr `3b6712d4`) and binding on the next author: THIS IS THE FOURTH FIX TO LAND ON ONE HEAD PRODUCER ONLY. IF A FIFTH INSTANCE ARRIVES, IT DOES NOT GET A FIFTH BESPOKE PATCH — RAISE SEO-003 AS AN RFC FIRST.** The seat's reasoning, recorded because it is the part that decays: the cost of not converging is concrete and recurring — each new page-identity fix has to reason about which producer sees it, gets a one-sided patch, and the guard set drifts further from the code with every round (`verify_site.py`'s `OG_PER_PAGE` exemption and `check_site_structural_validity.go`'s og:url exclusion are already two rounds behind). Four dated patches have now accreted on a split flagged architecture-scope on 2026-07-29 with still no owner decision. Proceeding here was judged right; treating a fifth as routine is not.
- **council round 1 (corr `3b6712d4`): APPROVED, 5 advisory objections, none high-severity, 12 seats (6 abstained).** Four seats asked for checks rather than changes; all were run and are recorded in `507_head_components_carry_lang_HOLD.sql`'s header and the lane NOTES. The two load-bearing answers: (1) **`assemblePage` really is the only page-artefact consumer of `site_components.rendered_html`** — enumerated rather than asserted, which is what `guardian` and `prior_art_librarian` objected to; the one candidate a loose grep surfaced (`save_sections_component_floor.go:169`) reads `page_components`, not `site_components`. (2) **`head-seo-standard` declares no `og_title`/`og_description`/`og_image` fields at all**, so those template branches have never been resolvable and there is no dangling `required:true` after their removal.
