### TL-001 — Tool widget clobber hazard (interactive content silently destroyed by content rebuild)
- **status:** deployed
- **status-evidence:** CONFIRMED 2026-06-22 (gamesdesign game-pathfinding, 18KB A* canvas overwritten 06-14) and again via code-level investigation naming it "M1"; "Fixes drafted, not implemented" as of the most recent evidence.
- **stage2-verified (2026-07-14):** partial → deployed — save_page_sections_action.go:394-411 has a live 'INTERACTIVITY REGRESSION BLOCKED' guard (committed 7cd1bb92d 'stop clobbering tools - shout loudly'); source_item_id is populated via work_item_id_field config (lines 421-450) and written into page_component_history with source='save_page_sections_overwrite'. All thre...
- **what:** A tool/game lives as a section's rendered_html, not a planned section, so any full rebuild (needs_page, link_resolution_rebuild, or the ordinary needs_content_page path) regenerates page_components from plan_sections and replaces the widget with a generic-text-block; the prose-based content-regression guard compares only visible text length after stripping tags, so it is structurally blind to script-heavy widgets. Mechanistically: `save_page_sections_action.go` does `DELETE FROM page_components WHERE page_id=$1` then re-inserts only the sections the content writer supplied — any side-written row not in that list (including a tool/game widget inserted by create_tool_component/deploy_tool at position 2) is destroyed on the next build. Old content is snapshotted to page_component_history (source='save_page_sections_overwrite') before delete, so wipes are recoverable/detectable. Fix layers drafted: an interactivity-aware save guard + carry-forward of interactive sections in save_page_sections, source_item_id stamping into page_component_history, and routing link maintenance through a preserve-sections path (page_rerender was ruled out for CTA re-resolution since it doesn't re-run link logic).

### TL-003 — Two divergent tool-creation paths (novel vs fork)
- **status:** deployed
- **status-evidence:** Documented as both existing, currently-running code paths.
- **what:** `create_tool_component_action.go` (the "novel" path) never sets pages.sections, leaving it default `[]`; `deploy_tool_action.go` (the "fork" path) sets pages.sections to `["hero-tool","tool-guide-intro","<toolFunction>","tool-cta"]`. The novel path remains more exposed to the clobber mechanism (TL-001) since the widget is a member of no section list anywhere.

### TL-013 — Tier-2 static acceptance checker + the anchor rule (discovery check `tool_acceptance`)
- **status:** deployed
- **status-evidence:** "Stage 5 — LIVE 2026-07-10 (first sweep proven)" — run cd0d9731 on v1.0.1107 produced exactly the pre-verified findings (2 improve_tool items + 2 acceptance-fail notes, check-level precision confirmed); anchor rule "SETTLED" 2026-07-09 after the #tableWrap inspection.
- **what:** A browserless discovery check (sibling of tool_health): loads the current travelling PLAN's criteria fence, fetches the deployed page (bounded 12s/2MB, cached per run), and evaluates the statically-visible subset under the ANCHOR RULE — validate only a criteria selector's ANCHOR (leftmost id/class token) against html_template (`#tableWrap` exists ⇒ `#tableWrap tr` passes since rows are JS-built and Tier 4 asserts them for real; `#xpTableBody` exists nowhere ⇒ fails ⇒ drop). Failures → one improve_tool item (criteria embedded as acceptance_test, 7-day cooldown, cancelled items excluded per migration 146) + an acceptance-fail note. Scope limit by construction: only generator-created tools have content_components rows; adopted/recreated page-section tools are invisible to Tier 2 (reached instead via Tier 4, which operates on pages). Implementation detail: CSS class tokens are whitespace-delimited (Go regexp `\b` wrongly splits on hyphens).

- **status:** deployed

- **what:** Two new check types in the shared Tier 2 static criteria evaluator, closing the largest measured gap in the experience register (13 of its 38 deferred clauses, across 9 of 9 entries — the `no-inert-control` invariant, which the register exists to enforce and could not check). `attribute_absent` — none of the listed attributes may be present on any matched element. `attribute_matches` — one attribute's value against `matches` and/or `not_matches` regexps; a MISSING attribute fails both forms. - **what:** A static detector for a defect class nothing on this platform could previously see: a deployed page whose own JavaScript addresses element ids the page does not contain and never creates, so the script throws on load and the visitor gets a tool with no controls. `datahelpers.OrphanElementRefs(pageHTML) []string` harvests ids referenced via `getElementById('x')` and `querySelector('#x')`, subtracts every id appearing anywhere in the page text (including inside script string literals, so markup a tool builds with `innerHTML` counts as present) and every id assigned at runtime (`el.id = 'x'`, `setAttribute('id','x')`), and returns the remainder. Two consumers: discovery check `orphan_element_refs` judges whole deployed pages (every component plus the site chrome, so a script reaching a nav element is not flagged) and files a `needs_human_review` item naming the missing ids; and `DeployToolToSiteAction` **refuses outright** to fork-and-deploy a library tool whose template fails the same test.
- **why it is decidable statically, unlike its neighbour:** `check_dead_controls` deliberately declines to judge "a `<button>` with no handler" from source, because JS binds at runtime and absence of evidence is not evidence. This is the opposite case — the id is a string literal, the document text either contains it or does not, and no runtime behaviour can conjure one the page never writes. The claim is about the artefact, not a prediction about it.
- **the hard refusal is measured, not brave:** all 32 library and fork tool templates were run through the check before it shipped and NONE flagged, so the pre-deploy gate cannot fire on anything that exists today. It is a guard against a future bad template, not a change to current behaviour.
- **LANDMINE, found 2026-07-29 by the owner and not by this check: it reads the page's own `rendered_html`, so a tool whose logic lives in an EXTERNAL script is invisible to it.** `micro-cms` addresses fourteen ids from `js/storage.js`, `editor.js`, `ui.js` and `app.js`; every one was missing and this check reported the page clean. **13 of webdesign.co.uk's 63 tools load relative `<script src>` files.** This is not a bug to patch here — it is structural: the check runs against the DATABASE, and those files live in S3, so a DB-side static check cannot read them without becoming a network check. **The external-script class belongs to the BROWSER tier**, which is precisely why widening the ladder's eligibility (TL-033) was the more important half of the same change. `webdesign_tools_repair/toolaudit.py` covers it in the meantime by fetching each page's scripts THROUGH the page and resolving their references against the loaded DOM.
- **landmine — it is deliberately one class, not all of them:** two tools that throw the identical `null`-reference error are NOT flagged (blueprint-compiler, micro-cms) because they address elements by class or compound selector. Widening the selector parse would trade the measured precision for coverage. Do not "improve" it into a general null-reference detector; that coverage belongs in the browser tier.
- **landmine — a page that INTERPOLATES its ids cannot be judged from source alone.** When the page contains an `id="${...}"` template its id set is computed, so the check loosens for that page only: a referenced name that also appears as a quoted string anywhere OTHER than a lookup argument is treated as present. Blanking the lookup arguments first is the load-bearing half — without it every referenced id trivially appears inside its own `getElementById` call and the check silently passes everything. The rule LOOSENS rather than disables, because four of the nine real findings are on tools that build markup dynamically AND are genuinely broken.
- **completion verification:** `VerifyOrphanElementRefsResolved` is registered for the item type, and re-checks THE IDS THE ITEM NAMED rather than the whole-page predicate — a verifier stricter than the fixer's remit strands correctly-handled items in `failed` (the `page_rerender` cautionary tale in `verifier_coverage_test.go`). A new orphan introduced elsewhere is logged and reported in the detail but never counted against the item. Registering the verifier obliged a matching entry in the claim-timeout sweep's exclusion list (migration 269) — that lockstep is pinned by `TestRegisteredVerifiersMatchClaimTimeoutExclusion` and is what caught the omission.

### TL-034 — `has_visible_area` — the Tier-4 check that separates "exists" from "usable"
- **status:** **built, live and CORRECT as of `v1.0.1216`** (2026-07-31 18:08 UTC). Text-driven boxes usually land on a fraction and passed, which is why it looked fine. - **landmine — its own test suite could never have caught that, and yours may have the same hole.** `browserPage.VisibleArea` is already typed `(float64, float64, bool, error)`, so the fault lay *below* the interface, in the decode of the library's result. `fakePage` returns `float64` by construction, so **`TestHasVisibleArea` stayed green for the whole life of the bug**, all five table cases including the exact 1146x0 shape. - **status-evidence:** Written 2026-07-30 against three MEASURED failures. `logic-architect`, `mind-map` and `pasteboard` all served work areas measuring **1146x0** — present in the DOM, zero height — with `.main-content` collapsed to 60px (its toolbar alone). `selector_exists` passed all three at both tiers; so did a browser probe that drove their internal functions. - **why it cannot be a Tier-2 check:** it measures a rendered box. A static read of HTML cannot compute layout, so a Tier-2 equivalent is not unbuilt — it is impossible. This is the clearest case yet for why the ladder needs a browser tier at all (cf. TL-012).
- **the root cause it points at, which is a defect CLASS:** all three tools were ported from STANDALONE PAGES whose `body` was the flex container (`body { display:flex; height:100vh; overflow:hidden }`). Inlined into a section, that rule (a) restyled the HOST page — the site's own body became a flex container with `overflow:hidden`, page scrolling included — and (b) still gave `.main-content` no flex parent, because the sidebar and main content sit inside the ported section rather than directly under `body`. This check runs post-settle in a real browser, so a selector matching nothing means the element genuinely is not there. Do not "harmonise" the two rules; they differ because what they can see differs.
- **landmine — it cannot tell `display:none` from a collapsed flex child.** Both measure 0x0 and both are reported the same way. That is deliberate: from the visitor's side there is no difference. If you need to distinguish them, that is a different check.
- **the transferable rule this produced:** **verify through the visitor's gesture, never through the tool's internal functions.** Yesterday's verification of pasteboard called `addItem(src)` directly and passed; the visitor's actual entry point is a paste event, and the work area it would paste into had no height. ### TL-037 — Tool numeric-equivalence gate (`toolgolden.py`): capture what a tool COMPUTES, so a rewrite can be proved equivalent
- **status:** **built, exercised, and proven able to fail** 2026-07-31. Golden captured for all 12 interactive pages on loancalculator.co.uk; round-tripped deterministically; caught a deliberately injected arithmetic error.
- **status-evidence:** Written because the owner asked for a site's calculators to be **rewritten** so the platform can build on them, and nothing in the platform verifies that a tool computes the right numbers. Measured, not assumed: `check_tool_acceptance.go` (TL-013) validates that **selectors exist** and its own header states static checks *"CONFIRM, never refute"*; `toolaudit.py` reports `RESPONDS`; and `grep` over `platform/orchestration/actions/` finds **no numeric or golden-value tool test of any kind**.
- **the measured gap this closes, PROVEN BY CONSTRUCTION:** a page containing **one `<input type=number>`, no script, no listener and nothing that could possibly compute** scores **`RESPONDS`**. `toolaudit.py`'s reactivity test is `changed = snap() !== before`, and `snap()` includes `'##' + all.map(e => e.value ?? '')` — the value of every control, **including the one the driver has just assigned**. So for any typed control (number, range, text, textarea, select) `changed` is true *by construction*, whatever the page does. Being fair to it, `RESPONDS` still certifies no console errors, no failed subresources, every id-reference resolving and a non-empty region — real signal, just not arithmetic. This is TL-012's argument one rung further out: **"responds" ≠ "computes".**
- **what:** A differential equivalence harness. Drives each tool in a real browser and records a full behavioural fingerprint — every id-bearing element's text **and** `computedStyle.display`, plus every control's value — for each of three input vectors, then `--compare` re-runs the identical vectors and diffs, marking each divergence `NUMBER` or `text/display`. Exit 1 on divergence.
- **the design decision worth reusing — vectors are derived from each field's OWN default** (`×1`, `×2`, `×0.5`, clamped to that field's declared `min`/`max`/`step`). A positionally-fixed vector would put a rate of 12345 into field 2 and drive the arithmetic into `NaN`, **where every implementation agrees and no real difference can surface**. Scaling a field's own default keeps every value inside its intended domain for any tool, with zero per-tool configuration. Second decision: the fingerprint is **every id-bearing element**, never "the output field" — guessing which element holds the answer is what made `toolaudit` blind twice (its faults 11/12), and these scripts address their regions by id because that is how they are written.
- **two gates, because one of them was originally framed wrong:** **A** — does the tool react to being driven at all (compares a `before` snapshot taken after setup, **excluding control values**, so setting a field cannot satisfy it). **B** — does the output depend on the input *values* (numeric tools only). The first version had only B, which is a no-op **by construction** for a tool with no numeric field to scale, and would have condemned three working tools (a button wizard, a checkbox tool, a text tracker) for ever — the same unpassable-gate shape as a wrong denominator. `scaled_numeric()` exempts them explicitly.
- **it REFUSES to write a golden file** when any tool is inert, input-independent, or failed to capture. Such a file certifies nothing and would mark a broken rewrite as byte-perfect; a partial one is worse, because the missing pages read as "nothing to check".
- **proven able to fail, which a round-trip alone cannot show:** changing one divisor on `standard-calc` (`(APR/100)/12` → `/11`) — a page that still loads, still responds, and still displays plausible money — is caught in **every** vector as `NUMBER` divergences: £202.29→£205.74, £332.54→£350.60, £175.31→£176.10. A £3.45/month error, £207 over the loan. **`toolaudit.py` scores that broken build `RESPONDS` and Tier 2 passes it.**
- **landmine — a capture taken mid-parse records the WRONG answers and reports success.** A bare `document.readyState == 'complete'` poll returned a DOM in which `.container` existed (so all inputs were present and drivable) while the inline `<script>` had not parsed — so `calculateLoan` was undefined and **every vector recorded £0.00 while the run succeeded**. A golden file from that state says every answer is £0.00 and would certify a completely broken rewrite. Guards: `settle()` requires the script count **and** the serialised DOM length to stop moving across consecutive reads, and `dom_shape` (`"2:13804"`) is stored in the golden file so a bad capture is **visible in every later diff** rather than inferred. If `dom_shape` differs between runs, distrust the comparison before reading the values.
- **second landmine — a modal dialog BLOCKS the renderer and CDP just times out with no stated cause.** `application-tracker`'s remove button calls `confirm()`, which killed a whole 12-page run as `timeout waiting for Runtime.evaluate`. `confirm/alert/prompt` are stubbed after settle; that is a real behaviour change (a tool gated on `confirm()` proceeds as if accepted) and it applies identically to every implementation, which is what a differential test needs.

### TL-038 — `computed_values`: a criteria check type that asserts what a calculator COMPUTES, and the emitter that authors it from a working tool
- **status:** **built, tested, and proven able to fail** 2026-07-31; INERT until the next chassis roll (Go change) and until a criteria fence names it. Nine fences emitted and decode-verified; none installed in `doc_plans` yet.
- **status-evidence:** This is the answer to TL-037's own closing question — *"whether this belongs in the criteria vocabulary as a check type rather than a standalone script"*. It does, and the reason is not tidiness: a harness only its author runs is worth exactly one rewrite. The owner's instruction was to make the numeric check *part of the tools workflow*, which means the platform running it unprompted.
- **what:** A Tier-4 check type. `steps` (the existing fill/click/select vocabulary, reused verbatim) drives the tool; `expect_values` — a new per-type field, selector → exact text — asserts what every named output then reads. Whitespace is the only latitude; currency symbol, digit grouping and trailing zeros are all compared verbatim, because "£303.44" becoming "303.44" or "£303.4400000000001" is a real defect on a money page. Enforcement is the existing `tool-acceptance-agent` schedule; no new dispatcher, no new storage, no new table.
- **the gap, restated as a ladder** — every rung below judges what a page CONTAINS; this is the only one that judges what it COMPUTES:
  `tool_health` has a script · `selector_exists` has a slot · `has_visible_area` you can see it · `interaction` it printed money · `computed_values` it printed **£303.44**.
- **why Tier 4 ONLY, and this is a JUDGEMENT not a gap.** A Tier-2 form confirming the anchors of `steps` and `expect_values` would be four lines, exactly as `interaction` has. It is deliberately absent. This check exists *because* a calculator can pass every other rung while computing nothing (TL-037: a page with one input, one output and no script scores `RESPONDS`). Giving it a static form that passes on anchor presence would mint that same failure one rung higher, under a name that reads like arithmetic was checked. **A green `computed_values` must mean the numbers were compared.**
- **scope reasoning, per the owner ruling of 2026-07-29 §1:** additive and inert — reachable by nothing until a fence names it — and it changes no guarantee of the shared mechanism. Tier 4 already refutes; a real browser post-settle already fails a page for what it serves. So this is normal council-gate scope, not an RFC. Contrast TL-035's note: the *cheaper*-looking option there (make screenshots unconditional) was the one that needed the heavier process. Consumers of the criteria vocabulary are named in the submission, not merely measured.
- **the emitter is the half that makes it usable.** `toolgolden.py --emit-criteria <dir>` converts a capture into fences. Hand-authoring exact values for 12 calculators × 3 vectors × N outputs is not maintainable, and hand-authoring is where TL-016's selector-invention class comes from. Two rules govern emission, both there to stop the fence asserting MORE than the capture proved:
  1. **REFUSE rather than approximate.** A control or pressed button with no `id` cannot be named in a selector. Emitting steps that skip it would drive the tool differently from the way the golden was taken, so the expected values would be wrong — and wrong expectations that fail look exactly like a broken tool.
