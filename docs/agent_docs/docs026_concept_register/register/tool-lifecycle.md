### TL-001 — Tool widget clobber hazard (interactive content silently destroyed by content rebuild)
- **status:** deployed
- **status-evidence:** CONFIRMED 2026-06-22 (gamesdesign game-pathfinding, 18KB A* canvas overwritten 06-14) and again via code-level investigation naming it "M1"; "Fixes drafted, not implemented" as of the most recent evidence.
- **stage2-verified (2026-07-14):** partial → deployed — save_page_sections_action.go:394-411 has a live 'INTERACTIVITY REGRESSION BLOCKED' guard (committed 7cd1bb92d 'stop clobbering tools - shout loudly'); source_item_id is populated via work_item_id_field config (lines 421-450) and written into page_component_history with source='save_page_sections_overwrite'. All thre...
- **what:** A tool/game lives as a section's rendered_html, not a planned section, so any full rebuild (needs_page, link_resolution_rebuild, or the ordinary needs_content_page path) regenerates page_components from plan_sections and replaces the widget with a generic-text-block; the prose-based content-regression guard compares only visible text length after stripping tags, so it is structurally blind to script-heavy widgets. Mechanistically: `save_page_sections_action.go` does `DELETE FROM page_components WHERE page_id=$1` then re-inserts only the sections the content writer supplied — any side-written row not in that list (including a tool/game widget inserted by create_tool_component/deploy_tool at position 2) is destroyed on the next build. Old content is snapshotted to page_component_history (source='save_page_sections_overwrite') before delete, so wipes are recoverable/detectable. Fix layers drafted: an interactivity-aware save guard + carry-forward of interactive sections in save_page_sections, source_item_id stamping into page_component_history, and routing link maintenance through a preserve-sections path (page_rerender was ruled out for CTA re-resolution since it doesn't re-run link logic).

### TL-013 — Tier-2 static acceptance checker + the anchor rule (discovery check `tool_acceptance`)
- **status:** deployed
- **status-evidence:** "Stage 5 — LIVE 2026-07-10 (first sweep proven)" — run cd0d9731 on v1.0.1107 produced exactly the pre-verified findings (2 improve_tool items + 2 acceptance-fail notes, check-level precision confirmed); anchor rule "SETTLED" 2026-07-09 after the #tableWrap inspection.
- **what:** A browserless discovery check (sibling of tool_health): loads the current travelling PLAN's criteria fence, fetches the deployed page (bounded 12s/2MB, cached per run), and evaluates the statically-visible subset under the ANCHOR RULE — validate only a criteria selector's ANCHOR (leftmost id/class token) against html_template (`#tableWrap` exists ⇒ `#tableWrap tr` passes since rows are JS-built and Tier 4 asserts them for real; `#xpTableBody` exists nowhere ⇒ fails ⇒ drop). Static validation can confirm a selector but never refute one — the DOM is constructed at runtime, so a check must never delete a rule merely because the DOM doesn't statically contain it. Plus shell checks (tool-doc header not leaked, no `<no value>` residue). No criteria → a needs_criteria note (30-day cooldown), never a fake pass. Failures → one improve_tool item (criteria embedded as acceptance_test, 7-day cooldown, cancelled items excluded per migration 146) + an acceptance-fail note. Scope limit by construction: only generator-created tools have content_components rows; adopted/recreated page-section tools are invisible to Tier 2 (reached instead via Tier 4, which operates on pages). Implementation detail: CSS class tokens are whitespace-delimited (Go regexp `\b` wrongly splits on hyphens).

### TL-016 — Composer selector invention & the delivered-reality principle (Option B)
- **status:** deployed
- **status-evidence:** CONFIRMED 2026-07-09 (#xpTableBody/#statsStrip token_anywhere=f); second sighting caught by Tier 2 itself 2026-07-10 (kebab #drop-chance vs real camelCase #dropChance); "DECIDED 2026-07-10: Option B — inline reality (user: 'I choose option B and surrender')"; migrations 143 (PLANs superseded) + 144 (composer fixed) applied and verified.
- **what:** Two recurring failure classes in machine-written acceptance criteria, and their durable remedies. (1) The PLAN-composer LLM invented DOM ids for assertion targets despite an explicit "never invent a selector" instruction — the rule held for controls it acts on and failed for things it asserts on; first instance corrected by a guarded supersede migration (which itself initially refused a valid runtime selector, leading to the anchor rule, TL-013); second caught automatically by the live Tier-2 sweep and corrected by migration 143. Remedy is Tier-2 static validation, not sterner prompts. ### TL-032 — Orphan element-reference detection (`OrphanElementRefs` + discovery check `orphan_element_refs`)
- **status:** built, not yet exercised — the code is live from the image carrying it, but the discovery check is opt-in per agent (`checks` array) and had raised no work item at the time of writing.
- **status-evidence:** MEASURED 2026-07-29 against the live DB: 98 deployed script-carrying pages fleet-wide → **9 flagged**, all 9 on webdesign.co.uk, each adjudicated by loading the live page at the URL the DATABASE gives and asking whether the flagged id resolves after load — every one fails to resolve; 32 library/fork tool templates → 0 flagged (unchanged, because the correction below only ever REMOVES candidates). Unit tests pin the live defect shapes, eight false-positive guards, and the regression case below.
- **> CORRECTED 2026-07-29, same day, before any verdict landed:** this entry first claimed **10** flagged with all 10 confirmed. Wrong on both counts. The "confirmation" had been run against a URL I CONSTRUCTED (`/tools/x.html`) instead of the one the database gives (`/tools/x/index.html`), so one page was confirmed against a 404. Re-adjudicated properly, the score was 9 true positives and **one false positive — css-filter-playground**, whose six sliders are built by `g.innerHTML = ` + "`" + `<input id="${f.name}">` + "`" + ` from an array of descriptors: present in the browser, absent from the source. Caught by the browser, not by re-reading the work. Two transferable lessons, both mine: **a verdict from a URL you built is a verdict about a page you invented**, and **a static id set is only knowable when the page does not compute it**.
- **what:** A static detector for a defect class nothing on this platform could previously see: a deployed page whose own JavaScript addresses element ids the page does not contain and never creates, so the script throws on load and the visitor gets a tool with no controls. `datahelpers.OrphanElementRefs(pageHTML) []string` harvests ids referenced via `getElementById('x')` and `querySelector('#x')`, subtracts every id appearing anywhere in the page text (including inside script string literals, so markup a tool builds with `innerHTML` counts as present) and every id assigned at runtime (`el.id = 'x'`, `setAttribute('id','x')`), and returns the remainder. Two consumers: discovery check `orphan_element_refs` judges whole deployed pages (every component plus the site chrome, so a script reaching a nav element is not flagged) and files a `needs_human_review` item naming the missing ids; and `DeployToolToSiteAction` **refuses outright** to fork-and-deploy a library tool whose template fails the same test.
- **why it is decidable statically, unlike its neighbour:** `check_dead_controls` deliberately declines to judge "a `<button>` with no handler" from source, because JS binds at runtime and absence of evidence is not evidence. This is the opposite case — the id is a string literal, the document text either contains it or does not, and no runtime behaviour can conjure one the page never writes. The claim is about the artefact, not a prediction about it.
- **the hard refusal is measured, not brave:** all 32 library and fork tool templates were run through the check before it shipped and NONE flagged, so the pre-deploy gate cannot fire on anything that exists today. It is a guard against a future bad template, not a change to current behaviour.
- **LANDMINE, found 2026-07-29 by the owner and not by this check: it reads the page's own `rendered_html`, so a tool whose logic lives in an EXTERNAL script is invisible to it.** `micro-cms` addresses fourteen ids from `js/storage.js`, `editor.js`, `ui.js` and `app.js`; every one was missing and this check reported the page clean. **13 of webdesign.co.uk's 63 tools load relative `<script src>` files.** This is not a bug to patch here — it is structural: the check runs against the DATABASE, and those files live in S3, so a DB-side static check cannot read them without becoming a network check. **The external-script class belongs to the BROWSER tier**, which is precisely why widening the ladder's eligibility (TL-033) was the more important half of the same change. `webdesign_tools_repair/toolaudit.py` covers it in the meantime by fetching each page's scripts THROUGH the page and resolving their references against the loaded DOM.
- **landmine — it is deliberately one class, not all of them:** two tools that throw the identical `null`-reference error are NOT flagged (blueprint-compiler, micro-cms) because they address elements by class or compound selector. Widening the selector parse would trade the measured precision for coverage. Do not "improve" it into a general null-reference detector; that coverage belongs in the browser tier.
- **landmine — a page that INTERPOLATES its ids cannot be judged from source alone.** When the page contains an `id="${...}"` template its id set is computed, so the check loosens for that page only: a referenced name that also appears as a quoted string anywhere OTHER than a lookup argument is treated as present. Blanking the lookup arguments first is the load-bearing half — without it every referenced id trivially appears inside its own `getElementById` call and the check silently passes everything. The rule LOOSENS rather than disables, because four of the nine real findings are on tools that build markup dynamically AND are genuinely broken.
- **completion verification:** `VerifyOrphanElementRefsResolved` is registered for the item type, and re-checks THE IDS THE ITEM NAMED rather than the whole-page predicate — a verifier stricter than the fixer's remit strands correctly-handled items in `failed` (the `page_rerender` cautionary tale in `verifier_coverage_test.go`). A new orphan introduced elsewhere is logged and reported in the detail but never counted against the item. Registering the verifier obliged a matching entry in the claim-timeout sweep's exclusion list (migration 269) — that lockstep is pinned by `TestRegisteredVerifiersMatchClaimTimeoutExclusion` and is what caught the omission.

### TL-033 — Ported tools were invisible to the whole acceptance ladder (eligibility + subject-key widening)
- **status:** deployed
- **status-evidence:** MEASURED 2026-07-29 against the live DB: the widened predicate makes 71 components newly eligible (webdesign.co.uk 63, gamesdesign.co.uk 6, vonc.com 2) across 71 DISTINCT subject keys, 0 colliding with an existing tool `function`, and exactly 1 already carrying a PLAN. Both consumers are criteria-gated, so the widening produces ONE acceptance run today.
- **what:** Every tier of the tool acceptance ladder opened its eligibility query with `cc.component_level = 'tool'`. webdesign.co.uk's 63 tools were PORTED as HTML blobs and live in ONE shared `content_components` row at `component_level='section'` (`function='ported-page'`, reused by 97 `page_components` across 97 pages), so the ladder has never returned one of them. That is the structural reason 63 tools — twenty visibly broken, ten with scripts addressing absent elements — shipped with no alarm from machinery built to catch exactly that. `tool_eligibility.go` now holds one shared predicate used by Tier 2 (`check_tool_acceptance`) and Tier 4 (`check_tool_acceptance_due`).
- **the half that is easy to miss:** widening the level test ALONE would not have worked. The ladder keys its subject on `cc.function`, which for all 63 is the literal `"ported-page"` — they would have collided onto one PLAN. **A ported tool's identity is its PAGE, not its component**, so the subject key is derived as the page name minus a leading `tool-`.
- **the sole-component clause is what keeps it honest:** a generated tool page carries four components (hero-tool, tool-guide-intro, the widget, tool-cta) and the widget is already eligible on its own level; admitting its siblings would key three content sections as if each were a tool. A ported page is one blob, so there is nothing to disambiguate. Four fleet pages are multi-section with no tool component (idea.uk 3, leopardessconsulting 1) — genuinely ambiguous, and still deliberately excluded rather than guessed at.
- **deliberately NOT applied to `tool_health`:** that check raises an `improve_tool` work item for ANY issue including cosmetic warnings, so widening it would drop ~71 items into the build queue in one pass, mostly about styling on pages whose real defect is missing markup. Revisit once the ported tools have PLANs and the noise can be judged per tool.
- **consequence for anyone repairing a ported tool:** a repair that does not also write a PLAN leaves the tool invisible again the moment you look away. Writing the PLAN is not documentation etiquette, it is the act that makes the tool testable.

### TL-034 — `has_visible_area` — the Tier-4 check that separates "exists" from "usable"
- **status:** built, not yet exercised — live from the image carrying it; no criteria fence names it yet.
- **status-evidence:** Written 2026-07-30 against three MEASURED failures. `logic-architect`, `mind-map` and `pasteboard` all served work areas measuring **1146x0** — present in the DOM, zero height — with `.main-content` collapsed to 60px (its toolbar alone). `selector_exists` passed all three at both tiers; so did a browser probe that drove their internal functions. The owner found them by opening the pages: *"I can't paste to or see any work area."*
- **what:** A Tier-4-only criteria check type. Measures the first match's `getBoundingClientRect()` and fails when the rendered box is smaller than a floor (default 24x24, overridable per check via `min_width` / `min_height`). `browserPage.VisibleArea(selector)` is the new seam; `experienceCheckTiers` records it as tier 4 and `experienceCheckTypeFields` declares its two optional keys so P7 refuses them on any other type. Five table-driven tests pin it, including the exact 1146x0 shape.
- **why it cannot be a Tier-2 check:** it measures a rendered box. A static read of HTML cannot compute layout, so a Tier-2 equivalent is not unbuilt — it is impossible. This is the clearest case yet for why the ladder needs a browser tier at all (cf. TL-012).
- **the root cause it points at, which is a defect CLASS:** all three tools were ported from STANDALONE PAGES whose `body` was the flex container (`body { display:flex; height:100vh; overflow:hidden }`). Inlined into a section, that rule (a) restyled the HOST page — the site's own body became a flex container with `overflow:hidden`, page scrolling included — and (b) still gave `.main-content` no flex parent, because the sidebar and main content sit inside the ported section rather than directly under `body`. So `flex: 1` was inert and the height collapsed. **Measured fleet-wide: exactly 3 pages carry page-scope CSS that escapes onto the host page, and they are these three.** Fixed by scoping the rule to a `.tool-shell` wrapper with a bounded height.
- **landmine — a missing element FAILS here, unlike the Tier-2 attribute checks.** `attribute_absent` must SKIP on zero matches because zero is the normal state for a client-side-rendered list. This check runs post-settle in a real browser, so a selector matching nothing means the element genuinely is not there. Do not "harmonise" the two rules; they differ because what they can see differs.
- **landmine — it cannot tell `display:none` from a collapsed flex child.** Both measure 0x0 and both are reported the same way. That is deliberate: from the visitor's side there is no difference. If you need to distinguish them, that is a different check.
- **the transferable rule this produced:** **verify through the visitor's gesture, never through the tool's internal functions.** Yesterday's verification of pasteboard called `addItem(src)` directly and passed; the visitor's actual entry point is a paste event, and the work area it would paste into had no height. A criteria fence must assert the tool's TERMINAL value (a sticker appears on a visible board) and not the first observable state change (an internal call mutated an array).

- **relations:** extends the criteria contract (TL-015) and is consumed by Tier 4 (TL-014); complements the static orphan-reference check (TL-032), which finds the opposite failure — markup the script needs that is absent — where this finds markup that is present and unusable; the ladder it sits in is TL-008; TL-012 is the standing argument it instantiates.

### TL-035 — `capture_renders` — a screenshot of a page that PASSED, because nothing was ever allowed to just look
- **status:** built, INERT until the next chassis roll (Go change) and until a caller sets the flag; no caller sets it yet.
- **status-evidence:** Written 2026-07-31. Measured gap, not a suspected one: `captureFailureEvidence` returned early on `if len(failing) == 0`, so the platform's only screenshot path fired **exclusively on failure**, and `render_audit_action.go` does not screenshot at all. Three defects reached the owner on 2026-07-30/31 — text flush against a card border on fundamentallyai.com (computed `padding: 0px 0px 0px 0px`), a row of "Read the rest" links 26px off their shared baseline, and overlapping value labels on the review-council simulator's comparison band — and **all three occurred on pages where every configured check PASSED.** No assertion covered spacing or baseline alignment, so nothing failed, so nothing was photographed, so nobody looked. All three were found by a human opening the page.
- **what:** An opt-in boolean `capture_renders` on `RunChecksRequest`. Set, it captures the full-page screenshot for every (url, profile) run rather than only failing ones, and files passing captures in a **new** `RunChecksResult.Renders []ScreenshotRef` list. Unset (the default) the action behaves exactly as before. One capture per run either way — opting in never doubles a failing run's cost.
- **why a SECOND list rather than making `Screenshots` unconditional — this is the load-bearing design decision:** three consumers in `platform/orchestration/actions/tool_acceptance_actions.go` (:650, :704, :970) attach `Screenshots` to a work item they are raising *because something failed*, and two of them do so **unfiltered** (`shotsForSpec(v.Shots, "")`; :704 is commented "what the page looked like when it failed"). Making the existing list unconditional would put a photograph of a perfectly good page into a failure ticket as its evidence — i.e. it would change what that list MEANS for callers who never asked for renders. A separate field changes nothing for them: **everything in `Screenshots` still evidences a failure and still names it in `FailingChecks`**, and `Renders` is absent unless a caller opts in. That is what keeps this additive rather than a renegotiation with three consumers.
- **scope reasoning, per the owner ruling of 2026-07-29:** this adds an opt-in capability reachable by nothing until a caller names it, and changes no guarantee of the shared mechanism — so it is normal council-gate scope, not an RFC. Had it been done by making `Screenshots` unconditional it *would* have changed a guarantee (a screenshot would no longer imply a failure) and would have needed the RFC route. The two options are worth contrasting because the cheap one is the one that needs the heavier process.
- **mutation-proven, not merely green:** three mutants, each caught. Ignore the flag and always capture → `TestRendersOffByDefault` **and** the pre-existing `TestP3NoScreenshotWhenAllPass` fail (the default-off guarantee). Invert the routing so failures file as renders → three tests fail including the pre-existing `TestP3ScreenshotCapturedOnFailure` (the consumer guarantee). Ignore the flag so renders never capture → `TestRendersCapturedOnPassWhenRequested` fails (the capability is inert). A fourth attempt (`if false`) only broke the build and proved nothing, which is itself the reminder that a mutant must compile to be a test.
- **what this does NOT close, stated plainly:** it makes the *capability* exist for anything already running `run_checks` with a criteria document. It does not put ordinary site pages in front of anyone — a brochure page has no criteria fence, so none of the three motivating defects would be caught by this flag alone. The remaining half is a caller: either criteria fences for site pages, or a render-and-review stage. That is S6/S7 in `features_open/027` / `staged_component_build/PROPOSAL_2026-07-30_step_by_step_build_with_stage_gates.md`, a separate thread by owner instruction. **Do not read this entry as "the looking problem is solved".**
- **landmine — a render is not a verdict.** `Renders` is evidence to look at, never something to decide by, and `FailingChecks` is empty on every entry by construction. Anything that starts treating a render's presence as signal has reintroduced exactly the ambiguity the second list exists to prevent.

Three surfaces render, one has a camera, and it was wired to fire only after a failure.
