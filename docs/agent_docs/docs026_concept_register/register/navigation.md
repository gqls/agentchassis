### NAV-003 — Stale pages from previous builds polluting nav + config-driven deactivation fix

### NAV-013 — The nav-membership contract: one declaration, one writer, and a rebuild REQUEST
- **status:** deployed
- **status-evidence:** commit `1884f1ee8` + `8c41e3eaf`, chassis **v1.0.1215**, pod-verified on both replicas. Council `4486f1a9-6d96-4767-9ddd-6ff5e92ba45c` **APPROVED** (12 reviewers, 0 unreadable, 2 medium objections, none high). Diagnosis loop `1d8085f0-b596-4cce-9417-f48227ac67d3` **CONFIRMED** the underlying mechanism, first iteration. `bugs_open/149` A2/A6, A4's recordable half, A5's child half. **Proven on a SECOND site 2026-07-31 18:16 UTC** (gaswholesalers.com, corr `fd85fc84`, chassis v1.0.1218): 19 active nav rows → 23, the four additions all in `utility` with clean labels, the 19 pre-existing labels unchanged. That site exercises the code the first one could not — `nav_label` NULL on all four pages, and the flat `/tools/tool-x.html` convention, so the `tool-` prefix strip ran in production for the first time. **The authored-label half below is council-APPROVED and NOT yet live** — `11c5c813-dfad-437e-b4a9-09c56475e8d2`, round 4, **"all reviewers approve"** (13 reviewers, 4 abstained, `gated_by_truncation: false`, no objection above low), commits `6fc1ff3ed` → `997c24baf` → `8cbc02c77`. Inert until the next chassis roll — not rolled on 07-31 because two other councils were mid-round (R13). Rounds 1–2 found two real defects in it; round 3 died on the fleet's API usage cap at 18:58, not on merit, and round 4 was the same submission re-sent byte-for-byte.
- **what:** The stated rule for nav membership, replacing two overlapping implicit ones: **`pages.in_header`/`in_footer` DECLARES nav membership; a page's URL shape may decide WHERE it appears, never WHETHER it appears.** Three parts. (1) `classifyPagesForNav` (`populate_nav_tables_action.go`) collapsed its two notions of "never primary" — one keyed on `page_type` (`blog-post`/`tool`/`entity-page`), one on URL prefix (`/tools/`, `/blog/`, `/guides/`, `/articles/`, `/case-studies/`, `/news/`, `/resources/`, `/insights/`) — into one. The URL-keyed rule used to `continue` out **before either flag was read**, so a nav-flagged child page was dropped entirely; it now demotes to `utility` (footer) exactly as the `page_type`-keyed rule always did. `section-index`/`blog-index`/`news-index`/`entity-directory` keep primary eligibility, keyed on `page_type` not URL. (2) **`site_nav_items` now has exactly ONE writer** — the derivation. `addToolToNav` (NAV-008) is deleted. (3) `RequestNavRebuild` (`nav_rebuild_request.go`) is how a page-creating action asks for its declaration to become real: one work item per site, `item_type` `nav_drift`, `handler_agent` `nav-updater`, `status` `triaged`, `item_key` `nav_rebuild:<site_id>`, `recurrenceExpected: true`. Called by `create_tool_component` and `deploy_tool_to_site`, which also now record `in_header`/`in_footer` explicitly instead of inheriting the schema default `TRUE`.
- **why a REQUEST and not a row (the transferable part):** a nav row is not a link. Chrome is a stored artefact (`bugs_open/117`/`118`), so writing `site_nav_items` changes no served page — while `check_orphan_pages` treats the presence of a nav row as reachability. Writing the row at creation time (which is what `bugs_open/149` A6 literally proposed) would have left the page exactly as unreachable **and silenced the only check that would have noticed**. `nav-updater`'s live workflow (`populate_nav_tables → render_site_components → create_rerender_items → get_pages_for_rerender`) is what actually makes a link ship, so the request invokes that.
- **the evidence, with its control:** a discovery-raised `nav_drift` item for gamesdesign.co.uk naming four `/tools/` pages was `complete` at 17:27:50 on 2026-07-29; all four were still absent from `site_nav_items` on 07-31. The **same** check, handler and action repaired robot-hands.com's `/learning-center.html` and `/news.html` — which differ only in not sitting under a child prefix.
- **the label half, and the fact that it initially covered only ONE of two paths (added 2026-07-31, second-site proof):** the contract carries a second rule — **a nav label never contains a path separator** — because routing child pages into nav for the first time fed path-shaped URLs into `navSimplifyLabel`, which title-cased the whole path (`Tools/Damage Formula Designer/Index`, six labels, gamesdesign's live footer). That was fixed and tested for every label the derivation **computes**. It was **not** true of the labels the planner **authors**: `navLabelForPage` returned a `pages.nav_label` verbatim whenever it was ≤30 chars, slash and all, so the invariant stopped at the function boundary beside the one that was reviewed. Found by proving the fix on a second site and measuring the **authored** column rather than the derived one — 8 live pages carry a `Tools / …` nav_label, 2 short enough to be trusted verbatim, and **ai-agent-orchestration.com was already serving a nav row labelled `Tools / AI Readiness Quiz`**. `navLabelDropCategoryPrefix` now takes the last `/`-separated segment of an authored label **before** the length test, so no slash survives and an oversized label still falls through to `navSimplifyLabel` rather than shedding a prefix to bypass the length guard. Last-segment rather than URL-derivation on purpose: deriving from the URL flattens the planner's capitalisation (`AI Readiness Quiz` → `Ai Readiness Quiz`).
- **LANDMINES for a caller:** (a) **a third caller from OUTSIDE `platform/orchestration/actions` is an RFC moment** — at that point this is a general on-ramp to the work-item queue and has never been reviewed as one (architecture seat, this round). (b) `recurrenceExpected: true` is load-bearing, not decoration: without it `insertWorkItem`'s two-strike rule brands the **third** request on a repeated `item_key` as `unresolved` — terminal, never dispatched — so the third tool added to a site would silently stop reaching the nav. (c) The `item_key` is **site-scoped**, so a second request while one is open writes nothing at all, including its own spec: read `spec.page_name` as "what prompted this", never "what this will fix". (d) The effect is **inert until a nav rebuild runs** — this ships no visible change on its own. (e) **There are FOUR label paths and only two of them are live** — if you go to change label behaviour, change `navSimplifyLabel`/`navLabelForPage` (`nav_tables.go`, `populate_nav_tables_action.go`) and leave `rerenderSimplifyNavLabel` (`rerender_pages_actions.go:440`) alone: it still contains the **pre-fix whole-path defect**, so it reads exactly like a live bug, but its only callers `rerenderGetHeaderNavFromDB`/`rerenderGetFooterNavFromDB` are reached from one commented-out line (`rerender_pages_actions.go:168`). `datahelpers.SimplifyNavLabel` takes a page **name**, not a URL, so it cannot title-case a path. `nav_tables.go`'s header comment says `navSimplifyLabel` "consolidates" the other two — that is the intent, not the state.

### NAV-014 — a site DECLARES its own header, and the fleet-wide tier table degrades to a fallback
- **status:** BUILT and unit-proven 2026-08-26 — `nav_declaration.go` + `nav_declaration_test.go` (32 subtests, **8 guards each proven load-bearing by mutation with a named failing test**). **NOT DECLARED BY ANY SITE: inert until `654_..._HOLD` applies after the roll.** Council `cb67cc71-b420-4399-9a52-f306d0f4bccf` **APPROVED round 1**, 6 advisory objections, none high; two of them moved the declaration to a different table before it shipped.
- **what:** `bugs_open/407`, at the owner's direction. Header membership was decided by a **hardcoded, FLEET-WIDE list of page NAMES** (`navPriorityTier`) and `nav_order` only sorted WITHIN a tier, so a site's own page at `nav_order` 1 sat behind every tier-2 page at `nav_order` 100 and the only ways to promote it were to rename it onto the list, edit the Go list for all 51 sites, or displace enough higher-tier pages that it arrived by elimination. Now a site declares `site_specs.data->'chrome'->'header_slots'` — an **ORDERED array of `pages.name`** — plus an optional `chrome.max_header_items`, and those pages take the leading primary slots **in the site's order, ahead of every undeclared candidate**. Undeclared candidates fill what remains by the existing tier/`nav_order` sort; overflow still goes to utility, so nothing vanishes. Parse is pure (`siteNavDeclarationFromSiteConfig`) with a `default | site_config | invalid` source, and an **`invalid` declaration is WARNed and reported, never silently defaulted** — being quietly ignored is the defect this entry removes.
- **why ORDERED and not a tier bump — measured, and it rules out the obvious cheaper fix:** half the damage is **same-tier ties**. `[MEASURED 2026-08-26]` gaswholesalers.com's header holds `why-gas-wholesalers`, `how-pricing-works` and `service-areas` — all tier 3, all at `nav_order` 100 — while tier-3 `pricing-transparency` at `nav_order` 100 is absent; the tie is broken by load order. Raising a page's tier fixes finetuning.uk and leaves that site exactly as it is.
- **why the fleet list could not simply be extended — also measured:** the previous remedy for this is *inside* the broken thing. Three site-specific names (`model-directory`, `adoption-tracker`, `protocol-tracker`) were hardcoded into the tier-2 map with a comment saying that as tier 3 they would be "the first thing dropped when max_header_items truncates". `[MEASURED 2026-08-26 at the SERVED page]` ai-agent-orchestration.com's header holds exactly 8 links and **ONE of those three is present; its two siblings are not.**
- **⚠ LANDMINE — the declaration OVERRIDES three membership guards, deliberately, and only three.** It beats the tier, the same-tier `nav_order` tie, `neverPrimaryTypes` (blog-post/tool/entity-page) and the child-URL bar — every one of those is a fleet-wide DEFAULT, and the point is that a default may not outrank the site's own word. It does **NOT** override the system-page exclusion (404/sitemap/robots) or the legal group: those are correctness rather than preference, and a site declaring one is TOLD so (`declared_ineligible`) rather than obeyed. **The undeclared path keeps every bar, unchanged.** The council's guardian seat is right that collapsing three guards into one opt-in deserves explicit owner sign-off; that is recorded as an owner decision in `bugs_open/407`, not assumed.
- **⚠ LANDMINE — a declared page is placed EVEN IF `in_header` is false, and removing that is a silent regression.** `sync_pages_to_db` upserts `in_header = EXCLUDED.in_header` on every re-plan, so a declaration subordinate to the flags is defeated by the next re-plan and the silence returns. The disagreement is reported (`declared_flag_disagreed`) so the plan can be corrected at its source.
- **⚠ LANDMINE — the WRONG homes, and why, because two of them look right.** `site_nav_items` AND `site_nav_groups` are both DELETEd for the site on every rebuild (`populate_nav_tables_action.go:160,163`) and re-derived — a declaration there survives nothing. `pages` columns are rewritten by the re-plan upsert. `sites.settings` was the first draft's answer and is wrong for a different reason: **`site_config.chrome` already holds per-site header config** (`header_cta_url`/`header_cta_label` on oufe.com, `compliance_lines` on two more, `[MEASURED 2026-08-26]`), so slots belong beside CTAs. - **⚠ LANDMINE — the tempting wrong fix is an EXHAUSTIVE reading.** If `header_slots` meant "the header is exactly this and nothing else", a new page gaining `in_header` would never appear until an operator edited the spec — recreating this bug's silence class from the other side.
