### OPP-004 — `check_register_coverage`: the register coverage cadence, on the commit path
- **status:** deployed (advisory; 9th check in `scripts/pattern-check.py`, run by `.githooks/pre-commit`)
- **what:** Fires when a commit **creates a workstream directory the concept register has never heard of**, naming both ways to go quiet — add a register entry, or add the directory to `102_coverage_ratchet.txt`. It closes `bugs_open/106`'s last open scope: the coverage SENSOR (`102_CHECK_register_coverage.py`, sensor + ratchet) already existed and worked, but ran only when a human remembered, which is the same detected-by-coincidence mechanism the bug was filed about, one step earlier. **A commit trigger was chosen over a cron deliberately**: a cron reports drift up to a week late to nobody in particular, whereas this reports it the instant it is created to the one person who can close it in ten seconds. Only NEW directories fire — the 43 already-uncovered workstreams are accepted backlog on the ratchet, and flagging active work on them every commit is how a check becomes wallpaper.
- **why it is registerable:** it is the enforcement half of the register's own coverage guarantee. Any workstream creating a new subsystem directory now learns, at creation, that the estate's capability index does not know about it.
- **measured before inclusion** (this file's own bar): **4 fires / 1,500 commits = 0.27%**, quieter than every existing check (README 0.7%, SUMMARY 2.0%, twin ~2%) — correct for a population of "commits creating a brand-new workstream". **Precision inspected because a very low rate and a dead check look identical:** all 4 genuine (`memory_index`, `bugs_sweep_2026_07`, `bugfix_066_spawn_image_tag`, `gemini_content_provider`), and the last two are exactly the pair 106's own triage records the sensor finding by hand on 2026-07-27 — the same gaps, now caught at creation.
- **verified by induced gap**, as `106` demands: two scratch workstreams staged → both fire; one added to the ratchet → only the other fires; the other given a register entry → it goes quiet too. Negative control: silent and 40 ms on a commit touching no workstream directory.
- **sources:** `scripts/pattern-check.py` (`check_register_coverage`); `docs/agent_docs/docs026_concept_register/102_CHECK_register_coverage.py`; `docs024/bugfix_106_register_coverage_cadence/` (PLAN, RUNBOOK, NOTES)
- **relations:** OPP-003 (sibling commit-path detector); `102_coverage_ratchet.txt`; the `verifier_coverage_test.go` sensor+ratchet shape it is modelled on; `bugs_closed/106`
- **landmine:** it **imports** the sensor rather than reimplementing `is_covered()` — one matching rule, one implementation, because two hand-maintained copies is the `idx_swi_dedup` ↔ `workItemTerminalStatuses` drift class. Change how coverage is decided in the sensor and the hook follows. The import is guarded: if the sensor moves, the check returns silently rather than breaking commits.
- **NOT in scope, deliberately:** it asks only whether a subsystem is *represented*, never whether an entry is *accurate*. **The register can be complete in coverage and stale in content, and nothing detects that** — two live instances hit on 2026-07-28 (a `verify-later` stating an expected answer that had been false for weeks, contributing to `bugs_closed/124` going unnoticed). Recorded, not fixed: a coverage check that starts auditing accuracy becomes slow, noisy and ignored.
- **verify-later:** does `check_register_coverage` still appear in `scripts/pattern-check.py`'s check tuple in `main()`, and does `./scripts/pattern-check.py` stay silent on a commit touching no workstream directory?

### OPP-006 — `check_register_entry_without_row`: the register's two halves ship together, or the commit says so
- **status:** deployed 2026-08-10 (advisory; 17th check in `scripts/pattern-check.py`, run by `.githooks/pre-commit`)
- **what:** Two arms on one trigger — a commit that ADDS a `### ABC-001` concept entry to a register category file. **Arm 1** fires when that id has no `| ABC-001 |` row in `000_concept_index.md` as the commit will contain it. The index table is what a session searches, so an entry with no row reads as *does not exist* and the next lane builds a second one — `bugs_open/106`'s failure mode, arriving one concept at a time. **Arm 2** fires when the id is already taken elsewhere in the register.
- **why a gate when DOC-074 already reports this daily:** because reporting it is measurably not enough, and this lane has the receipts. The watcher named a headline mismatch on **three consecutive mornings and nobody corrected it**. A report can only ask someone to repair the register afterwards; this fires in front of the one person who can close it in ten seconds, while they are still writing the entry. Same argument as OPP-004 one level up: put the check where the error is made.
- **measured before inclusion** (this file's bar), over the 14 days to 2026-08-10: **398 commits touched the register; 159 of them added at least one concept entry. 133 (84%) did it correctly and are silent. 26 commits (16%) shipped an entry with no row — 34 findings, 0 false positives on inspection.** Against the whole commit stream that is 26 / 3,324 = **0.8%**, quieter than the twin (~2%) and SUMMARY (2.0%) checks. Arm 2: **1 finding in 398 commits**, the known `LNK-031` collision.
- **the measurement that decides whether it is worth having, and it is not the fire rate.** A fire count cannot tell a real leak from a two-commit workflow the gate would merely nag. So: of the 34, **32 eventually got a row and the median entry waited 93 hours for it**; 23 of 32 took ≥24h; only 3 closed inside an hour. **21 were closed in one sweep by another session's 08-04 backfill commit** (`8f998e86b`), not by their authors. That is the shape of a leak somebody else pays for, not of a workflow.
- **it also corrects the rate this lane had been quoting.** The handoff estimated ~1 per 1.5 days from the watcher's own reports; the commit-level sweep says **~1.2/day** since the 08-04 backfill. The watcher undercounts *by construction* — it can only name entries still missing at 06:50, so a row backfilled the same afternoon (VIZ-015 at 0.0h, WII-010 at 0.8h) never appears in any daily row. **A report's count is bounded by its sampling interval; a commit sweep is not.**
- **⚠ LANDMINE — arm 2 was INERT in production while passing every test, and the shape is general.** `git grep <pattern> --cached` is not a synonym for `git grep --cached <pattern>`: git reads the trailing word as a REVISION and dies "unable to resolve revision: --cached". `sh()` captures stdout only, so that fatal arrives as an empty string — empty corpus, no collisions, no findings, **no error**. It passed every `--commit` audit, because there the sha legally follows the pattern; only staged mode was dead, and staged mode is the only mode the hook runs. Caught by a positive control that staged a known-duplicate id and REQUIRED a finding. The arm now asserts that the corpus it read contains the very headings the commit adds — true by construction — and prints an audible skip when it does not, so a broken read can never again pass as "no collisions".
- **⚠ LANDMINE — it reads `git show :<path>`, never the worktree, and that is not a detail.** The house rule here is `git commit <pathspec>`, which takes the named paths and ignores the index. An author who edited both files but named only the category file ships the entry alone, and a worktree read would call that clean — the same half-a-move failure LANDMINES records for `git mv`. There is a control for exactly this: row present in the worktree, not staged, must still fire.
- **it imports the watcher's parser** (`ENTRY_RE`, `ROW_RE`, `parse_rows` from `concept-register-drift-check/base/check.py`) rather than re-deriving them, for OPP-004's reason and one more specific to this pair: if the gate's idea of an entry heading ever diverged from the watcher's, a commit could pass the gate and then be reported by the CronJob for ever, with nothing to say which of the two was wrong. Guarded — if the watcher moves, the check returns silently rather than breaking commits.
- **NOT in scope, deliberately:** (1) it never writes the row. A row needs a one-line summary written by someone who understands the concept, which is the same reason DOC-074 reports and does not repair. (2) It does not check the reverse (a row with no entry) — the drift is one-directional by construction, since adding a concept is two edits and only the first is load-bearing for the author, and the index header's `comm` pair has never once found a row without an entry. (3) It says nothing about whether an entry is TRUE; that flank is still open and is the register lane's next question.
- **cost:** 0.12–0.16s when the register is touched, 0.05s otherwise (early return before any git call). Advisory — like everything in `pattern-check.py`, it never blocks; `PATTERN_CHECK_STRICT=1` opts a session into non-zero exits.
- **sources:** `scripts/pattern-check.py` (`check_register_entry_without_row`, `committed_content`); `deployments/kustomize/services/concept-register-drift-check/base/check.py` (the imported parser); `docs026_concept_register/RUNNING_NOTES_concept_register.md` (2026-08-10, the sweep and the five staged controls); `HANDOFF_2026-08-10_continue_here.md` item 1
- **relations:** DOC-074 `concept-register-drift-check` (the daily half — this is the same predicate moved to authoring time, and the two share one parser) · OPP-004 `check_register_coverage` (sibling commit-path detector, one level up: *is the subsystem represented at all*) · OPP-003 · `bugs_open/106` (the register-as-absence-evidence failure this drips into) · the `LNK-031`/`LNK-032` collision of 2026-08-08 (arm 2's motivating case)
- **verify-later:** does `check_register_entry_without_row` still appear in `main()`'s check tuple; does a staged entry with no row still produce a finding (the control that must never go quiet); and — the real question — **does the daily watcher's missing-row finding count fall to zero now that the class is caught at authoring time?** If it does not, the gate is being ignored rather than working, and that is a different problem with a different fix.
- > **ANSWERED 2026-08-11 — it was neither working nor ignored: it was INAUDIBLE, and the fix is OPP-007.** The gate's first live miss (`5c7b115c5`, three hours after shipping) was read back from that session's own transcript: the command ended `2>&1 | tail -8` and the recorded stdout is **exactly 8 lines**. The finding was computed correctly and thrown away by the session's own pipe. This is not one session's slip — **45% of multi-file commits since 2026-07-18 (1,199 of 2,669) never delivered the advisory block, 95% of those cut by a `| tail`, across 258 distinct sessions.** So the "is it being ignored?" branch of the verify-later above was never reachable on the evidence available in the register or the watcher; it needed the harness transcripts. **Nothing about this gate's predicate, fire rate or advisory posture changes** — the argument against giving it teeth stands, and the case for teeth was never made out. `FINDINGS_2026-08-11_advisory_delivery.md`.

### OPP-005 — Session scratchpads: versioned by a snapshot hook, reaped by content class
- **status:** deployed (2026-08-03; `CLAUDE_CODE_TMPDIR` moved to disk in `~/.claude/settings.json`, hook wired in `.claude/settings.json`, both tools in `scripts/`)
- **what:** Three coupled pieces that make the shared session-scratchpad tree survivable. (1) **`CLAUDE_CODE_TMPDIR=/home/ant/.claude-scratch`** — scratchpads move off the 16 GB `/tmp` tmpfs onto the main disk (212 GB free), ending the class where a full tmpfs makes a Bash call return **no output** (ENOSPC on the harness's own stdout capture, which reads like "the command found nothing", not like a disk error). (2) **`scripts/scratch-git-snapshot.py`** — a `PostToolUse` hook on `Write|Edit` that commits each written scratchpad file into a git repo at the scratch root, one file by pathspec, so a scratchpad stops being unrecoverable. (3) **`scripts/scratch-report.py`** — shows every session dir by age, size and content class, and reaps only what is provably reproducible.
- **why it is registerable:** any workstream on this machine writes to a scratchpad, and until now nothing versioned or bounded that tree. It is also the general answer to "how do we clean up shared temp safely", which every lane eventually asks.
- **the measurement the whole design rests on** — the two content classes have opposite risk profiles and the space is almost entirely in the safe one: **33 repo-extraction dirs = 12.13 GB = 99.3%**, versus **370 other entries = 88 MB = 0.7%**. A repo extraction is a `git archive HEAD` unpack (the shared-tree build check CLAUDE.md mandates); it is byte-for-byte reproducible from a sha, so deleting one loses nothing. The 0.7% is irreplaceable and small enough never to need deleting.
- **the separation is structural, not heuristic.** Extractions are created by `tar`/`git archive` in **Bash**; the hook fires on **Write|Edit**. So it is *incapable* of committing an extraction — no size rule is doing the work, and there is no threshold to misfire. The 5 MB cap in the hook is a backstop against a large generated artefact, not the class filter.
- **`.gitignore` is `*` and every add is `-f`.** The repo therefore contains only what was deliberately snapshotted, and `git status` next to 12 GB of untracked bulk returns **empty in 3 ms** instead of listing it. Showing untracked bulk is the report tool's job, not git's.
- **verified in both directions before wiring** (a guard that refuses everything passes a refusal test): positive — a real `Write` in a live session produced a commit, proving the hook fires without a restart; negative — a repo path outside any scratchpad and a 6 MB file were each refused, commit count unchanged; idempotence — re-firing on unchanged content adds no second commit.
- **`--reap` deletes only marker-verified extraction directories**, never a loose file, never a session dir, never anything it cannot positively identify (≥2 of `go.mod`/`platform`/`CLAUDE.md` at the directory top). It re-verifies at the moment of deletion, not just at scan time, and defaults to a dry run at a 2-day threshold.
- **sources:** `scripts/scratch-git-snapshot.py`; `scripts/scratch-report.py`; `~/.claude/settings.json` (`env.CLAUDE_CODE_TMPDIR`); `.claude/settings.json` (`PostToolUse`); `gauntlet_dead_cta/NOTES` 2026-08-03
- **relations:** `scripts/memory-git-snapshot.py` (same argument, same shape — an unversioned shared store is the hazard, and versioning it dissolves the class rather than policing writes); the `bugfix_177` LANDMINE on `/tmp` filling mid-build, which is the same outage seen from inside a build
- **landmine:** **two scratch roots are live at once after the move.** A running session keeps the tmpdir it launched with, so sessions started before 2026-08-03 keep writing to `/tmp` while new ones use the disk. `df -h /tmp` can therefore look healthy while the tree you are actually in is full, or the reverse. Both tools read **both** roots for this reason; a check that inspects only one will be confidently wrong for as long as the old sessions live.
- **NOT in scope, deliberately:** it does not reap hand-written files at all, at any age. They are 0.7% of the volume, so reaping them buys nothing measurable and risks the only irreplaceable thing in the tree.
- **verify-later:** does `git -C /home/ant/.claude-scratch/claude-1000 log` show commits from more than one session id (proving the hook is live fleet-wide, not just in the session that wired it), and does `scripts/scratch-report.py` still report both roots?

### OPP-007 — `commit-advisory-postuse.py`: the pre-commit advisory, re-emitted where a `| tail` cannot cut it
- **status:** deployed 2026-08-11 (advisory; `PostToolUse` hook on `Bash` in `.claude/settings.json`, wired from `scripts/commit-advisory-postuse.py`). Commit `05d8b379e` (the index row itself is in `3e9d2035d`, which swept it as a same-file passenger while this entry was being written — the hazard CLAUDE.md describes, arriving unprompted during a commit about commit hygiene).
- **what:** After any Bash call whose command contains `git commit` and whose output carries git's `[branch sha]` summary line, it re-runs `commit-scope-report.sh --commit <sha>` and `pattern-check.py --commit <sha>` and delivers the result through `hookSpecificOutput.additionalContext`. Out of band: it is not part of the command's stdout, so no pipe in the session's own command can remove it. Blocks the session already saw are dropped rather than repeated.
- **why it exists, and it is a delivery defect not an adoption one:** `.githooks/pre-commit` prints the commit-scope report and pattern-check's findings **first**; git prints its `[branch sha]` summary **last**. Sessions habitually run `git commit … 2>&1 | tail -5`, which is a head-cutter. **Measured 2026-08-11 across every commit made through the tool since the scope report shipped (2026-07-18) — 2,669 multi-file commits in this repo, read from the session transcripts: 1,470 (55%) delivered the block, 1,199 (45%) did not, and 1,137 of those misses (95%) were cut by the session's own `| tail`.** 258 distinct sessions did it, so it is a fleet-wide habit rather than one lane's tic. Figures move with the corpus — re-run `scripts/advisory-delivery-sweep.py`, do not quote these.
- **the control that makes it a finding and not a correlation:** among the misses `tail -N` is ≤8 in 1,031 of 1,137 cases (median 5); among commits that delivered the block **despite** a tail pipe, N is >8 in 465 of 595. Delivery tracks the pipe width, which is exactly what truncation predicts and is a result that could have come out otherwise. The sweep prints this control on every run. Second, independent control: for 666 of the misses the recorded stdout is **exactly N lines long** — output existed and was cut, arithmetic no content can fake.
- **what it settles for OPP-006, which asked this question in its own verify-later.** OPP-006 fired on `5c7b115c5` three hours after shipping and the two entries landed with no index row anyway; `HANDOFF_2026-08-10b` recorded that the honest first question was whether the session never saw the output or saw it and judged the row could wait — *"those have opposite fixes (delivery vs. enforcement), and nothing recorded so far distinguishes them."* Something did: the session transcript. That command ended `2>&1 | tail -8` and its recorded stdout is exactly 8 lines. **The gate was never ignored; it was inaudible.** No case for teeth was made out, and the argument in `pattern-check.py`'s docstring against blocking on a shared tree stands untouched.
- **why a harness hook rather than a git hook:** no git hook can win this. `post-commit` runs *before* git prints its summary (verified in a scratch repo), so its output is cut by the same `tail`. The only escape is to leave the command's stdout altogether, which is what `PostToolUse` does.
- **delivery is the whole point, so the delivery path is the load-bearing detail:** `hookSpecificOutput.additionalContext` on **stdout**, exit 0. A `PostToolUse` hook that writes to **stderr** and exits 0 reaches neither the model nor the transcript — `scripts/memory-index.py` was wired that way and was mute for six days while sessions hand-rolled the number it was computing. It is recorded in the `.jsonl` as an `attachment.stderr` record, so a grep for the banner text finds it and it looks exactly like delivery.
- **cost:** a substring test on the command and nothing else for ordinary Bash calls; ~0.1–0.5s when a commit is detected (measured: `pattern-check.py --commit` is 0.08s on a docs commit, 0.46s on a 5-file platform commit).
- **⚠ LANDMINE — it must never report against the wrong tree.** Sessions commit into other repos through the same Bash tool (the auto-memory git dir, scratch repos): 71 of 5,195 shas in the transcript corpus resolve nowhere in agentchassis. The sha is therefore checked with `git cat-file -e <sha>^{commit}` before anything is read, and an unresolvable sha exits silently. A scope report attributed to the wrong repo would be worse than no report.
- **NOT in scope, deliberately:** (1) it cannot block, and nothing here should — `PostToolUse` runs after the tool, so the commit already exists; this buys visibility one moment later, not enforcement. (2) It does not change what the checks look for; the predicates are untouched and both scripts keep their existing staged mode. (3) It does not help a commit made outside the Bash tool.
- **sources:** `scripts/commit-advisory-postuse.py`; `scripts/commit-scope-report.sh` (the new `--commit <sha>` mode); `.claude/settings.json` (`PostToolUse` matcher `Bash`); `docs026_concept_register/FINDINGS_2026-08-11_advisory_delivery.md` (the measurement, its two controls and the refuted first hypothesis)
- **relations:** OPP-006 `check_register_entry_without_row` (whose first live miss this explains, and whose verify-later this answers) · OPP-003 / OPP-004 (the other `pattern-check.py` detectors, which were being suppressed the same way and are equally repaired by this) · OPP-005 (the other `PostToolUse` hook in `.claude/settings.json`) · DOC-074 `concept-register-drift-check` (the daily half; unaffected — it never depended on a session reading anything) · `scripts/memory-index.py` (the stderr-and-exit-0 trap this deliberately avoids)
- **verify-later:** does the multi-file-commit delivery rate rise above 55% in the transcripts of the days after 2026-08-11 (re-run the sweep in the FINDINGS doc), and does the daily watcher's missing-row count now fall? If the rate rises and the watcher's count does **not**, then delivery was never the binding constraint and the enforcement question is genuinely open again — which is the outcome this entry would be wrong about.
