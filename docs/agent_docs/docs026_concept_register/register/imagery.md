### IMG-007 — Algorithmic imagery discovery checks (Phase 1 trio)
- **status:** deployed
- **status-evidence:** "Phases 1.1–1.4 all ✅ delivered 2026-05-08 (1.2/1.3 partial — check fires; symptom-path site needed)"; dispatch doc separately shows the checks live and routing work items.
- **what:** Three no-LLM Go discovery checks catching spec-to-delivery gaps at zero LLM cost: `unfulfilled_image_prompt` (planner asked for an image, no asset exists), `placeholder_image_in_use` (a hardcoded fallback path is rendered in `rendered_html` with no backing asset — the silent-failure case), and `image_url_404`. All follow the `DiscoveryCheck` interface, register via `init()`, and were appended to design-discovery-agent's `run_checks`. A ~12-item wishlist of further checks (alt-text, dimensions, orphans, cross-site contamination, multi-image underfill) was catalogued and mostly remains unbuilt. `unfulfilled_image_prompt`/`placeholder_image_in_use` emit `needs_imagery`/`needs_hero_image`/`needs_logo` to image-build-handler via the dispatch loop.
  **`image_url_404` REWRITTEN 2026-07-31 (`bugs_closed/128`, commit `beff42809`) and it is no longer the shape this entry described.** It used to compare a rendered path's basename against the site's active asset PURPOSE names, which — measured live over all 127 rendered image paths on 13 sites with HTTP as ground truth — reported **21 working images and was silent on 6 live 404s**. It now resolves through `storage.DeployedWebPath(asset_key, purpose)`, the same helper the five writers render with, making it the exact **inverse of the render-time resolver**: 1 false positive, 0 misses. Three consequences another workstream needs to know: it scans **`site_components` as well as `page_components`** (the chrome is on every page, and was never scanned); it also reports an `<img>` whose `src` is **empty** (no path, so no path predicate can see it, and an HTTP probe would score it 200); and it is now **flag-only** — its recognised-purpose routing branch was an exact duplicate of `placeholder_image_in_use` (same paths, purposes, item types, handler, precondition, same agent) and was deleted, so generation stays that check's remit alone. Dedup keys carry the file extension now (`image_url_404:logo.png`), because two files can share a basename and one of them can be the broken one.

### IMG-076 — Keyed-ground matting: a real alpha channel for a model with no alpha output (`KeyOutBackground`)

- **status: BUILT, NOT YET LIVE (2026-09-02).** Code complete, unit-tested, not yet built into an image or rolled — deployed would overstate it. `bugs_open/424`. Council submission not yet run at the time of this entry (owed alongside the commit, per CLAUDE.md's platform-change norm).
- **what:** Gemini's image family (the `banana` provider) has **no alpha-channel output at all** — every generation is flat RGB, so a prompt asking for "a transparent background" makes the model paint the checkerboard PICTURE of transparency as opaque pixels. Verified structurally on the shipped defect: served PNG colour type 2, no `tRNS` chunk. No prompt wording closes this — the property does not exist in the model's output space. The fix is architectural: ask for a colour the model **can** paint — a fixed, deterministic, saturated key (`#FF00FF`, never brand-derived, so it does not reopen the 2026-05-20 palette-contamination exclusion of `kind=logo` from `composedPaletteDirection`) — then remove it mathematically after generation.
  - **Two halves, one constant, two files.** The prose half (`LogoBackgroundKeyClause`, `LogoBackgroundKeySentinel`, `LogoBackgroundKeyHex` — `discovery_checks/default_brand_prompt.go`) is applied at the SAME choke point as `bugs_open/417`'s text policy (`generate_image_actions.go`'s `if kind == "logo"` block, via the new `applyLogoBackgroundPolicy`) rather than in the adapter — deliberately, so the clause lands in `assets.origin_prompt` where a census can see it, matching 417's own proven pattern (a clause built only in the adapter would be invisible there, the exact blindness bugs_open/028's negative-prompt fold already demonstrated for this same prompt path). The structured half (`KeyGround` on `ImageRequestData`, carried over Kafka) tells the adapter — which has no DB access and cannot re-derive policy from prose — the exact hex to matte for.
  - **The matte (`internal/adapters/imagegenerator/keyground.go`, `KeyOutBackground`)** is pure Go, no new dependency: a border flood-fill (BFS from the four image edges, within an `outer` colour-distance threshold) erases only background **connected to the outside of the picture** — the safety property that stops an interior element merely resembling the key from being punched through — plus a second, tighter pass for enclosed holes (a ring, a counter) anywhere within an `inner` threshold, whose safety rests entirely on the negative-prompt belt rather than on structure. Graded edges are despilled (unmixed against the key) so anti-aliasing doesn't carry a magenta fringe. Reads through `image.Image`/`color.Color`'s generic interface throughout, not a concrete 8-bit type — the live boxingonline logo asset this bug names is measured 16-bit PNG depth, and `color.Color.RGBA()` normalises any source depth to 16-bit, so an 8-bit-assuming implementation would have silently mishandled the very asset motivating the fix.
  - **Fails CLOSED (`dynamic_adapter.go`, `generateImage`):** after matting, if `stats.BorderKeyed < 0.95` the model did not honour the key-colour instruction (a checkerboard, an unrelated solid ground, a vignette) and the function returns an error rather than uploading. This is load-bearing specifically because generated assets have **no version history** — `assets` UPSERTs in place, no revert seam exists — so a refused generation leaves the existing asset in place, where a silently half-matted one would not.
- **why not the alternatives:** provider-side alpha is refuted (`ImageConfig`, `banana/api/types.go`, has one field — `AspectRatio` — a structural model limitation, not a missing knob); two-backdrop difference matting needs the foreground pixel-identical across two independent generations, which the model does not guarantee; ML background removal/segmentation is a new dependency, non-deterministic, and clips thin strokes — exactly what a mark is made of.
- **gating — why `KeyGround` carries the colour rather than a bare `kind=="logo"` check reappearing at the adapter:** traced end-to-end rather than assumed. `generate_image_actions.go` resolves `kind` — including the step-name fallback that closed 417's own legacy-parent gap (`stepNameKindHint`) — **before** dispatch, and only writes `imageData["kind"]` when non-empty; the adapter's `data.Kind` already reflects that same fully-resolved value. Gating `applyLogoBackgroundPolicy` on that resolution inherits 417's coverage rather than re-deriving it, and `KeyGround` is not a second, independent gate — it is the same decision expressed as the value the matting step needs. Not shipped opt-in-default-OFF per site: the owner's ruling (2026-09-02, *"the background behind a logo shouldn't be part of the logo"*) defines what a correct logo asset **is**, for every site, and a per-site opt-in would re-implement the bug as the default. Every kind other than `logo` sees an empty `KeyGround` and identical behaviour to before this seam existed.
- **⚠ does NOT fix `bugs_open/421`** (the same asset returning a two-panel design comp — mark on two different grounds in one image). A border flood-fill keys whichever ground touches the border; a comp could come back half-matted, which reads as a subtler bug than it is. The `BorderKeyed` guard gives some protection (a comp is likely to fail the ≥0.95 threshold outright) but this mechanism must not be read as having verified single-composition — 421 stays open and is checked independently.
- **⚠ the one place the design can misfire, by construction, not by bug:** the enclosed-hole pass keys any pixel anywhere within `inner` of the key colour, regardless of connectivity — a mark that legitimately used near-exact `#FF00FF` would be holed by it too, and the `BorderKeyed` guard cannot see this case (border coverage would still pass). Mitigated by the negative-prompt belt (`logoBackgroundNegatives`: magenta, `#ff00ff`), not eliminated by the code.
- **thresholds are `[UNMEASURED]` as constants** (`keyGroundInnerThreshold=48`, `keyGroundOuterThreshold=110`, `dynamic_adapter.go`) — derived from the interim ground-colour regeneration's observed model drift (~17 Euclidean RGB units off a requested hex), not yet from a magenta-keyed generation. Tune from the first real output and date the change.
