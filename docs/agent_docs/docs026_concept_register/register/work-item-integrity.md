### WII-005 — Work-item dedup index + two-strike anti-churn rule
- **status:** deployed
- **status-evidence:** running_notes_15(12) Part 8: "Key enabling discovery (insertWorkItem …): a built-in two-strike rule."

### WII-011 — Completion-verifier failure policy (`VerifierPolicy.FailOpenOnError`, fail-CLOSED default)
- **status:** **LIVE on chassis `v1.0.1268`, pod-verified on BOTH replicas 2026-08-08 — and the fail-closed branch is NOT YET EXERCISED.** Deployment is proven; behaviour is not, and the two must not be run together. Owner ruling on `architecture_review/RFC_017`, taken on a measurement, not an argument.
- **status-evidence:** **Pod-grep, both replicas, one exec each, with a negative control** (`bugs_open/153`): positives `fails closed (RFC_017)` = 1, `blocking completion (fail-closed)` = 1, `failing OPEN by explicit policy` = 1, `verification_unavailable` = 1; **negative** `failing open` (lowercase — the removed spelling) = **0**. The needle discriminates: `failing open` appears **twice** in the pre-change source (`git show 1c5d9ceb5^:…complete_work_item_verification.go` lines 64, 87) and **zero** times at HEAD. ⚠ **Honest limit — the "before" half is SOURCE-derived, not binary-derived:** the whole fleet is uniformly `v1.0.1268` (43 pods, checked), so no pre-roll chassis binary remained to read the needle at 1 on. The pre-roll baseline should have been taken before the roll and was not. Build/test evidence: `go build ./...` clean, `go test ./platform/orchestration/actions/...` green, and **mutation-proven** — restoring the old behaviour (`}, policy.FailOpenOnError` → `}, true`) fails `TestVerificationDecision` on exactly the two rows that encode the ruling (*"verifier error fails CLOSED by default"*, *"error beats a resolved result returned with it"*) and passes again on restore. That branch previously had **no test at all**, being reachable only through a live `*sql.DB`; extracting `verificationDecision` pure is what made the ruling assertable.
- **what is still UNPROVEN, stated so nobody reads the line above as more than it is:** the gate demonstrably ran post-roll — one `hardcoded_section_colors` item verified at 18:58:44Z, 63 seconds after the pods came up — but it returned `Resolved:true`, so **no error has been raised since the roll and the fail-closed branch has never executed in production.** That is expected rather than worrying: the error path has fired **twice in the registry's entire life**. Proof needs the absent-target case to recur; the recipe is in verify-later.
- **what:** The `ItemVerifier` registry's answer to *"the verifier could not run"*. Before this, **every** registered verifier failed **OPEN** — an error stamped the item `complete` and recorded the error under `result._verification`, a policy stated in a doc comment and inherited by all 8 verifiers. Now the registry fails **CLOSED** by default: an error routes the item into the attempt machinery (`attempt_count+1` → `triaged`, `failed` at max) exactly as a persisting defect does. `RegisterVerifier(itemType, v)` keeps its signature and silently becomes the safe registration; the old behaviour is reachable only via `RegisterVerifierWithPolicy(t, v, VerifierPolicy{FailOpenOnError: true})` — **an opt-in field with the unsafe default OFF**, per the owner's 2026-08-02 shared-seam ruling, because the previous authority was licensed by a comment that no reviewer of a calling check could see. `GetVerifier` now returns `(ItemVerifier, VerifierPolicy)` so a caller cannot consult the verifier while forgetting the terms; the zero policy is the safe one, so an ignored return value lands safe. **No verifier opts in today** — the flip is universal on purpose, and an opt-in must be argued at its registration site.
- **why (the measurement that decided it, RFC_017 §"The missing number"):** fail-open's stated justification was *"discovery re-detection + two-strike is the backstop"*. Over the registry's whole life the error path had fired **twice** (2 of 11 consultations ever), both on `empty_section`'s absent-target branch, and on **both** the page still declared the slot in `pages.sections` — so `Resolved:false` was the honest verdict, both items were stamped `complete` at `attempt_count` 0, and five days later **no re-detection had followed** although `findEmptySections`' own predicate still matched the components. The backstop missed the only two cases it was ever asked to catch. **Zero of the errors were infrastructural** — the transient-DB-blip case fail-open protects against has never once been observed.
- **collateral fix, and it is not cosmetic:** the blocked-completion message was hard-coded to *"post-fix verification found the defect still present"* and read its text from `payload["detail"]`. Once an error can block, that sentence records a finding the verifier never made — and on an error payload (whose text is under `"error"`) it would have come out **empty**. `blockedCompletionReason` now returns a distinct message and reason code per cause: `verification_unavailable` vs `verification_failed`. The stored payload also gains `fail_open`, so a future census can tell a completed error from a blocked one; the census that produced RFC_017 read exactly this column and could not.
- **the unparseable-spec branch takes the same policy, deliberately** — it is the same class ("verification could not run"), and exempting it would have left a second silent completion path behind the one this closes.
- **blast radius, enumerated rather than asserted (council `guardian` seat's `missing`, corrected after the round):** 34 error returns exist across the 8 verifiers. Most are infrastructural or malformed-input (DB error, scan failure, a spec with no `page_id`/`component_id`/`site_id`) — and for those, fail-closed's retry is the *correct* response. The deliberate "target absent → cannot distinguish a fix from a loss" branch, the one this flip actually re-aims, is on **4 of 8**: `check_empty_sections.go:411`, `check_truncated_component.go:271`, `check_content_duplication.go:631` (page gone), `check_page_canonical_collision.go:382` (site gone); `check_phantom_internal_links_fragments.go:284` is adjacent. **The submission said "2 of 8" and that was wrong by half** — grepped for the one spelling already read, not for the class. Consequence to expect after the roll: a `content_duplication` item whose page is genuinely deleted, and a `page_canonical_collision` item whose site is genuinely deleted, will now burn their attempts rather than complete.
- **LANDMINE (the reason this entry exists):** a `result._verification.status='error'` row **used to be a COMPLETED item, not a caught one** — annotated, honest-looking, and completed anyway. Any doc, query or belief formed before 2026-08-08 that reads an error row as "the gate stopped something" was wrong then and is right now, which is the worst possible way for a fact to change. Check `fail_open` on the payload, and check the item's own `status`; never infer the outcome from `status='error'`. Full entry in `LANDMINES.md`. ⚠ **`fail_open` dates ERROR rows only** — it is written on the error branch alone, so a `verified` or `defect_persists` payload carries no era marker in either era, and the first post-roll row (18:58:44Z, `verified`) duly has none. To date a non-error row, use the item's `updated_at` against the roll, not the payload shape.
- **operational consequence, named because it is a real cost:** with this live and `empty_section`'s verifier unchanged, its absent-target case now blocks → the item returns to the queue → the handler **rebuilds the page again, up to `max_attempts` (3)** → `failed`. For a structurally-unanswerable check that is three wasted rebuilds before a human sees it. The cheap remedy is per-verifier and already specified in `bugs_closed/032`'s "stronger option" (ask whether the page still declares the slot, return `Resolved:false`) — owned by `empty_sections_loop_integrity`, told 2026-08-08. RFC_017's option 3 (a third `Indeterminate` outcome that parks without burning attempts) remains the structural answer and was explicitly NOT taken; the owner chose the cheap reversible flip first, with the retry cost as the evidence that would justify the bigger change.
