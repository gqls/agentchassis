### WII-005 — Work-item dedup index + two-strike anti-churn rule
- **status:** deployed
- **status-evidence:** running_notes_15(12) Part 8: "Key enabling discovery (insertWorkItem …): a built-in two-strike rule."
- **what:** `idx_swi_dedup` is a partial UNIQUE(site_id,item_key) over non-terminal statuses only — terminal rows are excluded so a completed key can be requeued cleanly; ON CONFLICT DO NOTHING is the safe insert idiom. `insertWorkItem` adds an anti-churn brake over the same key, so discovery checks need no anti-churn logic of their own. A non-terminal flag (needs_human_review) deliberately holds the dedup slot, preventing re-trigger loops. Same rule as the work-dispatch register's WDS-007, described here from the dedup-index angle.
  **⚠ UPDATED 2026-08-23 (bugs_open/326) — the brake's two arms USED TO LOSE THE REQUEST, and this entry described that as normal.** It read: "an item_key with ≥2 terminal attempts in 7 days inserts as `unresolved`; <3h after a terminal item is suppressed". Both halves were accurate and both were defects: `unresolved` is in `workItemTerminalStatuses` AND absent from `workItemDispatchableStatuses`, so those rows were born undispatchable and outside the dedup index (**635 of 747** live `unresolved` rows carried the brand on 2026-08-23); and "suppressed" meant `return workItemWrite{}, nil` — no row, no error, and a caller-visible value identical to a genuine dedup, which is how a re-submitted customer build reported COMPLETED and queued nothing. **Both arms now DEFER**: the row is written at the requested status with `retry_after` set (window-remainder for the <3h arm, `maxBackoffMinutes`=720 for the two-strike arm), honoured by the claim, the dispatch loader and the completion verifier through the single renderer `workItemRetryNotPendingSQL`. The brake is unchanged in effect — nothing dispatches inside the window — and strengthened, because a deferred row now holds the dedup slot. No status list or index predicate changed. Kill switch `DISABLE_ANTI_CHURN_DEFERRAL` ships armed and restores the former behaviour exactly. `workItemWrite` gained `Deferred`/`DeferredUntil`/`PriorAttempts`, surfaced by `create_work_item` as `deferred`/`retry_after`/`prior_attempts`, so "your work is queued" and "your work was held back" are finally distinguishable.
  **The classification the brake depends on is `workItem.recurrenceExpected`, and it is opt-in** — an ACTION REQUEST (stage handoff, re-render request, re-submission) must set it; a DETECTED DEFECT must not. Silence opts IN to the brake, which is how this defect reached production twice (bugs_closed/024, then bugs_open/326 on a pipeline 024 never touched). **19 of 21** live keyed `create_work_item` steps had never declared either way on 2026-08-23; see WII-027 for the audit that now names them, and migration 572 for the five build-chain handoffs.
- **sources:** running_notes_15(12).md#part-8; HANDOFF_page_pipeline(11).md#schema-gotchas; RUNBOOK_linking_phantom_fixes(7).md#5
- **relations:** item_key canonicalization (WII-004); two-strike rule (work-dispatch register, WDS-007); sectionless durability stack (page-build-pipeline register, PBP-017); the undeclared-classification audit (WII-027); retry cooldown machinery (WII-024's failure-write contract, whose `maxBackoffMinutes` bound the two-strike deferral reuses)

- **what:** `fail_work_item` has always taken `error_message` as a config LITERAL — resolved through no path and no template, deliberately, so a message could not be mistaken for a data reference. That is sufficient for a refusal describing a FIXED situation ("tool-improver produced a structurally-collapsed component") and insufficient for one whose job is to report the OFFENDING VALUE. `error_message_template` is rendered with `text/template` over the run's `collected_data`, so a refusal can say *which* key was wrong and not merely which FIELD to go and look in — which is what owner ruling D1 (bugs_open/440) asks for. Absent, the code path does not run at all.
- **both failure modes are LOUD, and that is the design:** a refusal message is read by a human deciding what to do with a parked item, so a message that renders WRONG is worse than one that renders plainly. (1) `Option("missingkey=error")` is set, so a path that is not there is an error rather than a shrug. (2) A key that is PRESENT but nil is not caught by `missingkey` — `text/template` renders it as `<no value>` — so that is guarded explicitly; a refusal reading `routing_reason = '<no value>'` would send a reader hunting for a key that is not the problem. This is the trap `git_deployer_commit_message_test.go` already carries a regression test for. Both fall back to the static `error_message` **and file an `agent_error_log` entry** (`FAIL_WORK_ITEM_MESSAGE_TEMPLATE_FALLBACK`, severity `warning`) — its own code, because it answers "the message a human is reading is the FALLBACK, not the intended one", and nothing failed: the item parked correctly. Falling back silently would make a degraded message indistinguishable from the intended one.
- **⚠ the landmine is the CONFIG DECLARATION, not the template.** `ActionInputSpec.checksConfig()` is `CheckConfig || len(ConfigKeys) > 0`, so `fail_work_item`'s unknown-key detector had been **OFF for the whole of its life** (`UnknownConfigKeys` returning `checked=false`): `error_message` and `status_override` are read straight from `StepConfig.Config` and were declared nowhere. Declaring ONLY the new key would have ARMED `UnknownConfigKeys` against those two and emitted *"Step config carries keys this action does not read — they are silently ignored at execution"* about keys the action demonstrably reads — a detector making a true statement about the new key and a FALSE one about the old ones, on all 7 live steps. **All three are declared in one move.** `StrictConfig` stays unset, so an unknown key here warns rather than rejecting a live workflow — with it set, arming the detector would have taken live agents down instead of logging at them. General form in `LANDMINES.md`.
- **`ConfigKeys` costs nothing against the RFC_022 optional-key budget** — `cmd/config-key-audit/optionalbudget.go` excludes it by design ("ConfigKeys is deliberately NOT counted"), and the budget audit reads 0 shared actions over N=10 with this change in the tree.
- **mutation-proved, both run and observed failing rather than asserted:** drop `error_message` from `ConfigKeys` → the config test fails naming it on the live step shape; delete the `<no value>` guard → the present-but-nil test fails. The absent and present-but-nil cases are required to fail through DIFFERENT mechanisms (`missingkey=error` vs the guard) so that deleting one cannot be masked by the other — the first draft of that test collapsed the two states in its helper and passed for the wrong reason.

### WII-039 — a retraction may be made CONDITIONAL on a receipt: `ResolvedFinding.Receipt`, and the first consumer is the section-source drift closer
- **status:** **LIVE IN CODE 2026-09-03** (committed; inert until the next chassis roll — Go changes do not take effect until an image is rebuilt). One consumer in the same commit: `check_section_source_drift`. Council submission `009fabca-71c8-4f7b-9b23-f0b6605eb531`. **NOT RFC_022-exempt and I am not claiming it is** — the field is opt-in with the unsafe default OFF, but a live consumer names it in the same commit, so the third condition fails; ordinary council gate on the 2026-07-29 §1 test (it changes no guarantee an existing caller relies on, and ADDS one for callers that opt in).
- **what:** `CheckResult.Resolved` (RFC_010, WII-0xx) lets a discovery check close items it has POSITIVELY re-observed as fixed. Its safety property is that a retraction fires only on a positive observation — necessary, and **not sufficient for one class of check**. For a DIVERGENCE check, *"the finding no longer reproduces"* and *"the damage completed"* can be **the same observation**: `check_section_source_drift` files "the authoritative section list disagrees with `pages.sections`; the next build will overwrite the cache", and when the build duly does so, the two stores agree again — the finding stops reproducing precisely BECAUSE a human's composition was destroyed. A retraction on agreement alone would close, automatically and fleet-wide, exactly the cases that most need a human. `ResolvedFinding.Receipt *WorkItemSpec` makes the record of what was destroyed a **precondition** of the close: `resolveWorkItems` writes it FIRST, in the SAME transaction, and refuses the retraction if it can neither insert it nor confirm an open row already holds its key. `ResolvedFinding.Evidence map[string]interface{}` merges into the closed row's `result` jsonb so a machine close and a hand-written migration close record the same shape.
- **the rule it enforces, stated once:** **a check may retract a finding whose resolution DESTROYED something only by recording what was destroyed, in the same transaction.**
- **⚠ IT IS ON THE SEAM, NOT IN THE CHECK, AND THAT IS THE POINT.** `resolveWorkItems` has **2** callers as of 2026-09-03 (`discovery_checks.go:274`, `work_item_retraction.go:230`); a control in either caller protects only that one. The owner's 2026-08-02 ruling is why it is a field rather than a documented convention — *"a comment is not a control on a tree this many sessions share"*.
- **`!inserted` is CONFIRMED, never assumed.** `insertWorkItem` returns false for several different reasons — an open row already holds the key, the anti-churn brake held it back, the two-strike rule dropped it — and only the first means a durable record exists. Assuming it would turn a DROPPED receipt into a silent close, which is the exact hole the field exists to fill.
- **`Evidence` is appended CONDITIONALLY (`|| $7::jsonb` only when non-nil)**, so the six-argument `UPDATE` every existing caller's test asserts is byte-identical. A regression guard pins both directions (`TestEvidenceIsAppendedOnlyWhenSet` / `...LandsInResultWhenSet`) — appending it always-with-NULL would break other lanes' tests in a change they never asked for.
- **`WorkItemSpec.RecurrenceExpected`** is added in the same move (mapped by the new shared `workItemFromSpec`), because a SECOND loss on the same page is a second EVENT, not a repeat: without it the anti-churn brake drops or brands the re-file. Same reasoning as `page_divergence_overwritten`'s.
- **mutation-proved, run and observed failing rather than asserted:** 11 mutations of the check and 4 of the seam, each applied by script, each killing a NAMED test, source restored and diffed byte-identical. **One of the four SURVIVED first time** — deleting the receipt-insert error return left its test green because the flow fell through to the `!inserted` arm whose unmocked SELECT errors too, so a **guard in SERIES** did the work. The property held; the test's claim to pin that line did not. The test now asserts the specific message. Recorded because "the mutation passed, so the line is fine" is the wrong reading.

### WII-040 — `section_composition_lost`: the receipt for a divergence that resolved by DESTROYING a page's composition
- **status:** **LIVE IN CODE 2026-09-03**, inert until the next chassis roll. Filed ONLY by `check_section_source_drift`'s retraction path, and only ever in the same transaction as the retraction it justifies (WII-039). Zero rows on the estate at the time of writing — the backlog was cleared by migration `753` the same day.
- **what:** a flag-only `needs_human_review` item, **no handler**, recording that a `section_source_drift` finding resolved *against* the cache: sections `pages.sections` held at filing time, which the authority did not name, and which are absent from the page today. Key `section_composition_lost:<page>:<sha256[:12] of the ordered lost multiset>`, so distinct losses are distinct findings while an identical repeat dedups; `RecurrenceExpected` is set because a rescue-then-re-loss is a second event (`gripper-spec-sheet`'s actual history: added 2026-07-24, destroyed, rescued by migration `154`, destroyed again).
- **⚠ THE TEST IS `lost`, NOT `direction`, and the distinction is why the receipt is trustworthy.** Migration `753` classified by hand with a three-way equality (`cache_held` / `authority_won` / `third_list`). That LABEL cannot separate two real cases with opposite meanings: on `oufe.com/contact` the authority **restored** a section the cache had dropped (`authority_won`, nothing destroyed); on `robot-hands.com/gripper-catalog` it **deleted** one (`authority_won`, a live section gone). `direction` is still recorded on every close, byte-compatible with `753`, because LANDMINES tells readers to query `result->>'direction'`.
- **⚠ `lost` subtracts the MERGED list, not the raw cache.** A human-locked row the plan never names sits in the frozen cache and not in the frozen authority, so it lands in the cache-only set — and it is still on the page. Against the raw list it would read as lost, and this check would file a **false destruction receipt on every locked page on the estate** (13 fleet-wide when LOCK-008 shipped).
- **⚠ MULTISET, not set.** One live plan names `generic-text-block` **six** times on one page (`[MEASURED 2026-09-03]`). A set difference reports "nothing dropped" when six become five.
- **it COPIES its evidence, it does not point at it.** The drift row it justifies is closed in the same transaction and `site_work_items` is a ROLLING WINDOW, so a receipt holding only `drift_item_id` would resolve to nothing exactly when someone finally came to read it. The spec carries both frozen lists, today's list, the lost/gained multisets and `history_rows_for_lost_sections`.
- **what it can and cannot promise about recovery, because these are different claims and collapsing them is a real error:** the lost section's **BYTES** are recoverable when it had rendered — migration `357`'s trigger pair archives every deleted `page_components` row with `slot_name`, `position` and `rendered_html` (24 rows for `gripper-spec-sheet` alone, `[MEASURED 2026-09-03]`). The **LIST** is archived NOWHERE: every rebuild deletes every row, so `pages_sections_at_filing` on this receipt is the only surviving record that the page held those sections in that order. That asymmetry is why this receipt exists rather than a second archive table.
- **NO VERIFIER, and it can never have one** (classified `catJudgement` in `verifier_coverage_test.go`): the only mechanical re-observation is "the section is back", and its negation is equally "the removal was intended and accepted" — both are valid endings (`bugs_open/469` §5.1; of the two 2026-09-03 cases, the `idea.uk` lane judged theirs a benign rename and the `robot hands` lane confirmed theirs as damage with owner-backed provenance). A verifier would fail-closed on correctly-resolved items for ever.
- **the detection half, which is the only part acting BEFORE the loss:** the drift item now grades by consequence — `would_drop` / `would_add` / `would_drop_present` in the spec, severity `high` only when the sync-down will drop a name the page currently carries, and the summary leads with it. `would_drop_present` is deliberately not named `..._deployed`: the projection carries no `build_status`, so a `removed` row still matches (56 of 3,333 rows, an over-grade in the safe direction), and the check must not claim a measurement it did not make. `slot_name` is NULL on **0** of 3,333 rows, so the name match has no silent under-report.
