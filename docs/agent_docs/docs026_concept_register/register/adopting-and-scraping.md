### SCR-002 — Fetch-recorded provenance (`datahelpers.ExtractFetchProvenance`)
- **status:** built, inert until the chassis image rolls
- **status-evidence:** committed `2ebabf2ca` 2026-07-28 with tests; `platform/orchestration/datahelpers/fetch_provenance.go`. Not yet exercised by a live run — vet collection has been off since 2026-03-18.
- **what:** A shared reader that pulls `{SourceURL, SourceName, SourceType, CapturedAt}` out of a webscrape result, so a writer records where data came from **from the fetch record** rather than asking the LLM that produced the data. Every webscrape provider result already carries `url` + `captured_at`, set beside the HTTP call; this is the reader nobody had. Returns a `found` bool — an unreadable fetch record is a wiring fault to surface, never permission to store an observation unsourced. Accepts six response shapes because the adapter→coordinator chain has several unwrap points and a single-shape reader FAILS OPEN.
- **why it is callable by others:** any vertical that stores scraped observations (not just business-intel) can call it; the alternative each of them would otherwise write is "ask the model for its source", which is the rejected pattern.
- **sources:** bugs_open/100; docs024_key_docs_latest/bugfix_100_101_scrape_provenance/
- **relations:** `business_intel.data_observations` writer (business-intel-collection.md); the AI-asserted-claim remediation class (bugs_closed/043, bugs_closed/061); SQL 257 (the `NOT VALID` CHECK that makes the unsourced state unrepresentable)

### SCR-003 — Declared config-key contract + unknown-key detection (`ActionInputSpec.ConfigKeys`)
- **status:** deployed (live on chassis v1.0.1192); **58 of 152 actions adopted** as of 2026-07-28 evening — was 1 until `CheckConfig` landed. Read the live number from `scripts/audit-config-keys.sh`, not from this line
- **status-evidence:** committed `2ebabf2ca` 2026-07-28; `platform/orchestration/datahelpers/action_inputs.go` (`UnknownConfigKeys`, `IsStrictConfigAction`, `ListDeclaredConfigKeys`), wired in `platform/validation/workflow.go`. Live audit run **2026-07-28 ~19:15Z** reported 1 declared action, 208 undeclared, 726 undeclared (action,key) pairs; **re-run ~20:55Z after `CheckConfig`: 58 declared, 152 undeclared, 571 pairs.** Both figures are dated because this one moves.
- **what:** An action declares the step-config keys it actually reads; the workflow validator — the only place that sees an action name and its config together on every run — then reports keys the action does **not** read, instead of the runtime silently ignoring them. **Three states, not two** (`ConditionalKeys` added 2026-07-28 after the council's `editquality` seat caught the gap): *unknown* · *recognised* · *recognised but honoured only under a stated condition*. The third exists because declaring a key was itself a way of hiding it — see the CORRECTION on SCR-004. `StrictConfig` escalates the warning to a hard validation refusal once a contract is known complete. Opt-in per action by design: 811 distinct (action,key) pairs across 228 live actions make a fleet-wide allow-list a guess at scale, and an over-strict validator is a worse defect than the inert key it chases. `UnknownConfigKeys` returns a `checked` bool so "declared and clean" can never be read as "never examined". Extends the pre-existing spec registry (134 registrants, previously read by nothing but a parity test) rather than adding a second one.
- **UPDATED 2026-07-28 (evening) — `CheckConfig`, and why adoption was 1/152 rather than "slow".** Opt-in was gated on a non-empty `ConfigKeys`, a field that means something specific: *settings rather than references*. For the large class of actions whose every key is an `ExtractActionInputs` field, there was **no honest way to opt in** — you had to duplicate keys into a list they do not belong in, or misdescribe a reference as a setting. The cheapest correct action was to do nothing, and 151 actions did. `CheckConfig bool` now says only *"check me"*; the recognised set (`Required ∪ Optional ∪ ConfigKeys ∪ Deprecated`) is unchanged. **Prefer `CheckConfig` when the action passes its own spec to `ExtractActionInputs`** — that extractor reads `config[k]` for every `Required`/`Optional` key, so the spec is already a verified statement of what the action reads and opting in asserts nothing new. The three separate `len(ConfigKeys)==0` tests (runtime, strict-mode, offline audit) are now one method, `checksConfig()` — three chances for the runtime check and the audit to disagree about who is covered was itself the drift class this tool detects.
- **why it is callable by others:** any action author can opt in with one field and get typo/staleness detection for their step config; this is the general answer to the recurring "config that lies" class (bugs_closed/042, bugs_closed/127, bugs_open/101). **The one-line form is now `CheckConfig: true`** for the common case.
- **sources:** bugs_open/101 fix candidate 1; docs024_key_docs_latest/bugfix_100_101_scrape_provenance/
- **relations:** `registry_parity_test.go`; 016b §9 *"A registry that everything registers with and nothing reads"*; SCR-005 (what made the batch opt-in scopable)

### SCR-004 — Config-key coverage report (`scripts/audit-config-keys.sh`, `cmd/config-key-audit`)
- **status:** built and exercised (read-only; needs cluster access + `go run`)
- **status-evidence:** run against the live fleet 2026-07-28; found a fifth inert key (`add_protocol` on `domain-research-classifier/scrape_site`) that `bugs_open/101` had not identified.
- **CORRECTED 2026-07-28 (same day):** this entry originally read *"It now reports zero unknown keys and 208 undeclared actions"* as though the zero were a result. **It was not** — it was zero partly because the entry's own author had just declared the offending keys, which made them *recognised* and silenced the report on two live steps that still advertise a crawl `/scrape` cannot perform. Caught by the council gate's `editquality` seat, logged in `WRONG_CALLS.md` 2026-07-28. The report now carries a third **CONDITIONALLY HONOURED** section and, when UNKNOWN KEYS is empty while conditional keys are present, says in terms that "none" does not mean "no step misdescribes itself".
- **what:** Offline half of SCR-003. Asks the **binary** what each action declares (the declarations are Go, registered by `init()`; a source grep would quietly disagree with the running code) and joins that against every live `agent_definitions` step config. Reports **UNKNOWN KEYS** (action declared its contract, key is not in it — a real inert key) separately from **UNDECLARED ACTIONS** (not opted in, so nothing is known and nothing there is evidence of a bug), because the fix differs and conflating them makes the report unactionable. `--json` for the full machine-readable list; the text listing's cap is labelled a display limit, not a filter. **Fourth section added 2026-08-03 (`bugs_open/134`): SUSPICIOUS KEYS** — `cmd/config-key-audit --suspicious-keys` flags any live step-config key NAME carrying doc-notation punctuation (`?`, `*`, `:` or a space), walked with `validation.WalkSteps` so loop sub-workflow steps are covered, **independent of opt-in** — the one section that can speak about the ~150 undeclared actions, where 134's `category?`/`limit?` sat invisible for six weeks. Deliberately narrow character set so a finding is always signal; exit 1 on findings, exit 2 refusal over an empty export.
- **why it is callable by others:** it is the adoption ratchet for SCR-003 and it answers "is this config key real?" for any action, for anyone, without reading Go.
- **the number, dated because it moves:** **208 actions / 726 pairs undeclared, 1 declared** (2026-07-28 ~19:15Z) → **152 / 571 undeclared, 58 declared** (same evening, after `CheckConfig`). Read it from a run, not from this line.
- **sources:** docs024_key_docs_latest/bugfix_100_101_scrape_provenance/RUNBOOK_scrape_config_and_provenance.md

### SCR-005 — Config-key ADOPTION report (`cmd/config-key-audit --specs`)
- **status:** built and exercised (read-only; `go run`, no DB, no cluster)
- **status-evidence:** run 2026-07-28; produced the 56/34/85/30 split that scoped the batch opt-in in commit `ce9e28784`, which moved SCR-004's gap from 208 actions to 152.
- **CORRECTED 2026-07-28 (same evening, before it could mislead anyone):** first shipped as a SECOND BINARY, `cmd/config-key-coverage`. The council gate's `editquality` and `reuse_agent` seats objected to that independently (corr `07cf67c6`) — same registry API, same struct, same init-side-effect import, overlapping question — and they were right; *"two code paths independently solving overlapping problems that nobody unifies once both exist"* is a named failure pattern here. Folded into the existing tool as a **`--specs` flag** and the second binary deleted. **The default output is unchanged**, verified by re-running `scripts/audit-config-keys.sh` (its only consumer) and by diffing `--specs` against the deleted tool: 152 actions, **0 differing on any spec field**. The verdict was APPROVED — this was not owed, and doing it anyway is the point of an advisory objection.
- **what:** `--specs` dumps the **full** `ActionInputSpec` of every registered action as JSON — `required`, `optional`, `config_keys`, `deprecated`, `opted_in` — where `cmd/config-key-audit` dumps only the declared key set. Two MODES because they answer two questions: the default asks *"who has opted in?"*, `--specs` asks **"who is one line away?"**. `opted_in` is read from `ListDeclaredConfigKeys` membership rather than recomputed, so the flag cannot become a fourth copy of a gate that until today had three. Joined against `scripts/audit-config-keys.sh --json`, it classifies every undeclared action into: spec already covers every live key (safe one-line opt-in) · spec exists but misses live keys (needs reading) · no spec at all. Cross-referencing which of those files actually pass their spec to `ExtractActionInputs` separates *verified by construction* from *needs a human*. Refuses to print an empty object, for the same reason its sibling does: a dropped blank import would read as "nothing is declared" rather than failing.
- **why it is callable by others:** the expensive part of the coverage ratchet is proving what each action reads, and declaring a key an action does **not** read is worse than declaring nothing — it silences the detector for a dead key (`WRONG_CALLS.md` 2026-07-28). This is what makes the remaining ~152 tractable in batches instead of one hand-read action at a time, and it is the thing to run before claiming any action is or is not covered.
- **sources:** commits `ce9e28784` (built) + the consolidation commit; docs024_key_docs_latest/bugfix_100_101_scrape_provenance/NOTES §15-16
- **relations:** SCR-003 (`CheckConfig`), SCR-004 (the gap it drives down)

### SCR-006 — Deprecated aliases for LITERAL config settings (`ActionInputSpec.DeprecatedConfigKeys`, `datahelpers.ResolveConfigSetting`)
- **status:** ~~built, adopted by 4 actions, **inert until the next chassis roll** (Go change)~~ → **CORRECTED 2026-08-09: LIVE, runtime-witnessed, and the migration list it exists to drive is now DRAINED.** In the binary since v1.0.1267 (pod-grep, both controls, enumerated by image not label); behaviour witnessed in production on v1.0.1268 with a value that could have come out otherwise (`bugs_open/136` §11); and as of migration 349 **no live definition carries any of the three old spellings at any depth** — `scripts/audit-config-keys.sh` reports `DEPRECATED KEYS: none` alongside `UNKNOWN KEYS: none`. The aliases stay DECLARED and that is deliberate: they are the net for snapshot replays and stragglers, so an empty DEPRECATED section is the mechanism succeeding, not evidence it is unused.
- **status-evidence:** committed 2026-08-08; `platform/orchestration/datahelpers/config_key_aliases.go` (new) + the `DeprecatedConfigKeys` field, `UnknownConfigKeys` and `ListDeclaredConfigKeys` in `action_inputs.go`. Live-DB proof that the declarations join real definitions, run against production `agent_definitions` the same day: `scripts/audit-config-keys.sh` UNKNOWN KEYS went **4 → 1** (`execute_vision_prompt.ai_service`, `run_discovery_checks.check_domain`, `triage_detected_items.target_domain` cleared; `plan_sections.domain` deliberately left, it is a genuinely dead key on a hot agent), and the new DEPRECATED section names `create_work_item.item_domain`, `run_discovery_checks.check_domain`, `triage_detected_items.target_domain`. Each of the five guards was proven by MUTATION — break the rule, watch the named test fail, restore.
- **what:** A spec can declare that an old config key is an alias for a current one — `{"check_domain": "check_pipeline"}` — and `ResolveConfigSetting(config, spec, key, default, logger)` honours it at the action's own read site, warning when an alias supplies the value. **The estate already had `Deprecated`, and it does NOT cover this**: `Deprecated` is honoured only by `ExtractActionInputs` Strategy 3, which resolves the old key's VALUE as a dot-path into `collected_data`. That is a *reference* alias (`site_id_field` → `site_id`). A *setting* — a key whose value IS the value, read straight from `params.StepConfig.Config`, which is what `ConfigKeys` means — put into `Deprecated` would send the runtime looking for a `collected_data` key called `"content"`, find nothing, and take the default while the declaration read as wired. So an author renaming a setting had two options, hand-roll Go or do nothing, and of the three actions carrying the `domain` → `pipeline` rename, **one hand-rolled it and two did nothing**. Precedence is byte-for-byte the shim it replaces: canonical key → declared old names (sorted) → default; a non-string value under any name is absent, pinning the `.(string)` semantics every call site already had. Deliberately does **not** gate on `checksConfig()` — `create_work_item` carries an alias on nine live steps and has never opted into unknown-key detection, and coupling the two would make the mechanism's largest real user invisible (the same argument already written on `SingleOwner`).
- **why it is callable by others:** any action that renames a step-config setting can now keep the old name working, in three declared lines, and have the audit list the definitions still using it instead of the rename half-landing in silence. Reporting is the other half: `UnknownConfigKeys` recognises alias keys (calling one "unknown" would be false — the action does read it) and `scripts/audit-config-keys.sh` prints them in a new **DEPRECATED KEYS** section that does not affect the exit code, because they are wired. Without that section, declaring the alias would have *silenced* the detector — the recorded `WRONG_CALLS.md` 2026-07-28 mistake, committed by `bugs_closed/101`'s own fix.
- **the cost of not having it, measured:** `run_discovery_checks` took its `"design"` default for months while all three live callers wrote `check_domain`. Harmless while every check that propagated `dctx.Pipeline` happened to live on the agent whose config said `design` — and on 2026-08-04 two that do (`content_duplication`, `page_canonical_collision`) joined `completeness-discovery-agent`, whose config says `content`, and filed **four rows under `design`**. ~~`countDispatchableWorkItems` filters on `pipeline`, so a row under the wrong one is invisible to the count that should see it.~~ **CORRECTED 2026-08-09 — that last sentence is FALSE and this entry carried it for a day; it was refuted by `bugs_open/136` §6 on 2026-08-08, in the bug this entry cites.** `countDispatchableWorkItems` has exactly one caller (`triage_detect_items_action.go:189`) and the sole live carrier passes `"build"`, so rows under `design` and under `content` are **equally** invisible to it — the query cannot discriminate the two, so it cannot be evidence that confusing them costs anything. **A parameterised filter tells you what a query CAN discriminate, never what it DOES.** The accurate cost is weaker and still sufficient: the labels were correct-or-not by luck, and the first consumer to filter `design` vs `content` would have inherited whatever the default happened to write. Repaired under migration 349 (three rows; the fourth had vanished from the DB before anyone got to it).
