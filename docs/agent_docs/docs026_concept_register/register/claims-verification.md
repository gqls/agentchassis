### CLM-001 — `evidence_base` is a `site_specs` aspect, not a table
- **status:** deployed
- **what:** The per-site fact register lives at `site_specs.aspect='evidence_base'`, one current row per site under a partial unique index (`site_id, aspect) WHERE is_current`. So it is **never UPDATEd in place** — every change is supersede-then-insert in one transaction, carrying `pinned` forward or the row silently loses human-owned status. Shape (`datahelpers/claims.go:97-103`): `audit_doc`, `governing_rule`, `facts[]`, `banned_claims[]`, `allowed_entities[]`, plus a `writer_block` string the parsed struct does not model.

### CLM-002 — `ScanBannedClaims` is an unrestricted case-insensitive regex over prose
- **status:** deployed
- **status-evidence:** function body read 2026-07-27 at `claims.go:284-325` — blocks × patterns, `FindStringIndex`, nothing else.
- **what:** The banned-pattern scanner has **no numeric gating whatsoever**. It matches whatever patterns a site is given, about anyone, numeric or qualitative. Live registers already carry purely qualitative patterns (`leaderboard`, `live now`, `price target`, `years of experience`). Patterns compile as `(?i)`; an invalid regex degrades to a literal substring, so a typo never silently drops a ban. It scans *assertion blocks* extracted from HTML (`extractAssertions`, `claims.go:165-226`), which skips `script/style/head/code/pre` and cannot match across block boundaries.
- **why it matters:** this concept exists because its absence caused a live error. On 2026-07-26 a session concluded that qualitative claims were "invisible to every scanner", and wrote that into a live council seat, having read only the *numeric* scanner beside it. **The capability was never missing.** See CLM-003 for the limitation that was mistaken for a general one.
- **sources:** `claims.go:284-325`, `:121-128`, `:165-226`; `sql_for_agents/226`, `227`; `docs024_key_docs_latest/WRONG_CALLS.md` 2026-07-26
- **relations:** CLM-003 (the confusable neighbour), CLM-010, CLM-011

### CLM-008 — V5: citations survive only if the quote is still literally there
- **status:** deployed; first end-to-end completion 2026-07-27
- **what:** `verify_and_register_citations` re-fetches every cited URL and registers a claim only when its **verbatim quote** is present. The model proposes, the fetcher disposes. Three outcomes are held apart deliberately: quote found → stands; 200 but quote absent → `citation_lost` ("the published claim now rests on nothing"); fetch failed / 403 / PDF → `fetch_error`, **UNKNOWN, never drift** — "a paywall going up is not evidence the fact is wrong". Quote matching is forgiving on presentation (entities, curly quotes, nbsp, thousands separators) and strict on content.
- **status-evidence:** activated on v1.0.1140 (2026-07-20) but its smoke run failed on `bugs_open/047` and was never repeated; **first successful completion 2026-07-27**, 19 citations registered for oufe.com, most from `legislation.gov.uk`.
- **sources:** `platform/orchestration/actions/evidence_citations.go:9-21`; `datahelpers/citations.go:35-49`; `docs024_key_docs_latest/oufe/NOTES_oufe.md`

### CLM-011 — The overclaimed-reliability class, and the line that separates it
- **status:** deployed (2026-07-26/27)
- **what:** A promise about **our own** accuracy is a claim like any other and had never had a pattern written for it on any site. Controls now: a fleet-wide writer rule on both content writers ("never promise accuracy you cannot guarantee"), an `OVERCLAIMED RELIABILITY` contract on the compliance council seat with judge clauses, and tested banned patterns on oufe. The governing line, which generalises: **a site may describe what it DOES; it may not claim what that GUARANTEES.** "We cite every figure and date it" is a keepable process commitment; "a claim without a source does not appear here" asserts a completeness nobody can verify.
- **origin:** oufe.com shipped four such promises live, hours after the owner struck a weaker version of the same slogan.

### CLM-013 — series facts: many dated observations, each independently sourced
- **status:** deployed in `v1.0.1185` (pod-verified 2026-07-28) — **no live site holds a series fact yet**
- **status-evidence:** three distinctive string literals from `claims_series.go` found in the running binary, with a positive control. Added 2026-07-28, after this register file was first written.
- **what:** A fact could hold one `Value` and three dates — `accessed`, `published`, `verified_at` — **all provenance**, none of them the date the value *applies to*. `Observation{as_of, value, source, verified_at}` adds that, under two rules: **every observation carries its own source and never inherits the parent fact's**, and `as_of` is distinct from `verified_at`. `ValidateSeries` fails closed (≥2 observations, valid and unique `as_of`, a resolvable source per point); `numberSupported` gained a series branch, matching exactly even when the fact carries a `gte` tolerance.
- **why it matters:** without a series shape the only options were one fact per year (no series identity, so nothing can plot it and nothing knows a point is missing) or numbers embedded in a claim string, which is invisible to every scanner — the `bugs_open/043` failure mode. And the never-inherit rule is what stops interpolation entering as data.
- **the lesson attached to it:** round 1 of the council review found that `ValidateSeries` enforced the source rule while `numberSupported` never called it, so an unsourced observation still registered its value. **A rule enforced only in a validator is not enforced** — it must hold at the gate that decides. Both now share `observationHasResolvableSource`.
- **sources:** `platform/orchestration/datahelpers/claims_series.go`; `claims.go` (`Observations`, `numberSupported`); council correlation `da40ddf0` round 1

Wired at both enforcement surfaces (CLM-004) so they cannot drift.
- **the two design constraints that shaped it, both of which rule out the obvious mirror:**
  1. **It is NOT unioned into `EvidenceBase` at parse time**, though `voicetells.go` does exactly that for the voice layer. `EvidenceBase` is marshalled **back** to `site_specs` by `refresh_evidence_base_action.go` and `evidence_citations.go`, so seeding `eb.BannedClaims` would silently persist the fleet-wide set into every site's stored register through write paths that never intended to touch it — the trap `claims.go` already documents for `EvidenceFact.Kind`. ### CLM-014 — `cmd/claimscan`: run the live gate's own engine over exported page HTML, offline
- **status:** deployed (committed 2026-07-16), exercised fleet-wide 2026-07-28
- **status-evidence:** `go build ./cmd/claimscan` clean against the shared tree 2026-07-28; used that day for a 15-site / 908-component dry run whose positive control blocked 6 of 6 overclaim shapes and passed 3 of 3 legitimate sentences.
- **what:** An operator CLI that calls **the same shared scan functions as the deploy gate and the post-deploy sweep** (`ParseEvidenceBase` → `ExtractAssertionText` → `ScanBannedClaims` / `ScanUnregisteredNumbers`), against a TSV export of component HTML plus an `evidence_base` JSON file. So you can ask "what would this pattern set flag, on real copy, across any number of sites" **without deploying, migrating, or touching a site**. Prints `BANNED` / `NUMBER` lines and exits 1 when findings exist, so it works as a scripted acceptance gate.
- **why it earns an entry:** this is the tool that answers "measure the blast radius before you submit" for anything touching the claims layer, and it is the only way to test a candidate pattern set against copy other than the site it was written for. **A session on 2026-07-28 was about to build a second one** — it was found only by reading `sql_for_agents/226`'s verify footer to the end, not by grep. That is `bugs_open/106`'s failure mode landing on a tool that already existed.
- **landmines:** (1) the CLI prints the prefixes `BANNED`/`NUMBER`; `banned_claim` is the JSON `check` value and appears nowhere in the output, so grepping for it returns 0 on every site — a false all-clear. (2) An evidence file with `banned_claims` but no `facts[]` makes **every number** an unregistered-number finding; filter to `^BANNED`. (3) Some site copy is non-UTF-8, and plain `grep -c` returns **empty with no error** on those outputs — use `LC_ALL=C grep -ac`. (4) The documented export query uses `kubectl exec -i`, which **eats a `while read` loop's stdin** and silently scans only the first site.
- **UPDATED 2026-07-30 — landmines (3) and (4) both fired again on a session that had not read this entry, and (3)'s stated fix is INCOMPLETE.** Recorded here because the cost was ~15 minutes each time and the failure mode is a *clean scan*:
  - **(3) `LC_ALL=C` is not sufficient in the Claude Code shell.** `grep` there is a shell **function** wrapping `ugrep` with `-I` (skip binary), so a scan output containing one non-text byte returns **zero matches and prints nothing at all — not even `0` for `grep -c`** — with `LC_ALL=C` set or not. Exit code 1, no message, indistinguishable from a clean fleet. The working form is **`command grep -a`** (bypass the function), and the tell that you are in this trap rather than genuinely clean is that **`grep -c` printed nothing**: real grep always prints a number.
  - **(5) NEW — the export itself truncates mid-stream and the short file looks complete.** Two of fourteen sites came back short on one run (`finetuning.uk` 58 of 139 rows, `gamesdesign.co.uk` 30 of 67) with `kubectl` reporting `Copying stdout failed: read message: unexpected EOF` on stderr — which is easy to miss and does **not** make the file empty. A scan of that corpus is clean-looking and wrong. **Assert the row count against the DB per site before scanning, and retry until it matches**: finetuning.uk needed three attempts (77, then 113, then 139). The count query is the same predicate as the export.

A scanner that has gone quiet and one that is broken look identical from outside, so an absent or unrecognised page type stays noisy. A page type nobody has invented yet is scanned too.

### CLM-017 — the negation guard: a banned PHRASE is not a banned CLAIM
- **status:** **committed 2026-07-29** (`116fdffd8`), **INERT until the next chassis roll** — Go change, so the live fleet still runs the pre-guard matcher until an image ships. Council submitted (`8a41e1a5-e670-4e50-a875-f8418ee15738`), verdict pending at time of writing.
- **status-evidence:** dry-run with `cmd/claimscan` (CLM-014, the gate's own engine) over the **full live enforcement surface — 919 components / 14 sites, all `deployed`**, fleet-wide set plus each site's own register: **2 findings, 4 matches suppressed by the guard**, 0 findings on the other 12 sites. 21 unit tests in `claims_global_test.go`. Surface re-derived with `sites.status` **grouped, not filtered** — the gate never reads it.
- **what:** `negatedClaimMatch` in `datahelpers/claims.go`. A banned-claim pattern matches a **phrase**, but what is banned is an **assertion** — "every figure is independently verified" is a fabrication, and "where a figure has **not** been independently verified, that is stated" is the hedged disclosure the whole layer exists to encourage, containing the banned phrase verbatim. At blocker severity the second one fails a page build for being honest. The guard scans backwards from each match for a negation cue and drops the match if it finds one, so a denied claim is not reported.
  - **clause-local, and that is the whole safety property.** The backwards scan stops at the first comma or stronger boundary (`.!?;:,<>` newline, en/em dash), so a negation in a *different* clause cannot launder an overclaim: "we do not use AI, and every claim here is verified" still blocks. Window is 64 bytes; the longest real form measured is 13 ("has not been ").
  - **applies to per-site registers too, deliberately.** One matching rule, not two that drift (CLM-004). **The council raised this at medium from three seats** (corr `8a41e1a5`, round 1) — the per-site lanes never asked for it — and the answer is structural, not just "zero impact today": **all 84 per-site patterns across the 7 sites that have any were enumerated live 2026-07-29. Exactly 5 are negative constructions — the only class the guard could disarm — and all 5 are oufe.com's, all 5 verbatim copies of fleet-wide patterns, and all 5 pinned by `TestGuardDoesNotDisarmTheNegativeConstructionPatterns`** (their negation sits INSIDE the match; the guard only reads text BEFORE it). The other **79 carry no negation at all**, so the guard can only affect them on a page that denies them — the intended behaviour. Measured effect today: **0 suppressions on any per-site pattern across all 919 components**. **Affected consumers, named and told** per owner ruling 2026-07-29 §3: oufe.com (28 patterns — notice in `oufe/NOTES_oufe.md`), leopardessconsulting.co.uk (19), ai-agent-orchestration.com (10), vonc.com (9), relojistas.com (9), fundamentallyai.com (6), finetuning.uk (3). **NOT 9 sites — that was my own submission's error**: 9 have an `evidence_base` row, but robot-hands.com and gamesdesign.co.uk carry facts with **zero** patterns, so they are unaffected.
  - **it changed `ScanBannedClaims` from first-match to all-matches.** Occurrence counts are now of **surviving** matches, so a block that asserts once and denies once reports 1, not 2. A page author's count is no longer inflated by the sentences they got right.
- **the cue list is NARROW on purpose, and the near-misses are the useful part:** `without` and bare `no` are **excluded**, because both appear as intensifiers — "Without exception, every claim is verified", "There are no exceptions: every claim is verified" — and including them would silently disarm a real overclaim. `rarely`/`seldom` likewise ("our data is rarely wrong" is still an accuracy claim). **Known residual, stated rather than guarded:** "no figure here is independently verified" would still be a false positive; no sentence of that shape exists in the live corpus. Contractions are matched as `letter + n't` rather than a stem list, because the stems are irregular (`can't` is ca+n't, `won't` is wo+n't) and a stem list gets one wrong silently; curly apostrophes are included because that is what a renderer emits.
- **the suppression is logged AT THE BUILD GATE, not only in the CLI (added 2026-07-29, council round 1, architecture seat at medium).** The first version made suppression observable only in `cmd/claimscan` — a tool someone has to think to run. That is the `bugs_open/093` shape ("one call site of a shared judgement gets the rigorous fix; the sibling stays heuristic") in a change that cited 093 as a reason to care. `checkBannedClaims` now logs every suppressed match at **Info** with the site, pattern and snippet, so a guard that starts eating real findings shows up in the build log of the page it happened to. Two tests pin it, including that the lever being OFF reports no suppression for a scan that never ran.
- **call sites, enumerated rather than asserted** (the council asked; "the gate" is not singular): **2 in production** — `validate_page_content.go:1012` (V1a build gate, blocker) and `check_unverified_claims.go:405` (V1b post-deploy sweep, high) — plus `cmd/claimscan`. That is the CLM-004 pair and nothing else. **`ClaimFinding.Occurrences` has no branching consumer anywhere**: every use is display-only (a description string, a work-item field, a printf) and there is **not one comparison or threshold** on it in the tree, so counting survivors instead of raw hits is a cosmetic change in the honest direction.
- **the suppression is OBSERVABLE, which is the reason the extra API exists:** `ScanBannedClaimsIgnoringNegation` (the pre-guard behaviour, kept reachable as a control) and `ScanAllBannedClaimsWithSuppressed` (raises + suppressed, the second list derived by **subtraction** so a second guard implementation cannot disagree with the first). `claimscan -show-suppressed` prints them as `negated` lines, never counted as findings. **A silent suppressor and a dead gate are indistinguishable from outside** — this estate has been bitten by that shape repeatedly, and a guard on the strongest pattern in the set is exactly where it would hurt most.
- **THE LANDMINE, and it is about testing, not about regexes:** the test that was supposed to prove negated copy was safe had been **passing for a reason unrelated to negation** — the only pattern matching those sentences had been removed from the set. A pass from a check that cannot fail gets quoted later as "negated copy is handled". Assert the **mechanism**: `TestNegatedCopyIsSuppressedByTheGuardNotByAbsence` fails if the guard is deleted *and* fails (with "VACUOUS PASS") if the pattern is deleted. It caught a real error on its first run — a fixture filed as one of the four negated false positives that contains no negation at all.
- **the second landmine — narrowing a pattern by reasoning can make it INERT.** The restored pattern first shipped subject-anchored (content noun + `is/are` within N chars) to dodge a hypothetical false positive on "our accounts are independently audited". Over 919 live components the anchored form matched **nothing at all** — 0 findings, 0 suppressions — while the bare form found **2 real overclaims**. An inert pattern looks exactly like a well-behaved one. **Dry-run the pattern you are replacing next to the one replacing it**, in the same run.
