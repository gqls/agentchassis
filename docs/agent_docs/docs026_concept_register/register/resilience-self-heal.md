### RSH-001 — Dual-signal self-heal on missing spec dependency
- **status:** deployed
- **status-evidence:** "validate_composition_inputs both loud-logs AND queues a recovery work item on miss... the two-strike rule marks the item unresolved."
- **what:** A general resilience pattern for a Go action depending on a spec aspect that may not yet exist: emit a loud error log AND queue a recovery work item in the same failure path — the log is a durable dashboard signal, and the queued item is a genuine self-heal mechanism, since if it later runs successfully the originally-dependent item auto-redispatches. Repeated failures of the same recovery item accumulate via a two-strike rule into a terminal `unresolved` state rather than retrying forever.
- **sources:** old_design_and_styling/HANDOFF_2026-04-19_design_and_styling_composable_theme_and_site_design_planner_update4(3).md#"1. Status Summary", #"5. Decisions Made This Session" (docs024_archives unit)
- **relations:** site-design-planner Choice B scope; work-item two-strike/wont_fix pattern; composition resolver orphan-rows policy (RSH-002, same composition subsystem)
- **verify-later:** `validate_composition_inputs_action.go` implementation; two-strike rule location in the dispatch loop

### RSH-002 — Composition resolver orphan-rows policy
- **status:** aspirational
- **status-evidence:** "If install fails, those rows become orphans... we extend the existing database-cleanup scheduled task to sweep them. Draft SQL in draft_composition_orphan_cleanup.sql."
- **what:** Because the palette/typography_set resolvers each commit in their own transaction before `install_site_composition` runs, a failed install leaves orphaned rows behind. The accepted design tolerates this — low-cost orphans are allowed to occur and are swept up periodically by an extension to the existing `database-cleanup` scheduled task, rather than adding cross-resolver rollback/transaction coordination.

### RSH-003 — Retry-as-replay: an awaited request is re-sent, never rebuilt
- **status:** deployed (chassis v1.0.1193, migration 263; landed 2026-07-28)
- **status-evidence:** `awaited_requests.request_payload jsonb` live on clients_db; `RETRY_PAYLOAD_UNAVAILABLE`/`RETRY_SELF_ADDRESSED`/`MISROUTED_REQUEST` present in the v1.0.1193 binary and the deleted `is_retry` stub absent from it (present in v1.0.1192 — positive control).
- **what:** The platform-wide contract for retrying a timed-out awaited request. A sending action (`spawn_agent`, `call_agent`, and `spawn_remote_agent` via the same helper) records the exact `producer.Produce` arguments under the reserved result key `types.RetryPayloadKey`; `createAwaitedRequest` lifts it onto the awaited request and `InsertAwaitedRequest` persists it to `awaited_requests.request_payload` (deliberately `json:"-"` on the struct so it never enters the hot `orchestration_states.awaited_requests` JSONB). On timeout `handleRecoverableError` **replays** that message via `RetryPayload.ReplayRequest`, which re-stamps only `retry_version`, `message_id` and `timestamp` and regenerates the Kafka headers from the replayed message so headers and body cannot disagree. **The invariant: a retry differs from the original in those three fields and nothing else.** With no recorded payload the coordinator REFUSES to retry rather than synthesising one. **The landmine this exists to prevent:** the previous code rebuilt the retry from the *awaiting* orchestration's own state, so every retry carried the PARENT's `orchestration_id`, an empty body and `Action:"execute"` — the receiver resolved the parent's row, saw `AWAITING_RESPONSES`, declined the work and logged success (`bugs_closed/129`). Measured before the fix: 430 of 430 retried requests in 14 days took that path, 294 exhausted the budget.
- **open review question:** any NEW action that sends an awaited request must set `types.RetryPayloadKey` in its result or it gets **no retries at all** — a deliberate loud failure, countable via `SELECT step_name, count(*) FROM awaited_requests WHERE request_payload IS NULL AND sent_at > now() - interval '2 hours' GROUP BY 1`. Covered today because `call_agent`/`spawn_agent` are the only awaited senders seeded fleet-wide; that is a measured fact about `agent_definitions`, not a structural guarantee, so re-measure before assuming it still holds.
- **sources:** `platform/orchestration/types/retry_payload.go`; `platform/orchestration/coordinator.go` (`handleRecoverableError`, `handleOrchestrationStatus`, `createAwaitedRequest`); `platform/orchestration/state.go` (`awaitedRequestColumns`, `InsertAwaitedRequest`); `docs/agent_docs/sql_for_agents/263_awaited_requests_request_payload.sql`; `bugs_closed/129_HANDOFF_2026-07-28_spawned_child_adopts_parents_orchestration_row_and_silently_declines_the_work.md`
- **relations:** the awaited-request timeout driver (`bugs_closed/003` F2 fast path + durable ticker) is what *calls* this; the adapter re-execute branch in `handleRecoverableError` is the deliberately-untouched alternative (rejected for agents because re-executing `spawn_agent` spawns a second pod — the `bugs_open/124` double-dispatch class); spawn→call handshake failures (`agent_error_log` "timed out after 3 retries")
- **verify-later:** whether the `MISROUTED_REQUEST` child-side guard ever fires in practice; if it does, some sender other than the two covered ones is setting identity wrongly

### RSH-004 — A local action executes under a deadline (`local_action_timeout_seconds`)
- **status:** **DEPLOYED and PROVEN LIVE 2026-08-03** — pod-grepped on both replicas (`local_action_timeout_seconds` 1, `DISABLE_LOCAL_ACTION_TIMEOUT` 1, control `Executing local action` 3, same exec) and then **INDUCED in production**. Council `2c6800e6` **APPROVED**. `fe34fd04f` + `893cb6483`.
- **status-evidence — INDUCED, not merely deployed:** armed `local_action_timeout_seconds: 0.001` on `endpoint-health-checker.check_health` (snapshot first, one 60s tick, immediate revert asserted by a `DO`/`RAISE`). Orchestration `4433e0e6` returned `FAILED` with `local action "check_endpoint_health" ... exceeded its deadline ... : query endpoints: context deadline exceeded`. That single line confirms the deadline fired, **the context reached inside the action** (its own DB call was cancelled — the premise for choosing a ctx deadline over goroutine-abandonment), the orchestration failed cleanly rather than parking at `EXECUTING_STEP`, and the error self-describes. Next tick `COMPLETED` normally.
- **landmine — `models.Step.Name` is EMPTY on the live coordinator path.** The induction's error read `on step ""` while `state.CurrentStep` was `check_health`; the coordinator's own log line at `:1325` has the same hole. **No unit test could catch it — every fixture sets `Name`.** `localActionContext` now takes the resolved name as a *required argument* so it cannot silently read an empty field (`893cb6483`). If you log a step name anywhere on this path, use `state.CurrentStep`.
- **status-evidence:** seven tests in `platform/orchestration/local_action_deadline_test.go`, of which the three risky behaviours are **proven able to FAIL by mutation** — removing the bound, wiring it to `timeout_seconds`, and making a malformed value mean unbounded — each failing for its own reason with a diagnostic message. Verified against a clean `git archive HEAD` because two other sessions had the tree's actions package and git adapter non-building at the time.
- **what:** `executeLocalAction` now derives a deadline via `localActionContext` and passes it to the handler, so **no local action can run unbounded**. Before this, nothing in `continueExecution -> executeStep -> executeLocalAction -> executeAction` bounded the call (`coordinator.go:1563` recovers panics and bounds nothing), and a blocked action parked its orchestration at `EXECUTING_STEP` while holding the dispatch loop's `site_work_items` row in `claimed` (`bugs_open/169` part A). **Default 7200s** (owner ruling 2026-08-03: every step limited, default very generous). Sized from the **longest observed legitimate local action** — `med_scrape_prices` at ~1391s — **not from a percentile**: an earlier 600s cut, justified off the all-step p99.9, would have killed that action on every run, because one 20-minute action is invisible in a population of 91,210 mostly-sub-second steps (`WRONG_CALLS.md` 2026-08-03). An action consuming >50% of its budget is now logged **while still succeeding**, so the ceiling moving is heard about before anything is cut. Per-step override `local_action_timeout_seconds`; **`<=0` means explicitly unbounded** and logs a Warn every time; `DISABLE_LOCAL_ACTION_TIMEOUT=true` is a fleet-wide kill switch restoring the exact previous behaviour with no rebuild. A **malformed** value falls back to the DEFAULT, never to unbounded, so a config typo cannot silently restore the defect. A `DeadlineExceeded` is wrapped to name the action, the step and the elapsed time, then routed through the existing `handleActionError` path so `error_step` is unchanged.
- **why the default is 600s and not tighter:** measured over `orchestration_state_audit` 2026-07-31..08-02 — **6,951** spawn-step executions, p50 0s, p95 18s, p99 **24s**, and **exactly one** above 300s, at 14,475s. The distribution is bimodal with nothing between seconds and hours. All-step p99 26s, p99.9 214s. **A too-tight bound breaking working pipelines fleet-wide is a worse defect than the rare hang**, so the default errs ~25x toward "let it finish".
- **landmine — this is NOT `timeout_seconds`, and must never be wired to it.** Of the 64 live steps carrying `timeout_seconds`, **53 are `call_agent`**, and most of the rest are waiting semantics too (`await_approval` carries **86400**, `request_human_input`, `dispatch_thunder_*`). That key means *"how long to wait for something EXTERNAL"*. Wiring the execution bound to it would make one shared word mean two things depending on the step it sits on — the class **RFC 006** was decided on — and would hand `await_approval` a 24-hour execution deadline it never asked for. Pinned by `TestTheBoundIgnoresTimeoutSecondsEntirely`.
- **landmine — a ctx deadline only cuts ctx-AWARE work.** An action that ignores `ctx` (a bare `time.Sleep`) still runs to completion; this bounds the common case, it is **not** a hard kill. Goroutine-abandonment was considered and rejected: it would regain control from a ctx-ignoring action but leaks the goroutine, and a late write from an abandoned action into a step the coordinator has already failed is a worse hazard than the hang.
- **open review question:** whether the 600s default holds once the improvement loop and other disabled schedulers are switched back on — the measured window is 3 days of a partly-idle fleet. Re-measure the spawn-step p99 before trusting the constant, and prefer raising the default to reaching for the kill switch.
- **sources:** `platform/orchestration/coordinator.go` (`localActionContext`, `defaultLocalActionTimeout`, `localActionTimeoutKey`, `disableLocalActionTimeoutEnv`); `platform/orchestration/local_action_deadline_test.go`; `bugs_open/169`; `docs024_key_docs_latest/bugfix_169_spawn_step_unbounded/`
- **relations:** `bugs_open/029` (hung spawns saturate the dispatch concurrency group — same family, different phase); `bugs_open/075` (dead-pod ownership, infinite retry); RSH-003 (retry-as-replay); the `claimed-item-timeout` reaper, which is what previously released the work item and is a mitigation rather than a fix
- **verify-later:** after the next roll, a step that exceeds its deadline must FAIL with an error naming the action and elapsed time rather than sitting at `EXECUTING_STEP` — and `orchestration_state_audit` should show no run ending at a `*_spawn_handler` step with `new_status` stuck.

### RSH-005 — The permanent-vs-transient failure classifier is a typed seam, and the durable record no longer depends on it being right
- **status:** built (inert until the next chassis roll); config half: none — this is Go only.
- **status-evidence:** `go test ./platform/messaging/ ./platform/agentbase/` green; the classifier tests are **mutation-proven** — reverting `MatchedPermanentFailure` to the pre-fix prose-only body fails `ReproducesTheBug_needleMissesButCodeMatches`, `SurvivesPercentWWrapping` and `ExplicitlyRetryableIsNeverPermanent` with the intended messages. **NOT yet proven in the cluster** — needs a roll plus the induced probe; see verify-later.
- **what:** Two layers decide whether a failed message is permanently broken (drop it, record it, never retry) or transient (hand it to the parent's retry policy): `MessageProcessor.handleError` and `agentbase.Agent.processMessage`. Both used to decide by **case-sensitive substring match over the error's prose** (`ValidationErrorNeedles`). `MatchedPermanentFailure` replaces that as the single entry point: it matches the **typed `DomainError.Code`** against a closed list (`NonRetryablePermanentCodes` = `ErrWorkflowInvalid`, `ErrValidation`) via `errors.As`, so the classification survives rewording, capitalisation and `%w` wrapping; the substring list remains **only as a fallback for errors carrying no `DomainError`**. An error built `AsRetryable` returns "not permanent" immediately and never reaches the fallback. It returns an audit **token** rather than a bool — `code:WORKFLOW_INVALID` for a typed match, the bare needle for a fallback match — preserving 034's auditability property and making the two distinguishable in a query. Separately, `agentbase` now writes an `agent_error_log` row on **every** non-dropped processing failure (`recordFailedProcessing`), so the durable record no longer depends on the classification being correct.
- **why it is registerable:** every agent type on the platform transits this seam, and it decides two things that matter fleet-wide — whether work is retried, and whether a failure is visible at all. It is also the deferred structural fix `bugs_closed/034` named in its own header ("replacing it with a typed sentinel … is deliberately NOT attempted here") and left open; `bugs_open/195` is the bill for that deferral coming due.
- **sources:** `platform/messaging/validation_drop.go#MatchedPermanentFailure`, `#NonRetryablePermanentCodes`; `platform/errors/errors.go#AsDomainError`, `#CodeOf`; `platform/messaging/processor.go#handleError`; `platform/agentbase/agent.go#recordFailedProcessing`; `platform/messaging/validation_drop_test.go#TestMatchedPermanentFailure`; `platform/agentbase/agent_test.go#TestAgentbaseUsesSharedPermanentClassifier`; `bugs_open/195`; `bugs_closed/034`
- **relations:** `bugs_closed/034` (unified the two needle lists and made the DROP durable — this makes the classification typed and the record unconditional); `bugs_open/029` (its hung-spawn reading is **falsified** for this path — see landmine); WFA-009 (`extract_fields.required`, the same "fail where it happened, naming the cause" principle one layer up)
- **landmine:** **the parent IS told, and that is the problem — the failure response is SUCCESS-shaped.** On the non-permanent path `handleError` calls `sendErrorResponse`, whose context comes from `CreateResponseContext("complete", 100)` (`platform/messaging/context.go:79`) — status header **`complete`**, `Success: true`, with the failure only in the body map. The coordinator switches on that header (`coordinator.go:316-331`), so `complete` routes to `handleCompleteResponse` and the parent marks the awaited step **complete, with the error blob as its step data**. So "the parent hangs" is wrong, and "the parent is correctly told" is also wrong. **This is NOT fixed by RSH-005** — it is 034's candidate-3 residue and wants its own bug file. Second landmine: **do not "fix" the fallback by case-folding it.** Lower-casing would widen every documented mis-match hazard (`invalid connection`, `invalid memory address`, `x509 … invalid`) to its capitalised variants; the needles are pinned byte-for-byte by `TestValidationNeedlesAreTheOnesBothLayersUsed` for exactly this reason. Third: a non-retryable `DomainError` whose code is **not** on the list still falls through to the substring fallback — deliberate, so this change only ever ADDS permanent classifications and never removes an existing drop.
- **measured, not asserted:** the retry-disposition change is confined, today, to one construction site — `ErrWorkflowInvalid` is built in exactly **one** non-test place (`processor.go:280`, the `ValidateWorkflow` rejection), and `ErrValidation` in one (`internal/agents/contentcreator/agent.go:226`) which sends it as a response and never returns it through the classifier. Baseline for the new row class: `agent_error_log` carried **1,301 rows/24h** when `bugs_open/195` was filed, against **0** rows for the probe correlation — the positive control proving a row was reachable.
- **review status:** submitted to the council gate 2026-08-04 alongside the commit; `Council-Submitted:` trailer, never `Council-Reviewed:` on an unread verdict. Scope argued explicitly: by owner ruling 2026-07-29 §1 the RFC trigger is whether a shared mechanism's **guarantees** change — they do, in the direction of *strengthening* ("every processing failure now leaves a queryable row"), and the direct precedent (034's own needle unification, a fleet-wide retry-semantics change on this same seam) shipped default-ON and was approved. An opt-in default-OFF switch was considered and rejected on the ground that **the current behaviour IS the unsafe default**: failing open, classifying permanent errors as transient and recording nothing.
- **verify-later:** pod-grep every replica with a control. **NOT `PROCESSING_FAILED`** — measured 2026-08-05 on v1.0.1252, that returns **0 on a binary that fully carries this change**: it is a short literal Go compiles to an immediate comparison that never reaches rodata (the standing short-literal landmine, which this entry's first draft walked straight into). Use a LONG distinctive sentence instead: `grep -ac 'processing failed and was NOT classified permanent' /app/agent-chassis` → **1** on both replicas (measured), alongside the pre-existing positive control `grep -ac 'message dropped without retry or error response'` → **1** (proves the probe reads the binary you think it does). Then the behavioural check no build can give: induce the fault (a throwaway agent whose only step is `{"action":"complete"}` — invalid, because `complete` is a step NAME whose action is `complete_workflow`) and assert `SELECT error_code, context->>'matched_needle' FROM agent_error_log WHERE context->>'correlation_id'='<probe>'` returns exactly one row, `VALIDATION_ERROR_DROPPED` with `matched_needle = 'code:WORKFLOW_INVALID'`. Baseline to beat: **0 rows**, needle-HIT **0** (probe `34268b8a-…`, chassis v1.0.1250). Adoption census that should stay honest: `SELECT error_code, count(*) FROM agent_error_log WHERE created_at > now() - interval '24 hours' GROUP BY 1;` — a `PROCESSING_FAILED` class appearing is the mechanism firing.

### RSH-006 — The retryable-side classifier is a typed seam with a census-derived fallback, and retry-vs-terminal is no longer decided by case-sensitive prose
- **status:** ~~built (inert until the next chassis roll)~~ **live** — corrected 2026-08-06 by the `bugs_open/207` lane: proven on real traffic on v1.0.1259 the same morning it was written (`bugs_closed/197` closed LIVE; dispositions measured in `agent_error_log`: 122 `connection` + 56 `deadline exceeded` recoverable). The stale line outlived its truth within hours — the standing register-status landmine, caught by a reader, cost one re-measure. Go-only; no config half.
- **status-evidence:** `go test ./platform/messaging/ ./platform/agentbase/` green; **five mutations each flip named tests** — un-folding the case fold fails the capitalised census cases, deleting `deadline exceeded` fails the 885-row headline case, re-adding bare `503` fails the hex-UUID case, killing the Retryable=false fall-through fails the `InternalError`-wrapped-deadline case, and reverting agent.go to a local substring helper fails the AST guard on both prongs. **NOT yet proven in the cluster** — see verify-later.
- **what:** `MatchedTransientFailure` (`platform/messaging/retryable_transient.go`) replaces two disagreeing classifiers as the ONE answer to "can a retry succeed?": agentbase's private `isRecoverableError` (three case-SENSITIVE needles, no nil guard — **deleted**) and `platform/errors.IsRecoverable` (twelve case-folded patterns, **zero callers fleet-wide — deleted**). Typed-first: an explicit `AsRetryable` outranks everything (`retryable:<code>` token); then a closed code list `{AGENT_TIMEOUT, AGENT_OVERLOADED, RATE_LIMITED}` (`code:<code>`); then a case-folded, census-derived needle fallback (bare needle token). A `Retryable=false` DomainError with an unlisted code deliberately falls through to the needles — `InternalError()` defaults `Retryable=false` while routinely wrapping a transient cause, so classifying on the flag would re-create the bug one level up. The verdict becomes the wire status via `getErrorStatus`, and both it and the audit token are now written into `agent_error_log.context` (`retry_disposition`, `transient_matched`) by `recordFailedProcessing`, so the after-census reads a column the classifier does not consume. `ErrorInfo.Code` on the wire now comes from `wireErrorCode` (typed code or the legacy literal), ending the disagreement between the DB row and the wire about the same failure.
- **why it is registerable:** one function decides retry-vs-terminal for every agent's processing failure, fleet-wide. The census (2026-08-06, population = the 2,996 `agent_error_log` rows that actually reached this seam, courtesy of RSH-005's unconditional recorder): **885 rows (~30%) contained "deadline exceeded" and were made TERMINAL** — transient by definition, work lost that a retry would save; **882 rows missed on capitalisation alone** (bugs_closed/195's capital-letter defect, live on the sibling); rate-limit/5xx prose 37 rows, 20 missed.
- **sources:** `platform/messaging/retryable_transient.go` (+`_test.go`); `platform/agentbase/agent.go#handleProcessingError`, `#recordFailedProcessing`, `#wireErrorCode`; `platform/agentbase/agent_test.go#TestAgentbaseClassifiesThroughTheSharedTransientClassifier`; `bugs_open/197`; census in the new file's header.
- **relations:** RSH-005 (the permanent twin — every error reaching this seam was already judged not-permanent there); bugs_closed/034 (the two-lists drift this closes on the retryable side); bugs_open/196 (the ACTIVE lane whose processor senders stay typed-only — see landmine 2); bugs_open/173 (substep failure semantics change from terminal-on-first to up-to-3).
- **landmine 1 — do NOT "complete" the needle list from the deleted `IsRecoverable`'s:** bare `502`/`503`/`504` are REJECTED because the dominant message shape nests correlation UUIDs, which are hex — `503` matches inside an arbitrary ID and classifies a permanent failure as retryable off its own correlation id. `unreachable`/`network` are rejected on ZERO census rows. The pinning test (`TestTransientNeedlesAreTheJudgedList`) makes any list change re-argue the header.
- **landmine 2 — the processor's sender claims FIRST on the orchestrated path.** Post-196, `processor.sendErrorResponse` sends a typed-only error response *before* agentbase's, and the coordinator's `ClaimAwaitedRequest` makes the first response the deciding one (`DUPLICATE_SKIPPED` for the loser). So do not assert THIS seam's verdict from `orchestration_states` without pod-grepping which response claimed — and the live behavioural flip is smaller than the census's raw 885 until the 196 lane converges its senders (their call, scheduled, not a passenger edit here). **RESOLVED 2026-08-06 (`bugs_open/207` lane):** both senders now decide through `RetryDisposition` (RSH-007) — committed, live from the next chassis roll; until that roll the pre-emption caveat above still applies to the running fleet.
- **landmine 3 — the `retry_version >= 3` cap (coordinator.go `handleRecoverableError`) is now load-bearing for a WIDER population**, with the independent adapter cap from bugs_open/075 beside it. No backoff exists on the recoverable arm (known gap, not fixed here). Anyone raising either cap changes this change's risk maths and must re-read this entry.
- **landmine 4 — accepted over-matches, measured not hypothetical:** SSL/TLS *certificate* errors match `connection` inside "establish a secure connection" (live rows quoted in the file header) and buy 3 futile retries; `dial tcp` admits NXDOMAIN typos to the same. Both documented in the header and pinned visible by a test (`SSLOverMatchIsKnownAndBounded`).
- **review status:** submitted to the council gate 2026-08-06 alongside the commit, `Council-Submitted:` trailer. Scope argued per the 2026-08-02 §2 ruling: the seam already exists and already decides; the current behaviour (transient failures made terminal, capitalised needles silently missed) IS the unsafe default; 195's identical argument was approved. Unlike 195 the flip is behaviourally live — disclosed and bounded (3-retry cap + adapter cap + processor pre-emption).
- **verify-later:** pod-grep both replicas with a LONG literal — `grep -ac 'retry disposition decided by shared transient classifier' /app/agent-chassis` → 1 (short literals compile to immediates and grep 0 on a carrying binary — the RSH-005 lesson) — plus a pre-existing long literal as positive control. Then the induction pair: a deadline-exceeded-shaped probe must show `context->>'retry_disposition'='error_recoverable'`, `awaited_requests.retry_version ≥ 1`, and terminal at `Max retries exceeded` after 3 (proving the bound); an `unclassifiable failure xyzzy` probe must stay `retry_version=0`, one attempt. ### RSH-007 — RetryDisposition sequences the two failure classifiers, and the failure senders converge onto it
- **status:** LIVE since v1.0.1262, proven by induction 2026-08-07 (`Council-Reviewed: 155f4730-4526-4523-83d0-3ce4c4fc9f1c`, APPROVED r1). **UPDATED 2026-08-08 (`bugs_open/217`): the implementation MOVED to `platform/errors` (`transient_failure.go` + `permanent_failure.go`) and the THIRD sender converged** — `SagaCoordinator.notifyParentOfFailure` (child-orchestration failures, previously hardcoded `error_unrecoverable`) now classifies through `RetryDisposition` over its failure prose. The move is forced by the import graph: messaging imports orchestration (the drop recorder), so the coordinator could not reach the classifier where it lived. `platform/messaging` keeps re-exports aliasing the ONE implementation — every prior caller and pinning test unchanged, agentbase untouched. Third-sender convergence **LIVE + PROVEN on v1.0.1269 (2026-08-08 22:14Z induction: this sender answered a deadline-exceeded child-orchestration failure `error_recoverable`, still first, and the re-driven parent produced a real void-topic replay at retry_version=1)**; council APPROVED r1 (`Council-Submitted: 471a969e-3546-4d34-bc9c-a481aca7f1d6`, verdict read). The convergence series 207→216→217 is complete: every chassis failure sender decides through this seam.
- **what:** `messaging.RetryDisposition(err) (recoverable bool, matched string)` (`platform/messaging/retryable_transient.go`) asks the two registered classifiers **in their documented order** — `MatchedPermanentFailure` first (drop, never retry; token `permanent:<token>`), then `MatchedTransientFailure` (retry can cure; its token), else terminal (`""`). Both processor failure senders (`sendWorkflowFailureResponse`, `sendErrorResponse` — previously typed-only via `errors.IsRetryable`, a flag with no production setter) now decide status AND `ErrorInfo.Recoverable` through it, and log the disposition + token. Closes `bugs_open/207` (the 197 round's tracked residual): untyped transient failures — ~30% of the census, 1,001 of 3,399 rows on 2026-08-06 — stop being terminal on the orchestrated path, where the processor's response claims the awaited request first.
- **why it is registerable:** a new exported helper on the shared failure seam. Any future failure path that cannot guarantee permanent-before-transient by call order (the way agentbase does) should call THIS, not `MatchedTransientFailure` directly — the sequencing is the contract, not a convention.
