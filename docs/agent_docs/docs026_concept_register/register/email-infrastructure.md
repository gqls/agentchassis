### EMAIL-002 — Transactional email sending realities (587-only, relay filtering, SES + per-domain DKIM)
- **status:** deployed
- **status-evidence:** "DECISIVE: MailChannels blocks leopardess.uk DIRECT outbound too → must leave MailChannels" (2026-06-11); SES live in production same day; EMAIL doc header codifies the lesson for the future provisioner.
- **what:** Hard-won operational truths now standing framework guidance: ~~cloud boxes can't use outbound SMTP 25/465~~ **CORRECTED 2026-08-16 — this is HOST-SPECIFIC, not a property of cloud boxes; see the narrowing below** (Hetzner leaves only 587 submission open — the cPanel UI advertising 465 misleads); Go's smtp.SendMail does STARTTLS not implicit-TLS, so a 465 path needs a tls.Dial branch; shared-host relays (Clook→MailChannels) content-filter legitimate transactional mail (a `From:`-like line + raw JSON in a body triggered "Spam Content"); therefore transactional sending needs a **dedicated sender (AWS SES eu-west-2) with the operator domain's own DKIM**, bodies kept clean, and the mailer async/bounded so a hung send can't freeze the request path. Gotcha: SES SMTP_USER is the AKIA access-key-id, not the IAM user name (535s otherwise). Chronology: Clook both-ways → catch-all/Default-Address fixes → MailChannels blocks → SES.
- **NARROWING 2026-08-16 (gripper dossier lane), [MEASURED] on the island, one counterexample:** *"cloud boxes can't use outbound SMTP 25/465"* is **false as a general rule** — it is true of **Hetzner**, which is the box this entry was written from. Measured from the gripper island (`toolsapisuk.vs.mythic-beasts.com`, **Mythic Beasts**, IP 176.126.243.183) against `mail.contactforsales.com`: **465 is fully open** — TLS handshake completes, Exim answers `220 rs17.uk-noc.com ESMTP Exim 4.99.5`, `EHLO` returns `250`, and **`250-AUTH PLAIN LOGIN` is advertised to that IP**. 587 is open too (same Exim banner), so both paths work there. **The lesson that survives is the CHECK, not the conclusion:** never infer a box's outbound-465 reachability from another box (a dev-box AUTH success proves nothing about the deploy target), and never from the provider's cPanel screen — *measure from the host that will actually send*, with `openssl s_client -connect <host>:465` and read for the `220`. The Go `tls.Dial`-vs-STARTTLS half of this entry is unaffected and still correct; `platform/mailer.UsesImplicitTLS` implements exactly that fork on `port == "465"`. Also captured while there, useful for capacity: the relay advertises `SIZE 52428800` and `LIMITS MAILMAX=1000`.

### EMAIL-003 — The post-delivery follow-up: a second customer email with its own once-only claim, suppressed by the confirm button
- **status:** built, seeded DISABLED, and it can currently select NOBODY — see the two blockers below. "Deployed" would overstate all three parts of it.
- **status-evidence:** `[MEASURED 2026-09-04]` `scheduled_tasks.delivery-followup-send` is seeded with `enabled = false` and migration `775`'s verify ABORTS if it is anything else. The Go half is committed (`f89dfa31d`) and INERT until a chassis image rolls. And `775`'s verify reports `1 of 1` handed-over sites unreachable, which is the state described under "open review question".
- **what:** The estate's SECOND (and only other) customer-facing email, a week or so after delivery, repeating where the hosting instructions live and offering the confirm link again. Three parts: `delivery.ClaimFollowup` (`platform/delivery/handover.go`), the `send_followup_email` action (registry, `Category: site`), and migrations `774` (the `sites.followup_sent_at` claim column) + `775` (the `delivery-followup-sender` agent and its schedule, modelled on `zip-link-refresh`).
  **Two properties are the whole point of the design.** (1) AT-MOST-ONCE is a property of the UPDATE, not of anyone remembering: `UPDATE sites SET followup_sent_at = … WHERE … AND followup_sent_at IS NULL RETURNING …`, exactly as `StampHandover` claims on `handed_over_at IS NULL`. A scheduled thing that emails customers fails not by never sending but by sending nightly, and this is the only shape that makes that unrepresentable. (2) SUPPRESSION IS INSIDE THAT SAME STATEMENT: `transfer_confirmed_at IS NULL` is re-checked at claim time, not only in the scheduler's `pre_query`, because a customer who presses the confirm button between the SELECT and the dispatch landing must not be emailed. This is the **first reader `sites.transfer_confirmed_at` has ever had** (`bugs_open/477`: the column had been written and read by nothing since it shipped).
  **It cannot be a config variant of `delivery-email-sender`.** That agent's action goes through `delivery.Claim` → `StampHandover`, which returns `ErrAlreadyDelivered` for any site already handed over — i.e. exactly the population a follow-up targets. Adding a skip-the-claim switch there would remove the guard that stops a retry double-emailing a customer, on the estate's only customer mail path.
  The copy is CONFIG (owner-editable, no roll) and carries `{{instructions_url}}`, never the hosting steps themselves — `bugs_open/475`'s rule: anything that can go out of date lives on the page, never in a copy the customer already holds.
- **sources:** `bugs_open/477`; `docs/agent_docs/docs024_key_docs_latest/bugfix_477_delivery_followup/` (PLAN, NOTES, README_where_we_are); `platform/delivery/handover.go` (`ClaimFollowup`, `ConfirmTokenURL`); `platform/orchestration/actions/send_followup_email_action.go`; `docs/agent_docs/sql_for_agents/774_*.sql`, `775_*.sql`; council `Council-Submitted: 3555a7a1-cf53-4b3b-91ba-4907a2e43ae4`
- **relations:** `delivery-email-sender` + `delivery.Claim`/`StampHandover` (`sql_for_agents/651`, the once-only delivery it deliberately does NOT reuse); `zip-link-refresh` (the scheduled site-selecting sender it is modelled on); `bugs_open/475` (the instructions page this email points at, and the rule that keeps it a pointer); `bugs_open/476`; migration `776` (the same false promise in the delivery email's own `body_template`, fixed by the `site_delivery_and_editor` lane)
- **open review question — TWO blockers, neither of them code:**
  1. **The owner has NOT ruled on the interval.** "a week or so" is not a number. The action REFUSES to run without `followup_after_days` rather than defaulting, so the placeholder `7` in `775` cannot quietly become the decision.
  2. **⚠ THERE IS NO DURABLE RECORD OF WHO A DELIVERED SITE WAS DELIVERED TO, so today this sender can reach nobody at all.** `[MEASURED 2026-09-04]` `build_queue` — the only permitted recipient source (`651` header, corrected 2026-08-31 under `bugs_open/420`; `sites.email` explicitly forbidden) — has **ZERO** rows for idea.uk, the only site ever handed over, because it was a rehearsal delivered to a hand-typed address and never went through the order pipeline. The obvious fallback fails too: `orchestration_states` records the address used, but its **oldest row is under 24 hours old** (6,662 rows, oldest 2026-09-03 11:47Z), and the follow-up is due in seven days. The fix is to stamp the recipient onto the site row in the same statement that stamps `handed_over_at` (`platform/delivery/prepare.go`), routed to the `site_delivery_and_editor` lane. **This was found by a DEMAND CONTROL, not by review** — the `pre_query` returns 0 either way, and a sender that can never select anybody looks exactly like one with nothing due.
