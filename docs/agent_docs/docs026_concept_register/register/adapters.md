### ADP-001 — Adapter/response message envelope contract (normative)
- **status:** deployed
- **status-evidence:** "003-vs-FOCUS contradiction RESOLVED empirically (2026-06-11) from coordinator.go + git/thunder/dynamic/websearch adapters"; 035 §1 "last verified against code 2026-06-11"; live `003_contracts_and_standards(8).md` now reads "Moved to 035_adapter_guide.md §1 … now the single source for it."
- **what:** Any reply to a chassis request must be recognised as an awaited response or it silently falls to process-as-work (row stuck waiting, ~10-min retries, no error). The load-bearing field is `in_response_to_request_id` = the incoming `request_id` (`request_id` itself is only a fallback; "reuse both" is the safest pattern — this is the git-adapter's favoured pattern). `action`/payload are read from the message BODY, not headers. Response headers must be a typed Go struct with real bools — a `map[string]string` sending string-bools fails unmarshal and silently drops the reply pre-claim; this exact bug caused a real multi-day thunder-adapter production outage (matcher fix, 2026-05-22). Sends must go via `ProduceWithValidation`, never plain `Produce`. A sibling race requires local dispatches to call `preRegisterAwaitedRequest` before sending (confirmed fixed in prod 2026-06-09). The contract was originally duplicated and drifted between doc 003 and `FOCUS_adapter_design`, then single-sourced into `035_adapter_guide.md` after empirical verification against `coordinator.go` and four live adapters (websearch-adapter was flagged as the one adapter still on the deprecated string-bool/plain-`Produce` path).
- **sources:** docs024_key_docs_latest/035_adapter_guide.md#1; NOTES_running_synthesis_principles(59) 2026-06-11 envelope-contract entries; debugging_old/003_contracts_and_standards_v11.md#"Adapter Response Envelope Contract"; docs/_archive/.../adapter(4).go, analyser_request_action(1).go
- **relations:** Adapter response-header tier taxonomy (ADP-002); awaited_requests; O(K²) batch presign; Analyser adapter (ADP-009)
- **verify-later:** ValidateOutgoingMessage field list; platform/orchestration/types ResponseHeaders/ResponseMessage; platform/orchestration/coordinator.go ProcessResponse; whether websearch-adapter has since migrated off the string-bool map

### ADP-003 — Adapter design pattern / guide (adapter vs agent vs inline; canonical microservice structure)
- **status:** deployed
- **status-evidence:** FOCUS_adapter_design(3): "Canonical guide for building long-running cluster services… Examples drawn from the working adapters in the repository." An earlier legacy telling (docs 0123) codifies the same pattern for image-generator/firecrawl/webscrape/playwright/git adapters. The FOCUS_adapter_design(3) context-pack copy is now a frozen snapshot; the live guide has moved on to `docs024_key_docs_latest/035_adapter_guide.md` (38KB, Jun 2026).
- **what:** The decision rule for when to build an adapter at all (one external API + multiple internal callers → adapter; long per-orchestration work → spawned agent; short single-agent call → inline; shared infra like DB/Kafka → nothing), plus the canonical shape: Go agents never embed heavy dependencies — a workflow action produces a Kafka message to `system.adapter.<name>.requests` (or an internal HTTP call) and a containerised worker service (Python or Go) in its own Deployment consumes via a shared consumer group, does the work, and replies to the reply_to topic. Canonical structure: ordered `NewAdapter` with manual cleanup on every failure path, sequential fetch-handle-loop (no goroutine-per-message by default), `handleMessage` parse/dispatch/respond, health endpoints, `sync.Once` shutdown, config YAML field-name traps, credentials from env only. External GPU/API providers get a dedicated Go proxy adapter holding the secret key and translating request formats — swap providers by changing one adapter, no workflow changes.
- **sources:** working/flywheel_docs/FOCUS_adapter_design(3).md (whole); docs003_firecrawl/README.0123.actions_needed_firstdraftpython.md; docs004_website_capture_project/playwright/implementation_roadmap.md; docs001_flow_general/README.097a.imagecreationandstorageflow.md

### ADP-017 — Shared reply-delivery policy: an undeliverable reply becomes a deliverable error
- **status:** deployed (live on `web-scrape-adapter` v1.0.1209, verified 2026-07-30 on all 3 replicas; still carried by v1.0.1211 after another session's roll, re-verified). Council-approved `7478233b-3986-4505-a747-c059dc87e9e7`, architecture seat `ARCHITECTURE_SIGNAL: point_fix`.
- **⚠ THIS REGISTRATION DOES NOT PRE-CLEAR WIDER ADOPTION.** The architecture seat approved it as a point fix *and said so explicitly*: "when adoption widens past webscrape, that IS the RFC moment (it changes 4 services' caller-observable failure behaviour) — the author should not treat ADP-017 registration here as pre-clearing that later expansion." So a thread adopting `DeliverReply` at the reasoning / contentcreator / websearch / thunder sites needs an RFC, not this entry. The guardian seat's objection in the same round was precisely that "inert today" does not mean inert once a ready-made shared function is sitting in `platform/kafka` for eight more callers — its contained alternative was to keep the helper package-local to `internal/adapters/webscrape` and defer promotion until a second SERVICE needed it. The architecture seat's `point_fix` read superseded that within the same round (the multi-package trigger has not fired: one consuming top-level package, two call sites), but the guardian's reasoning is the standing reason the caveat above exists.
- **status-evidence:** `platform/kafka/reply_delivery.go` + `reply_delivery_test.go` (19 passing assertions, verified to fail when the degrade branch is neutered). Adopted by both webscrape reply paths in the same commit; the batch path's private copy deleted. Census that motivated it, run 2026-07-30: `grep -rn "MessageSizeTooLarge\|Message Size Too Large" --include=*.go .` returned **one** file (`internal/adapters/webscrape/batch_handler.go`) while `grep -rn "Failed to produce"` returned **nine** reply-producing sites across five services — so the rule held at 1 of 9.
- **what:** `platform/kafka.DeliverReply(...)` is the one implementation of what to do when the broker refuses a reply: produce; on a NON-size error return `FailedTransient` unchanged (resending may work, so the coordinator's existing retry stays in charge); on a size refusal call the caller's `ReplyDegrader` and resend **exactly once**; if that is also refused return `FailedUndeliverable`, which the caller **must** answer with an error response. Paired with the exported predicate `IsMessageTooLarge(err)` (typed `errors.Is`/`errors.As` against kafka-go's `MessageSizeTooLarge` and `MessageTooLargeError`, then a substring fallback for composite `kafka.WriteErrors` the unwrap chain does not reach). Outcomes are a typed `DeliveryOutcome` with an `Answered()` helper rather than a bool, so a fourth outcome added later cannot silently read as delivered. The *policy* is shared; the two things that genuinely differ per adapter — how to shrink an oversized payload, and what its error envelope looks like — stay with the caller as a callback and a return value. The rule itself predates this entry (016b §9, from `bugs_closed/062`): *a response that cannot be delivered must become a deliverable error, never silence* — the caller listens on the reply topic, not on the pod's logs, and 062 measured callers starving through 4 × 180s of retries on a failure that could never succeed.
- **why it is shared rather than copied:** `bugs_open/133` found the rule implemented once, unexported, at one of nine sites. The obvious fix for the eighth site was to copy that block — which is precisely the defect `bugs_closed/144` was about (two hand-written implementations of one rule, which then drift), and the reuse seat objected to that exact shape in 144's own council round. **This is a platform seam** under CLAUDE.md's 2026-07-28/29 owner rulings: it is additive and inert (nothing changes for any producer until a call site opts in), so per the 2026-07-29 ruling §1 it adds an opt-in capability rather than changing what a shared mechanism *guarantees*, and goes through the normal council gate rather than an RFC. No ordering constraint is claimed (condition (1) retired 2026-07-29). Registered in the commit that ships it, per condition (2).
- **landmine:** `DeliverReply` returning `FailedUndeliverable` is the whole mechanism, and it is a **return value a caller can ignore** — an adapter that calls it and drops the outcome compiles, passes `platform/kafka`'s tests, and reintroduces the silent starve. That is why the adoption tests live in the *adapter* package (`internal/adapters/webscrape/reply_delivery_test.go`) and assert an error response actually goes out, not merely that the policy classified correctly.
- **the other eight consumers, named not merely measured** (2026-07-29 ruling §3): `internal/agents/reasoning/agent.go`, `internal/agents/contentcreator/agent.go` (×2), `internal/adapters/websearch/adapter.go` (×2), `internal/adapters/thunder/adapter.go` (×2), and webscrape's own error-response paths. All still log-and-return. Adopting them changes what their callers observe on failure (an error response instead of a timeout), which is four other services' behaviour, so it is filed as its own reviewed change rather than smuggled in here.
