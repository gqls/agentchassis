### REB-001 — F3 scoped reason-stamped rerender (dependent-page scoping + reason propagation)
- **status:** deployed
- **status-evidence:** "F3 PROVEN END-TO-END (scoping to exactly the five, reason propagation, gate, section-rerender execution)"; fleet on v1.0.1088.
- **what:** Three coupled changes making a component regen's triggered re-render actually repair sections, scoped to the blast radius: F3a — `create_rerender_items` accepts `reason`+`component_id`; when reason ∈ {section_data_resolved, image_landed} AND component_id is set, it queries the component's dependent pages (page_components JOIN pages) and creates reason-stamped `page_rerender` items only for those; no signals → unchanged assemble-only all-pages behaviour. Either half alone degrades safely to assemble-only. ### REB-002 — Assemble-only vs section re-render distinction (the `reason` gate)
- **status:** deployed
- **status-evidence:** "a bare needs_rerender is assemble-only and just re-ships the empty shell"; gate `reason ∈ {image_landed, section_data_resolved}` confirmed from rerender_page_sections source.
- **what:** Two fundamentally different re-render depths: an assemble-only pass re-assembles/re-ships existing `rendered_html` (cannot repair content), while a section re-render (`rerender_page_sections`, gated on reason image_landed/section_data_resolved) regenerates each section's HTML from stored `content_data` against the current template, no LLM. A `reason` dropped anywhere along the chain silently downgrades to assemble-only — an inert "fix" caught only by checking the consuming step's config. Central operational lesson of the investigation.
- **sources:** NOTES(43).md §2 Correction 3, §6, §9a; PLAN(1).md Phase 4; RUNBOOK_pre_cleanup_backup.md §The-problem
- **⚠ 2026-08-26 — THE VOCABULARY NOW HAS ONE DEFINITION, AND THE ENTRY ABOVE UNDERSTATES IT.** The line "gate `reason ∈ {image_landed, section_data_resolved}`" was true when written and is **two values short**: the live gate is a FIVE-value allow-list, and it grew on 2026-08-18 when migrations `460` (`template_changed`) and `473` (`literal_markdown`) each appended one, **on the same day, by different lanes, neither touching Go** (`bugs_closed/404 (CLOSED 2026-09-04)`). The definition is now `livespec.RerenderSectionReasons` — the vocabulary plus, per value, whether it scopes the fan-out by component and whether it stamps without one. The live gate is ASSERTED against it (declarations `workflow.page-rerender.check_rerender_mode.reasons` and `…​.value_count`), never generated from it: **DB config cannot import Go**, so a migration author pastes `CheckRerenderModeConditionClause()`'s output and the daily `live-declaration-drift-check` holds it.
- **⚠ LANDMINE — EVERY READER THAT DOES NOT KNOW A VALUE FAILS TOWARD `assemble`, WHICH IS THE SILENT DIRECTION.** The gate's `else_step` is `render_page`; the item creator's unknown reason leaves the item carrying no reason at all, which the gate then reads as assemble. A vocabulary whose readers failed toward RE-RESOLVE would announce itself — too many re-renders, and you would notice. Failing toward assemble means the estate's preferred, safe, cheap mode is also its silent-failure mode: green status, nothing changed. `bugs_open/283` §13 had to measure it end to end (111 items completed, page DEPLOYED, served bytes unchanged) before anyone believed it.
- **⚠ LANDMINE — THERE ARE FOUR READERS, NOT THREE, AND ALL FOUR NOW NAME THE VOCABULARY.** The live gate; `create_rerender_items` (both branches, and they are DIFFERENT tests — one narrows which pages, one decides whether a reason is carried at all); and **two per-value feature gates in `rerender_page_sections_action.go`** — `shouldStripLiteralMarkdown` and the CTA recompute — which `bugs_closed/404 (CLOSED 2026-09-04)` did not list. Leaving those two as bare literals would have reduced four copies to two rather than one, which two council seats objected to independently. They read named constants now, so retiring or renaming a value breaks COMPILATION at every reader instead of silently disarming one.
- **⚠ LANDMINE — `spec.reason` IS TWO FIELDS WEARING ONE NAME.** `[MEASURED 2026-08-26]` **sixteen** distinct strings are in use on `page_rerender` items across live and archive, and four are free prose — whole sentences, a bug reference, an operator's note. Humans annotate; the gate routes. One Go producer does it deliberately too (`adopt_verbatim.go` stamps `verbatim_adoption_deploy` on items that are SUPPOSED to assemble). **So an undeclared reason is WARNED and reported in the step result, never refused** — refusing would be new authority on a shared seam with a live counter-example. Splitting annotation from routing key is the real repair and is RFC-scope, deferred.
- **⚠ the vocabulary spans THREE item types**, so "which reasons reach the gate" is not answered by looking at `page_rerender` alone: `literal_markdown` arrives ONLY on `item_type='literal_markdown'` items, and `template_changed` also rides 65 `section_edit` items where nothing reads `spec.reason` at all.
- **the commit-time half**: `livespec/rerender_reasons_test.go` scans the migration corpus for reason literals and fails on an undeclared one, naming the file and the value — what would have caught 460 and 473 on the day. ⚠ Its first version accepted single-quoted literals only, matched 12 of them, **and every one was a PROSE COMMENT**: a migration writes the condition inside a SQL string, so the quotes are doubled. It could not see either executable line it exists to catch. It now accepts both forms and carries positive controls naming 460 and 473, so a regex that stops matching the real shape fails loudly instead of reporting a clean corpus.
- **relations:** F3 scoped rerender (REB-001, makes the reason survive — and its designed degrade, reason-without-component_id falls back to assemble, is preserved for the legacy pair on purpose); rerender fossilisation (REB-005, site-level analogue); carry-forward path (REB-003); `bugs_closed/404 (CLOSED 2026-09-04)` (the drift and its fix); `bugs_open/363` / `platform/livespec` (why the declaration is against the LIVE object and not a migration file); `bugs_open/098` (the archived-page resurrection the fixer's query was open to until migration 656)
- **verify-later:** `rerender_page_sections_action.go` reason gate; page-rerender workflow's routing on spec.reason; and after migration 656 applies, the `live-declaration-drift-check` at 07:00 UTC should read all three new declarations clean — ⚠ **apply 656 BEFORE the binary rolls**, or the auditor exits 1 with a finding that is TRUE (the live query genuinely lacks the filter), which is how an auditor gets learned-to-ignore

### REB-003 — Carry-forward path and the carry fingerprint
- **status:** deployed
- **status-evidence:** "per-page save-style row updates + identical bytes = the rerender_page_sections CARRY path fingerprint," confirmed by data.
- **what:** In `rerender_page_sections`, a section is carried (`carryStoredSection` re-emits the stored HTML unchanged) for one of two DIFFERENT reasons that used to be indistinguishable from outside: (a) `planSection` readiness fails (an unresolvable required field, or an empty template) — a legitimate, non-fatal fallback; (b) **the section's component could not be resolved at all** — `bugs_open/182` (FIXED 2026-08-03, `a43be1e70`, LIVE v1.0.1240): when `page_components.slot_name` is positional (not any component's name/function), nothing resolved, so on some sites (loancalculator.co.uk: 100% of slots) EVERY section took this branch and the run still reported success. Fixed by resolving `component_id` first (the row's own identity, previously read and unused) and — the part that actually closes the door — failing the step when a section resolves via **neither** id nor name, naming every such slot. `save_sections` still writes carried bytes back with a fresh `updated_at` but identical content FOR THE LEGITIMATE (a) CASE; case (b) now aborts before `save_sections` runs at all.
- **sources:** NOTES(43).md §9u, §9v; BUNDLE(3).md §3; `bugs_open/182` → `bugs_closed/182`
- **relations:** section readiness model (page-build-pipeline register, PBP-003, the gate it consults); auto-escalation (REB-004); recovery playbook
- **verify-later:** rerender_page_sections_action.go: planSection, carryStoredSection, resolveComponent, rerenderResolution

### REB-005 — Rerender fossilisation (reassembly re-ships stale renders; template changes need a full rebuild)
- **status:** deployed
- **status-evidence:** "deployed hero consumes legacy var(--accent-color…) — sections are stale old-template renders… A full page-build-handler rebuild is required; needs_rerender would re-fossilise," evidenced directly from deployed HTML.
- **what:** The rerender handler reassembles stored `page_components.rendered_html` and injects `site_components.rendered_html` — it does not re-render component templates — so sites can live indefinitely on reassemblies of early renders while the library advances (one site served renders of long-inactive components for weeks). Template/library changes only reach pages through a section re-render or a full page-build-handler rebuild; chrome only through render_site_components. Settled a documented cross-doc contradiction by direct evidence — the same finding independently confirmed on a different site in the page-build-pipeline register (PBP-001).
- **sources:** RUNBOOK_scheme_to_components(18).md Check 3/4 RESULTS; running_notes_scheme_to_components(22).md #Sh, #So
- **relations:** rebuild vs rerender semantics (page-build-pipeline register, PBP-001, same mechanism independently confirmed); assemble-only vs section re-render (REB-002); chrome refresh gating (REB-006)
- **verify-later:** rerender_single_page_action.go; which paths run RenderComponent vs re-ship stored HTML

### REB-006 — Chrome refresh gating (render_site_components, force_rerender, repoint-before-rerender)
- **status:** deployed
- **status-evidence:** "renderAndStoreSiteComponent joins the PINNED site_components.component_id with no is_active filter, and without force_rerender SKIPS non-empty slots" (code fact); a repoint was executed and confirmed (UPDATE 1 ×2).
- **what:** Site chrome (header/footer/head) is rendered and stored by `render_site_components`, a path separate from page builds (page-build-handler is not among its invoking agents — a page rebuild never refreshes chrome). Its join honours the pinned `component_id` with no `is_active` filter and skips non-empty slots unless `force_rerender: true` (only rerender-pages v6 passes it, gated on `spec.refresh_site_components` — page-build-pipeline register PBP-002). Operational consequence: repoint the pinned rows to the fixed/active components BEFORE forcing the re-render, and refresh stored chrome before a rebuild so later automatic rerenders can't re-inject stale dark chrome.
- **sources:** RUNBOOK_scheme_to_components(18).md W4b + STEP-1 RESULTS; running_notes(22).md §Sy-Ta; w4b_03_read_rerender_config.sql
- **relations:** rerender-pages v6 workflow (page-build-pipeline register, PBP-002); rerender fossilisation (REB-005); F3 scoped rerender (REB-001, same agent)
- **verify-later:** render_site_components_action.go:345-430; rerender-pages v6 check_refresh_components gate
