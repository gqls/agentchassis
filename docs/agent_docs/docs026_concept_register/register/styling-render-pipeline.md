### STY-013 — Dual chrome render paths (build-fresh vs stale rerender-injected)
- **status:** deployed
- **status-evidence:** W4b executed and verified 2026-07-02 (header 3750→6258B, footer color-mix in); an earlier, less specific read of the same mechanism (from a parallel vonc-site thread) had flagged the paired-variable fix as not yet confirmed deployed — superseded by this dated, code-verified remedy.
- **what:** Chrome has two render paths: the page-compile path (page-build-handler → CompilePageSections → InjectHeader/Footer → RenderHeader/Footer) renders fresh, while `render_site_components` writes `site_components.rendered_html`, which the rerender path injects into pages unconditionally. The pinned-component join ignores `is_active`, and non-force runs skip non-empty slots — so stale renders of deactivated components ("fossilised" chrome, tagged by legacy `--accent-color` vars) persist indefinitely; nothing refreshes `site_components` on deactivation and `needs_rerender` just re-fossilises. Remedy pattern: repoint `site_components.component_id` to the active components first (rendered_html left in place so there's no chrome-less window), then trigger rerender-pages with `spec.refresh_site_components: true` — repoint-before-force_rerender ordering matters, or the old dark chrome re-renders.

- **what:** two leaf primitives in `datahelpers`, plus the seam that makes their absence loud. **`UpperFirst(s)`** upper-cases the FIRST RUNE and leaves the rest byte-identical — the rune-safe replacement for the `strings.ToUpper(s[:1]) + s[1:]` idiom, which this estate hand-rolled at **8 call sites as of 2026-09-02** and which is a BYTE slice: given a word whose first rune is multi-byte it hands `ToUpper` a lone lead byte (decoded as U+FFFD) and re-attaches the orphaned continuation bytes. **`InvalidUTF8At(s)`** returns the byte OFFSET of the first invalid sequence with a `QuoteToASCII`'d window around it — pure ASCII, so the report is itself storable.
- **why it is not a tidy-up: Postgres REFUSES invalid UTF-8**, so a severed rune does not degrade quietly — it kills the statement that tries to persist it. `render_site_components`' footer store failed with `invalid byte sequence for encoding "UTF8": 0x80 (SQLSTATE 22021)` on **2 live sites** because a page title contained a STANDALONE em-dash, which `strings.Fields` makes its own word, so `w[:1]` cut it after one byte. boxingonline.com had been failing since 2026-08-31; garden-tools.uk since **2026-08-23**, i.e. ten days unnoticed, because of the observability half below.
- **the discriminating census (2026-09-02), stated because a weaker one had already been run and did not discriminate:** "the footer contains multi-byte characters" explains nothing — 32 of 32 stored footers contain them and all stored fine. The cause must CUT at a byte offset. Sites whose services-column labels (the same predicate the query uses, within its `LIMIT 6`) contain a word whose FIRST rune is multi-byte: **exactly 2 — boxingonline.com and garden-tools.uk**. Sites whose `site_components` footer is not `build_status='rendered'`: **exactly the same 2**. Every other footer on the fleet is `rendered` with a matching digest. Zero false positives, zero false negatives.
- **the observability half (`bugs_open/423` half 1), and why it is the enabling defect:** `renderAndStoreSiteComponent`'s store-failure branch logged the error and returned a **nil** error, so the caller's `chrome_render_failed` map never heard it: the step completed SUCCESS with `rendered.footer=false` as its only trace, `ineligible_chrome` and `locked_slots_preserved` empty. Two sessions spent about an hour eliminating locks, component eligibility and empty `content_data` before a live pod-log capture named the actual refusal. That branch now takes the **same** surface the execution-failure branch already had (STY-057's `chrome_render_failed`), with the same disposition: previous bytes keep serving; a site with **nothing** stored for the slot fails the step.

The gate reports the OFFSET and the neighbouring text, so **the next** byte-indexed slice introduced anywhere upstream of this seam is attributable in one read. It **REFUSES rather than sanitises**: `strings.ToValidUTF8` would make the store succeed, and this path has no gate downstream — whatever it stores is what the site serves (STY-057) — so sanitising would ship silently mangled text over working chrome AND leave the upstream cut in place to keep producing it.
