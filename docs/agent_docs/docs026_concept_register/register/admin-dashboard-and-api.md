### ADM-012 — Approval fan-out: one human APPROVE can file N follow-on work items, opt-in per checkpoint
- **status:** built, committed, **NOT live** — the Go half is in `internal/core-manager/admin` and needs an admin/core-manager image and a roll. Config half (migration `750`, copy-editor) is harmless before that roll: an older binary simply ignores the new keys.
- **status-evidence:** committed `33dfeed3a` 2026-09-03, revised through `a09d4594c` / `01b85c30a` / `b10e85387` / `bfc2925ce`. **9 tests** (`internal/core-manager/admin/approve_fan_out_test.go`), **10 mutations across 4 council rounds, all killed**; `verify-head-builds.sh --test ./internal/core-manager/...` green against HEAD `3d27e5bd8`. Council `d04c1bc1-b9a3-41bb-b144-1d101e68e542` **APPROVED at round 3** (rounds 1 and 2 were REVISE and each found a real defect). To check whether it is live: `git merge-base --is-ancestor 33dfeed3a <the admin-dashboard build stamp>`.
- **what:** `checkpoint_for_review` parks work for a human and embeds an `on_approve` block; `HandleApproveWorkItem` (`POST /admin/work-items/:item_id/approve`) turns the press of APPROVE into a follow-on work item. It could previously file **exactly one**, which is wrong for any reviewer that proposes a LIST — a copy edit touching two sections has no single target. `on_approve` now takes two optional keys: **`fan_out_from`** (names an array in the approved data; files one follow-on per element, merging that element's own fields at the **top** of the child spec, where the handler agent's action inputs read them) and **`defaults`** (fields the proposal does not itself carry — e.g. `edit_type`). Merge order is defaults → `include_fields` → element fields → provenance **last**, so an element cannot overwrite `approved_by` / `source_item_id`. Both keys default **absent**: an `on_approve` naming neither behaves byte-identically to before (owner ruling 2026-08-02 §2 — new authority on a shared seam ships opt-in with the unsafe side OFF). Four further properties worth knowing before you use it. (a) A fanned-out element whose `page_component_id` no longer resolves on that site is **refused and reported**, never filed — a rerender replaces the component row with a new id, and `[MEASURED 2026-09-03]` 3 of 31 parked edits already pointed at a deleted row. (b) An element whose target may have MOVED since the proposal is **warned about and still filed**, NOT refused: `page_components.updated_at` cannot distinguish a content edit from a status-only write (LANDMINES), so a refusal on it would decline fresh approvals. A real refusal needs the proposer to stamp each edit with the target's `content_hash` — an open follow-up recorded in `bugs_open/466`, and copy-editor's change, not this handler's. (c) All children of one approval share a `batch_id`. (d) The review row's `result` records `follow_on_items[]`, `skipped_edits[]`, `stale_warnings[]` and `fan_out_note`, so `complete` is no longer the only thing an approver can see — and a per-element INSERT failure lands in `skipped_edits` rather than quietly shortening the list.
- **⚠ the same change repaired `include_fields`, which had NEVER worked.** It resolved its names against the review item's **spec**, and `checkpoint_for_review` writes a fixed key set that can never hold them. `[MEASURED 2026-09-03, all history]` **42** mentions across **21** items since 2026-08-24, **0** resolvable. It now falls back to the approved body (spec still consulted first, so nothing that worked can change), and a name absent from both is written **absent** rather than as an explicit `null`. **This does not mean you can put arbitrary fields at a review item's spec top** — you still cannot; put them in `review_data`, or supply them via `defaults`.
- **sources:** `internal/core-manager/admin/site_admin_handlers.go` (`HandleApproveWorkItem`); `platform/orchestration/actions/checkpoint_for_review_action.go`; `docs/agent_docs/sql_for_agents/750_copy_editor_approval_fans_out_one_section_edit_per_edit.sql`; `bugs_open/466`
- **⚠ this handler's `result` write is the DELIVERY GATE's only evidence.** `platform/delivery.Reviewed()` asks `status = 'complete' AND result ? 'approved_by'`. The fan-out appends a second jsonb object to that write, which puts the key one edit from a right-hand-side collision (`||` lets the right side win) and one from annihilation (`jsonb || NULL` is NULL). The second is closed by `COALESCE(…, '{}'::jsonb)`; the first is held by a test. Neither was reachable when found. **Do not add a key named `approved_by` to that object.**
- **relations:** admin API (ADM-002, the HITL review flow this sits in) · `checkpoint_for_review` (the producer half) · `section-editor` / `load_edit_context` / `apply_section_edit` (the first consumer, via copy-editor) · `bugs_open/033` (why the path was never exercised, so the deadness was invisible rather than latent) · `LANDMINES.md#checkpointforreview-writes-a-fixed-key-set`
- **verify-later:** whether a second consumer adopts `fan_out_from` — as of 2026-09-03 copy-editor is the only one, and the only other `on_approve` producer (`fork_theme_from_site_action.go`) has no `item_type`, no `include_fields` and no `checkpoint: true`, so it 400s before reaching this handler
