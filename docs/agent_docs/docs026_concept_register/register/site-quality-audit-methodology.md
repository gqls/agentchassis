### SQAM-001 — Three-way split quality-gap diagnostic method (stuck / poor / out-of-scope)
- **status:** aspirational
- **status-evidence:** Framed as the mission-defining method for the whole runbook: "measure which legs never dispatched, which dispatched but produced poor output, and which were never in scope at all, then fix in that order."
- **what:** A triage discipline for closing the gap between "a site deploys" and "a site is best-in-class for its vertical": split every quality shortfall into (A) dispatched-but-stuck-or-never-delivered (chrome/design/imagery — fix first), (B) delivered-but-poor (content depth, link integrity — fix second), and (C) never-in-scope (feeds/news/graphics/games never planned for — planning-criteria fixes, not build bugs — fixed third). Explicitly evidence-first: "0-rows not decisive until the query is checked." This is the audit method that the Site Quality Programme (SQ-001) applies operationally.
- **sources:** dartsonline.com_site_quality/RUNBOOK_site_quality.md#THE TASK,#THE THREE-WAY SPLIT

### SQAM-002 — Baseline mechanical quality measurement methodology
- **status:** deployed
- **status-evidence:** A concrete, dated (2026-07-06) measured table exists: per-page bytes/nav/img/svg/script/css-var-refs/stylesheet-links counts for four rendered pages.
- **what:** A cheap, deterministic, pre-LLM measurement pass over a site's rendered HTML output (byte count, `<nav>` count, `<img>` count, `<svg>` count, `<script>` count, CSS custom-property reference count, stylesheet link count) used to form falsifiable hypotheses about missing pipeline stages before spending any LLM audit budget.

- **relations:** Site-chrome rendering gap (SQ-002); Three-way split quality-gap diagnostic method (SQAM-001)
- **verify-later:** repeatability of this measurement as a scheduled/automated check vs one-off manual pass

### SQAM-003 — Independent-oracle arithmetic validation for calculators (correctness, not consistency)
- **status:** built and exercised on one site (loanandmortgagecalculator.co.uk, 2026-08-08); no automated schedule, no platform integration yet — nothing else calls it
- **status-evidence:** 176 checks across 18 tools driven against the live site in a real browser; 143 PASS / 27 FAIL / 6 CONVENTION, plus 21 class-C invariant checks. Found two defect families that every existing check had certified as fine: `bugs_open/225` (SDLT running an HMRC rule that expired 2025-03-31, flat £5,000 under-quote) and `bugs_open/224` (a 0% rate breaking six of seven calculators).
- **what:** A method and a runnable harness for asking whether a calculator gives the RIGHT answer, as distinct from the same answer as last time. Four parts, each of which is the part that fails if omitted. (1) **Independence by construction** — the per-tool spec is authored from the page's visible `<label>`, button text and result caption (`inventory.py`), never from its `<script>`, and the calculation body is opened only AFTER a check has failed; an oracle transcribed from the code it checks agrees with the bug. (2) **Expectations from published definitions** (`oracles.py`: the annuity formula, the gov.uk SDLT bands with their effective dates, amortisation run month-by-month, arithmetic identities) — no reference to the artefact under test. (3) **Boundary vectors chosen per tool**, on band edges and degenerate inputs (0% rate, one-month term, zero balloon, the £40,000 SDLT floor), because a generic harness that scales each field's own default to stay in-domain can never land on an edge. (4) **Controls that must come out red** — mutate the expectation, mutate the input parse, and judge each vector against a NEIGHBOURING vector's expectations on the real page; the criterion is "no check may PASS under mutation", and stray passes are excluded by printed name (`NON-TEST`, `MUTATION DID NOT BITE`) rather than by loosening a threshold. Two reporting distinctions carry most of the signal: a defensible alternative CONVENTION (billed vs exact payment) is separated from a NAMED WRONG ANSWER (an expired tax rule), because one bucket for both lets the machinery that names a cause excuse it; and tolerance is derived from the tool's own display precision and printed on every line, since a whole-pound display cannot be checked to the penny by anyone. Includes `run_determinism`, which drives one vector by two routes to detect a guarded handler that writes nothing and leaves a stale answer on screen — a failure no value comparison and no single primed reading can see. Class C tools (scoring models with no external right answer) get labelled INVARIANT checks instead — monotonicity, bounds, determinism, state round-trip, and the genuinely-arithmetic aggregation inside a scoring tool — explicitly reported as weaker evidence than an oracle.
- **sources:** loanandmortgagecalculator_couk/oracle.py, oracles.py, oracle_driver.py, invariants.py, inventory.py; loanandmortgagecalculator_couk/REPORT_2026-08-08_arithmetic_validation.md; RUNBOOK_loanandmortgagecalculator_couk.md §13; 016b §9 ("A regression baseline recorded from a NEVER-CORRECT artefact"); bugs_open/224, bugs_open/225
- **relations:** complements — does NOT replace — the behavioural golden (`loancalculator_couk/toolgolden.py`, `golden_compare_post.py`), which proves consistency and structurally cannot refute; `oracle_driver.Driver` subclasses `toolgolden.Runner` for browser handling. Upstream of `--emit-criteria` / `computed_values`: emitting Tier-4 criteria from an un-oracled tool pins its wrong answers into the acceptance record and then defends them, so this is the gate that should precede emission. Baseline mechanical quality measurement methodology (SQAM-002).
- **verify-later:** whether the oracle specs belong in the platform (a `computed_values` criteria emitter fed from `oracles.py`) rather than in a lane directory; and whether the class-A/B/C classification generalises to other calculator sites (loancalculator.co.uk, mortgagecalculator.co.uk carry overlapping tools)
