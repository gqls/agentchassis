A Crucial Concept

The agents in the website builder team (like site-architect) don't run in their own dedicated pods. Instead, their tasks are picked up by one of the generic agent-chassis pods you have running. We need to find the unique IDs of your newly spawned agents and then look for those IDs in the agent-chassis logs.

Step 2.1: Find Your Newly Spawned Agent IDs

The spawn_group action creates new rows in the agent_instances table. Let's find the IDs for the agents in your new team.

    Command:
    Bash

    kubectl exec -it postgres-clients-0 -n ai-persona-system -- psql -U clients_user -d clients_db -c "SELECT name, id, config->>'agent_type' as type FROM client_demo_client.agent_instances ORDER BY created_at DESC LIMIT 10;"

    Action: Look for the new agents like site-architect, html-developer, etc., and note their UUIDs.

Step 2.2: Watch the agent-chassis Logs

Now, stream the logs from all agent-chassis pods and look for activity related to your new agent IDs.

    Command: (Run this in another new terminal)
    Bash

    kubectl logs -f -n ai-persona-system deployment/agent-chassis

What You'll See:

As the workflow progresses, you'll see log entries from the agent-chassis pods that are tagged with the specific agent_instance_id you found in the previous step. This is how you can trace the work of each individual agent as it executes its part of the plan.

Your agent pods (e.g., content-creator-agent) act as generic engines waiting for work. The command below doesn't create new pods; instead, it creates a new

task in the database by spawning an "agent group". An available engine then picks up this task and executes the specific workflow.

    Get a Shell in the Kafka Pod This command places you inside the cluster, ready to send the message.

Step-by-Step Guide to Your First Website Build 🚀

Running the website builder is the perfect way to see the whole system collaborate. It's a fantastic example of a complex task being broken down and executed by a specialized team of agents.

Based on my analysis of your code, here’s a step-by-step guide to how it works and how you can run it.

High-Level Overview

The process begins when a request is made to spawn an agent group of type website-builder. An orchestrator agent takes over and directs a team of specialized agents to perform the necessary tasks: planning the site structure, designing visuals, developing the code, and finally publishing the result.

Step 1: The Trigger - Spawning the Team

Everything starts with a spawn_group action for the website-builder group type. This is the starting pistol for the entire operation.

    What happens? The SagaCoordinator receives this request and looks up the website-builder definition in the agent_groups table of your database.

    Key Files:

        platform/orchestration/actions/spawn_actions.go: Contains the SpawnGroupAction logic.

        platform/database/migrations/007_initial_website_builder_group.sql: Defines the initial team composition and workflow.

Step 2: The Orchestrator Takes Charge

Once the group is spawned, the website-builder agent itself acts as the orchestrator. It follows a predefined workflow to manage the project from start to finish.

    What happens? The orchestrator follows the orchestration_workflow defined for its group. It calls other agents in a specific sequence to build the website.

    The Workflow Plan:

        analyze_domain: Calls the domain-analyst agent to research the business type.

        architect_site: Calls the site-architect to plan the website's structure and pages.

        gather_content: A fan_out step that runs two agents in parallel: the content-researcher (a content-creator agent) and the visual-designer to gather text and images.

        develop_site: Calls the html-developer to write the actual HTML, CSS, and JS code.

        publish_site: Calls the site-publisher to deploy the finished website.

    Key File: platform/database/migrations/005_website_builder_agents.sql is crucial as it defines the entire orchestration logic and the capabilities of each agent involved.

Step 3: The Specialist Agents Do the Work

Each agent in the group has its own specialized workflow.

    What happens? The orchestrator sends tasks to specific Kafka topics, and the corresponding agents pick them up.

        The domain-analyst uses the web-search adapter to research the industry.

        The site-architect pauses for human approval after creating the site structure, showing how you've integrated human-in-the-loop actions.

        The visual-designer calls the image-generator adapter to create a logo and other visuals.

        The html-developer uses a fan_out to generate code for multiple pages in parallel.

    Key Files:

        internal/agents/*: The implementation for each agent type resides here.

        internal/adapters/*: The logic for external-facing agents like web search and image generation.

How to Run Your First Website Build

The easiest way to trigger this entire process is to send a Kafka message that kicks off the workflow. You have a handy tool for this in tools/kafka-producer/send_test_message.go.

Step-by-Step Command Guide:

    Ensure your services are running, especially the core-manager and all the necessary agents (domain-analyst, site-architect, etc.).

    Build the Kafka producer tool (if you haven't already):

    go build -o ./bin/tools/kafka-producer ./tools/kafka-producer/send_test_message.go

Craft the initial message. The workflow starts by spawning the website-builder group. We'll send a message to a generic agent whose job is to kick off this process.

Send the Kafka Message:
Execute the following command from your project root. This command sends a message to the system.agent.generic.process topic, which will be picked up by a generic agent that then executes the spawn_group action.

./bin/tools/kafka-producer \
  -agent="generic" \
  -payload='{
    "action": "spawn_group",
    "data": {
      "group_type": "website-builder"
    }
  }' \
  -wait


After running this, you can use your database inspection tool (tools/db-inspector/check_state.go) to watch the orchestrator_state table and see the workflow progress from step to step!
