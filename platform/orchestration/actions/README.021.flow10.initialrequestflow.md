Root Cause

The issue lies within the logic of messaging/context.go:NewMessageContext.

    The function correctly parses the incoming headers into an initial context object (senderCtx). The logs confirm this senderCtx contains message_type: "request".

    However, for any message that isn't a response or an initialize action, the function enters an else block.

    Inside this block, it creates a brand new, minimal ExecutionContext object (execCtx). It only populates a few fields like OrchestrationID and CorrelationID.

    Crucially, it does not copy the MessageType field (or most other fields) from the original senderCtx into this new execCtx.

    This new, incomplete execCtx is then assigned to the MessageContext.

    When ValidateContext() is called later, it checks this new context, finds MessageType is an empty string, and returns the validation error you are seeing.

The Core Principle 🎯

The fundamental pattern is a chain of delegation:

    A parent agent starts or continues an orchestration with its own OrchestrationID.

    When it calls a child agent, it creates a new ExecutionContext for that child.

    In the child's context:

        The child gets a new, unique OrchestrationID for the specific task it's being given.

        The parent's OrchestrationID is put into the child's ParentOrchestrationID field.

    The parent tells the child exactly where to send its response by setting the responses_topic header in the message.

This creates a clear hierarchy, allowing the parent to manage many child tasks while each child focuses only on its own work.

The Initialization Handshake 🤝

Here is the more detailed sequence for a single spawn_agent action, such as spawn_adder:

Step 2a: generic Agent Sends initialize Request

This is the first message sent from the parent (generic agent) to the new pod (adder agent).

    Action: The spawn_agent action dispatches an initialize request.

    ExecutionContext state of the message sent to the adder:

        OrchestrationID: A new UUID for this initialization task (e.g., d4e5f6a7-...).

        ParentOrchestrationID: 3b2927cc-... (the generic agent's main orchestration ID).

        Action: initialize.

        responses_topic: The job-specific topic for the generic agent's orchestration (e.g., job.<stable_identity>.responses).

    Parent State: The generic agent's orchestrator now pauses the workflow. It is in a "waiting" state, specifically for a response to the initialize request it just sent. It will not proceed to spawn_multiplier yet.

Step 2b: adder Agent Confirms with initialized Response

The newly started adder pod receives the initialize message. The code in processor.go (around line 1172) specifically handles this action. It configures itself (e.g., sets its internal agentRole to "adder") and then sends a confirmation response.

    Action: The adder agent's initializer.SendInitializationResponse() function sends a response message back.

    ExecutionContext state of the confirmation sent from the adder:

        MessageType: response.

        Status: complete or a similar success indicator.

        InResponseTo block: Contains the request_id of the initialize message from Step 2a.

        OrchestrationID: d4e5f6a7-... (its own ID for the initialization task).

        ParentOrchestrationID: 3b2927cc-... (the parent's ID).

    Parent State: The generic agent's orchestrator, listening on its job topic, receives this confirmation. It matches the response to the waiting spawn_adder step. Now that the step is confirmed, the orchestrator resumes the workflow and moves on to the next step, spawn_multiplier.

The core issue is about responsibility.

    The Sender of a message is responsible for creating the context. When the generic agent decides to spawn or call the adder agent, it is the generic agent's job to correctly construct the headers, including setting its own OrchestrationID as the child's ParentOrchestrationID.

    The Receiver's NewMessageContext function is only responsible for reading and deserializing that context. It should trust the headers it receives.

The old logic was flawed because the receiver was trying to do the sender's job. It was trying to guess the relationship based on the message type, leading to incorrect context creation and the validation errors you saw.

How the Correct Behavior Works Now

Let's trace the ParentOrchestrationID with the new, correct logic.

    Client -> generic agent

        The client sends a message with ParentOrchestrationID = "" (or the header is absent).

        The generic agent's NewMessageContext reads the headers exactly as they are. The ExecutionContext inside the generic agent correctly has an empty ParentOrchestrationID.

    generic agent -> adder agent (initialize request)

        The spawn_agent action within the generic agent prepares the new message.

        It takes its own OrchestrationID (3b2927cc-...) and explicitly places it in the parent_orchestration_id header of the outgoing message.

        It also creates a new, unique OrchestrationID for the child's task.

    adder agent receives the message

        The adder agent's NewMessageContext is called.

        It simply reads the headers. It sees parent_orchestration_id is 3b2927cc-... and populates its ExecutionContext accordingly. No special logic is needed. It just accepts the context it was given.
