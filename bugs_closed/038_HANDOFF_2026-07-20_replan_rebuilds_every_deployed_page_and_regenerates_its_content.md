# Handoff — a re-plan rebuilds EVERY deployed page and regenerates its content

**Filed 2026-07-20**, measured while verifying the `/bugs_open/001` fix live on dartsonline.com.
`001` secured a built page's **structure**; this is the other half — its **copy**. They are
independent defects and fixing one does not touch the other.

## The defect

`decideEmit` (`platform/orchestration/actions/reconcile_site_plan_action.go:341`) decides whether a
plan page needs building. Its "already built, leave it alone" branch requires the page's
`built_from_plan_version` to equal the **current plan id**:

```go
if !realised.BuiltFromPlanVersion.Valid { return "stale" }
if realised.BuiltFromPlanVersion.UUID != planID { return "stale" }
return "skip_built"
```

A re-plan writes a **new** `site_plans` row, so `planID` changes for the whole site at once. Every
deployed page therefore fails that equality and comes back `"stale"` → a `needs_page` item →
page-build-handler rebuilds it → **the page's components are regenerated by the LLM**.

`built_from_plan_version` is only ever *filled*, never re-stamped for an unchanged page:
`site_db_actions.go:1127` uses `COALESCE(pages.built_from_plan_version, EXCLUDED.…)`, so an existing
value is preserved, and the page-status writer (`v3_site_actions.go:663-674`) stamps it on deploy.
Nothing says "this page's composition did not change; carry its stamp forward".

## Evidence (dartsonline.com, 2026-07-20, plan `fba367c9` → `5d438145`)

`orchestration_states.collected_data->'reconcile_result'` for run `c342cffa`:

```json
{"pages_total": 17, "pages_emitted": 16, "pages_skipped_built": 0,
 "pages_review_emitted": 1, "rerender_emitted": true}
```

**`pages_skipped_built: 0`.** All three deployed pages (`about`, `new-arrivals`,
`shipping-returns`) were emitted, each with `spec.reason = "stale"`:

```sql
SELECT item_type, status, summary, spec->>'reason'
FROM site_work_items WHERE site_id='5fe8785b-223d-41a3-88ee-c07187622381'
  AND source='reconcile_site_plan' AND created_at > '2026-07-20 09:40';
-- Build about page (stale) / Build new-arrivals page (stale) / Build shipping-returns page (stale)
```

`about` then rebuilt at 09:48:51 — every one of its four `page_components` rows has
`created_at == updated_at == 09:48:51`, i.e. all four were **written fresh**, not reused.

Note what this means alongside `001`: the 001 fix worked, and `about` kept its exact section list
(`hero-about, about-content, differentiators, call-to-action`). The **structure** was preserved and
the **content inside it was regenerated anyway**. A guard on composition does not protect copy.

## Why it matters

1. **Human-reviewed copy has an undefined shelf life.** Any page a person has read, corrected and
   approved is silently rewritten by the next re-plan of that site, even when the plan asks for no
   change to that page. `page_components` has `locked_at` / `lock_type` / `lock_expires_at` and the
   discovery checks honour them — whether this rebuild path does is **unverified**, and is the first
   thing to check (see fix candidate 3).
2. **It is a fabrication surface.** Regenerating copy re-runs the writer against whatever
   evidence/spec it has now. On a site governed by "no claim ships without an evidence row", an
   unrequested rewrite is where audited-out claims come back.
3. **It is pure waste at scale.** A re-plan of a 35-page site re-runs the content writer for all 35
   deployed pages to end up, in the common case, at the same composition. That is the whole point of
   `skip_built`, and it currently never fires after the first plan.

## Fix candidates

1. **Re-stamp instead of rebuild when nothing changed (preferred).** In the reconciler, compare the
   plan's section list for a page against `pages.sections`. If they match and the page is
   `deployed`, update `built_from_plan_version` to the new plan id and return `skip_built` rather
   than `stale`. This makes "stale" mean *the plan actually changed this page*, which is what the
   name implies and what the caller assumes. Note `pages.sections` stores component **functions**,
   and the plan stores what the LLM wrote — compare after the same normalisation
   `write_site_plan_action.go` applies, or the comparison will false-negative (see `/bugs_open/039`).
2. **Carry the stamp at sync time.** Have `sync_pages` re-stamp `built_from_plan_version` for any
   page whose synced composition is unchanged. Cheaper, but it moves a reconciler concern into the
   writer and is easy to get wrong for genuinely-changed pages.
3. **Honour content locks in the rebuild path, whatever else is decided.** Independent of 1 and 2:
   a rebuild must not overwrite a `page_components` row with `locked_at IS NOT NULL`. If it already
   does honour them, say so in the code and close that half; if not, this is the smallest change
   that stops human review being discarded.

Candidate 1 is the structural fix; 3 is worth doing regardless, because "the plan genuinely changed
this page" still should not silently discard reviewed copy — it should surface a diff for review
(`/bugs_open/033` is the missing surface for exactly that class).

## How to verify a fix

1. Re-plan a site whose deployed pages the LLM re-proposes identically. Assert
   `reconcile_result.pages_skipped_built` equals the number of unchanged deployed pages, and that
   **no** `needs_page` item is emitted for them.
2. Assert those pages' `page_components.updated_at` are **unchanged** afterwards — the artefact, not
   the status.
3. Assert a page the plan genuinely re-composes IS still emitted (do not fix this by never
   rebuilding).
4. Lock a `page_components` row (`locked_at`), force a rebuild of its page, and assert the locked
   row survives.

> **CORRECTION to candidate 1 as written above.** It says "compare the plan's section list for a
> page against `pages.sections`". **That comparison cannot work**, and it would have been the wrong
> fix. The build-site-planner workflow runs `write_site_plan → sync_pages → reconcile_site_plan`
> (`docs/agent_docs/sql_for_agents/053_build_site_planner.sql:8`). `sync_pages`
> (`SyncPagesToDBAction`) upserts every plan page with `sections = EXCLUDED.sections`
> (`platform/orchestration/actions/site_db_actions.go:1126`), sourcing sections from the **new**
> plan. So by the time `reconcile_site_plan` runs, `pages.sections` has **already been overwritten to
> equal the new plan** — comparing plan-sections to `pages.sections` is a tautology (always equal),
> which would make it *always* re-stamp and *never* rebuild, discarding genuinely re-composed pages.
> Nothing else writes `pages.sections`: the deploy-time writer `UpdatePageStatusAction`
> (`v3_site_actions.go:671-680`) stamps `built_from_plan_version` but does **not** touch `sections`.
>
> **Live confirmation (2026-07-21):** of 144 deployed pages fleet-wide, 138 are stamped
> `built_from_plan_version = current plan`; the 6 built from an older version all have
> `pages.sections` matching the **current** plan's `site_plan_sections`, not their build plan's — the
> fingerprint of the sync overwrite.

**What shipped instead — a plan-to-plan comparison on `site_plan_sections`, which is per-plan and
immutable.** In `decideEmit` (`platform/orchestration/actions/reconcile_site_plan_action.go`), a
page that is `deployed` from an **older** plan version is no longer unconditionally `stale`. The
reconciler now loads the ordered section list (normalised via `NormalizeComponentFunction`) for the
current plan **and** for the plan version the page was built from, both from `site_plan_sections`. If
the two lists are identical, the page's composition did not change: it returns a new `"restamp"`
decision, the caller updates `built_from_plan_version` to the current plan **in the same
transaction**, and the page is skipped. A genuine change (different list, reorder, or the built-from
list is unknown) still returns `"stale"` → rebuild.

Why plan-to-plan and not "compare against the realised composition (`page_components`)": both plans
were written by the same `write_site_plan` path, so comparing them is apples-to-apples and needs no
name↔function resolution (`/bugs_open/039`). The signal answers the exact question — *did this
re-plan change the spec for this page?* — and it is robust to the sync overwrite. **Boundary:** if a
past build diverged from its plan (a `/bugs_open/039` hollow stub, or a `/bugs_open/001` drop that
got snapped back), plan-to-plan can skip a page whose live composition doesn't match its plan. That
is out of scope here — rebuilding under an identical plan would reproduce the same divergence, so it
is no worse; correctness-of-a-past-build belongs to 001/037/039.

**Safety direction.** A false *positive* (rebuild a page we could have skipped) is the status quo —
merely wasteful. A false *negative* (skip a page that actually changed) is the dangerous direction,
so `"restamp"` is gated on **positive** evidence: the built-from plan must carry a non-nil section
list for the page that equals the current one. Absence of evidence (nil built-from list) falls
through to a rebuild.

Result now also reports `pages_restamped` alongside `pages_skipped_built` (re-stamped pages count
into `pages_skipped_built` so it stays the total of deployed-and-unchanged pages, satisfying
verify-step 1).
