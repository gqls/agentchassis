It will have a correlation id which we can make up for this starter message
It will have the sender agent id (core manager or user) which we can make up for this starter message
It will have a request_id from core manager (made up for now)
It might have a step id from the core manager's orchestration so that core manager can correlate the requests to the steps, although the request id will probably take care of this, but somewhere there should be a correlation between a step id which might have multiple requests and responses attached to it. So a step id might be a useful label or it might just be confusing. 

so we need a step to request ids relation in the database.

The agent-chassis will have a simple orchestration which is to spawn the website builder group which is just one agent.

The agent-chassis agent should take the request from core manager/user, spawn the website builder, await responses - deal with a variety of responses e.g. awaiting response, error recoverable, error unrecoverable, correct response with data. It should then present that data back to core manager. It might at other times have a second step in it's orchestration to filter the responses and make sure they make sense for instance. It will then send a response back to core manager, the website might already have been saved in s3 so it may not contain the website data (or it might in another plan). So every agent needs to be able to handle these different types of response. They can record they have received them, or can record the ones that they correctly received and processed.

If they receive a response like awaiting response then they shouldn't necessarily pass that back up the chain in a message.

If they receive two or more identical messages with the same in_response_to id and the same step_id then they should deal with it properly e.g. just get rid of that message and ignore it. If the first message is garbled or not what is expected then a rerequest could happen but that would be the same step id with a different request id and a limited number of retries. hmm maybe we need a different id for this or it will get confusing as we won't know which retry they are responding to, or maybe it doesn't matter - they just respond to the first good one.

If another agent-chassis agent instance sends a message for the same step by accident which I guess might happen, it shouldn't have a different request id, it should have the same request id and the same step id, so the receiver of the response should know how many requests it expects from a step.

## Critical Design Decisions

### 1. Step-to-Request Mapping Table

**Database Schema:**
```sql
CREATE TABLE step_request_mapping (
    step_id UUID PRIMARY KEY,
    orchestration_id UUID NOT NULL,
    request_ids UUID[] NOT NULL,  -- Array of request IDs for this step
    expected_responses INTEGER DEFAULT 1,
    received_responses INTEGER DEFAULT 0,
    retry_count INTEGER DEFAULT 0,
    max_retries INTEGER DEFAULT 3,
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    FOREIGN KEY (orchestration_id) REFERENCES orchestration_states(orchestration_id)
);
```

### 2. Response Types and Handling

```python
RESPONSE_HANDLERS = {
```

### 3. Deduplication Strategy

```python
def handle_response(response):
    # Create response key for deduplication
    response_key = f"{response.in_response_to}:{response.status}:{hash(response.body)}"
    
    if response_key in processed_responses:
        log.info("Duplicate response ignored", response_key)
        return
    
    # For status updates, only keep latest
    if response.status in ['awaiting', 'processing']:
        # These can be received multiple times
        update_progress(response)
    elif response.status in ['complete', 'error_unrecoverable']:
        # Terminal states - only process once
        if is_step_complete(response.in_response_to):
            log.warn("Step already complete", response.in_response_to)
            return
        mark_step_complete(response.in_response_to)
        process_terminal_response(response)
```

### 4. Retry Logic with Same Step, Different Request

```python
def retry_step(step_id, attempt_number):
    # Same step, new request ID for retry
    new_request_id = uuid()
    
    # Update mapping
    step_request_mapping[step_id].request_ids.append(new_request_id)
    step_request_mapping[step_id].retry_count = attempt_number
    
    # Track both old and new request IDs
    awaited_requests.add(new_request_id)
    
    # Send retry with new request ID but same step context
    retry_message = {
        'headers': {
            'step_id': step_id,  # SAME step
            'request_id': new_request_id,  # NEW request
            'retry_attempt': attempt_number
        }
    }
```

```

2. Agent-Chassis → Test-One-v1 (calculate 2+2)
3. Test-One-v1 → Agent-Chassis (result: 4)
4. Agent-Chassis → Core Manager (complete: 4)
```

### Scenario 2: Duplicate Messages
```
1. Core Manager → Agent-Chassis (spawn test agent)
2. Agent-Chassis → Test-One-v1 (calculate 2+2)
3. Test-One-v1 → Agent-Chassis (result: 4)
4. Test-One-v1 → Agent-Chassis (result: 4) [DUPLICATE]
5. Agent-Chassis detects duplicate, ignores
6. Agent-Chassis → Core Manager (complete: 4) [ONCE]
```

### Scenario 3: Retry on Error
```
1. Core Manager → Agent-Chassis (spawn test agent)
2. Agent-Chassis → Test-One-v1 (calculate 2+2) [REQ_001]
3. Test-One-v1 → Agent-Chassis (error_recoverable)
4. Agent-Chassis → Test-One-v1 (retry with REQ_002, same step)
5. Test-One-v1 → Agent-Chassis (result: 4)
6. Agent-Chassis → Core Manager (complete: 4)
```

## Key Invariants to Maintain

1. **Each agent creates its OWN orchestration_id**
2. **Request IDs are unique per message, step IDs per orchestration step**
3. **Track request_ids in awaited lists, not step_ids**
4. **Response's in_response_to must match a tracked request_id**
5. **Terminal responses processed only once per step**
6. **Progress updates don't propagate up the chain**
7. **Parent context preserved but not used as own identity**
