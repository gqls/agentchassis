At 100,000 concurrent agents
Kafka is your first stress point — but not throughput, it's topic count.
Right now, every spawned agent gets two dedicated topics: job.{stable_identity}.requests and job.{stable_identity}.responses. At 100K agents, that's 200K topics. Kafka can technically handle this — large Kafka clusters run with hundreds of thousands of topics — but each topic has partitions (you're using 2 per topic), so you're looking at 400K partitions. A well-tuned Kafka cluster can handle around 200K partitions per broker before controller election and metadata propagation starts degrading. So you'd need roughly 3-5 brokers minimum just for the partition count, more like 8-10 for production headroom.
The bigger issue is topic creation churn. Your agents are Jobs — they spin up, create topics, do work, and exit. If you're cycling through 100K agents over a few hours, you're creating and (presumably) deleting hundreds of thousands of topics. Kafka's controller hates this. Topic creation involves writing to ZooKeeper (or the KRaft metadata log), propagating metadata to all brokers, and waiting for leader election on each partition. Your logs already show this — the "Waiting for topic to propagate to all brokers" messages with multiple attempts.
The fix: Stop creating per-agent topics. Instead, use a pool of shared work queues. Agents can be routed by a key in the message header (you already have correlation_id, orchestration_id, and sender_agent_id in your headers). A modest number of partitioned topics like system.agent-work.requests with 50-100 partitions, using the orchestration_id as the partition key, would handle 100K agents without creating a single new topic. Your chassis code would need to filter messages by agent ID instead of relying on topic isolation, but it's a straightforward change.
PostgreSQL is your second stress point.
Every agent lifecycle involves: reading its agent_definition at startup, creating/updating rows in orchestration_states, and writing content results. At 100K agents, the reads aren't the problem — agent definitions are a small table, easily cached. The problem is write contention on orchestration_states. Each workflow step transition does an UPDATE. If agents are averaging 5 steps each, and you're turning over 100K agents in an hour, that's ~140 writes/second. A single Postgres instance handles this fine.
But if 100K agents are all active simultaneously and hitting steps at the same time, you could see bursts of thousands of writes per second. PgBouncer helps with connection pooling (you already use it), but the real concern is lock contention if multiple agents are updating related rows, and WAL (write-ahead log) throughput. At this scale, you want your Postgres on fast NVMe storage and you might want to partition the orchestration_states table by date or client_id.
Kubernetes is your third stress point.
Each agent is a K8s Job, which means a Pod. 100K simultaneous Pods is well beyond what a single cluster handles comfortably. The standard guidance is around 5,000 nodes / 150,000 pods per cluster, but that assumes reasonable node density. More practically, the K8s API server and etcd become bottlenecks. Every Job creation is an etcd write. Every Pod scheduling event is a scheduler cycle. Every Pod status update goes through the API server. At 100K Jobs being created, scheduled, running, and completing — etcd will suffer.
At Rackspace specifically, you'd be limited by the number of nodes you can provision and the speed at which their infrastructure responds to scheduling requests.
The fix at 100K: You probably want 5-10 clusters with 10-20K agents each, using the dispatch pattern I described earlier. The dispatch layer distributes work across clusters, and each cluster's K8s API only sees its own share of the load.
At 1,000,000 agents
Now the game changes. Every layer needs a different approach.
Kafka: Shared topic pools are mandatory. You absolutely cannot create 2M topics. Even with shared pools, 1M agents producing and consuming messages means real throughput. If each agent exchanges 10 messages during its lifecycle (spawn, initialize, a few workflow steps, complete), that's 10M messages. If this happens over an hour, it's ~2,800 messages/second — Kafka handles this easily on a modest cluster. If it happens in 10 minutes, it's ~17K messages/second — still fine for a well-configured cluster with 10+ brokers. The bottleneck isn't message throughput, it's consumer group coordination. If you have 1M consumers in a single consumer group, rebalancing will be catastrophic. You'd want agents grouped into smaller consumer groups by cluster or by work type, each consuming from shared topic partitions.
PostgreSQL: 1M agents writing to orchestration_states means you need to rethink the storage layer. Options are: Citus (distributed Postgres, shards across nodes), CockroachDB (distributed, multi-region, survives node failures), or a sharding strategy where each cluster writes to a local Postgres and a reconciliation process merges state. I'd lean toward CockroachDB for this use case — it gives you multi-region writes without manual sharding, and your query patterns (lookup by correlation_id/orchestration_id) map well to its distributed key-value layer.
Alternatively, you could move orchestration state out of Postgres entirely and into something like Redis Cluster or Apache Cassandra for the hot path (current step, status), keeping Postgres only for the cold path (completed workflow history, content output). Your orchestration state updates are essentially key-value writes — they don't need relational joins.
Kubernetes: 1M simultaneous Jobs across Rackspace data centres means you'd need perhaps 50-100 clusters. But more fundamentally, you'd want to question whether K8s Jobs is still the right execution model. The overhead per Job is significant — Pod scheduling, image pull, container startup, sidecar injection, etcd records. For short-lived agents that run for 30 seconds to a few minutes, that overhead dominates.
At this scale, you'd likely want to shift from "one Job per agent" to "agent worker pools." Instead of spawning a new Pod for each agent, you'd have long-running worker Pods (like your current agent-chassis deployment) that pull agent work from the shared Kafka topics, execute workflows in-process (or in goroutines), and move on to the next one. Your chassis already has the orchestration engine — it just needs to run multiple workflows concurrently instead of one-per-Pod. This eliminates the K8s scheduling bottleneck entirely. You'd scale by adjusting the replica count on the worker deployment, not by creating Jobs.
Network: Cross-data-centre Kafka traffic becomes meaningful at 1M agents. If your Kafka cluster is in London and you have workers in Dallas, every message has ~100ms round-trip latency. There are several layers to this problem.
The fundamental query patterns
When you're looking at a tree of agents, you're really only ever doing a few things: going down (what are this agent's children and their results?), going up (who is this agent's parent chain back to root?), looking sideways (what are this agent's siblings — the other children of the same parent?), and searching across the whole tree by some property (find me all agents of type research-agent that failed, regardless of where they sit in the tree).
Going down one level is trivial — you already have the index:
sqlSELECT orchestration_id, owner_agent_type, orchestration_name,
       status, current_step, final_result
FROM orchestration_states
WHERE parent_orchestration_id = $1
```

Going up is also straightforward — follow `parent_orchestration_id` iteratively. But at 1M agents with trees 8-10 levels deep, doing recursive queries gets expensive. This is where Postgres **materialised path** helps. The idea is that each agent stores not just its parent, but its entire ancestry as a string:
```
/root-orch-id/level1-orch-id/level2-orch-id/this-orch-id
You'd add a column like tree_path ltree to orchestration_states. Postgres has a built-in ltree extension specifically for this. With it, you can do things that would otherwise require recursive CTEs in a single indexed query:
sql-- All descendants of a given agent (at any depth)
SELECT * FROM orchestration_states
WHERE tree_path <@ 'root_id.level1_id.target_id';

-- All ancestors of a given agent
SELECT * FROM orchestration_states
WHERE tree_path @> 'root_id.level1_id.level2_id.leaf_id';

-- All agents at depth 3 in a given run
SELECT * FROM orchestration_states
WHERE tree_path ~ '*.*.*.* ' AND correlation_id = $1;
```

The `ltree` index makes these fast even at millions of rows. Setting the path is cheap — when spawning a child, the parent just prepends its own path to the child's ID. You're already passing parent context during spawn in your Kafka headers, so adding the path is a small change in `spawn_actions.go`.

## The practical navigation interface

But raw SQL isn't how you'd actually use this day to day. What you'd want is an API and eventually a UI that lets you do something like a filesystem:
```
GET /trees/{correlation_id}
  → returns the root agent with summary stats (total agents, depth, status counts)

GET /trees/{correlation_id}/root/children
  → returns immediate children of the root

GET /agents/{orchestration_id}
  → returns this agent's full state (collected_data, final_result, status)

GET /agents/{orchestration_id}/children
  → returns its children

GET /agents/{orchestration_id}/ancestors
  → returns the path from root to this agent

GET /agents/{orchestration_id}/subtree?max_depth=2
  → returns this agent and all descendants up to 2 levels deep

GET /trees/{correlation_id}/search?agent_type=research-agent&status=FAILED
  → finds all matching agents anywhere in the tree
This maps directly onto your existing API patterns in the core-manager. You already have SystemHandlers that query orchestration_states — these would be new endpoints on the same service.
The summary problem
At 1M agents, you don't want to load the whole tree. What you actually want at any given level is a summary — "this parent has 47 children, 43 completed, 3 failed, 1 running" — not the full details of all 47. The details come when you drill in.
This means each parent agent should store an aggregated summary of its subtree. You already have subtree_agents as a jsonb field. At completion, when a child reports back to its parent, the parent could update its own subtree_agents with a running count:
json{
  "total_children": 47,
  "by_status": {"COMPLETED": 43, "FAILED": 3, "RUNNING": 1},
  "by_type": {"research-agent": 12, "content-creator-hero": 5, ...},
  "total_descendants": 2340,
  "deepest_level": 4,
  "failed_subtrees": ["orch-id-1", "orch-id-2", "orch-id-3"]
}
This lets you render a tree view where you see summary counts at each node and only load the details when you expand a node. The root's subtree_agents gives you the whole-run dashboard in a single row read.
Tagging and semantic navigation
For the more interesting simulations — the economy simulation, the ecological model, the job market — you'd want to navigate by meaning, not just by tree position. "Show me all the agents representing fast food businesses that went bankrupt" or "find the river corridor agents that reported water table drops."
This means agents need semantic tags. You could add a tags jsonb column (or use a separate agent_tags table with a GIN index), and have agents tag themselves during execution:
json{
  "domain": "fast-food",
  "sub_domain": "pizza-delivery",
  "region": "midlands",
  "outcome": "bankrupt",
  "bankrupt_month": 14
}
Then:
sqlSELECT orchestration_id, orchestration_name, final_result
FROM orchestration_states
WHERE correlation_id = $1
  AND tags @> '{"domain": "fast-food", "outcome": "bankrupt"}';
GIN indexes on jsonb make this fast. The tags are set by the agent's workflow — a simple step at the end of execution that writes a structured summary of what this agent represents.
The live view problem
During a run, you want to watch the tree growing in real time. Polling the database works for small trees but not for 1M agents. Here's where your existing Kafka architecture helps — every agent already publishes messages to topics. You'd add a lightweight consumer that listens to a system.tree.events topic (or just taps the existing response topics) and maintains an in-memory tree structure for the current run. A WebSocket endpoint on your API serves this to a browser-based tree viewer.
The viewer doesn't show 1M nodes — it shows the top few levels with aggregate counts, and you expand on demand (which triggers the REST API queries above). The WebSocket pushes count updates in real time: "node X just went from 42/47 complete to 43/47 complete."
At 1M scale specifically
The ltree path approach works up to a few million rows on a single Postgres instance. Beyond that, you'd want to consider partitioning orchestration_states by correlation_id (each run gets its own partition), so queries within a single run are fast and old runs can be archived or dropped cheaply.
For the really large simulations, you might also want a separate lightweight "tree index" table that stores only the navigation-relevant fields (orchestration_id, parent_id, tree_path, agent_type, status, tags) without the heavy jsonb blobs (collected_data, final_result). This table stays small enough to scan quickly for tree operations, and you join to the full table only when the user drills into a specific agent's details.
sqlCREATE TABLE agent_tree_index (
    orchestration_id uuid PRIMARY KEY,
    correlation_id uuid NOT NULL,
    parent_orchestration_id uuid,
    tree_path ltree,
    depth int,
    agent_type varchar(50),
    agent_role varchar(50),
    orchestration_name varchar(255),
    status varchar(50),
    tags jsonb DEFAULT '{}',
    child_count int DEFAULT 0,
    descendant_count int DEFAULT 0,
    created_at timestamptz DEFAULT now(),
    completed_at timestamptz
);

CREATE INDEX idx_tree_path ON agent_tree_index USING gist (tree_path);
CREATE INDEX idx_tree_correlation ON agent_tree_index (correlation_id);
CREATE INDEX idx_tree_tags ON agent_tree_index USING gin (tags);
CREATE INDEX idx_tree_type ON agent_tree_index (correlation_id, agent_type);
This table has maybe 200 bytes per row. A million rows is 200MB — fits comfortably in Postgres's buffer cache. Every tree navigation query hits this table, and you only go to the full orchestration_states when someone clicks "show me this agent's actual output."
The user experience
Practically, you'd navigate the tree the same way you navigate a filesystem or a profiler's call tree. Start at the root, see a summary of branches with status indicators (green/red/yellow), expand the branch you're interested in, see the next level of summaries, keep drilling until you find the specific agent whose output you want to inspect. Search by tags or agent type when you know what you're looking for but not where it is. The ltree path gives you breadcrumbs at the top: root > uk-economy > fast-food-sector > pizza-delivery > dominos-agent-47 so you always know where you are in the hierarchy.
