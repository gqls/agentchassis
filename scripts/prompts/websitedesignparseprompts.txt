This is a fantastic line of thinking, and you've correctly identified the major components and challenges. This is moving from a simple "page conversion" to a "Design System Abstraction Engine," which is a far more powerful and interesting project.

You are absolutely right: a hybrid approach is the only one that will work. Relying purely on the DOM is a nightmare, and relying purely on screenshots is superficial. The "magic" is in correlating the two.

Let's critically discuss your points using the "agent framework" you suggested. This is the perfect way to structure it. We can define specialized agents, all open-source, that work in concert.

### The Open-Source Agent Framework

Here's a breakdown of the agents, their open-source tools, and their "checks and balances."

#### 1\. The "Capture Agent" (The Data Collector)

This agent's job is to reliably get *all* the data you mentioned, including the tricky parts like hover states and scroll animations.

  * **Primary Tool:** **Playwright** or **Puppeteer**. These are open-source, Google-backed (Playwright is from Microsoft) browser automation libraries. They are *far* more reliable than simple screenshot tools.
  * **Tasks:**
      * **Static Capture:** Load a URL, disable JavaScript (to get the "base" HTML), save the full-page screenshot, and save the DOM.
      * **Dynamic Capture:** Re-load with JavaScript enabled. Programmatically scroll down the page, taking screenshots at 200ms intervals to create a "film strip" (which you can stitch into a video).
      * **Hover/Interaction Capture:** Programmatically find all `<a>`, `<button>`, and `[role="button"]` elements. For each one, "mouse over" it, wait 500ms, and take a screenshot of just that element's bounding box.
      * **Computed Style Capture:** Execute JavaScript in the console (as you suggested) to get `window.getComputedStyle()` for specific elements.
  * **Output:** A project folder for `boxing-tickets.com` containing: `desktop.png`, `mobile.png`, `page.html`, `page-with-js.html`, `scroll_animation.mp4`, and a folder of `hover_states/`.
  * **Open-Source Check:** This agent is deterministic. The check is "Did all files get created?"

-----

#### 2\. The "Vision Agent" (The Visual Deconstructor)

This agent knows nothing about code. It only looks at the visual data from Agent 1.

  * **Primary Tools:**
      * **UI Detection:** **YOLOv8** (as you said) or an equivalent model trained on the UI-element datasets you found (like `YashJain/UI-Elements-Detection-Dataset`).
      * **OCR:** **Tesseract** (classic, highly reliable open-source) or an ML model from Hugging Face like **`microsoft/trocr`**.
      * **Color/Image Analysis:** **Pillow** (Python imaging library) and **scikit-learn** (using KMeans clustering to find the 5 dominant colors in the screenshots).
      * **Motion Analysis:** **OpenCV** (for processing the `scroll_animation.mp4`). It can use "optical flow" to detect *what* elements are moving, in *which* direction, and at *what* speed (e.g., "parallax effect detected on hero background").
  * **Task:** It parses the `desktop.png` and `mobile.png` and produces a "Visual Map" (as a JSON file) that looks like:
    ```json
    [
      {"type": "navbar", "bbox": [0, 0, 1920, 80]},
      {"type": "text", "bbox": [150, 200, 800, 300], "content": "Witness the Action Live"},
      {"type": "button", "bbox": [400, 500, 200, 50], "content": "VIEW ALL EVENTS"},
      {"type": "image", "bbox": [960, 150, 800, 900]}
    ]
    ```
  * **Output:** `visual_map.json`, `color_palette.json`, `motion_report.json`.

-----

#### 3\. The "Code Agent" (The Framework Stripper)

This agent is a code specialist. It knows nothing about the visual layout. Its job is to ingest the messy `page.html` and "purify" it.

  * **Primary Tools:**
      * **Deterministic:** **BeautifulSoup** (Python) for initial parsing. **Regex** (for targeted `find/replace`).
      * **AI (LLM):** A local, open-source code-generation model. **`codellama/CodeLlama-7b`** or **`mistralai/Mistral-7B-Instruct`** (run via Ollama, LM Studio, or a similar local tool) is perfect for this.
  * **Task:** This is your "reusable tool."
    1.  **First Pass (Deterministic):** Use BeautifulSoup to strip all `<script>`, `<style>`, and known-junk tags.
    2.  **Second Pass (AI-Assisted):** You feed the LLM a messy snippet (e.g., an Elementor button wrapped in 10 `divs`) and prompt it:
        > "Analyze the computed styles for the innermost element. Refactor this block into a single, semantic HTML element (e.g., `<button>`) and a single CSS class that replicates its appearance. Remove all framework-specific classes like 'elementor-widget-container'."
    3.  **Learning:** As you said, once you've done this for Elementor, you have a set of "recipes" (prompt templates) that you can re-use for any Elementor site. The agent "learns" to identify and refactor this bloat.
  * **Output:** `cleaned.html` (with a *semantic* but *basic* structure) and `cleaned.css` (with many potentially unused, refactored styles).

-----

#### 4\. The "Synthesis Agent" (The "Checks and Balances")

This is the most critical agent. It's the "manager" that looks at the work of Agent 2 (Vision) and Agent 3 (Code) to build the final product.

  * **Primary Tool:** A **multimodal LLM** (like **LLaVA**, which is open-source) or a powerful code LLM (Agent 3's model).
  * **Task (The "Correlation"):** This is the core of your idea.
    1.  The agent takes the `visual_map.json` from Agent 2.
    2.  It iterates through each item. *Item 1: `{"type": "button", "bbox": [400, 500, 200, 50]}`.*
    3.  It then "asks" Agent 3's code (`cleaned.html`) to find a corresponding element within those coordinates.
    4.  **This is the check and balance:**
          * **If a match is found:** It extracts the refactored CSS from Agent 3 and applies it to the new, semantic element.
          * **If no match is found (or the code is too messy):** It *ignores* the messy code from Agent 3. It "trusts" the visual model (Agent 2) and asks a separate model (like the `HuggingFaceM4/VLM_WebSight_finetuned`) to generate a *new* component from the *screenshot snippet* that matches the visual parameters.
  * **Output:** `final_template.html` and `final_style.css`. This is the clean, portable, 1-to-1 recreation.

What you're describing is the holy grail of this kind of work: creating a **Composable, Semantically-Labeled Design Library**. You're not just ripping a site; you're abstracting its *design patterns* into a palette you can use to paint new, original work.

This absolutely maps to an agent-based framework, but it redefines the final agent's role. It's no longer a "Synthesis Agent" that builds one page; it's a **"Librarian Agent"** that classifies and files components for future use.

Let's critically discuss this new, more powerful framework.

### The New Agent Framework: From Conversion to Library

The first three agents are similar, but their goals are more refined.

#### 1\. The "Capture Agent" (Same as before)

  * **Job:** Get all the raw assets from a target site.
  * **Tools:** **Playwright** (for screenshots, video capture, and DOM saving) and **BeautifulSoup** (for initial HTML parsing).
  * **Output:** A raw data folder for the target site.

#### 2\. The "Vision Agent" (Now with Classification)

  * **Job:** Visually deconstruct the screenshots and classify components.
  * **Tools:** **YOLOv8** (for bounding boxes), **Tesseract/TrOCR** (for text), **OpenCV** (for motion), **KMeans** (for color palettes).
  * **New Task:** This agent doesn't just say "this is a button". It analyzes the *context*.
      * Is this button in a navbar? Label it `nav-button`.
      * Is it the only big button in the hero? Label it `primary-cta-button`.
      * Is it small and under a blog post? Label it `read-more-link`.
  * **Output:** A `visual_map.json` with *semantic guesses* (e.g., `{"type": "primary-cta-button", "bbox": [...]}`).

#### 3\. The "Code Agent" (Now an Extractor)

  * **Job:** Isolate and purify code for *individual* components.
  * **Tools:** **BeautifulSoup**, **Regex**, and a local code LLM like **CodeLlama**.
  * **New Task:** Instead of cleaning the *whole page*, it receives a "job" from the Librarian Agent (e.g., "The Vision Agent found a `primary-cta-button` at `bbox: [400, 500, 200, 50]`. Find the corresponding DOM element and extract its HTML and computed CSS.").
  * **Output:** A snippet of *standalone, portable* code (e.g., `<button class="btn-style-001">...</button>` and `.btn-style-001 { ... }`).

-----

### The New Agents: Where Your Idea Comes to Life

This is where your new goals are implemented.

#### 4\. The "Librarian Agent" (The Core of Your Idea)

  * **Job:** Correlate the visual and code snippets, assign semantic labels, and save them to a component database.

  * **Tools:** A **multimodal LLM (like LLaVA)** or a powerful code LLM, plus a **Vector Database** (like Chroma or FAISS, both open-source).

  * **Task:** This is the "checks and balances" manager.

    1.  It gets the `primary-cta-button` from Agent 2 and the `btn-style-001` snippet from Agent 3.
    2.  It *correlates* them to confirm they are the same element.
    3.  It then *enriches* this component with labels. It analyzes the text ("View All Events"), the context (Hero section), and the visual style (red, uppercase) to add semantic tags.

  * **Output (The Component Database):** This is the "mix and match" library you want. It's a database where each entry is a JSON object like this:

    ```json
    {
      "component_id": "bx-001-hero-cta",
      "source_site": "boxing-tickets.com",
      "base_type": "button",
      "semantic_label": "primary-call-to-action",
      "tags": ["hero", "cta", "red", "uppercase", "jost-font"],
      "html": "<button class=\"bx-001-cta\">View All Events</button>",
      "css": ".bx-001-cta { background: #CC0000; ... }",
      "behavior_id": "bhv-001-fade-in"
    }
    ```

#### 5\. The "Behavior Agent" (The Interactivity Expert)

  * **Job:** Analyze the "reams of JavaScript" to find, extract, and simplify *reusable behaviors*.
  * **Tools:** A **code LLM** (CodeLlama) and static analysis tools.
  * **Task:**
    1.  It scans the original JS files for event listeners (`.on('scroll')`, `.on('click')`).
    2.  It identifies common patterns (e.g., "on scroll, if element is in view, add class `is-visible`").
    3.  It refactors this into a clean, standalone, vanilla JS function (e.g., `function setupScrollFadeIn(selector) { ... }`).
    4.  It saves this as `bhv-001-fade-in` in a behavior library, which the Librarian Agent can then link to components.

### The "Layout-First" Methodical Process

The key insight you have is to separate the **Layout (the "where")** from the **Component (the "what")**. This is the core of a real design system. Here’s a methodical, open-source-first process based on your idea.

#### Stage 1: Abstract Layout Segmentation (The "Wiremap")

We don't start with the messy HTML divs. We start with the *visual render* and create a *true* wireframe from it.

* **Process:** Instead of a complex UI model, we use a classic, open-source computer vision algorithm. The most common one for this is a **Recursive XY-Cut** algorithm.
* **How it works:**
    1.  It takes the full-page screenshot (from our Capture Agent).
    2.  It finds the largest "river" of horizontal whitespace and "cuts" the page into blocks (e.g., Header, Hero, Main Content).
    3.  Then, for each of those blocks, it finds the largest vertical "rivers" of whitespace and "cuts" them (e.g., Main Content -> Sidebar, Article).
    4.  It repeats this recursively until it has a tree of all the main layout blocks.
* **Result:** You get a simple JSON "layout tree" of bounding boxes, like:
    * `[Page] -> [Block 1: [0, 0, 100, 10]]` (Header)
    * `[Page] -> [Block 2: [0, 10, 100, 40]]` (Hero)
    * `[Page] -> [Block 3: [0, 50, 70, 50]]` (Left Column)
    * `[Page] -> [Block 4: [70, 50, 30, 50]]` (Right Column)

This is the *true*, simple "wiremap" you were looking for. It's just a "list of divs" with their positions, completely independent of Elementor.

#### Stage 2: Semantic Labeling (The "Purpose")

Now we have a list of empty, labeled blocks. We need to understand their purpose. This is where your "eye-tracking" and "semantic" ideas come in, and where AI is perfect.

* **Process:** We use an open-source **Multimodal LLM** (like **LLaVA**).
* **How it works:** For each block from Stage 1:
    1.  We crop the screenshot to that block's bounding box.
    2.  We feed the *image snippet* to LLaVA.
    3.  We **prompt** it with a classification task: "You are a web design expert. Analyze this image of a website section. What is its semantic purpose? Choose from: `Hero`, `Navigation`, `Feature-List`, `CTA-Section`, `Testimonial`, `Footer`, `Content-Block`".
    4.  LLaVA, seeing the large text and button, will label `Block 2` as `Hero`.
* **Labeling Importance (Your "Eye-Tracking" Idea):** This is a brilliant and simple heuristic. We can add this rule to our labeler:
    * Is the block at the top of the page (`y-position < 800px`)? Label `importance: high`.
    * Does it contain a `primary-cta-button`? Label `importance: high`.
    * Is it in the footer (`y-position > 3000px`)? Label `importance: low`.

#### Stage 3: Component Population (The "Mix and Match")

Now we have our empty, labeled wireframe. This wireframe becomes a "shopping list" for our component-building agents.

* **Process:** We go back to the agents we discussed previously, but now they have a specific, bounded job.
* **How it works:**
    1.  The **Librarian Agent** looks at the `Hero` wireframe block.
    2.  It runs the **Vision Agent** (YOLOv8 + `YashJain/UI-Elements-Detection-Dataset`) *only* on the screenshot snippet for the Hero block.
    3.  It finds: "1 `text-heading`", "1 `button`".
    4.  It then tells the **Code Agent**: "Find the DOM node for the `button` inside the `Hero` block's bounding box. Extract, clean, and save it to the Component Library."
    5.  The Librarian saves the component with its new context: `semantic_label: "primary-cta-button"`, `parent_section: "hero"`.

### The 6-Agent Framework for Design Abstraction

**1. The "Site Profiler" Agent (Handles Variety)**
* **Job:** Classifies the site's *purpose* to create a semantic dictionary.
* **Tools:** An open-source **Text Classification Model** (like a fine-tuned BERT).
* **Output:** `{"goal": "e-commerce", "vertical": "event-tickets"}`. This label is passed to all other agents to add context to their labeling.

**2. The "Capture" Agent (Gathers Raw Data)**
* **Job:** Capture *everything* about the target site.
* **Tools:**
    * **Playwright:** Takes static screenshots (desktop/mobile), saves the raw DOM.
    * **`rrweb`:** An open-source session replay library. This agent will use `rrweb` to record a "session" (scrolls, mouse moves, clicks) and save it.
* **Output:** A folder in your S3 bucket: `[site-name]/raw/` containing `desktop.png`, `page.html`, `session-recording.json`.

**3. The "Layout" Agent (Generates Structure)**
* **Job:** Generate a *semantically pure wireframe* from the screenshot.
* **Tools:**
    * **Recursive XY-Cut** (CV algorithm) to find the main layout blocks.
    * **LLaVA** (Multimodal LLM) to label each block based on its image and the site's `goal` (e.g., `hero-cta`, `trust-builder-content`).
    * **`HuggingFaceM4/VLM_WebSight_finetuned`** (or similar) to generate clean, semantic HTML/CSS *structure* for each block, using CSS variables for style (e.g., `background-color: var(--primary-color);`).
* **Output:** `clean-layout.html` and `clean-layout.css`.

**4. The "Style Extractor" Agent (Gets Your Colors/Fonts)**
* **Job:** Get the *real*, pixel-perfect "cosmetic" CSS from the original site.
* **Tools:** **Playwright**.
* **Process:** This agent loads the *original* `page.html` and uses `window.getComputedStyle()` to extract the *exact* style values. It ignores layout (flex, grid) and only grabs:
    * `color`
    * `background-color`
    * `font-family`
    * `font-size`, `font-weight`
    * `border-radius`, `box-shadow`
* **Output:** A JSON object of CSS variables: `{"--primary-color": "#CC0000", "--body-font": "Jost, sans-serif", ...}`.

**5. The "Behavior" Agent (The "JavaScript Refactorer")**
This is the new, critical agent that completes the picture.

* **Job:** Capture, classify, and refactor messy JS interactions into clean, reusable vanilla JS modules.
* **Tools:** **CodeLlama** (or another code LLM), **`rrweb`**, and DevTools techniques.
* **Process:**
    1.  **Analyze:** It first looks for *triggers* in the original code, using methods from debugging tools to find event listeners (`.on('click')`, `IntersectionObserver`).
    2.  **Classify:** It watches the `rrweb` session replay and correlates the *trigger* (e.g., user scrolls) with the *result* (e.g., an element fades in). It then classifies this using a standard vocabulary: `parallax-scroll`, `micro-interaction-hover`, `scroll-fade-in`.
    3.  **Refactor:** This is the key. It feeds the *messy, original* jQuery function to **CodeLlama**.
    4.  **Prompt:** "Here is a jQuery `on.('scroll')` function that animates an element. Refactor this into a modern, dependency-free vanilla JavaScript function that uses `IntersectionObserver` for the same effect."
* **Output:** A clean JS file: `scroll-fade-in.js`.

**6. The "Publisher & Librarian" Agent (Your Asset Manager)**
* **Job:** Synthesize all outputs into your databases and auto-publish your findings.
* **Tools:** Your **Postgres** DB, **S3** (Backblaze), and a static site generator (like **Astro**).

  * **Best Models:**
      * **Open-Source:** **`HuggingFaceM4/VLM_WebSight_finetuned`**.
      * **API (for MVP):** Gemini Pro Vision or Claude 3 (with a vision-to-code prompt).
  * **Process:** Iterates the `layout_map` from Agent 3, feeding each screenshot snippet to the model.
  * **Output:** `clean.html` (e.g., `<section class="hero-001">...`) and `clean.css` (e.g., `.hero-001 { background: var(--primary-color); }`).

#### Agent 5: Style Extractor (Extract-Style)

  * **Purpose:** To get the *real* "cosmetic" design tokens (colors, fonts).
  * **Structure:** A **Playwright** script.
  * **Best Models:** None (Deterministic).
  * **Process:** Loads the *original* site and runs `window.getComputedStyle()` on elements within each block's `bbox`. It extracts only cosmetic styles.
  * **JSON Output (to Librarian):**
    ```json
    {
      "block_id": "blk-001",
      "tokens": {
        "--primary-color": "#CC0000",
        "--text-color-inverted": "#FFFEFE",
        "--heading-font": "Jost, sans-serif",
        "--heading-font-weight": "700",
        "--border-radius-main": "0px"
      }
    }
    ```

#### Agent 6: Behavior Extractor

  * **Purpose:** To find, classify, and refactor messy JS into clean, reusable modules.
  * **Structure:** Python script, `transformers`, `rrweb-player` (JS lib).
  * **Models:**
      * **Open-Source:** **`codellama/CodeLlama`**.
      * **API (for MVP):** Claude or Gemini (with a code refactoring prompt).
  * **Process:**
    1.  Analyzes the `rrweb` session to classify the interaction (e.g., `scroll-fade-in`).
    2.  Finds the original messy JS function (e.g., an Elementor jQuery plugin).
    3.  Feeds the messy code to CodeLlama for refactoring into vanilla JS.
  * **Output:** A standalone `.js` file (e.g., `scroll-fade-in.js`) and a behavior label.

### 2\. 🗄️ The "Library & Storage" Group (The Hub)

This is the central "write" agent that all other groups depend on.

#### Agent 7: Librarian

  * **Purpose:** The single, asynchronous "write" agent that populates your central databases.
  * **Structure:** Python script using `psycopg2` (for Postgres), `boto3` (for S3/Backblaze), and `sentence-transformers` (for CLIP).

As you requested, here is a reduced plan to start.

2.  **Deterministic Agents to Build Now:**
      * **Agent 2 (Capture Bot):** Write this **Playwright** script. It's essential.
      * **Agent 5 (Style Extractor):** Write this `getComputedStyle` **Playwright** script. It's essential for your color palette goal.
      * **Agent 7 (Librarian):** Set up your **Postgres DB** and **S3** bucket. Write the simple Python scripts to `INSERT` data and `PUT` files.
3.  **Use APIs for Everything Else (For Now):**
      * **Agent 1 (Profiler):** Use **Claude/Gemini** (Prompt: "Classify this text...").
      * **Agent 6 (Behavior):** Use **Claude/Gemini** (Prompt: "Refactor this JS...").
      * **Agent 10 (Strategist):** Use **Claude/Gemini** as the main "brain" for your app.

This MVP plan gets you the *full end-to-end framework* running immediately. You build the deterministic data plumbing yourself and use **LLaVA** for the core visual task, while temporarily outsourcing the other complex AI reasoning to the APIs you already have.

LLaVA is designed to run on a **GPU**, but it *can* run on a **CPU**.

For any practical use in our project, you will want to run it on a GPU. The performance difference is not small; it's the difference between being usable and unusable.

Here’s a more detailed breakdown.

### 🚀 For Inference (Running the Model)

* **GPU (Recommended):** This is the typical and intended way to run LLaVA. The performance is dramatically faster. For example, a modern GPU can process 30-100+ tokens/second, while a CPU might only process 2-10 tokens/second.
    * **VRAM:** The key requirement is GPU memory (VRAM).
    * **7B Models:** For a standard 7-billion parameter model (like `llava-v1.5-7b`), you'll need at least **16GB of VRAM** for good performance.
    * **Quantized Models:** By using a "quantized" version (a slightly less precise but much smaller model), you can run it on GPUs with as little as **6-8GB of VRAM**.
* **CPU (Possible, but very slow):** You can run LLaVA on a CPU-only machine, but it will be very slow (e.g., 2-3 tokens per second). This is fine for initial testing to see if a model works, but it's not fast enough for our `Layout & Labeling` agent, which needs to process many images.

### 🧠 For Training (Fine-Tuning with LoRa)

* **GPU (Required):** Training or fine-tuning (even with LoRa) is a much more demanding task. This absolutely **requires a GPU**. While LoRa is very efficient, you will still need a capable GPU with a good amount of VRAM (e.g., 16GB+) to train your custom `my-layout-labeler` model.
* **CPU:** You cannot practically train or fine-tune on a CPU.

**Conclusion:** For your Kubernetes setup, you will want to deploy LLaVA to a node that has an **NVIDIA GPU**. You'll pass the image and prompt from your Go agent to this GPU-powered service (like an Ollama container) to get a response in seconds, rather than minutes.
